## Mandatory workflow — do not freelance

- **Picking up any story:** invoke the `implement-story` skill. Do not write implementation code by hand outside it.
- **Anything failing** (a contract, the accumulated suite, lint, CI, or the `enforce-contract-first` hook blocking a write) — **or resuming a story a prior session left uncommitted mid-implementation** (e.g. a usage-quota cutoff ending the session before the commit step): invoke the `heal-contract-failure` skill. Do not patch it ad hoc, and do not assume uncommitted state is still correct just because nothing failed — re-validate it the same way.
- A `PreToolUse` hook (`.claude/hooks/enforce-contract-first.cjs`) mechanically blocks writes to `<repo>/src/**` before any contract test exists in that repo — this is enforced, not just documented. If it doesn't seem to be firing in a fresh session, run `/hooks` once to reload config.
- Both skills end by appending to [`docs/implementation-log.md`](docs/implementation-log.md) — commit hash, files touched, verified against git by `docs/templates/check-implementation-log.cjs`, not just asserted. It has one entry per completed story/healing pass (most recently Story 6.23, as of 2026-08-18 — check the log's own last entry, not this number, for the true current state); append to it, never edit or remove an existing entry.
- **Delegating story/healing work to an Agent subagent does not exempt it from this section — the subagent must be told explicitly.** A spawned agent has no memory of this file; it only follows what its own prompt says. A delegation prompt asking a subagent to pick up a story or fix a failure must name `implement-story` or `heal-contract-failure` explicitly and instruct it to invoke that skill — describing the story/bug and hoping the subagent infers the process is exactly the "freelancing" this section exists to rule out, one level removed.
- **Concurrent agents in `social-listening-core` are now supported; `social-listening-admin` is not yet — and neither repo isolates real shared Azure state.** As of `56aec12` (2026-08-24), `implement-story`/`heal-contract-failure` open with a Step 0 that provisions an isolated `git worktree` per story (`../socialengage-story-<X.Y>` on branch `feat/story-<X.Y>`, merged back into `main` and torn down at the end of the skill), and `social-listening-core`'s Jest harness (`jest.global-setup.js`/`jest.global-teardown.js`) no longer points every run at one fixed `social_listening_test` database — each run now clones its own physically-isolated `test_run_<ts>_<pid>_<rand>` database from a `social_listening_template` base in <50ms, with retry/backoff if two runs' `CREATE DATABASE ... TEMPLATE` collide. That resolves the fixed-container collision this section used to warn about, for `social-listening-core` only.
  - **`social-listening-admin` was not touched by that change.** Its contract suite still presumably shares fixed state across runs — treat concurrent agents against `social-listening-admin` as unsafe until its own harness is verified or brought up to the same per-run-isolation pattern.
  - **Real, shared Azure resources are still unisolated regardless of repo.** Both repos exercise real Key Vault, Service Bus, and Blob Storage (ADR-0014/0015/0016/0029, never mocked) — worktree and database isolation don't touch this. Two `implement-story`/`heal-contract-failure` passes running at the same time, even in `social-listening-core` alone, can still race on that shared cloud state. Until that's addressed, concurrent agents should stick to stories that don't exercise the same tenant/credential/queue paths, and any collision here should be treated as this known gap, not a new regression.
  - **Documentation Steward correction, 2026-09-09:** the line above claiming `docs/implementation-methodology.md` "does not yet have an Amendment Log entry for this change" is itself stale — commit `4878510` (2026-08-25), the same commit that wrote this section's own text, also added the 2026-08-24 Amendment Log entry for this exact change (see that file's Amendment Log, "Story-level Git worktree isolation plus per-run Postgres template-database cloning"). The "worth adding" note was simply never removed once the entry landed in the same commit.

## Facts worth not re-deriving

- Two separate repos (`social-listening-core` backend, `social-listening-admin` Next.js UI) — ADR-0001. Both now exist on disk as subdirectories of this workspace; the eventual real repo split still hasn't happened, so cross-repo commits are still logged against this single workspace repo per each Implementation Log entry's own pre-split note.
- TypeScript/Node.js throughout, Azure-native (Postgres + RLS, Key Vault, Service Bus, Entra External ID, Azure AI Language) — ADR-0016, ADR-0015, ADR-0014, ADR-0029, spec §2. All three of Key Vault, Service Bus, and Blob Storage are real provisioned Azure resources this project's contracts run against, not mocks.
- Multi-tenant with database-level isolation as a from-day-one property, not retrofitted — ADR-0015. Real authentication now sits in front of it too: `Authorization: Bearer` (Entra External ID) resolved server-side against real `tenants`/`users` tables under RLS — `X-Tenant-Id` is fully retired as a trust mechanism (Story 5.10/ADR-0033).
- Connector order originally decided: RSS/News first, then Reddit — spec §10, `implementation-plan.md` Phase 1. RSS/News shipped as two connectors (GNews API, Story 2.7; Newswire RSS, Story 2.6), plus a tenant-owned-feed RSS connector (ADR-0050, Story 2.11). The roster then grew well beyond that original ordering, each via its own ADR: Wikipedia (ADR-0042, Story 2.13), Facebook (ADR-0059, Story 2.15, this project's first `authMode:'oauth'`/Tier-3-only connector), Brave Search and Bing Search (ADR-0065/0066, Stories 2.21/2.22, active watchlist-sourcing search connectors — later also reused as one-off research helpers for the Composer Deep Research agent, Story 2.31), Instagram (ADR-0068, Story 2.24), and LinkedIn (ADR-0069, Story 2.25). Reddit itself has still not been started.
- Solo project shapes several decisions directly — lightweight CI (no CODEOWNERS, no OpenAPI governance yet), and ADR-0020's distributed rate-limit gate is explicitly deferred until a second concurrent instance is ever actually run, not built speculatively.
- Credential/connector authority is ownership-tier-aware (ADR-0028, built by Story 1.7): no system-wide credentials; tenant-wide credentials only by Tenant-Admin; user-bound credentials self-activated by the user.
- Admin UI's own auth mechanism is a server-side (BFF) session, no bearer token in browser JS, no third-party auth framework adopted at v1 — ADR-0036. `GET /v1/me` (Story 5.11) is now built, so role-gating (Story 6.2) and the Platform Admin console (Story 6.6) both ship against a real resolved identity, not the degrade-to-`null` fallback.
