## 2. Executive Summary

SocialEngage's publishing surface currently only supports text and link-card outbound posts. Real social media management requires images, videos, and per-asset targeting so a single composed post can be dispatched to the right Facebook Page, LinkedIn profile, or other social asset. Without these capabilities, users must leave the product and upload content directly on each platform, fragmenting the publishing workflow.

This document defines the business requirements for media upload, asset storage, per-asset targeting, and connector-specific asset translation. The solution introduces a `POST /v1/outbound/media` endpoint that stores uploaded media in Azure Blob under a tenant-scoped container, persists metadata in a new `media_assets` table, and returns a short-lived presigned URL. Composed posts may then reference one or more assets and target them to specific pages or accounts via `assetTargets`. Each `SocialConnector` with `publish?()` translates the generic asset request into the platform-specific upload and returns clear, actionable errors when a platform rejects an asset.

The expected outcome is richer outbound content, support for multi-page publishing, and a foundation for video and link-card previews in v1 while keeping the door open for advanced scheduling, AI copy assistance, and approval workflows in later releases.

## 4. Scope

### 4.1 In Scope

- `POST /v1/outbound/media` multipart/form-data upload for images and videos
- Tenant-scoped Azure Blob storage and a new `media_assets` table
- Presigned 24-hour download URLs returned to the client and connectors
- `assets` array inside `OutboundPost` with `image`, `video`, and `link-card` types
- `assetTargets` map of `platformId` to page/account target for multi-asset publishing
- `GET /v1/connectors/:platformId/targets` to list available pages/accounts
- Image validation: JPEG, PNG, GIF, WebP; max 8 MB
- Video validation: MP4, MOV; max 512 MB (v1 support limited to images and link cards for most connectors)
- Link cards using a supplied URL and optional `mediaId` image; OpenGraph metadata may be used for preview
- Connector-specific translation of generic assets into platform-native uploads
- Error codes `400 MISSING_ASSET_TARGET` and `422 PLATFORM_ASSET_REJECTED`

### 4.2 Out of Scope

- Full video publishing for all connectors in v1 (support is connector-specific; most connectors start with images and link cards)
- AI copy assistance, alt-text generation, and image suitability review
- Advanced approval workflows beyond the simple state machine already in `outbound_activities`
- Smart scheduling and optimal send-time prediction
- Bulk CSV publishing and recurring posts
- Media thumbnail/previews generated by the backend for the UI
- Automatic cleanup and expiry of unreferenced media assets

### 4.3 Assumptions

- Azure Blob Storage is already provisioned and used for other features
- `outbound_activities` and `SocialConnector.publish?()` are already in place or will land before this feature
- A tenant has at least one connected platform asset (Facebook Page, LinkedIn page, etc.) that supports publishing
- The Polypost Composer will provide the drag/drop media UX and platform preview tabs

### 4.4 Constraints

- Multi-tenant data must remain isolated: media blobs and `media_assets` rows are scoped to a single tenant
- OAuth write scopes for each platform must be verified before `publish()` is called; asset upload itself does not bypass scope checks
- Per-platform size, format, and caption rules differ and must be enforced by the connector, not by a single central validator
- Presigned Blob URLs expire after 24 hours, so connectors must download and re-upload to the platform within that window

## 6. Current State (As-Is)

Publishing in SocialEngage is text-only or link-card only. The `POST /v1/outbound/posts` contract accepts a text body and target assets, but there is no mechanism to:

- Upload an image or video and reference it in a post
- Store media with tenant isolation and presigned access for connectors
- Specify which page or account should receive which asset in a multi-target post
- Translate a generic asset request into the Facebook, LinkedIn, or X upload formats

**Pain points:**
- Users must leave the product to publish image or video content
- Multi-page tenants (e.g., multiple Facebook Pages) cannot direct a post to the right page from the composer
- Platform-specific rejection reasons are opaque when a generic post is sent

---

## 7. Future State (To-Be)

A user opens the Polypost Composer, writes a message, and either attaches an image/video or creates a link card. The user can upload media directly from the browser; the backend stores it in Azure Blob and returns a `mediaId`. The composer then lets the user pick which page or account each platform should target via `assetTargets`. When the user publishes or schedules the post, the backend:

1. Validates OAuth scopes and asset rules for each target platform
2. Passes the generic `OutboundPost` and assets to each connector
3. Lets each connector download the media from the presigned Blob URL and re-upload to the native platform
4. Records the result in `outbound_activities` as `sent`, `failed`, or `cancelled`

**Expected capabilities:**
- Rich posts with images, videos, and link cards
- Per-asset targeting across multiple pages or accounts
- Platform-specific previews and validation feedback in the composer
- Clear, typed error messages when a platform rejects an asset

## 8. Business Requirements

### 8.1 Functional Requirements

| ID | Requirement | Priority | Acceptance Criteria | Owner |
|---|---|---|---|---|
| FR-001 | The system shall provide `POST /v1/outbound/media` accepting `multipart/form-data` file uploads | Must | Endpoint accepts a file, tenant context, and returns `mediaId`, `url`, `mimeType`, and `sizeBytes` | Backend Lead |
| FR-002 | The system shall store uploaded media in a tenant-scoped Azure Blob container and persist metadata in `media_assets` | Must | `media_assets` contains `id`, `tenant_id`, `owner_id`, `blob_path`, `mime_type`, `size_bytes`, and `created_at` | Backend Lead |
| FR-003 | The system shall return a presigned Blob URL valid for 24 hours on media upload | Must | Connectors and UI can download the file for 24 hours; after expiry a new URL is required | Backend Lead |
| FR-004 | `OutboundPost` shall accept an `assets` array with `image`, `video`, and `link-card` entries | Must | `POST /v1/outbound/posts` accepts `assets` and `assetTargets` fields | Backend Lead |
| FR-005 | The system shall support `assetTargets` mapping `platformId` to a target page/account | Must | A post can specify different targets for different platforms; missing required target returns `400 MISSING_ASSET_TARGET` | Backend Lead |
| FR-006 | The system shall expose `GET /v1/connectors/:platformId/targets` to list available pages/accounts | Must | Returns pages, boards, or accounts the user may publish to for that platform | Backend Lead |
| FR-007 | The system shall validate uploaded image and video formats and sizes | Must | Images: JPEG, PNG, GIF, WebP; max 8 MB. Videos: MP4, MOV; max 512 MB. Invalid files are rejected before storage | Backend Lead |
| FR-008 | The system shall support `link-card` assets using a provided URL and optional `mediaId` image | Should | Composer can attach a link with optional preview image; connector may use OpenGraph metadata or attach the URL directly | Backend Lead |
| FR-009 | Each `SocialConnector` with `publish?()` shall translate generic assets to platform-specific uploads | Must | Connector downloads from presigned URL and re-uploads to platform; rejects with `422 PLATFORM_ASSET_REJECTED` and reason | Backend Lead |
| FR-010 | The composer shall provide a media upload drop zone and per-target preview | Should | Tenant-User can drag/drop media, see per-platform preview, and pick `assetTargets` | Frontend Lead |
| FR-011 | The system shall include clear error responses for missing asset targets and rejected assets | Must | `400 MISSING_ASSET_TARGET` and `422 PLATFORM_ASSET_REJECTED` are returned with human-readable messages | Backend Lead |

### 8.2 Non-Functional Requirements

| ID | Requirement | Category | Priority | Acceptance Criteria |
|---|---|---|---|---|
| NFR-001 | Uploaded media must be isolated to the uploading tenant and accessible only via presigned URLs | Security | Must | No cross-tenant Blob access; `media_assets` is RLS-scoped by `tenant_id` |
| NFR-002 | An 8 MB image upload should complete end-to-end within 5 seconds under normal conditions | Performance | Should | Measured in contract and UI tests |
| NFR-003 | Connector `publish()` must fail gracefully and record the reason without crashing the scheduler | Reliability | Must | Failed publishes update `outbound_activities.status` to `failed` with `error_message` |
| NFR-004 | Media upload and storage must support 512 MB video files when enabled by a connector | Scalability | Should | Contract tests demonstrate accepted video size for the relevant connector |
| NFR-005 | Media access and publishing actions must be auditable per tenant | Compliance | Should | `media_assets` records `owner_id` and `created_at`; `outbound_activities` records publish attempts |
| NFR-006 | The composer must provide accessible, keyboard-navigable media upload and preview controls | Usability | Should | WCAG 2.1 AA keyboard and screen-reader guidance applied to media drop zone and target selector |

## 9. Business Rules

| ID | Rule |
|---|---|
| BRU-001 | Every uploaded media file is stored in an Azure Blob path scoped to the uploading tenant |
| BRU-002 | `media_assets` records the tenant, owner, MIME type, size in bytes, and creation timestamp for every file |
| BRU-003 | The download URL returned for a media asset is a presigned Blob URL valid for 24 hours |
| BRU-004 | Only supported image formats (JPEG, PNG, GIF, WebP) and video formats (MP4, MOV) may be uploaded |
| BRU-005 | Image uploads may not exceed 8 MB; video uploads may not exceed 512 MB |
| BRU-006 | A `link-card` must contain a URL and may optionally reference an uploaded image by `mediaId` |
| BRU-007 | If a platform requires a target page/account and none is selected, the publish request returns `400 MISSING_ASSET_TARGET` |
| BRU-008 | A single composed post may target different pages or accounts on different platforms |
| BRU-009 | Each connector decides how many images, videos, or link cards the platform allows and how to upload them |
| BRU-010 | When a platform rejects an asset for size, format, or policy reasons, the connector returns `422 PLATFORM_ASSET_REJECTED` with a reason |
| BRU-011 | Video upload is supported only where the connector explicitly enables it; most connectors start with images and link cards |

| Data Element | Description | Source | Owner | Sensitivity |
|---|---|---|---|---|
| `media_assets.id` | Unique identifier for an uploaded media file | Generated by system | Backend | Internal |
| `media_assets.tenant_id` | Tenant that owns the media | Entra / tenant context | Backend | Tenant boundary |
| `media_assets.owner_id` | User who uploaded the media | Authenticated user | Backend | Personal data (user reference) |

| `OutboundPost.assetTargets` | Map of platform IDs to target page/account IDs | Composer | Backend | User content |
| `GET /v1/connectors/:platformId/targets` response | List of pages/accounts available for publishing | Connector/platform APIs | Backend | Tenant content |

## 14. Acceptance Criteria

- `POST /v1/outbound/media` accepts a multipart file upload and returns `mediaId`, `url`, `mimeType`, and `sizeBytes`
- Uploaded files land in a tenant-scoped Azure Blob container and are recorded in `media_assets` with `tenant_id`, `owner_id`, `blob_path`, `mime_type`, `size_bytes`, and `created_at`
- The returned `url` is a presigned Blob URL valid for 24 hours
- `POST /v1/outbound/posts` accepts `assets` and `assetTargets` alongside text and schedules
- `GET /v1/connectors/:platformId/targets` returns the pages/accounts the caller can publish to
- Missing required `assetTargets` for a platform returns `400 MISSING_ASSET_TARGET`
- Image uploads are validated for supported types and max 8 MB; video uploads are validated for supported types and max 512 MB
- A `link-card` asset accepts a URL and an optional `mediaId` for its preview image
- Connectors translate generic assets to platform-specific uploads and return `422 PLATFORM_ASSET_REJECTED` with a reason when the platform rejects an asset
- The composer UI provides a media upload drop zone, per-platform preview, and an `assetTargets` selector
- Scheduled publishing works with media attachments

## 15. Glossary

| Term | Definition |
|---|---|
| **Asset** | A media item or link card attached to an outbound post; can be an image, video, or link card |
| **Asset Target** | The specific page, account, or board on a platform that should receive a post or an asset |
| **Asset Targets Map** | `assetTargets` in `OutboundPost`, mapping `platformId` to the target page/account identifier |
| **Connector Asset Translation** | The process by which a `SocialConnector` converts a generic asset request into the platform's native upload and post format |
| **Link Card** | An outbound post component consisting of a URL, optional title/description from OpenGraph, and an optional preview image |
| **Media Asset** | A record in `media_assets` plus the corresponding object in Azure Blob Storage |
| **Outbound Post** | The canonical composed message and its associated assets, targets, and scheduling information sent to `POST /v1/outbound/posts` |
| **Platform ID** | The short identifier for a connected platform (e.g., `facebook`, `linkedin`, `x`) used in `assetTargets` |
| **Presigned URL** | A time-limited Azure Blob Storage URL that allows a client or connector to download an uploaded media file |
| **SocialConnector** | The abstraction that handles platform-specific operations such as ingestion, publishing, and reply for a social network |
