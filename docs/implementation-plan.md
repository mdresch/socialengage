# Implementation & Delivery Plan — Social Listening / Insights Subsystem

Sequences the [user stories](user-stories/README.md) — grounded in the [ADRs](adr/README.md) — into build phases. Originally 23 stories/ADRs (2026-07-29); 25 after Story 2.6/ADR-0024 and Story 1.4/ADR-0025 were each added and accepted the same day they were drafted (2026-07-30); 26 after Story 2.7/ADR-0026 (RSS/News connector — GNews API) was drafted 2026-07-31 and accepted by Menno later the same day — see `docs/adr/README.md`'s footnotes 6/7/8. Unlike the first two additions, ADR-0026 wasn't self-accepted by the same session that drafted it (the drafting persona doesn't hold acceptance authority), so Story 2.7 was briefly Blocked before Menno's separate review — it is now Ready, same as every other story that predates this paragraph's next update. **Now 34 stories total**, after a seven-ADR batch (ADR-0029–ADR-0035, `docs/adr/README.md` footnote 11) drafted 2026-08-03 added Story 1.6 (retroactive, formalizing already-shipped connect/disconnect work), Story 1.7 (ADR-0034), and Stories 5.6–5.10 (ADR-0029–ADR-0033) — sequenced below into a **new Phase 4.5**, not folded into Phase 0–4 (which predate the multi-tenant model entirely) or Phase 5 (cross-cutting hardening work with no stories of its own) — see Phase 4.5's own goal statement for the reasoning. This is a dependency-ordered plan, not a calendar: no durations or sprint lengths are estimated. This is a solo-developer personal project (confirmed 2026-07-29), so "no team-scale process" is a deliberate choice throughout this plan (see Phase 0's testing/CI recommendation and Phase 4's note on multi-instance work), not just an absence of data to estimate against.

## How to read this

- **Ready** stories (34 of 34, as of 2026-08-03 — ADR-0034's acceptance moved Story 1.7 from Blocked to Ready, the last one; every story in this series is now Ready) are sourced from Accepted ADRs (or, for Stories 1.5/1.6, from unstoried Phase 1 work already built) and can be built as written. "Ready" is not the same as "built yet," though: several Ready stories (e.g. 2.4, 2.5, 3.5, 3.6, 4.4) are still deliberately scheduled for a later phase — see each one's own scheduling note. Story 2.7 was Ready-but-unbuilt as of 2026-07-31; it's been built since, 2026-08-01 — see Phase 1's own note below.
- **Blocked** stories: **none, as of 2026-08-03.** ADR-0034 (Story 1.7) and ADR-0035 (admin UI shape, no story) were both accepted 2026-08-03, closing out this seven-ADR batch entirely (ADR-0030 revised at review to add a narrow break-glass mechanism; ADR-0031 revised at review to add sign-up domain capture; ADR-0032 revised at review to add `access_ends_at`; ADR-0033 accepted as drafted; ADR-0034's flagged Tenant-Admin-revocation reading confirmed; ADR-0035's rule-of-three recommendation decided — see `docs/user-stories/README.md`'s new "No-story ADR convention" section). **Phase 4.5 is now fully unblocked.**
- **This plan is not the whole scope.** The original 23 stories cover architecturally significant decisions — that's what the ADR series was for. Ordinary CRUD surface (watchlist create/read/update/delete, connector connect/disconnect endpoints, the admin UI's screens) was never architecturally interesting enough to warrant its own ADR, but it's real, necessary work that has to happen alongside the storied work. It's called out per phase below so it isn't invisible.
- **Not covered at all:** Brand Reputation & Alerts, Social Care, Social Selling — explicitly deferred to be designed separately once this subsystem ships (spec §1, §9). Nothing in this plan builds toward them beyond leaving the REST API and Service Bus events they'll eventually consume. See [`docs/future-subsystems.md`](future-subsystems.md) for what's parked against each one, rather than just "out of scope."
- **How each story actually gets built** (scope discipline, contract-first testing, component `SKILL.md`s, permanent regression suite) is a separate concern from *when* — see [`docs/implementation-methodology.md`](implementation-methodology.md), operationalized as the `implement-story` Claude Code skill. This plan says what and when; that document and skill say how, uniformly, for every story in every phase below.

## Decisions resolved 2026-07-29

Three things needed an answer that nothing in the ADR series or spec resolved on its own — two were spec's own long-standing open questions (§10), one was a judgment call surfaced by phasing the work. All three are now decided (see spec §10 for the authoritative record):

1. **Which platform ships first:** RSS/News first (poll-only, API-key auth, no paid tier — cheapest way to validate the full pipeline without also debugging OAuth and rate-limit-tier economics in the same pass), then Reddit second (poll, OAuth, real rate limits, real boolean-query needs) specifically to prove the `ProviderConnector` abstraction (ADR-0002) generalizes rather than having been shaped around only the first connector.
2. **Testing strategy and CI/CD:** deliberately lightweight, matching a solo-developer project rather than team-scale process — GitHub Actions on push/PR running lint, type-check, and unit tests for both repos, plus one integration-test tier against an ephemeral/dockerized Postgres (RLS and JSONB behavior need real Postgres, not a mock). No CODEOWNERS, no OpenAPI-first contract-testing pipeline yet — consistent with those already being deferred in `docs/adr/README.md`'s "explicitly not drafted" list, for the same underlying reason: that's process built for contributors and consumers that don't exist yet.
3. **All 23 ADRs in this series are now Accepted (2026-07-29).** ADR-0017 (API versioning) and ADR-0019 (event schema versioning) were accepted ahead of the phases that would otherwise touch them — both were cheap to decide now and expensive to retrofit after real endpoints/consumers exist. ADR-0018 (data retention and archival) — `rawPayload` at 90 days, `IngestionRun` at 18 months, both configurable — and ADR-0020–0023 were accepted on their normal schedule, not early for a scheduling reason; each simply resolved its own open implementation-default questions at acceptance (see each ADR's "Acceptance note"). Being Accepted doesn't pull a story's *build* forward, though: Stories 3.5, 2.4, 2.5, 3.6, and 4.4 are all Ready now but stay scheduled for Phase 4 below, same as before acceptance — only the "needs an ADR decision before this phase can close" gate is gone, not the phase sequencing itself. One acceptance has a real code consequence worth flagging here: ADR-0023's rate-relative failure threshold partially supersedes the flat rule Stories 2.3 and 4.3 already shipped with (see ADR-0009's and ADR-0010's "Supersession update" notes) — their code stays as shipped until Story 2.5 is actually built, which is when that healing happens, not now.

## Phase 4 — Multi-connector scale-out and hardening

**Goal:** everything that only matters once there's more than one connector, more than one instance, or real data volume — deliberately sequenced after Phase 1–3 prove the architecture on a small footprint, not before.

**Stories:** 3.6 (watchlist AST + capability matrix — becomes valuable once a 3rd+ connector makes native/fallback drift a real risk), 2.4 (bounded queues, DLQ, distributed `RequestGate` state), 2.5 (proportional failure threshold, replacing 2.3's flat rule — best tuned once real differently-paced connectors exist to tune it against), 4.4 (derived-data caching — needed once read volume justifies it), 3.5 (tiered retention/archival — needed once storage volume, not correctness, is the driver), 2.6 (Newswire connector — GlobeNewswire + PR Newswire direct RSS, ADR-0024, accepted 2026-07-30, outside the original 23-ADR scope).
**Also build, not storied:** third and fourth connectors (whichever platforms are prioritized next) — Story 2.6/ADR-0024 is the first of these to get its own ADR, because of the issuer-as-Author modeling decision it needed, not because connector selection itself became storied work generally.

**2026-08-06 — Wikipedia now looks like a stronger next-connector candidate than Reddit, based on real (if secondary-sourced) research, not yet a decision.** Reddit's own access terms were checked properly for the first time (`docs/open-decisions.md`'s own dated entry has the full account): self-service API registration closed in late 2025, new access requires approval that's reportedly "slow and often silent" for exactly SocialEngage's own commercial use case, and Reddit's Data API Terms impose a 48-hour content-deletion-propagation obligation that doesn't fit anything ADR-0018/ADR-0039 currently design for. X, YouTube, and Meta were checked the same day and each carries its own real friction (X: pay-per-use with a plausible-to-hit 2M-read/month ceiling; YouTube: a retention-window conflict with ADR-0018; Meta: owned-page access is easy, but the actual public-listening capability is unconfirmed and was historically restricted platform-wide). Wikipedia, by contrast, came back clean: self-service, no approval gate, commercial reuse of content explicitly permitted, and its own CC BY-SA attribution model (link to an article's contributor history) resolves the multi-author data-model friction a Wikipedia connector would otherwise hit against ADR-0004's single-author-per-post assumption. This doesn't reorder Phase 4 on its own — Reddit was never storied here, only named as "the next platform" informally — but it's real grounding for whichever platform actually gets picked up next, and a real ADR (the same bar ADR-0024/0026 held Newswire/GNews to) would be needed before either Wikipedia or Reddit is actually built.

**Solo-project note on Story 2.4 specifically:** its whole premise (ADR-0020) is correctness under more than one `social-listening-core` instance running concurrently. For a solo-operated deployment, that condition may not arise for a long time, if ever — there's no team driving a scaling need, and a single instance may simply be enough. Don't build the Redis-backed distributed gate speculatively; a single-instance in-process `RequestGate` already satisfies ADR-0003 correctly on its own. Treat the distributed-gate half as "build when you actually deploy a second concurrent instance," not "build in Phase 4 on schedule" — it may end up the last piece of this entire plan to actually get built, or never, and that's fine. **Update 2026-07-30:** the other half — bounded queue TTL/depth ceiling and per-request dead-lettering, "relevant even on a single instance" per ADR-0020's own framing — has shipped (see `docs/implementation-log.md`); only the distributed-gate half remains deferred by this note.

**Deliverable:** `social-listening-core` runs correctly as more than one instance under load; a genuinely-broken low-frequency connector and a flaky high-frequency one are both judged fairly by auto-disable; storage growth is bounded without losing analytically-relevant history.

## Phase 4.5 — Multi-tenant identity & access foundation

**Goal:** close the authentication and tenant/user-identity gap this project has flagged as release-blocking since before any tenant existed — `Business-Case-v6.0.md` Risk R-04 ("No authentication mechanism exists... release-blocking... once external users are contemplated") and `docs/adr/README.md`'s own 2026-07-30 candidate-ADR framing ("(1) authentication mechanism — blocks everything else"). Six stories, sourced from a seven-ADR batch (ADR-0029–ADR-0035, see `docs/adr/README.md` footnote 11), built in strict dependency order. **All seven ADRs (0029–0035) accepted 2026-08-03** — every story in this phase (5.6–5.10, 1.7) is Ready. Phase 4.5 is fully unblocked, the same day it was drafted. **A seventh story, 5.11, was added 2026-08-05** — see the dependency-chain list and its own dated note below; the "six stories... built in strict dependency order" framing in this paragraph describes this phase's original scope, not its current one.

**Why this is its own phase, not folded into Phase 0–4 or Phase 5 — stated explicitly, as this plan's own task required:**
- **Not Phase 0–4:** every one of those phases predates the multi-tenant Admin/Tenant/User model entirely — Phase 0's own deliverable already shipped a tenant-isolated database built around a bare `tenant_id` UUID convention with no real caller identity behind it, and Phases 1–4 were built and, in most cases, already shipped against that same placeholder. Retrofitting this batch into any of those phases would misrepresent when it actually became buildable (only once ADR-0028's ownership-tier principle and this session's Entra decision existed) and would require reopening already-closed phases.
- **Not Phase 5:** Phase 5 ("Production readiness," below) is explicitly "not storied, not phase-specific to any ADR" — cross-cutting hardening and go-live verification against properties this project's ADR series *already* argued for. This batch is the opposite: six real, ADR-sourced, contract-testable stories that *themselves* need to exist before Phase 5's own "load/chaos testing against the isolation guarantees this whole series argued for" claim can even be evaluated against a real caller identity rather than a self-declared header. Burying six foundational stories inside a phase whose own goal statement says "not storied" would hide them, not schedule them.
- **A new phase, not a renumbering of Phase 5 onward:** "Phase 5" is referenced by name in seven other project documents (`Business-Case-v6.0.md`'s Milestone M7, several `Project Management Plans/*.md` files, `docs/open-items-and-deferred-work.md`, ADR-0027) — renumbering it to "Phase 6" to make room would touch every one of those files for no decision-relevant reason. Inserting a new phase between 4 and 5 avoids that blast radius entirely, consistent with this plan's own existing practice of sequencing insertions without renumbering (Story 2.6/ADR-0024 shipped as Phase 4 work ahead of Phase 1's own connector without renumbering anything).

**Stories, in strict dependency order (each one's own Status line named this chain while their source ADRs were still Proposed; all six are now Ready, all seven ADRs Accepted):**

1. **5.6** (ADR-0029 — Entra External ID authentication) — the root; nothing else in this phase can be built first.
2. **5.7** (ADR-0030 — Platform Admin's audited `BYPASSRLS` role) — depends on 5.6 for the caller identity a Platform Admin action authenticates.
3. **5.8** (ADR-0031 — `tenants` table + RLS) — depends on 5.7's bypass role to be provisioned/administered at all.
4. **5.9** (ADR-0032 — `users` table, RLS, and request-time identity resolution) — depends on 5.8 (`tenants.id` is `users.tenant_id`'s foreign-key target) and reuses 5.7's bypass-role pattern for its own narrower identity-resolution role.
