# ADR-0096: Daily digest email

**Status:** Proposed (2026-08-23)

**Authorizes:** a timezone-aware, user-configurable daily digest email that summarizes the user's watchlist activity using precomputed analytics views and bounded, optional AI summary.

**Source:** `docs/product-research/feature-designs/24-daily-digest-email.md` and `docs/product-research/feature-adr-scoping.md`

---

## Context

### 1. Users need a morning summary
`docs/product-research/feature-designs/24-daily-digest-email.md` describes a daily email for `Tenant-Reader` and `Tenant-Brand-Reputation-Manager` that summarizes the previous 24 hours of mentions, sentiment, top topics, and notable posts.

### 2. Timezones and schedules vary
Users are in different timezones and have different working hours. A `send_at_utc` field lets each user choose when the digest arrives in their local morning.

### 3. Precomputed views make this cheap
`ADR-0087` (Preconfigured analytics views) already aggregates daily counts. The digest can render from those tables instead of scanning `social_posts` for every recipient.

---

## Decision

### 1. New `user_digest_preferences` table
```sql
user_digest_preferences (
  id uuid,
  user_id uuid,
  tenant_id uuid,
  is_enabled boolean default true,
  send_at_utc time,                -- e.g. '07:00:00'
  timezone text,                   -- e.g. 'Europe/Amsterdam'
  watchlist_ids uuid[],            -- empty means all watchlists the user owns or can see
  include_ai_summary boolean default true,
  include_top_posts boolean default true,
  include_topic_breakdown boolean default true,
  last_sent_at timestamptz
);
```

### 2. Digest scheduler
- A worker runs every hour and checks `user_digest_preferences` for users whose `send_at_utc` in their `timezone` is in the past and whose `last_sent_at` is older than 20 hours.
- For each qualifying user, it generates the digest for the previous 24-hour window ending at the scheduled send time.

### 3. Digest content
```ts
{
  tenantName: string;
  date: string;
  totalMentions: number;
  sentiment: { positive: number; negative: number; neutral: number; mixed: number };
  topTopics: Array<{ topic: string; count: number; delta: number }>;
  topPlatforms: Array<{ platform: string; count: number }>;
  notablePosts: Array<{ postId: string; excerpt: string; platform: string; url: string }>;
  aiSummary?: string;          // optional, generated from top posts
}
```

- `totalMentions`, `sentiment`, and `topTopics` come from `*DailyCount` tables (ADR-0087).
- `notablePosts` are the top-N posts by reach or engagement from the user's watchlists.
- `aiSummary` is generated by `AIProviderConnector.research()` from the `notablePosts` snippets if `include_ai_summary` is true.

### 4. Email delivery
- Azure Communication Services or a tenant-configured SMTP relay.
- Subject: `"<tenant> daily digest — <date>"`.
- Plain-text and HTML bodies are generated from the digest content.
- `POST /v1/users/me/digest-preferences` lets the user configure preferences.
- `POST /v1/users/me/digest-previews` returns a one-off preview without scheduling.

### 5. Quota and cost guards
- AI summary is bounded to one call per user per day.
- `notablePosts` is capped at 5 posts.
- Total digest recipients per hour are rate-limited to prevent email provider quota exhaustion.

---

## Consequences

1. **User re-engagement:** users who do not log in daily still see the platform's value.
2. **Precomputed views pay off:** the digest uses `*DailyCount` tables and is fast.
3. **Email cost:** a daily email per active user creates ongoing cost. The feature is opt-in per user.
4. **Foundation for `RAG`:** `ADR-0084` `ask` can later power a more nuanced AI summary.

---

## Alternatives considered

1. **Send a real-time notification for every mention instead of a digest.**
   - *Rejected:* it is noisy and expensive. Alerts (`ADR-0091`) already handle real-time thresholds; the digest is a summary.

2. **Generate the digest on demand when the user opens the email.**
   - *Rejected:* it would require the email to fetch live data and is impractical. Digests are pre-rendered at send time.

3. **Use `social_posts` scans instead of precomputed views.**
   - *Rejected:* it would be slow for large tenants and would not scale. Precomputed views are the intended source.

---

## Open questions

- Should the digest use the tenant's default timezone or the user's personal timezone?
- How are `notablePosts` selected — by reach, engagement, sentiment change, or a blend?
- Should users be able to subscribe other users to a digest, or only themselves?
- How are unsubscribes handled for tenant-configured SMTP vs. Azure Communication Services?
