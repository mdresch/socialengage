# ADR-0060: Facebook connector — one user may connect more than one Page (cardinality, not credential-tier, change)

**Status: Accepted (2026-08-18)** — drafted by the AI Business & Requirements Analyst persona, left Proposed per this persona's own charter boundary (it does not hold ADR-acceptance authority), then reviewed and approved by Menno (Sponsor) the same day, verbatim: *"yes and i can now Approve the ADR 00060"*. Accepted as revised — the four-point external-review amendment round from earlier the same day (the `orphaned`-status auto-transition, `/select-page`'s structured partial-failure response, sequential per-Page polling reusing `RequestGate`'s existing serialization, and `GET .../pages`'s `parentConnectionActive` field) is in effect, not just the initial draft. See Amendment Log.

## Context

### The real business need, stated plainly

Story 6.23 (built, Story-2.15/ADR-0059-backed) ships a real, working OAuth connect flow against the live Meta Graph API. Menno's own live test confirmed `/me/accounts` correctly returns every real Facebook Page he personally administers — a long list spanning multiple organizations and cities (S&C MVP, Sustainable Army, several "CBA `<city>`" business pages across Amsterdam, Brazil, Melbourne, Singapore, New York, and London, a personal "Menno Drescher" page, and others). The Page picker (`FacebookPagePickerModal` in `social-listening-admin/src/app/tenant/connectors/ConnectorsClient.tsx`) is single-select today — a `role="radiogroup"` of `<input type="radio">` rows (lines 412–426), submitting exactly one `pageId` to `select-page`.

The only path Story 6.23 supports for a second Page is: a different tenant user personally administers that Page on Facebook and personally runs their own OAuth flow (ADR-0059 Decision §4's Tier-3-only rule — *"neither Tenant-Admin nor Platform Admin may create or activate a user-bound credential on a user's behalf"*). That path is structurally sound but practically closed for a tenant whose real license seat count caps at 5 users (ADR-0032, a real business rule) when one person legitimately administers far more than 5 Pages themselves. **The gap this ADR closes: can one person's one OAuth grant — which already returns every Page they administer in a single `/me/accounts` call — result in more than one stored, actively-polled Facebook connection, instead of forcing a choice of exactly one?**

### What does not change

ADR-0059 Decision §4's finding is not invalidated by this need and is not reopened here: Meta's Graph API has no organizational/app-only grant for an ordinary Page-connect flow — every Page access token is still derived from one specific individual's own long-lived User access token (verified directly against `developers.facebook.com`'s Access Token Guide, ADR-0059 Decision §4). What changes is purely **how many Page-derived credentials that one individual's one OAuth grant may result in**, not who may hold them or how they're obtained. See "Note on relation to ADR-0059" below.

### What was verified directly in this codebase before drafting, not assumed from Story 6.27's own stub text

- **`social-listening-core/src/credentials/credentialStore.ts`** — `storeCredential(tenantId, platformId, plaintext, keyVaultKeyId, ownerType, userId)` (lines 25–49) has no uniqueness constraint preventing more than one row for the same `(tenantId, platformId, ownerType, userId)` 4-tuple; confirmed against `migrations/0019_add_platform_credentials_ownership_tier.sql`, whose only added constraint (`platform_credentials_owner_shape`) checks the `owner_type`/`user_id` shape, not uniqueness. However, **the two functions that read/write against that 4-tuple structurally assume at most one *live* row**:
  - `getLatestCredentialId()` (lines 58–77) is `SELECT id ... ORDER BY created_at DESC LIMIT 1` — if two Page credentials existed for the same user today, only the most-recently-connected Page would ever be resolved by this function; the other would silently become permanently unreachable, not merely stale.
  - `deleteCredential()` (lines 110–131), for `ownerType: 'user'`, runs `DELETE FROM platform_credentials WHERE tenant_id = $1 AND platform_id = $2 AND owner_type = 'user' AND user_id = $3` — scoped only to the 4-tuple, with **no Page-level discriminator at all**. Disconnecting one Page today would delete every credential row matching that tuple. This exact call is not currently reachable from the live UI for Facebook — `ConnectorsClient.tsx`'s own comment (line ~494) states *"a `tenantScopeAllowed:false` platform (Facebook) has no tenant-wide credential to disconnect at all; defensive even though no UI path currently offers a Disconnect control for it"* — so this is a real, found, **latent** gap, not a live bug, the same "found while investigating, named precisely" treatment ADR-0057 gave its own role-gating discovery.
- **`social-listening-core/src/http/versions/v1/facebookOAuthRouter.ts`** — `/exchange` (lines 107–133) already fetches and caches **every** Page the user administers, with real access tokens, server-side, keyed by a single-use `sessionToken`. `/select-page` (lines 144–185) accepts exactly one `pageId` per call, calls `storeCredential(..., 'user', userId)` once, and deletes the session entry — single-use, so today a second call with the same `sessionToken` (to pick a second Page) is impossible; the session token is consumed by the first selection.
- **`social-listening-core/src/connectors/facebook/pollFacebook.ts`** — `pollFacebook(tenantId, userId)` (lines 46–126) calls `getLatestCredentialId(tenantId, FACEBOOK_PROVIDER_ID, 'user', userId)` once (line 55) and polls exactly the one Page that resolves to. There is structurally no loop over "this user's Pages" anywhere in this function today.
- **`social-listening-core/src/connectors/connectorHealth.ts`** — `deriveConnectorHealth(tenantId, platformId)` (lines 64–156) queries `ingestion_runs WHERE platform_id = $1`, with **no `user_id` or Page-level filter of any kind**. Confirmed directly: `ingestion_runs`' own schema (`migrations/0011_partition_ingestion_runs.sql`, columns listed lines 24–38) carries `tenant_id`/`platform_id`/`trigger_type`/`connector_version`/`status`/timestamps/`posts_ingested`/`posts_skipped`/`error_summary`/`retryable` — no `user_id`, no Page discriminator. `runIngestionAttempt()` (`social-listening-core/src/ingestion/runIngestionAttempt.ts`, lines 46–70) takes `connectorInfo: StartIngestionRunInput` = `{ platformId, triggerType, connectorVersion }` only — no `userId` is threaded through today at all. **A real, pre-existing gap this investigation surfaces that predates this ADR's own multi-Page ask:** if two different tenant users each connect their own Tier-3 Facebook Page today, their `ConnectorHealth` is already blended into one `(tenantId, 'facebook')` signal, indistinguishable by user, let alone by Page. This ADR's own multi-Page ask makes the consequence of that pre-existing gap materially worse (one person's several Pages, not just several people's one Page each, now blend together) — it does not create the underlying gap.
- **Precedent for additive, nullable, connector-scoped columns on `ingestion_runs` already exists in this exact table**: `migrations/0032_add_ingestion_runs_credential_failure_flag.sql` added `is_credential_failure` this same way (Story 2.15) — additive, nullable, populated by Facebook's own credential-failure classification, `NULL` for every other connector, zero behavior change for existing consumers. This is the direct precedent this ADR's own Decision §3 follows for a new `page_id` column.
- **`social-listening-admin/src/app/tenant/connectors/ConnectorsClient.tsx`** — `FacebookPagePickerModal` (lines 360–443) is confirmed single-select: one `radiogroup`, one `selectedId` state variable, one `handleConfirm()` POST. `platformVariant()` (lines 194–211) computes exactly one `StatusBadgeVariant` for the whole "Facebook" card, and the connected-state footer (lines 612–622) shows exactly one `facebookConnectedPage` name with one `ActivateDeactivateButton` — there is no per-Page list anywhere in this component today.

### The ADR-0057 precedent — evaluated explicitly, not assumed to transfer

ADR-0057 is the closest prior instance of "a connector originally designed single-X evolves to multi-X" (tenant-owned-feed's single-activation screen becoming a real multi-feed list, with `GET`/`PATCH`/`DELETE` endpoints, all `tenant_admin`-only). Its *shape* — a list endpoint, a soft-removal endpoint, a real per-item list UI replacing a single-state screen, no invented cap on count — transfers well and this ADR reuses it deliberately (see Decision §4/§6 below). **Its *scope*, however, does not transfer directly, and the difference is structural, not cosmetic:** ADR-0057's multi-feed administration is **tenant-wide** — any `tenant_admin` may list, edit, or remove any of the tenant's feeds, because a tenant-owned-feed activation is a Tier-2-shaped, tenant-wide resource. This connector's multi-Page cardinality is **per-user, Tier 3** — per ADR-0059 Decision §4 and ADR-0028 §3's own operative rule (*"neither Tenant-Admin nor Platform Admin may create or activate a user-bound credential on a user's behalf"*), a connected Page belongs to the individual who personally authorized it, and no `tenant_admin`-gated endpoint may list, edit, or remove another user's connected Pages. Any new REST surface this ADR's Decision proposes must therefore authorize on **"the caller's own `userId`,"** never on `role === 'tenant_admin'` — the opposite gate ADR-0057 used. This is named explicitly here because it is the one place a naive copy of ADR-0057's pattern would get the authorization model wrong.

## Decision

### 1. Storage shape: a new, small child table (`facebook_connected_pages`) referencing `platform_credentials` by id — not a discriminator column on `platform_credentials` itself, and not overloading `getLatestCredentialId()`/`deleteCredential()`

**Chosen, with reasoning, not left open:**

```sql
CREATE TABLE facebook_connected_pages (
  id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id     UUID NOT NULL,
  user_id       UUID NOT NULL REFERENCES users(id),
  page_id       TEXT NOT NULL,          -- Meta's own Page id
  page_name     TEXT NOT NULL,          -- cached display name, refreshed on (re)connect
  credential_id UUID NOT NULL REFERENCES platform_credentials(id),
  status        TEXT NOT NULL DEFAULT 'connected' CHECK (status IN ('connected', 'removed', 'orphaned')),
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (tenant_id, user_id, page_id)
);
-- RLS: standard tenant_isolation policy (ADR-0015), scoped by tenant_id, same as every other tenant table.
```

- **`platform_credentials` itself needs zero schema change.** `storeCredential()` already inserts one row per call with no uniqueness constraint blocking a second row for the same 4-tuple (confirmed, Context above) — one row per connected Page, exactly as it already does for a single Page today, continues unchanged. `readCredential(tenantId, credentialId)` already reads by a specific id, not by tuple-lookup — also unchanged, and already exactly what a multi-Page world needs.
- **Why a child table and not a `pageId` column added directly to `platform_credentials`:** `platform_credentials` is this project's deliberately generic, provider-agnostic envelope-encryption store — GNews, Newswire's absence of one, Azure AI Language, Azure OpenAI, and Facebook all share it, and none of its existing code knows or needs to know what's inside a given row's encrypted plaintext. Adding a Facebook-specific `page_id` *plaintext* column onto this shared table would be a modeling leak — the one connector-specific concept living permanently on a table every other connector also writes to. A separate, Facebook-scoped table keeps that leak contained to the one connector that needs it, mirroring ADR-0051's own already-established precedent of a **separate**, ownership-scoped table (`connector_activations`/`connector_user_activations`) for a concept orthogonal to credential storage rather than bolting new columns onto `platform_credentials` for it.
- **Why a real, queryable child table and not "just insert more `platform_credentials` rows and rely on the caller to remember which is which":** the Admin UI's own real need (Decision §6) is to list a user's connected Pages by name and status *without* decrypting anything — Key Vault unwrap + AES-GCM decrypt on every row just to render a list of Page names would be needless cost and needless plaintext-in-memory exposure for a read that doesn't need the secret at all. `facebook_connected_pages` carries exactly the non-secret fields (`page_id`, `page_name`, `status`) a list screen needs, and points at the actual secret (`credential_id`) only when a poll attempt or admin action needs to read it — the same separation ADR-0051 already drew between plaintext activation/list state and opaque credential storage, applied here at Page granularity instead of connector granularity.
- **Soft-removal (`status: 'removed'`), never a hard `DELETE`** — reuses ADR-0057 Decision §1's own reasoning directly: preserves the audit trail of which Pages were ever connected and when, the same "never discarded"/reversible-in-spirit framing this project already applies to `raw_payload` (ADR-0018), `accessEndsAt` (ADR-0032), and tenant offboarding's own grace period. Removing a Page also triggers a real `platform_credentials` deletion of that specific row (via the new `deleteCredentialById()` function, Decision §2) — the secret itself is destroyed immediately even though the `facebook_connected_pages` row survives as history, matching this project's existing pattern of destroying secret material promptly while retaining non-secret audit rows.
- **Re-selecting an already-connected Page (re-running the OAuth flow and picking a Page that's already `connected`) must `UPDATE`, not `INSERT`-and-violate-`UNIQUE`** — refreshes `credential_id` (a fresh token replaces the old one) and `page_name`, leaves `status = 'connected'`. This is the natural token-refresh/re-consent path named as an open concern in ADR-0059 Decision §4 (*"a documented re-consent path is still needed"*) — this ADR gives it a concrete mechanism for the multi-Page case specifically: re-running `select-page` for a Page id already present is an upsert, not a duplicate-row error.
- **Added at review (see Amendment Log) — a re-consent `/exchange` call whose returned Page list no longer includes a previously-`connected` `page_id` auto-transitions that row to a new `orphaned` status, never left silently stale.** This covers the real case where an individual loses admin rights to one specific Page (or removes SocialEngage's app from it) without losing their own Facebook account or their other Pages — `/me/accounts` simply stops returning that Page id on the next full re-consent. Detected only opportunistically, whenever `/exchange` runs for that user — no polling or webhook mechanism exists (or is proposed here) to proactively notice a Page's disappearance from `/me/accounts` without the user re-authorizing. `orphaned` is distinct from `removed`: `removed` is the tenant's own deliberate disconnect action (Decision §5); `orphaned` means Meta's own access grant for that specific Page ended without anyone in this product ever clicking "disconnect." `pollFacebook()`'s per-Page loop (Decision §3) excludes both `removed` and `orphaned` rows identically — only `status = 'connected'` rows are ever polled.

### 2. `credentialStore.ts` gains one small, additive function — its existing exported functions are not reworked

`storeCredential()` and `readCredential()` need zero change. `getLatestCredentialId()` and `deleteCredential()` also need **zero change to their existing signatures or behavior** — every other connector in this project's roster (GNews, tenant-wide credentials generally) still needs and correctly gets "the one live credential for this tuple," and reworking those two functions to be Page-aware would be a change with no benefit to any caller except Facebook's own new code. Instead:

```ts
export async function deleteCredentialById(tenantId: string, credentialId: string): Promise<void>
```

A new, narrowly-scoped, additive function — deletes exactly one row by its own primary key, tenant-scoped via `withTenant()` like every other function in this file. Facebook's own per-Page disconnect path (Decision §5) calls this, never the existing tuple-scoped `deleteCredential()`. This keeps every existing caller of `getLatestCredentialId()`/`deleteCredential()` (GNews's connect/disconnect, tenant-wide credential flows generally) completely untouched — the same "smallest additive mechanism, don't rework a shared function for one caller's new need" discipline ADR-0057 Decision §4 already applied when it added new store functions rather than widening existing ones.

### 3. `pollFacebook(tenantId, userId)` becomes a per-user fan-out over that user's connected Pages, one `IngestionRun` per Page

`pollFacebook()` is rewritten to: (a) list every `status = 'connected'` row in `facebook_connected_pages` for `(tenantId, userId)`; (b) for each row, run the existing per-Page ingest logic (credential read → `fetchFacebookPagePosts`/`fetchFacebookPageMetadata` → author upsert → per-post insert/enrich/publish, i.e. everything `pollFacebook()`'s current body already does, lines 59–123) as its own, independent `runIngestionAttempt()` call; (c) one Page's failure (a `ClassifiableError` thrown mid-attempt) is caught and does not prevent the next Page in the loop from being attempted — this is not optional: it is the direct, load-bearing consequence of the actual business need (Menno wants his ~15 Pages polled independently; one revoked grant among them must not silently stop the other 14).

**Added at review (see Amendment Log) — the per-Page loop runs sequentially, one Page's entire attempt (including its own `gatedAcquire()` call) completing before the next begins; never `Promise.all()`-style concurrent fan-out.** This is a real, explicit, cost-free mitigation for the increased-call-volume risk named in Consequences below, and requires no new mechanism: `gatedAcquire()`/`acquireForProvider()` (`requestGate.ts`) already serializes every acquisition sharing one `(tenantId, providerId)` key through a single `withKeyLock()` queue (confirmed directly, `requestGate.ts` lines 61–72, 111–126) and already paces requests against the shared window budget by sleeping and retrying once it's exhausted, rather than bursting (`acquireOnce()`, lines 74–102) — a true concurrent burst against Meta sharing this connector's key is already structurally prevented today, for one Page or thirty. Sequential iteration is the only addition this ADR makes; a second, redundant jitter/delay layer inside `pollFacebook()` itself is deliberately not added, since it would duplicate work `RequestGate` already does.

**`ingestion_runs` gains one new, nullable column: `page_id TEXT`** — following the exact precedent `migrations/0032_add_ingestion_runs_credential_failure_flag.sql` already set for `is_credential_failure` (additive, nullable, populated by Facebook's own poll path only, `NULL` for every other connector and every pre-existing Facebook row, zero migration risk to any other connector's queries). `StartIngestionRunInput` (`runIngestionAttempt.ts`) gains an optional `pageId?: string` field, threaded through into the `INSERT` `ingestionRunStore.ts` already performs. **This is the load-bearing piece that makes Decision §4 (per-Page health) possible** — without a Page discriminator on the audit-anchor table itself (ADR-0005), there is no data to derive per-Page health from at all.

### 4. Connector health: becomes genuinely Page-aware, not left platform-level — a real recommendation, not a shrug between two options

**The trade-off, named plainly:** leaving `deriveConnectorHealth(tenantId, platformId)` exactly as it is today would mean one revoked Page grant among Menno's ~15 either (a) gets averaged into `degraded`/`failing` across all of them, giving no way to tell *which* Page needs reconnecting, or (b) if it's the most recent run, forces the whole connector into `reconnect_required` (per the existing "most recent run's `is_credential_failure`" override, `connectorHealth.ts` lines 139–141), falsely alarming on 14 healthy Pages because the 15th's token expired. **Both outcomes are real, user-visible failures of the entire feature's stated purpose** — Menno's whole reason for wanting multi-Page support is to manage many Pages *independently*; a health signal that can't tell them apart defeats that purpose at the exact point a tenant would need it most (deciding which Page to reconnect).

**Recommendation: `deriveConnectorHealth()` gains a new, optional third parameter, `pageId?: string`.**

```ts
export async function deriveConnectorHealth(
  tenantId: string,
  platformId: string,
  pageId?: string
): Promise<ConnectorHealth>
```

- When `pageId` is omitted, behavior is **byte-for-byte unchanged** for every existing caller and every existing connector — the query stays `WHERE platform_id = $1`, exactly as today. This preserves the existing platform-level "Facebook" card badge in `ConnectorsClient.tsx` as a real, useful rollup (something needs attention, at a glance) with zero behavior change to any non-Facebook connector.
- When `pageId` is supplied, the query becomes `WHERE platform_id = $1 AND page_id = $2` — a real, independent health signal per connected Page, derived from that Page's own `ingestion_runs` rows only (populated by Decision §3's new column). This is what the new per-Page list UI (Decision §6) calls, one badge per row.
- `runIngestionAttempt()`'s own before/after health-snapshot calls (lines 52, 62 of `runIngestionAttempt.ts`) pass `options.connectorInfo.pageId` through when present — so `ConnectorHealthChangedEvent` publishing (ADR-0058) also becomes per-Page for Facebook specifically, with zero change to any other connector's event-publishing behavior (every other connector's `connectorInfo` never sets `pageId`, so this argument is always `undefined` for them).

**This is a materially bigger change than leaving health platform-level would have been** — a new column, a new function parameter, new call sites threading it through — named honestly as a real cost, not minimized. It is recommended anyway because the alternative doesn't just under-serve the feature, it actively misleads a tenant about which of their several Pages actually needs attention, the same category of "silent failure, wrong or absent signal" problem ADR-0059 Decision §4 already named as serious enough to warrant a dedicated `reconnect_required` status in the first place.

**A real, named edge case this ADR does not fully resolve:** if two different tenant users each independently hold an admin role on the *same* underlying Facebook Page and both connect it (two distinct `credential_id`s, same `page_id`, different `user_id`), a `pageId`-only health query would blend both users' attempts for that one Page together. This is likely rare in practice and is not designed around here — named in Open Questions, not solved, rather than adding `user_id` to the health-derivation key pre-emptively for a case with no confirmed real occurrence yet (the same "don't invent a constraint with no demonstrated need" discipline ADR-0057 Decision §3 already applied to feed-count caps).

### 5. New REST endpoints — authorized on the caller's own `userId`, never `tenant_admin`

```
GET    /v1/connectors/facebook/pages           — list the caller's own connected Pages (status='connected' and 'removed', for history)
DELETE /v1/connectors/facebook/pages/:id       — soft-remove one of the caller's own connected Pages
```

- **Both endpoints resolve `userId` from the caller's own resolved identity (`requireTenantUserIdentity`), exactly like `/select-page` already does — never from a request-body or path value, and never gated on `role === 'tenant_admin'`.** This is the one place ADR-0057's tenant-wide-CRUD shape does *not* transfer (see Context above) — a `tenant_admin` calling either endpoint sees and can only affect their own connected Pages, same as any other `tenant_user` would, because these are Tier-3, personally-authorized resources per ADR-0028 §3's own rule, not tenant-wide ones.
- `GET .../pages` returns `{ parentConnectionActive: boolean, pages: [{ id, pageId, pageName, status, connectorHealth }] }`, where `connectorHealth` is computed via `deriveConnectorHealth(tenantId, 'facebook', pageId)` (Decision §4) — one call per row. No pagination is added at v1; a person's own Page count (tens, not thousands) does not need it, matching this project's existing "don't build ahead of a demonstrated need" discipline. **`parentConnectionActive` added at review (see Amendment Log):** computed once per request via the already-existing `isConnectorActive(tenantId, 'facebook', 'user', userId)` (`connectorActivationStore.ts`, confirmed it already returns exactly this boolean with no new function needed) — a single top-level field, not duplicated per row, since it is the same value for every Page a given user has connected. This is what Decision §6's UI-copy requirement (the "N Pages connected, but your connection is deactivated" banner) renders from directly, rather than requiring the frontend to separately fetch and cross-reference `ConnectorInitialState.isActive` from an unrelated response.
- `DELETE .../pages/:id` sets `status = 'removed'` on that one `facebook_connected_pages` row (scoped to the caller's own `userId`, a cross-user id is `404`, not `403`, matching ADR-0044 §5c's own established "another user's private resource is 404, never 403" convention for personal resources) and calls the new `deleteCredentialById()` (Decision §2) against that row's own `credential_id`.
- **No `PATCH`-equivalent to ADR-0057's `feedUrl` edit exists here, deliberately.** Nothing about a connected Page is user-editable in place — its identity (`page_id`) and its access token both come from Meta, not from tenant input; a Page needing a fresh token is handled by re-running the OAuth flow and re-selecting it (Decision §1's upsert behavior), not by editing a field.
- `/exchange` and `/select-page` (`facebookOAuthRouter.ts`) are revised: `/select-page` accepts `pageIds: string[]` (plural) instead of a single `pageId`, looping over the selections within one request and writing one `platform_credentials` row + one `facebook_connected_pages` row per selected Page — the exact endpoint-shape change the new multi-select picker (Decision §6) needs to call. The existing single-`pageId` request shape is not preserved as a fallback; this endpoint has no external caller outside `social-listening-admin`, so there is no compatibility obligation to carry forward (unlike a public API contract).
  - **Partial-failure handling, added at review (see Amendment Log):** each `pageId` in the batch is processed independently — one Page's write failure (e.g. a transient `storeCredential()`/Key Vault error) never aborts or rolls back any other Page's already-succeeded write, the identical "one failure never blocks the rest" principle Decision §3 already applies to polling, applied here to writing. No shared database transaction wraps the whole batch: each Page's `storeCredential()` call plus its paired `facebook_connected_pages` upsert is already atomic at the single-row level, and there is no correctness requirement that all-or-nothing apply *across* different Pages' independent credentials — wrapping the batch in one transaction would only add cost (holding row locks open across N sequential Key-Vault-wrapping calls) with no matching benefit. Response shape: `{ connected: { pageId: string; pageName: string }[]; errors: { pageId: string; reason: string }[] }` — the multi-select confirmation UI (Decision §6) renders both lists, so a partial outcome (e.g. 12 of 15 Pages connected, 3 failed) is visible and actionable, never silently collapsed into one opaque success/failure boolean.

### 6. Admin UI: multi-select Page picker, plus a real per-Page connected-list

Named as real, necessary follow-on UI scope for Story 6.27's own Acceptance Criteria to design in full — **this ADR does not itself write Acceptance Criteria**, matching this series' own "no story expansion until ADR acceptance" precedent:

- `FacebookPagePickerModal` (`ConnectorsClient.tsx`, lines 360–443) becomes multi-select — checkboxes in place of the current `radiogroup`/`radio` rows, a "Connect N selected Pages" action in place of "Connect this Page," calling the revised plural `/select-page` (Decision §5).
- A new per-Page connected-list, replacing the current single `facebookConnectedPage` name + one `ActivateDeactivateButton` (lines 612–622) — one row per connected Page (name, per-Page `ConnectorHealth` badge via Decision §4, an individual "Disconnect this Page" action calling `DELETE /v1/connectors/facebook/pages/:id`), and a persistent "Connect another Page" action that re-enters the OAuth flow. Mirrors ADR-0057 Decision §6's own per-row-list shape directly.
- **The existing per-user `ActivateDeactivateButton` (`ownerType: 'user'`) stays exactly where it is — one on/off switch per `(tenantId, userId, 'facebook')`, covering *all* of that user's connected Pages collectively, not per-Page.** This mirrors ADR-0057 Decision §6's own explicit separation between per-feed rows and the connector-wide activation switch, and needs the same UI-copy discipline ADR-0057 Decision §6 already named: if a user's personal Facebook connector is deactivated, the per-Page list must say so plainly (e.g. *"N Pages connected, but your personal Facebook connection is currently deactivated — none of them are being polled"*), not just show every row as "Connected" with no explanation for why nothing is being ingested.
- **The card-level `reconnect_required` remediation action needs to change meaning.** Today, `variant === 'reconnect_required'` renders a single "Reconnect Facebook" link that restarts the *entire* OAuth flow from scratch (`ConnectorsClient.tsx` lines 608–611) — under multi-Page, this would force re-selecting every already-healthy Page again just to fix the one broken one. The per-Page list's own row-level action should carry the actual remediation (re-running OAuth scoped to just that Page, where Meta's own flow allows it), with the card-level badge staying a pure "something needs attention, look at your Page list" signal. Not designed in full here — named as necessary scope for Story 6.27.

## Consequences

**Positive**

- Closes the real, concrete business gap Menno named directly — one person's one OAuth grant can now result in as many connected, independently-polled, independently-monitored Pages as they actually administer, with no seat-count workaround required.
- `platform_credentials` needs zero schema change and zero rework of its existing exported functions (`storeCredential`, `readCredential`, `getLatestCredentialId`, `deleteCredential` all keep their current signatures and behavior) — every non-Facebook caller of this shared, provider-agnostic store is completely unaffected.
- Surfaces and fixes, as a direct consequence of this design, a real latent bug found while investigating (`deleteCredential('user')`'s all-rows-for-tuple deletion, Context above) before it could ever be triggered live, by giving Facebook's own disconnect path a narrower, additive function (`deleteCredentialById`) instead.
- Per-Page health (Decision §4) gives a tenant an actionable signal — which specific Page needs reconnecting — rather than an ambiguous aggregate, directly serving the stated reason multiple Pages matter (independent management, not just independent ingestion).
- Reuses ADR-0057's list/soft-remove UI and endpoint shape where it genuinely fits, while explicitly correcting the one place its precedent would have produced the wrong authorization model (tenant-wide vs. per-user) if copied uncritically.

**Negative**

- **A real, non-trivial schema and code-path expansion**, not a UI-only change: a new table (`facebook_connected_pages`), a new nullable column on `ingestion_runs` (`page_id`), a new `deriveConnectorHealth()` parameter threaded through `runIngestionAttempt()`'s two call sites, a new additive `credentialStore.ts` function, two new REST endpoints, and a revised (breaking, not backward-compatible) `/select-page` request shape. Named honestly as materially bigger than "let the picker allow multiple checkboxes," which is the risk this ADR exists to prevent understating.
- **`pollFacebook()`'s fan-out means one user's poll cycle now makes N times as many Graph API calls as today, against a `RequestGate` still keyed only by `(tenantId, providerId)` (ADR-0003), not per-user or per-Page.** If multiple tenant users each connect several Pages, all of their calls draw from one shared, tenant-wide rate budget under Facebook's own connector `getRateLimitConfig()` placeholder (`facebookConnector.ts` line 158, already an explicitly-named flat placeholder, not the real per-Page Engaged-Users ceiling). **Verified at review (see Amendment Log): `RequestGate` (`requestGate.ts`) already serializes and paces every call sharing one key rather than bursting, so the risk is not an uncontrolled concurrent burst against Meta — it is the shared budget being divided across more callers, causing later Pages in a large fan-out to wait longer, up to `RequestGate`'s own 6-hour queue TTL (ADR-0020), before a `QueueTtlExceededError` abandons that Page's attempt for the cycle.** This ADR does not redesign `RequestGate`'s keying — named as a real, concrete follow-up risk in Open Questions, not solved here, consistent with ADR-0020's own precedent of deferring distributed/multi-dimensional rate-limit work until a real, demonstrated need forces it.
- **The `pageId`-only health-derivation key has a real, named blind spot** (Decision §4's own edge case: two different users independently connecting the same underlying Page) — not solved, left as an Open Question.
- **`/select-page`'s request-shape change is a breaking change to that endpoint**, not additive — acceptable only because its sole caller is `social-listening-admin` itself, both under this ADR's own control; would not be acceptable if this endpoint had any external/public caller.
- **One `IngestionRun` per connected Page per poll cycle materially increases `ingestion_runs` row volume** for any tenant user with many connected Pages — the same category of unbounded-growth concern ADR-0057's own Consequences named for feed count, here scaled by Page count instead. Not bounded here; no real, demonstrated cap exists to justify inventing one.

## Alternatives Considered

| Alternative | Disposition |
|---|---|
| **Add a `page_id` (or generic) discriminator column directly to `platform_credentials`, keep `getLatestCredentialId()`/`deleteCredential()` as the only lookup path, widen them to take an optional discriminator** | Rejected. Leaks a Facebook-specific concept onto a shared, provider-agnostic table every other connector also writes to; still requires decrypting every candidate row just to list Page names for the UI, which a separate, unencrypted child table avoids entirely. |
| **Reopen ADR-0059 Decision §4 and allow a Tier 2 (tenant-wide) path instead, so a Tenant-Admin could connect Pages on behalf of the team** | Rejected. Meta's own OAuth mechanics haven't changed — there is still no app-only/organizational grant for an ordinary Page-connect flow (ADR-0059 Decision §4, re-confirmed, not re-derived, here). This is a cardinality question, not a credential-ownership question; reopening Tier 3 vs. Tier 2 would relitigate a settled, structurally-grounded finding to solve a problem that doesn't require touching it. |
| **Keep `deriveConnectorHealth()` platform-level only, accept the false-alarm/masking trade-off** | Considered, rejected as the primary design, but the platform-level rollup is *kept* as a secondary, zero-cost view (Decision §4's backward-compatible default). Rejected as the *only* signal because it defeats the feature's own stated purpose — independently monitoring many Pages — at the exact moment a tenant needs to know which one is broken. |
| **One shared `IngestionRun` per poll cycle covering all of a user's Pages, rather than one per Page** | Rejected. Provides no data for per-Page health derivation at all (Decision §4 depends on a per-Page `ingestion_runs` row existing), and blends one broken Page's failure into an aggregate `postsIngested`/`postsSkipped` count that can't attribute results to a specific Page — a strictly worse audit shape than ADR-0005's own "IngestionRun as the acquisition/audit anchor" already implies for a per-source attempt. |
| **Copy ADR-0057's tenant_admin-only endpoint authorization directly** | Rejected, argued explicitly in Context — this connector's Pages are Tier-3, per-user resources; a `tenant_admin` gate would violate ADR-0028 §3's own rule that no one may create, list, or remove another user's user-bound credential on their behalf. |
| **A hard cap on Pages-per-user** | Considered, deferred — no real, demonstrated constraint (support burden, cost, abuse pattern) backs a specific number today, the same "don't invent a ceiling with no evidence" reasoning ADR-0057 Decision §3 already applied to feed count. |

## Open questions for decision

- **`RequestGate`'s `(tenantId, providerId)` keying does not account for per-Page or per-user call volume** — a real, concrete risk once one user's poll cycle fans out across many Pages, worse still if multiple users each connect several Pages under the same tenant. Sequential per-Page polling (Decision §3, added at review) mitigates the burst/concurrency shape of this risk by reusing `RequestGate`'s own existing serialization — it does not mitigate the shared-budget-division shape (more callers drawing from one still-flat, still-placeholder ceiling). Not redesigned here; needs its own follow-up (possibly a Story-time addition, possibly its own ADR if the fix turns out to be structural, e.g. keying by `(tenantId, providerId, userId)`) — deliberately not pre-emptively built, since no real, measured fan-out volume yet demonstrates the shared budget is actually insufficient, the same "don't invent a fix for an unmeasured need" discipline ADR-0057 Decision §3 already applied to feed-count caps. **Note:** an external review round (see Amendment Log) additionally claimed this fan-out would trigger Meta's specific "Error Code 4 (Application request limit reached)" — that specific claim is not primary-source-verified against `developers.facebook.com` in this session and is recorded here as unconfirmed, not asserted as fact anywhere in this ADR's own Decision text, per this project's own ADR-0059 verification bar.
- **The Facebook `getRateLimitConfig()` flat placeholder (`facebookConnector.ts` line 158) becomes proportionally less accurate the more Pages one user connects** — ADR-0059's own Open Questions already named the real per-Page (4,800 × Engaged Users) ceiling as unimplemented; this ADR sharpens why closing that gap matters more once fan-out is real, without closing it itself.
- **The two-users-connecting-the-same-underlying-Page health-blending edge case** (Decision §4) — named, not resolved; revisit only if a real occurrence surfaces, not speculatively.
- **The card-level `reconnect_required` remediation action's own redesign** (Decision §6's last bullet) — named as necessary UI scope, left for Story 6.27's own Acceptance Criteria to design.
- **Whether `GET .../pages` needs pagination** — not needed at any Page count seen so far; revisit only if a real tenant's Page count grows large enough to matter.
- **No user story is expanded by this ADR.** Per this project's own established "no story expansion until ADR acceptance" precedent, Story 6.27's own text (`docs/user-stories/epic-6-tenant-admin-ui.md`) is left exactly as-is by this drafting pass — a human updates it once this ADR is actually accepted.

## A standing check applied, not skipped: author rights

Multi-Page cardinality does not change ADR-0059 Decision §5's own organization-as-Author modeling, and does not introduce a new author-rights question of its own — checked explicitly, not assumed. Each connected Page remains its own distinct `Author` row (`Author.externalAuthorId` = that Page's own Meta `id`), upserted once per Page per poll (Decision §3's own per-Page fan-out keeps this true — one `upsertAuthor()` call per Page's own posts, exactly as today's single-Page code already does, just repeated N times instead of once). Attribution stays per-Page and is never merged, reassigned, or blended across a user's several connected Pages, and content harvested via one Tier-3 credential remains ordinary tenant-wide-visible data exactly as ADR-0028's own Clarification and ADR-0059 Decision §4 already establish — unaffected by how many Pages that credential-holder happens to connect. Comment/mention ingestion remains out of scope, unchanged from ADR-0059 Decision §5's own deferral over the unresolved third-party personal-data question — this ADR does not reopen or narrow that deferral.

## Note on relation to ADR-0059 (Accepted, 2026-08-18)

**This ADR does not change, reopen, or supersede any part of ADR-0059 Decision §4 — Tier 3 (user-bound), no Tier 2 path, stays exactly as accepted.** ADR-0059 Decision §4 answers *who* may hold a Facebook credential and *how* it is obtained (the connecting individual's own OAuth grant, self-activated, never on another's behalf); this ADR answers a different, previously-unaddressed question — *how many* Page-derived credentials one such individual's one grant may result in. The two questions are independent: Meta's own OAuth mechanics that grounded ADR-0059's Tier-3 finding (no app-only/organizational grant exists for an ordinary Page-connect flow) are unchanged and are not re-litigated here; this ADR's own Decision §1's schema choice and Decision §3's poll-fan-out both operate entirely *within* the Tier-3-only credential model ADR-0059 already established, extending it to admit more than one credential row per credential-holder rather than replacing or widening who that credential-holder may be. **Per this project's own governance convention (`docs/adr/README.md`'s governance table), this is a genuine "Note on relation" — it records that a new, later ADR extends a prior Accepted ADR's decision along an axis that ADR was silent on, without altering that ADR's own Decision or Consequences text**, the same category ADR-0059 itself used for its own "Note on relation to ADR-0027" and "Note on relation to ADR-0028" sections.
