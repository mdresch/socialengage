## Context

Three things are already on record and Accepted, but none of them state *who, organizationally, is authorized to create a credential* — only *how* a credential is stored (ADR-0014), and *that* it must not be pooled across connecting parties (ADR-0027):

- **ADR-0014** (Accepted) defines envelope-encrypted storage and OAuth-preferred/API-key-fallback. It is entirely silent on organizational creation authority — it covers encryption mechanism and OAuth-vs-API-key preference only, nothing about which role within a tenant may create the credential it then stores.
- **ADR-0026** (Accepted) states "each tenant registers their own free GNews API key... per-tenant credential, not a shared pool" — but does not say which role *within* a tenant performs that registration, because no tenant/role model existed at the time it was drafted.
- **ADR-0027** (Accepted) generalizes "no pooling or sharing" and "no contracting on anyone's behalf" as a rule governing SocialEngage's own relationship to a data source, for whichever entity "the connecting party" turns out to be. Its own Decision text already lists the data sources this covers as "a social platform, an AI enrichment provider, a newswire, a general-news API — `Stakeholder-Register.md` S-03/S-05" — a detail this ADR returns to below, because it creates a scope question this ADR does not resolve either. ADR-0027's own "Open questions for decision" section explicitly left "the exact mechanics of 'whoever connects' once the Users model exists" to candidate ADRs #1–#4, not itself.
- `docs/adr/README.md`'s 2026-07-30 "Multi-tenant Admin/Tenant/User model" brainstorm — **not yet drafted as an ADR** — floats a three-tier model (Platform Admin → Tenant, with its own Tenant-Admin role → Tenant User) and a Platform-Admin boundary that "leans toward provisioning-only... zero tenant-data access — floated, not locked." `Stakeholder-Register.md`'s own Tenant-Admin persona entry (§1) already describes this role as managing "that tenant's own users, connectors, and watchlists" once it exists — consistent with, though not itself authority for, what Menno now states directly.

Menno's statement this session (verbatim, Amendment Log below) adds exactly the layer none of the above provide: **who is authorized to create a credential, at each of three ownership scopes.** This ADR formalizes that statement as an explicit, durable principle — the same move ADR-0027 made for the connector-architecture question, and the same governance-table category (`docs/adr/README.md`'s fifth row: a new ADR formalizing something a prior Accepted ADR's Decision text already assumed but never stated as project-wide policy) applies to this ADR's first tier, which is largely already implicit in ADR-0027's "no pooling" bullet. Tiers two and three are not already implicit anywhere in this project's Accepted ADRs — they are new content, sourced only from Menno's statement this session, with no prior shipped code or ADR language to point to as precedent. That distinction is stated plainly here rather than blurred, consistent with this persona's own evidentiary standard.

**A genuine scope tension this ADR does not resolve, and flags rather than silently picking a side on:** ADR-0027's Decision text, as already Accepted, explicitly includes "an AI enrichment provider" among the "data sources" its no-pooling rule covers (citing `Stakeholder-Register.md` S-05). Today's plan for Azure AI Language (ADR-0002's `AIProviderConnector`, `docs/project docs/Project Management Plans/Cost-Management-Plan.md`'s "~$100... Enrichment pipeline" line item) reads as a single project-operated Azure subscription used across every tenant for enrichment — a system-wide credential in every practical sense, budgeted and billed at the project level, not itemized per tenant. Read literally and without qualification, "System wide credentials will not be created" would prohibit exactly that model and require either a per-tenant or per-user Azure AI Language credential — a materially different, uncosted, unbudgeted architecture change nobody has proposed or evaluated. This ADR does not decide that question; it is named explicitly in Open Questions below and this persona's recommendation is that Menno confirm the intended scope before this ADR is accepted, not after.

**Follow-up, 2026-08-03 (Amendment Log below): named at the time as suggestive evidence, not yet as resolution.** Menno's clarifying follow-up (grounding tiers 2/3 in concrete social-platform account-type examples — see Decision below) drew every one of its examples from `SocialConnector` territory: company Pages, multi-admin Groups, personal profiles. None referenced `AIProviderConnector` credentials or Azure AI Language at all. At the time this was recorded as suggestive but not dispositive, since the follow-up was elicited by a question specifically about sharpening the tier 2/tier 3 distinction, not about this ADR's outer scope boundary. **Superseded within the same session — see the resolution immediately below.**

**Resolved, 2026-08-03 (second follow-up; Amendment Log below).** Menno directly answered the scope question this Context section originally flagged as open, verbatim: *"the client tenant will own this connector and enrichment should be cost incurred and settled between the connecting vendor and the end users."* **"No system-wide credentials" does reach `AIProviderConnector` credentials — there is no AI-enrichment carve-out.** Concretely: the tenant owns its own `AIProviderConnector` credential (e.g., its own Azure AI Language subscription/key) — this is not a special case requiring its own rule, it is simply an instance of this ADR's own **Tier 2** (tenant-wide, created by Tenant-Admin), the same as a GNews API key (ADR-0026) or a Company Page/Group connection. There is no project-operated, SocialEngage-held Azure AI Language subscription shared across every tenant. Cost is incurred and settled directly between the vendor (Microsoft/Azure) and the tenant — not billed, marked up, or intermediated by SocialEngage in any way. This is not a new principle; it is ADR-0027's own already-Accepted "no intermediary in billing or pricing" bullet, applied to the AI-enrichment case that ADR-0027's own Decision text named as covered (`Stakeholder-Register.md` S-05) but that nobody had checked against the current cost plan until this ADR's drafting surfaced the conflict. **This has a real, material consequence for `docs/project docs/Project Management Plans/Cost-Management-Plan.md`'s existing "~$100... Enrichment pipeline" project-level cost line, which assumed a single project-operated subscription — that assumption no longer holds; flagged with a dated note in that document itself, not re-derived here (a separate costing exercise, out of this ADR's own scope).**

## Decision

Credential-creation authority is scoped to exactly one of three tiers. Each tier governs *who may create* a credential of that scope — not how it is stored (ADR-0014 already governs that) or whether it may be shared once created (ADR-0027 already governs that for the SocialEngage-to-source relationship).

1. **No system-wide (platform-level) credential is ever created for a connecting party's own relationship with an external data source.** SocialEngage never creates, provisions, or holds a single platform-wide credential that stands in for, or is shared across, every tenant's or user's own relationship with a data source covered by ADR-0027's "connecting party" framing (today: GNews, per ADR-0026; the newswire sources, which use no credential at all, per ADR-0024; future connectors including Reddit). This is a restatement, at the point of *creation* rather than only non-sharing, of ADR-0027's already-Accepted "No pooling or sharing" bullet — no new decision is made here beyond making explicit that such a credential is never created in the first place, not merely never pooled after the fact. **Resolved 2026-08-03 (Context, "Resolved" note above; Amendment Log below): Azure AI Language / `AIProviderConnector` credentials are not a system-wide exception — they are tenant-owned, tier 2 credentials**, same as any other provider a tenant registers its own credential for (ADR-0026's GNews model). This tier's blanket "no system-wide credential" rule was never in tension with that outcome; the earlier open question was whether AI-enrichment credentials might need to stay project-operated as an exception to this tier, and Menno's resolution confirms they do not. **Postgres, Key Vault, and Service Bus remain outside this tier's scope entirely, and always were** — they are SocialEngage's own operational infrastructure for running the platform itself, not a connecting party's relationship with an external data source a tenant or user chooses to use; this tier only ever governed the latter, and including the former alongside Azure AI Language in this ADR's original drafting overstated the ambiguity.

2. **Tenant-wide credentials are created only by Tenant-Admin.** A credential representing a tenant's own relationship with a data source, usable across that tenant's users generally (today's GNews model, ADR-0026, once a tenant/role model exists to enforce it) may be created only by whichever role or capacity the eventual Admin-tier design (candidate ADR #2, `docs/adr/README.md`'s 2026-07-30 governance note) designates as holding tenant-administrative authority within that tenant — referred to here, as the brainstorm note and `Stakeholder-Register.md`'s own Tenant-Admin persona entry already do, as "Tenant-Admin." Not by an ordinary Tenant User acting alone, and not by Platform Admin reaching into a tenant whose data it does not own — consistent with, but not itself deciding or locking in, the brainstorm's floated "Platform Admin... zero tenant-data access" boundary. **This ADR does not decide Tenant-Admin's exact RLS mechanics, table shape, or how that role is authenticated** — those remain candidate ADR #2's and #4's job, exactly as ADR-0027 left "whoever the connecting party turns out to be" to candidate ADRs #1–#4 rather than deciding it itself. What this ADR fixes is narrower: whichever role ends up filling that capacity is the sole holder of tenant-wide credential-creation authority within its own tenant. **Concrete grounding, added 2026-08-03 (Amendment Log below):** a tenant-wide credential is one representing an organizational asset the social platform itself models as shared or multi-administered — Menno's own examples are "company pages, groups with multiple admins, etc." (a Facebook/LinkedIn Company Page; a Facebook Group with multiple admins) — not an individually-owned account. The test for tier 2 is the *platform's own account/asset model*, not merely "who happens to use it within the tenant."

3. **User-bound credentials are made available by the system, but created only by the user's own act of activation.** A credential representing an individual user's own relationship with a data source (a future Reddit OAuth grant is the concrete driver named in `Business-Case-v6.0.md`'s 2026-08-03 note) may be surfaced or offered as a connectable option to a user — e.g., through Tenant-Admin's tenant-level connector configuration making a platform available to connect — but the credential itself is created only by that user personally performing the activation (their own OAuth grant, or entering their own API key). Neither Tenant-Admin nor Platform Admin may create or activate a user-bound credential on a user's behalf. This directly extends ADR-0027's "no contracting on anyone's behalf" principle one level deeper: ADR-0027 already established that SocialEngage itself never accepts a data source's terms on a connecting party's behalf; this tier establishes that *within* a tenant, no other party — not even that tenant's own administrator — may do so on an individual user's behalf either. **Concrete grounding, added 2026-08-03 (Amendment Log below):** a user-bound credential is one issued by the platform to a single individual, granting access to that individual's own account — Menno's own framing is "user accounts... issued to a user and provide access to a user account in social media. personal pages, which remain private to the users." A personal profile stays private to the user who owns it; the tenant, and Tenant-Admin, have no visibility into or authority over it beyond whatever the user chooses to connect.

**The operative test distinguishing tier 2 from tier 3 is which credential/grant type a connector's capability actually authenticates through, not merely which account types a platform happens to expose.** **Corrected 2026-08-03 (Amendment Log below) — the version of this paragraph first drafted the same day overstated Reddit's case; the correction follows below rather than replacing it silently.** Some platforms expose only personal accounts with no organizational/app-level read path at all — for those, any connection is squarely tier 3. Other platforms, **Reddit included, expose both an app-only path and a personal-account path, and a single connector for that platform can use both tiers for different capabilities**: Reddit's own OAuth2 API (verified directly against `github.com/reddit-archive/reddit/wiki/OAuth2`) offers a `client_credentials` / `installed_client` "userless" grant — an app-level credential, registered once, bound to no individual Reddit account, suitable for reading public subreddit content — alongside the standard `authorization_code` grant, tied to one specific Reddit account, needed only for capabilities that require that individual's own account context (their private subscriptions, voting, DMs, posting as them). **A Reddit connector's core public-content-monitoring capability is therefore tier 2** (an app-only credential, created by Tenant-Admin, not bound to any individual's personal account) **— it is not, as first drafted, "squarely tier 3, never tier 2."** A tier 3 personal Reddit connection remains available, and would be needed, only for a future capability that genuinely requires an individual user's own Reddit account context — nothing named in this project's plan yet requires that, but this ADR doesn't foreclose it. **Concrete example, added 2026-08-03, confirmed against the same OAuth2 source:** any capability that acts *as* a specific Reddit account — replying to a post, sending a message, voting, submitting a comment — requires the `authorization_code` grant, since an app-only token has no identity to act as; such a capability would be tier 3 by necessity, not by choice, and per this ADR's own tier-3 rule, not even Tenant-Admin could perform that activation on a user's behalf. **This is named here only as an architectural fact, not as new scope**: this subsystem (Social Listening/Insights) does not build any respond/reply/message capability — `Business-Case-v6.0.md` and the Project Charter both place "CRM-adjacent workflows (case routing, lead generation)" out of scope, deferred to a future, separately-chartered Social Care subsystem. If that subsystem is ever built, this is the credential-tier rule it would need to follow for Reddit; it is not a capability this ADR or this subsystem's roadmap adds. Parked as a named requirement against that future subsystem in `docs/future-subsystems.md`'s Social Care section, so it isn't lost between now and whenever Social Care is actually chartered. A future Facebook or LinkedIn connector could similarly support either a Company Page/Group (tier 2) or an individual's personal profile (tier 3) — which tier(s) a given connector actually implements is decided connector-by-connector as each is built, verified against that platform's own current API/OAuth documentation the same way ADR-0024's and ADR-0026's own drafting verified their sources, not assumed by this ADR.

**This principle governs regardless of how candidate ADRs #1, #2, and #4 resolve the exact tenant/role/user table shapes and authentication mechanism.** It is a constraint those ADRs must be drafted to satisfy, the same relationship ADR-0027 already has to that same set of candidate ADRs — not a decision that depends on them being resolved first.

## Consequences

**Positive**
- Closes a real, named gap before it has occasion to be improvised under schedule pressure: candidate ADR #2 (Admin-tier design) and candidate ADR #4 (`users` table shape) now have a settled, written answer to "who is allowed to create a credential at each scope" before either is drafted, the same benefit ADR-0027 named for the connecting-party question generally.
- Makes explicit, for the first time in this series, that a tenant's own administrator cannot act on an individual user's behalf when a credential is inherently personal (tier 3) — a real and non-obvious constraint that nothing currently on record would otherwise stop a future connect-flow (candidate ADR #6) from designing around by default (e.g., an admin "connect this user's Reddit for them" convenience feature).
- Gives `Stakeholder-Register.md`'s already-described Tenant-Admin persona ("manages that tenant's own users, connectors, and watchlists") a concrete, sourced authority boundary rather than an unstated assumption.

**Negative**
- **Unlike ADR-0027, tiers 2 and 3 have no shipped code or prior ADR language behind them.** ADR-0027 could point to two live connectors (ADR-0024, ADR-0026) already practicing its principle; this ADR's tiers 2 and 3 are pure forward policy, sourced solely from Menno's statement this session, because no `tenants`/`users` table, no authentication mechanism, and no Admin-tier role exist anywhere in this codebase yet (`Business-Case-v6.0.md` §2's traceability matrix: "Open — `X-Tenant-Id` remains an unauthenticated client-supplied placeholder; no `tenants`/`users` table exists"). That is stated plainly here rather than dressed up as a formalization of existing practice, which it is not for tiers 2/3.
- **Resolved 2026-08-03 (was: unresolved tension, see Context's "Resolved" note and Amendment Log).** The AI-enrichment scope question was a real tension with ADR-0027's own already-Accepted Decision text — not a new problem this ADR introduced, but one this ADR's generalized "no system-wide credential" rule sharpened enough to surface. Menno resolved it directly: Azure AI Language / `AIProviderConnector` credentials are tenant-owned (tier 2), with cost settled directly between the tenant and the vendor — no SocialEngage-operated shared subscription. This is now a real, material, and previously uncosted architecture and budget change: `docs/project docs/Project Management Plans/Cost-Management-Plan.md`'s existing "~$100... Enrichment pipeline" line item assumed the opposite (a single project-operated subscription) and needs re-deriving — flagged there with a dated note, not re-costed by this ADR.
- Naming Tenant-Admin as the tenant-wide credential-creation authority, even while explicitly declining to decide its mechanics, still uses a specific role name from a brainstorm that is not yet an accepted ADR. If candidate ADR #2 ultimately designs a materially different Admin-tier shape (e.g., no single "Tenant-Admin" role, but a permission grantable to multiple tenant members), this ADR's Decision text would need revisiting for terminology, even if its underlying principle (broader-than-user, narrower-than-platform authority is required) survives unchanged.

## Alternatives Considered

- **Wait for candidate ADR #2 (Admin-tier design) and #4 (`users` table shape) to be drafted, and fold this principle into whichever settles authentication/roles** — rejected, for the same reason ADR-0027's own Alternatives Considered rejected the analogous wait: this principle does not depend on those decisions' mechanics (see Decision's final paragraph), and leaving it undrafted risks a future ADR improvising a different answer under schedule pressure without ever having to argue against a written rule first.
- **Scope this ADR to tier 1 only** (the part already substantially implicit in ADR-0027's "no pooling" bullet), and leave tiers 2/3 entirely undocumented until the Users model exists — considered, rejected. Menno stated all three tiers as one integrated policy; splitting off the two tiers with no current precedent while keeping only the one that's already redundant with ADR-0027 would under-serve the actual instruction and re-introduce the same "no written rule to argue against" risk tier 1's own precedent (ADR-0027) was built specifically to avoid.
- **Fold this directly into the still-brainstormed "Multi-tenant Admin/Tenant/User model" note in `docs/adr/README.md`** instead of drafting a numbered ADR — rejected. That note is explicitly not yet drafted as a decision, and Menno's statement here is Sponsor-stated policy, not brainstorm material; the project's own governance convention treats a Sponsor-stated durable principle as ADR material, not README prose (see ADR-0027's own precedent, drafted the same way from a directly-stated principle rather than from spec text).

## Clarification (2026-08-03)

**Credential tier governs credential *ownership*, not harvested-data *visibility* — this ADR does not conflate the two, and neither should a future reader.** Prompted by Menno asking directly whether Reddit's personal-account nature means the posts a connection retrieves are somehow scoped to only the harvesting user, rather than the whole tenant.

They are not — and per the Decision's 2026-08-03 correction above, the premise needs updating too: the Reddit connector's core public-content capability is expected to authenticate via a **tier 2, app-only credential** (Tenant-Admin-created, bound to no individual Reddit account), not a personal tier-3 grant. So for public-content monitoring specifically, there typically is no "harvesting user" at all — the tenant's own app credential does the polling directly, the same shape as GNews's tenant-wide API key (ADR-0026). **The visibility point holds regardless of which tier actually authenticated the poll**, which is the more durable half of this Clarification: whether a post was fetched via a tier 2 app-only credential or (for some future, not-yet-named capability) a tier 3 personal one, the *posts retrieved* are a separate concern from the credential, already governed elsewhere — ADR-0004 normalizes the post's `Author` per `(tenantId, platformId, externalAuthorId)`, ADR-0005 anchors it to an `IngestionRun`, and ADR-0015 enforces visibility purely by `tenantId` via RLS. None of those three ADRs have any concept of "visible only to the user whose credential harvested this row" — nothing in this project's data model scopes visibility any narrower than the tenant. Once ingested, a Reddit post is ordinary tenant-wide data, exactly like Newswire's or GNews's output, regardless of which credential — tenant's own app-only grant, or (hypothetically) an individual user's personal one — happened to poll it.

Concretely: yes, public Reddit posts polled via one user's personal, self-activated Reddit connection (tier 3) are intended to come into the tenant-wide watchlist review, the same as every other connector's harvested content (tier 2 or tier 3 alike) — respecting the credential's personal ownership does not require, or imply, restricting the resulting data's visibility.

**This clarification is bounded to genuinely public content.** It assumes the connector only polls Reddit's public listing/search surface (public subreddit posts and comments) — never the authenticating user's private messages, saved/private items, or private-subreddit content visible to that user's own account but not publicly accessible. Verifying that boundary against Reddit's actual published API terms, the same "compliance-by-construction" discipline ADR-0024's and ADR-0026's own drafting applied to their sources, is a job for whichever future ADR specs the real Reddit connector — not decided or resolved here.

This isn't a new decision; it's a mechanical consequence of this ADR's own tiers (credential creation only) combined with ADR-0004/0005/0015 (already-Accepted, already governing how ingested data is modeled and made visible), made explicit here because the question surfaced during this ADR's own drafting, before any Reddit connector exists to demonstrate it in code — the same trigger ADR-0013's own Clarification section used.

## Clarification (2026-08-17)

**Azure AI Language and Azure OpenAI credentials are Tier 2 *only* — no Tier 3/personal variant exists for either, full stop.** Found live: a real tenant activated Azure AI Language via the personal (`ownerType: 'user'`) control on `/tenant/connectors`, which succeeded with no error — but `enrichPost.ts` (`social-listening-core`) only ever reads a tenant-wide credential and a tenant-wide activation row for any `AIProviderConnector`; the personal activation had no effect whatsoever, silently. Nothing in this ADR's own Decision §1 text, nor anywhere else in this codebase before this Clarification, actually said tier 3 was *unavailable* for these two providers — only that tier 2 applied. Reddit, discussed at length in this same Decision, explicitly supports *both* tiers for different capabilities; a future reader could reasonably have assumed Azure AI Language/OpenAI might too.

They do not, and this Clarification states why: **the operative test this ADR's own Decision already establishes — "which credential/grant type a connector's capability actually authenticates through, not merely which account types a platform happens to expose" — resolves the question on its own.** An Azure AI Language/OpenAI API key authenticates an Azure subscription/resource (an organizational asset, provisioned by and billed to the tenant, per this ADR's own already-Resolved Context note), never an individual's own personal account the way a Tier 3 grant requires by definition (§3's own "issued to a user... personal pages, which remain private to the user" framing). There is no natural "personal Azure AI Language account" concept for an individual tenant user to hold one of, structurally unlike Reddit's own personal-account OAuth grant. This is not a new principle; it's the same test already applied, just not previously applied explicitly to this specific pair of providers.

**Mechanical consequence, closed the same day this Clarification was written:** `connectorsRouter.ts`'s `ownerType: 'user'` rejection (previously scoped only to `authMode: 'none'` platforms, per ADR-0051 Decision §1) was generalized to also reject any `AIProviderConnector`, applied to both `POST .../connect` (which had no such check at all before this fix) and `POST .../activate` — closing the gap at the surface to match the behavior `enrichPost.ts` already had at the point of use. See `social-listening-admin`'s `connector-connect-disconnect/SKILL.md` and `connector-status-view/SKILL.md` for the matching UI-side fix (a new `personalScopeAllowed` flag removing the misleading personal-scope controls from the two AI provider cards entirely), and `contracts/epic-1/story-1.7...`'s AC8 / `story-1.11...`'s AC12 (`social-listening-core`) for the new contract coverage.

## A note on this ADR's own place in the series' conventions

**No user story accompanies this ADR at drafting time — but not for the same reason ADR-0027 has none.** ADR-0027 has no story because its principle was *already satisfied by shipped code* (ADR-0024, ADR-0026) without any further build. This ADR's tiers 2 and 3 are the opposite case: nothing can be built against them yet, because no `tenants`/`users` table, no authentication mechanism, and no Admin-tier role exist for a contract test to target (`docs/implementation-methodology.md`'s contract-first discipline has nothing to write a Jest contract against here). Tier 1 alone is already satisfied today, for the same reason ADR-0027's is. Recommendation: **no story now; the buildable interface this principle implies (an authorization check on a credential-creation endpoint, a `credential_owner_type` field or equivalent, a user-activation flow) should be captured by whichever of candidate ADR #4's or #6's own stories eventually implements it**, with this ADR cited as the governing constraint at that time — not treated as a second instance of ADR-0027's specific "permanently no story" exception, since the underlying reason differs. `docs/user-stories/README.md` should be updated to record this distinction when this ADR is accepted, so the "no story" cases don't silently collapse into one undifferentiated category.
