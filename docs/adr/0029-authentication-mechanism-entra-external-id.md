# ADR-0029: Authentication mechanism — Microsoft Entra External ID, integrated as a thin, pluggable OIDC token issuer

**Status:** Accepted (2026-08-03) — drafted by the AI Business & Requirements Analyst persona, revised in place three times the same day (Alternatives Considered/Consequences below carry the full record), then reviewed and accepted by Menno. First of a seven-ADR batch (candidate ADRs #1–#7, `docs/adr/README.md`'s 2026-07-30 governance note); ADRs #2–#7 (this session) assume this ADR's shape — their own acceptance remains separate and pending.
**Acceptance note (2026-08-03):** Accepted by Menno, verbatim: *"reviewed ADR 0029 and approved."* All four "Open Questions for decision" below remain open at acceptance — none are resolved by it, including the `oid`-vs-`sub` claim conflict and the unconfirmed per-MAU overage rate, both flagged for verification against a real issued token/live pricing before anything downstream relies on them.
**Source:** Provider selection (Microsoft Entra External ID) is a fixed input, decided directly by Menno (Sponsor) this session, explicitly for consistency with this project's existing Azure-native, avoid-bespoke precedent (ADR-0014's Alternatives Considered rejecting a bespoke KMS in favor of Key Vault for the same reason) and its free tier at solo/small-tenant scale — not re-litigated here. Everything else in this ADR (integration shape, claims usage, data-ownership boundary, tenant-model mapping) originates from this drafting pass, verified against Microsoft's own current documentation as cited inline, plus two mid-drafting course corrections from Menno (Amendment Log).

## Context

No authentication mechanism exists anywhere in this project. Every `/v1` endpoint trusts a client-supplied `X-Tenant-Id` header as its entire tenant boundary — `Business-Case-v6.0.md` §2/§6 name this explicitly ("`X-Tenant-Id` remains an unauthenticated client-supplied placeholder") and Risk R-04 rates it High/High, "release-blocking... once external users are contemplated." `docs/adr/README.md`'s 2026-07-30 governance note lists "(1) authentication mechanism — blocks everything else" as the first of seven still-undrafted candidate ADRs; this is that ADR.

Two already-Accepted ADRs constrain, without deciding, this one: **ADR-0027** requires that whoever "the connecting party" turns out to be (a tenant or an individual user) independently holds their own credential with each data source — orthogonal to *how SocialEngage itself* authenticates a caller, which is this ADR's actual subject. **ADR-0028** requires that tenant-wide credential creation be restricted to a "Tenant-Admin" role and user-bound credential activation to the owning user alone — it explicitly declined to decide Tenant-Admin's "exact identity, authentication, and RLS mechanics," leaving that to this batch (candidate ADR #2). This ADR gives the underlying authentication mechanism those constraints will run on top of; it does not itself decide Admin-tier mechanics (#2), the `tenants`/`users` schemas (#3/#4), or how `X-Tenant-Id` is actually retired in code (#5) — each is its own, later ADR in this same batch.

## Decision

**Provider (fixed input, not re-litigated):** Microsoft Entra External ID — Microsoft's Azure-native customer-identity and access management (CIAM) service, the successor to Azure AD B2C. Confirmed directly against Microsoft's own tenant-configurations documentation: *"Effective May 1, 2025, Azure AD B2C will no longer be available to purchase for new customers"* (`learn.microsoft.com/en-us/entra/external-id/tenant-configurations`) — B2C is not merely superseded in Menno's framing, it is literally unpurchasable for a new project as of this drafting date, which independently confirms there is no live "stay on B2C" alternative to weigh.

### 1. One Entra "external tenant," not one per SocialEngage tenant — the two uses of "tenant" must not be conflated

Microsoft Entra's own tenant-configurations documentation defines an *external tenant* as a distinct Entra directory configuration "exclusively for Microsoft Entra External ID scenarios where you want to publish apps to consumers or business customers" — one external tenant is the correct unit for an entire consumer/business-customer-facing product, not one per customer organization the product serves (`learn.microsoft.com/en-us/entra/external-id/tenant-configurations`). **SocialEngage provisions exactly one Entra external tenant, shared across every SocialEngage tenant (customer organization) this project ever onboards.** Every person who signs in — regardless of which SocialEngage tenant they belong to — authenticates into this same single Entra directory.

This has a direct, load-bearing consequence for token claims: the ID/access token's `tid` claim (per Microsoft's own ID Token Claims Reference, `learn.microsoft.com/en-us/entra/identity-platform/id-token-claims-reference`, "Represents the tenant that the user is signing in to") will be **constant across every SocialEngage tenant**, since there is only one Entra tenant. **`tid` therefore carries no SocialEngage-tenant-discriminating meaning and must never be used, read, or relied on to determine which SocialEngage tenant a caller belongs to.** SocialEngage tenant membership, role, and license status are modeled and enforced exclusively in SocialEngage's own Postgres tables and RLS policies (candidate ADR #3/#4, ADR-0015) — never inferred from any Entra tenant boundary, group, organization, or directory-role construct. This is the first concrete instance of a general principle stated below (§2).

### 2. Entra is a pluggable OIDC token issuer only — never the source of truth for tenant membership, role, or license data

- `social-listening-core` validates Entra-issued tokens via standard OIDC mechanics only: issuer + JWKS discovery (`https://{tenant-subdomain}.ciamlogin.com/{tenant-id}/v2.0/.well-known/openid-configuration`, the documented External ID/CIAM discovery URL pattern — confirmed via Microsoft's own troubleshooting documentation for signature-validation errors, `learn.microsoft.com/en-us/troubleshoot/entra/entra-id/app-integration/troubleshooting-signature-validation-errors`) and the standard OIDC claim set. **No code path in `social-listening-core` may require an Entra-specific SDK call (e.g. MSAL) or a Microsoft Graph API call to make an authorization decision at request time.** Standard, generic JWT/JWKS verification (issuer allow-list + signature check against the published JWKS) is sufficient and is the only mechanism this ADR sanctions for the core's own token validation. (The admin UI's own sign-in flow may reasonably use a standard OIDC client library, including Microsoft's, for the interactive redirect/PKCE dance itself — that is a UI-layer implementation choice, not an architectural dependency the core inherits.)
- Two app registrations are created inside the single external tenant above: `social-listening-admin` (the interactive client, Authorization Code + PKCE) and a `social-listening-core` API resource (the audience whose access tokens the core validates). Both registrations live in the one external tenant per §1 — there is no multi-tenant/single-tenant app-registration question to resolve the way a workforce-tenant B2B scenario would have, since this project never accepts sign-ins from a *different* organization's own Entra directory.
- **Canonical external identifier: the token's `sub` claim.** Confirmed present by default in both ID and access tokens per Microsoft's own ID Token Claims Reference ("The subject of the information in the token... immutable and can't be reassigned or reused"). `sub` is used purely as an opaque foreign key into SocialEngage's own `users.external_subject` column (candidate ADR #4) — never combined with, or substituted for, an authorization decision itself. **`oid` is not used as the primary identifier in this v1 design, and its availability in External ID (CIAM) tokens is a genuine, unresolved documentation conflict**, named honestly rather than asserted either way: Microsoft's general ID Token Claims Reference documents `oid` as included by default when the `profile` scope is granted, but a Microsoft Q&A source (`learn.microsoft.com/en-us/answers/questions/2134225`) states the `oid` claim is *not* included in ID tokens for Microsoft Entra External ID (CIAM) tenants specifically — this could not be confirmed to this project's own primary-source bar (Microsoft's own *External ID* claims reference, as distinct from the general identity-platform one, does not itself state this either way) and is logged as an Open Question below rather than relied on. `sub`'s own documented caveat — that it is pairwise per *(recipient app, tenant, user)*, so two different apps get two different `sub` values for the same person — does not create a multi-value problem here, because this project registers, and will only ever register, exactly one API-resource app inside the one external tenant; every access token `social-listening-core` validates is issued for that same single audience, so `sub` is stable per user for every request this project's own code ever sees.
- Tenant membership, Tenant-Admin role, and license/seat status are owned and enforced exclusively by SocialEngage's own Postgres tables and RLS policies (ADR-0015; candidate ADR #3/#4) — **never** inferred from any Entra-side group membership, organizational-role claim, or directory attribute.

### 3. Data ownership: exactly one source of truth per field — no dual-write/sync model

A general, reusable rule, stated once here so future fields (whatever they turn out to be) are evaluated against a stated principle rather than improvised case-by-case:

1. **Default: SocialEngage's own Postgres `users` table (candidate ADR #4) is the source of truth for user data.** Profile fields (display name; any future Office/AD-style attribute this project might ever want, e.g. department or job title), tenant membership, role, and license/seat status all live there, filled in at invite/onboarding time — never fetched from, or synced with, Entra or any external directory.
2. **Exception A — data inherent to an external connected platform, accessed via that user's own credential, is never duplicated into Postgres.** This is ADR-0028's Tier 3 model made explicit for the data-ownership question, not re-derived here: if a user has their own personal connection to an external platform (ADR-0028's worked example — a personal Reddit OAuth grant), that platform's own profile data (karma, account age, whatever it exposes) lives on that platform, fetched live via the user's own credential when actually needed, never mirrored into a Postgres copy that can drift stale.
3. **Exception B — a field deliberately decided to live on the user's Entra profile itself is owned by Entra, not Postgres, as a one-time, explicit decision at the point it's introduced.** If this project ever wants a field tied to the authentication credential itself rather than SocialEngage's own record, that decision names Entra as the field's authoritative source at that time — it is never stored as a synced duplicate in both places. **No field ever has two owners.**

**In this v1 design, only bare OIDC auth claims (email, `sub`) touch Entra at all.** Every profile field this project has named a need for so far — display name, `Stakeholder-Register.md`'s Tenant-Admin/Tenant User roles — is Postgres-owned (candidate ADR #4); Exception B's path is unused, named only so a future addition is evaluated against this rule rather than improvised.

### 4. Invite-only onboarding vs. Entra's own self-service sign-up

Entra External ID's own "user flows" support self-service sign-up for external tenants (`learn.microsoft.com/en-us/entra/external-id/self-service-sign-up-overview`; confirmed applicable to external/customer tenants via the claims-mapping reference's own "user flow attribute" language). No verified Entra-side mechanism was found, to this project's own evidentiary bar, to cleanly disable self-service sign-up outright at the tenant level while still allowing invited users to complete a first sign-in. **SocialEngage's own application layer, not Entra, enforces the brainstormed invite-only, license-gated onboarding model** (`docs/adr/README.md`'s 2026-07-30 note): Tenant-Admin creates a `users` row in `invited` status (candidate ADR #4) before the person ever authenticates; at first successful Entra sign-in matching that invited email, the resolved `sub` is linked to the pending row and status moves to `active`. **An authenticated Entra sign-in with no matching invitation is rejected at the application layer (401/403)** — Entra permitting the sign-up is not, by itself, SocialEngage access. Whether to additionally restrict Entra's own user-flow configuration (belt-and-suspenders) is left to candidate ADR #4's own implementation.

### 5. Pricing

Confirmed directly against Microsoft's own pricing page (`azure.microsoft.com/en-us/pricing/details/microsoft-entra-external-id/`): **the first 50,000 monthly active users (MAU) are free**, recurring monthly, no credit card gate implied by the page's own framing ("get started... for free and only pay for what you use as your business grows"). The exact per-MAU overage rate beyond that free tier was not renderable on the fetched page itself (a dynamic pricing calculator, not static page text) — a secondary search summary suggested "$0.03/MAU (launch-discounted $0.01625 until May 2025)," but this figure is **not confirmed to this project's own primary-source bar** and is not asserted as fact; logged as an Open Question. At this project's current and realistically near-term scale (one operator, no onboarded external tenant yet), the free tier is expected to cover MAU volume with substantial headroom regardless of the exact overage rate.

## Alternatives Considered

- **Azure AD B2C** (the direct predecessor) — not viable: closed to new-customer purchase since 1 May 2025, per Microsoft's own documentation (§ above). Not a live alternative to weigh.
- **A bespoke username/password + session-store implementation** — rejected, contradicts this project's own established Azure-native, avoid-bespoke precedent (ADR-0014's Key-Vault-over-bespoke-KMS reasoning), and reintroduces password-storage/MFA/session-security surface this project has no operational reason to own itself.
- **Auth0, Clerk, Supabase Auth, Firebase Authentication (via its own OIDC support)** — each is a real, viable OIDC-compliant CIAM alternative, and each is named here deliberately: this ADR's entire "thin, pluggable OIDC issuer" design (§2) is built specifically so that a future migration to any one of these remains realistic, addressing Menno's own direct question about migration difficulty. Rejected as the *initial* choice only for the stated, fixed reasons (Azure-native consistency, free tier) — not because they are architecturally incompatible with this project's design.
- **Cross-tenant B2B federation with each customer's own Microsoft 365/Entra ID workforce directory**, using Graph API delegated permissions to pull each customer's real department/job-title/organizational data live — considered and explicitly rejected for v1. This would avoid double-entry of profile data for enterprise customers already on Microsoft 365, but it is a materially larger integration than anything currently named in the design spec or `Stakeholder-Register.md`, and it is exactly the kind of deep, Entra-specific coupling §2's portability design is deliberately built to avoid. Rejected under this project's own established "don't build ahead of a demonstrated need" discipline (ADR-0020's deferred distributed rate-limit gate is the precedent for this kind of call) — named here as a consciously deferred future consideration, not something never considered, should a real enterprise-customer need for it ever materialize.
- **A coexisting `X-Tenant-Id` fallback alongside real authentication** ("just in case") — not decided here (candidate ADR #5's job), but flagged: any design that keeps a client-trusted tenant header alive alongside real auth reopens the exact spoofing vector this batch exists to close, and should not be assumed as a soft landing.

## Consequences

**Positive**
- Consistent with this project's own established Azure-native precedent, and free at this project's current and realistically near-term scale (50,000 MAU free, confirmed primary source).
- The "thin, pluggable OIDC issuer" design bounds the blast radius of a future provider swap concretely: per §2/§3, a future migration to another OIDC-compliant provider is mainly (a) a re-point of OIDC issuer/JWKS configuration, since `social-listening-core` never calls an Entra-specific API to authorize a request; (b) a one-time forced password reset or parallel-running re-linking window for existing users (true of any provider-to-provider migration — password hashes are never portable, regardless of which two providers are involved); and (c) rebuilding whatever sign-up/sign-in UI customization existed (Entra's "user flows," or the equivalent on any future provider) — not a rebuild of the authorization model itself, since that already lives entirely in SocialEngage's own Postgres tables per §2/§3.
- "Single source of truth per field" (§3) prevents a class of bug this project has not yet had occasion to hit but would eventually: a profile field silently drifting because two systems both claim to own it.

**Negative**
- **A genuine, unavoidable lock-in remains, named plainly rather than hidden:** password/credential migration is never portable to a new provider under any design — a future swap still requires a forced reset or a parallel-running re-linking window for every existing user. Entra's own sign-up/sign-in UI customization ("user flows") is not portable either — a future provider swap requires rebuilding that UI layer specifically. Both are true of every CIAM provider's equivalent customization layer, not an Entra-specific penalty, but they are real costs of *any* future migration, not eliminated by this ADR's thin-issuer design — only bounded to those two items instead of a full authorization-model rewrite.
- The exact per-MAU overage rate is not confirmed to this project's own primary-source bar (§5) — a real, if currently low-stakes, gap.
- Invite-only enforcement is an application-layer check, not an Entra-native one (§4) — a bug that skips or misconfigures that check would let any successfully-authenticated Entra user in, regardless of invitation status; this is a real implementation risk to flag for whoever builds candidate ADR #4's story, not eliminated by this ADR.
- The `oid`-vs-`sub` claim question (§2) is left genuinely unresolved, not asserted either way — a future implementer must verify directly against a real token from this project's own external tenant before assuming either claim's availability.

## Open Questions for decision

- **Whether `oid` is actually present in this project's own External ID (CIAM) tokens** — conflicting, not-primary-confirmed documentation (§2); verify against a real issued token before relying on it for anything beyond `sub`.
- **The exact per-MAU overage price beyond the confirmed 50,000-free tier** — not confirmed to primary-source bar (§5).
- **Whether Entra's own user-flow sign-up should additionally be restricted at the IdP configuration level**, on top of the application-layer invite check (§4) — a defense-in-depth question, not decided here.
- **Machine-to-machine (M2M) authentication needs** — Entra External ID's M2M Authentication add-on (client-credentials/OAuth2, transaction-billed) exists but is not needed by anything named in this batch; flagged only so it isn't rediscovered as a surprise if a future service-to-service auth need arises.
