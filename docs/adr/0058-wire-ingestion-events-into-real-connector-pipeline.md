# ADR-0058: Wire `SocialPostIngestedEvent`/`ConnectorHealthChangedEvent` publishing into the real ingestion pipeline

**Status:** Accepted (2026-08-17)

**Source:** Not specified in any prior ADR. `ingestion-events/SKILL.md`'s own "Known gaps" section already names it plainly: *"Nothing actually calls `publishEvent()` from the ingestion pipeline yet... that wiring is separate, not-yet-storied work (no ADR mandates *when* in the pipeline publishing happens, only the payload shape and transport guarantees)."* Found live while scoping Story 2.13 (Wikipedia connector) — Menno flagged directly ("i remember the service bus needs to be hooked up for the functionaltiy to work appropriatly"), and investigation confirmed the gap is real, project-wide (affects every existing connector, not just the one being added), and materially deeper than "add one function call" — see Context.

---

## Context

### The mechanism is real and proven; nothing in the real ingestion path calls it

`publishEvent()` (`src/events/serviceBusPublisher.ts`) sends a real message to the real `social-listening-events` topic on the real `social-listening-dev` Service Bus namespace, setting `tenantId`/`schemaVersion` as application properties (ADR-0013/ADR-0019). `buildSocialPostIngestedEvent()`/`buildConnectorHealthChangedEvent()` construct the two thin payload shapes ADR-0012 decided. All of this is real, contract-verified directly against live Service Bus infrastructure (Stories 5.1/5.2/5.5's own contracts).

**Confirmed directly, not assumed:** grepped every file under `src/connectors/`, `src/posts/`, and `src/ingestion/` for any call to `publishEvent`/`ServiceBusClient`/`sendMessages` — zero matches. `src/events/serviceBusPublisher.ts` is imported only by its own contract tests (`story-5.2`, `story-5.5`) and, unrelatedly, `blobArchiveClient.ts`. None of the three real connectors (`pollGNewsSearch.ts`, `pollNewswireFeeds.ts`, `pollTenantOwnedFeed.ts`) publish anything after a successful `insertSocialPost()`. This is the same category of gap ADR-0052 found and closed for the polling scheduler itself (`registerSocialConnector()` had no real production call site until Story 1.13) — a real mechanism, fully built and tested in isolation, with no real caller wiring it into the path that actually matters.

### `watchlistId` being a required field is the harder part of this gap, not an afterthought

`SocialPostIngestedEvent.watchlistId` is `string` — not optional, not nullable (`src/events/socialPostIngestedEvent.ts`, confirmed directly). But real ingestion (a connector's poll cycle) inserts posts unconditionally, independent of any tenant's watchlist configuration — GNews's own `pollGNewsSearch()` runs against a single hardcoded default query (`'technology'`), not a watchlist's own terms. Watchlist matching (`resolveWatchlistAstDispatch()`/`matchPostsForWatchlistAst()`, `src/watchlists/dispatch.ts`) is applied later, at query/read time — confirmed directly against Story 2.11's own AC10 test, which calls `matchPostsForWatchlistAst()` over an already-fetched, already-inserted items array, not during ingestion itself.

**This means the current, already-Accepted event shape has never actually been exercised against a real ingestion flow.** Story 5.1's own contract proves `buildSocialPostIngestedEvent()`'s shape using a fixture literal, `watchlistId: 'watchlist-1'` (confirmed directly) — not a real watchlist match. A newly-ingested post may match zero, one, or several of a tenant's watchlists; the required, singular `watchlistId` field implies exactly one, an assumption nothing in this codebase has resolved.

### `listWatchlists()` cannot answer "every active watchlist for this tenant" — it's owner-scoped, not tenant-scoped

Confirmed directly against `src/watchlists/watchlistStore.ts`: `listWatchlists(tenantId, userId, options)` requires a `userId` and is RLS-scoped by both tenant *and* the specific owning user (ADR-0044 §5c) — a real, deliberate design choice for the Admin UI's own "see my own watchlists" screen, not an oversight. A connector's poll cycle runs per-`tenantId` only, with no "acting user" context at all. There is no existing function that answers "every active watchlist across every user in this tenant" — the query shape ingestion-time matching actually needs does not exist yet.

### `ConnectorHealthChangedEvent` has no stored "previous" state to diff against

`deriveConnectorHealth()` (ADR-0009) computes `ConnectorHealth` fresh from `ingestion_runs`/`platform_credentials` at read time — there is no `previous_status` column anywhere (confirmed directly, `connectorHealth.ts` read in full). Detecting a "change" requires comparing a before-and-after snapshot around the one event that could plausibly shift it: a poll attempt completing. `runIngestionAttempt()` — the one shared function every connector already calls — is the natural, and only, place this comparison can happen without a new per-connector wiring burden.

---

## Decision

### 1. `SocialPostIngestedEvent`: published from each connector's own per-post ingest loop, one event per matching watchlist

After a successful `insertSocialPost()`, each connector's own ingest function (`ingestGNewsArticles()`, `ingestNewswireItems()`, `ingestTenantOwnedFeedItems()`, and Wikipedia's own equivalent once Story 2.13 resumes) fetches the tenant's active watchlists scoped to its own `platformId` (new store function, §3 below), resolves dispatch per watchlist (`resolveWatchlistAstDispatch()`, already built, unmodified), and checks the just-inserted post against each one (`matchPostsForWatchlistAst()`, already built, unmodified). **One `SocialPostIngestedEvent` is published per matching watchlist** — a post matching three watchlists publishes three events, each a real, distinct "this specific watchlist just got a hit" signal a subscriber cares about individually; a post matching zero watchlists publishes none. This requires no change to the already-Accepted `SocialPostIngestedEvent` shape (`watchlistId` stays required) — it resolves the gap in Context by actually running real matching before publishing, rather than changing what was decided.

This is a real, deliberate per-connector code change (touching all three existing connectors plus Wikipedia) — not achievable by wiring it once into a shared function, since only the connector's own ingest loop knows the connector object (`resolveWatchlistAstDispatch()` needs it) and the just-inserted post's real content.

### 2. `ConnectorHealthChangedEvent`: published once, from inside `runIngestionAttempt()` itself

`runIngestionAttempt()` calls `deriveConnectorHealth(tenantId, platformId)` once immediately before opening the new `IngestionRun`, and once again immediately after closing it (success or failure) — the comparison naturally has both snapshots. If `status` differs, `runIngestionAttempt()` publishes one `ConnectorHealthChangedEvent`. **This requires zero per-connector wiring** — every connector, present and future, gets this automatically the moment it calls `runIngestionAttempt()`, the same "no core pipeline change for new connector registration" property ADR-0048 already established for connector registration itself, extended here to event publishing.

### 3. New store function: `listActiveWatchlistsForTenant(tenantId)` — tenant-wide, not owner-scoped

A new function in `watchlistStore.ts`, distinct from the existing, deliberately owner-scoped `listWatchlists(tenantId, userId)` — this one is a system/ingestion-context read, RLS-scoped by `tenantId` alone (no owning-user filter), returning every `is_active = true` row regardless of which user created it. Ingestion has no "acting user"; a tenant's watchlist coverage for matching purposes is not owner-partitioned from the platform's own point of view, only from the Admin UI's "whose list is this" point of view. Filtered by the calling connector's own `platform_ids` membership before AST resolution, so a connector never evaluates a watchlist that doesn't target it.

### 4. Publishing is best-effort — a Service Bus failure never fails real ingestion

Both publish call sites wrap `publishEvent()` in a catch-and-log, never a re-throw — the same "never throws, ingestion proceeds regardless" precedent `enrichPost()` already established for a downstream, non-critical side effect (ADR-0038). A tenant's real ingestion (posts actually stored, queryable via `GET /v1/posts`) must never fail or roll back because Service Bus was briefly unreachable — REST remains the source of truth (ADR-0012's own framing), events are a secondary, best-effort notification layer on top of it.

### 5. Scope: all three existing connectors, wired in the same pass — not partial

GNews, Newswire, and tenant-owned-feed all gain the same change in this story. Wikipedia (Story 2.13, paused pending this ADR) gains it as part of its own original build once resumed, not as a separate follow-up — every real connector publishes events from day one of this ADR's acceptance, none left as a named future gap.

### 6. Implementation safeguards (added at Menno's own review, same day, before acceptance)

Three concrete safeguards, required at Story time, not left as generalized Open Questions:

- **Fetch watchlists once per poll batch, not once per post.** `listActiveWatchlistsForTenant(tenantId)` (§3) is called exactly once per connector poll cycle (e.g. once at the top of `ingestGNewsArticles()`), filtered to the connector's own `platformId`, and the resulting array passed down through the per-post loop — never re-queried inside it. A per-post query against this table would turn one poll cycle's DB load into O(posts) queries instead of O(1), a real, avoidable spike this ADR's own Consequences already flagged as unmeasured; this closes the most obvious version of that risk at design time rather than leaving it purely as a later performance question.
- **Publish only after the post-insertion transaction has actually committed**, not from inside it and not from a still-open transaction. `publishEvent()` is called after `insertSocialPost()`'s own `await` has resolved and control has returned past any surrounding transaction boundary — never interleaved with it. Prevents a real, concrete race: a subscriber reacting to a `SocialPostIngestedEvent` by calling `GET /v1/posts/:id` before the insert is visible to a read replica or a not-yet-committed transaction, which the thin-events model (ADR-0012's own "fetch on demand" framing) depends on not happening.
- **No throttling built for v1 (per Alternatives Considered), but real Service Bus message-throughput must be watched during this story's own staging validation**, not just asserted safe in prose — a single popular post matching many tenant watchlists is a real, named fan-out risk (Consequences), and this is the one point in the build where it's cheap to notice if the naive per-match-event design is already a problem in practice, before any subscriber depends on the current cardinality.

## Consequences

**Positive**
- Closes a real, honestly-self-documented gap (`ingestion-events/SKILL.md`'s own "Known gaps" already named it) rather than letting it persist as new connectors keep getting added without ever exercising the event-publishing path for real.
- `SocialPostIngestedEvent`'s already-Accepted shape needs no change — the gap was never the shape, it was that nothing ever ran real matching before publishing.
- `ConnectorHealthChangedEvent`'s placement inside `runIngestionAttempt()` means this ADR's own second half requires zero future per-connector wiring — a real, durable simplification for whoever builds the next connector.
- Reuses every piece of already-built, already-tested machinery (`resolveWatchlistAstDispatch`, `matchPostsForWatchlistAst`, `deriveConnectorHealth`, `publishEvent`, `build*Event`) — no new mechanism invented, only new callers of existing ones.

**Negative**
- **Real, new per-poll-cycle cost**: every successfully-inserted post now triggers a tenant-wide watchlist fetch plus AST evaluation against every platform-matching watchlist, for every connector's every poll cycle. Not measured against real tenant-scale watchlist counts; a real, named performance question if a tenant ever accumulates a very large number of active watchlists — not solved here.
- **A post matching many watchlists publishes many events** — intentional (Decision §1), but a real fan-out multiplier on Service Bus message volume that didn't exist before this ADR; not bounded or throttled.
- **`listActiveWatchlistsForTenant()` is a second, structurally similar but differently-scoped watchlist-listing function** living alongside the existing owner-scoped `listWatchlists()` — a real, if narrow, surface-area increase or a future contributor could reach for.
- **No subscriber consumes these events in production today** — this ADR makes real publishing happen, but doesn't change the fact that ADR-0019's own "Known gaps" already names no real coordinated-cutover subscriber existing yet (e.g. a future Brand Reputation & Alerts feature). Real events will flow into a topic with no real listener, until one is built — not a reason to defer, since the publish-side gap is what's being closed here, but named so it isn't mistaken for "and now alerts work."

## Alternatives Considered

| Alternative | Disposition |
|---|---|
| **Publish `SocialPostIngestedEvent` unconditionally, one per post, with `watchlistId` made optional/nullable** | Rejected. Requires amending the already-Accepted ADR-0012 event shape for a field every real subscriber would need to branch on (`watchlistId === null` meaning "not relevant to any watchlist," which is arguably not an event worth publishing at all) — a real shape change to avoid doing real matching, not a genuine simplification. |
| **Publish `SocialPostIngestedEvent` from inside `insertSocialPost()` itself, achieving zero per-connector wiring like the health event** | Rejected. `insertSocialPost()` has no visibility into the calling connector's own object (needed for `resolveWatchlistAstDispatch()`) or into watchlist matching at all — moving matching logic into the generic post-insert store function would be a real layering violation, conflating "write a row" with "evaluate every active watchlist." |
| **A single, generic per-tenant "listWatchlists ignoring owner" mode added as an optional parameter to the existing `listWatchlists()`** | Considered; rejected in favor of a separate, distinctly-named function. Overloading the existing owner-scoped function's own meaning (an Admin-UI-facing, RLS-by-owner read) with a second, system-context mode risks a real security-relevant mistake — a future caller passing the wrong flag and silently seeing every user's watchlists in an Admin-UI context. A separate function name makes the two meanings impossible to confuse at the call site. |
| **Defer entirely, ship Wikipedia (Story 2.13) without event publishing, matching the other three connectors' current gap** | Rejected, per Menno's own explicit direction after this gap was raised — the pre-existing gap across all three connectors is exactly the reason to fix it now, comprehensively, rather than let a fourth connector ship into the same hole. |
| **A throttle/dedup layer bounding fan-out from a post matching many watchlists** | Considered; deferred, not designed. No real multi-watchlist-match volume data exists yet to size a throttle against — the same "don't build ahead of a demonstrated need" discipline this project applies elsewhere (ADR-0020's precedent). Named in Consequences as a real, unresolved question. |

## Open Questions

- [ ] **[Q-0058-1]** **Real-scale performance of per-post, per-poll-cycle watchlist evaluation** — not measured. Revisit if a tenant's real active-watchlist count or ingestion volume makes this a measured bottleneck, not speculatively.
- [ ] **[Q-0058-2]** **Whether a post matching many watchlists should be throttled/deduped/batched into fewer Service Bus messages** — named, not designed (Alternatives Considered).
- [ ] **[Q-0058-3]** **`ConnectorHealthChangedEvent`'s own tenant-wide vs. per-tenant-per-platform granularity at scale** — `runIngestionAttempt()` already runs per-`(tenantId, platformId)` pair, so this falls out naturally, but hasn't been stress-tested against many tenants polling many connectors concurrently.
- [ ] **[Q-0058-4]** **Real subscriber existence** — this ADR closes the publish-side gap only; no real consumer of either event type is designed or built here (ADR-0019's own already-named gap, unchanged by this ADR).

- **2026-08-17, later still the same day — two real corrections found and fixed during Story 5.19's own implementation, not assumed away.**
  1. **`listActiveWatchlistsForTenant()`'s own SQL mechanism was underspecified by Decision §3's original text.** Implementation surfaced that `watchlists`' actual RLS policy (`migrations/0025_watchlists_ownership_and_versioning.sql`) requires `app.user_id` to match a real owner, with no "omit it to see everyone" fallback — a naive tenant-only `withTenant()` call would silently return zero rows, not every user's watchlists. Investigated two mechanisms directly rather than assumed: a new, narrowly-scoped Postgres role (mirroring `platform_admin_role`/`tenant_deletion_role`'s existing precedent) vs. iterating the tenant's own users and reusing the existing, unmodified `listWatchlists()` once per user. Further investigation found `tenant_deletion_role` — which already holds a `GRANT SELECT, DELETE ON watchlists` — does **not** actually bypass this policy either (it's deliberately not `BYPASSRLS`, so the same `user_id` predicate still applies); real tenant offboarding never queries `watchlists` directly for this reason, relying on `ON DELETE CASCADE` via the `users` table instead. So no existing precedent in this codebase actually solves "read every user's watchlist in one tenant-wide query." Given that, and given watchlists are deliberately, privately per-user (ADR-0044 §5c, no Tenant-Admin override), Menno's own explicit direction was to **not** mint a new standing elevated-privilege credential to save a small, poll-batch-scoped loop — `listActiveWatchlistsForTenant()` iterates `listUsers()` and calls the existing `listWatchlists()` per user instead. No new migration, role, or RLS policy change of any kind.
  2. **Decision §1's "reuses `resolveWatchlistAstDispatch()`/`matchPostsForWatchlistAst()`, already built, unmodified" was a real correctness bug, caught by this story's own AC3 contract, not by inspection.** GNews already declares real `supportedQueryFeatures` (`AND`/`OR`/`NOT`/`TERM`, Story 2.7) — `resolveWatchlistAstDispatch()` therefore resolves `'native'` for any TERM-based watchlist query, and `'native'` mode's own contract (Story 2.7 AC3, Story 3.6/ADR-0021) is a pass-through: it presumes the connector's own outbound fetch was already parameterized by that exact query. None of the three real connectors do that — each polls one fixed query/feed set (GNews's own hardcoded default; Newswire's/tenant-owned-feed's fixed feed URLs), completely unrelated to any individual watchlist's terms. Trusting `'native'` here would have matched every TERM-capable watchlist targeting GNews unconditionally, regardless of real post content — silently defeating the entire purpose of watchlist-based notification. Fixed by always using the fallback evaluator (`matchesAst`) directly for this post-hoc "does this specific already-ingested post match this specific watchlist" purpose, never the dispatch/native shortcut, which is reserved for a genuinely different case (a connector's own poll call actually driven by a specific watchlist's translated query) that doesn't exist in this pipeline yet. Decision §1's text above is left as originally accepted, per this project's own "historical record, append corrections" convention — this note is the correction of record; `ingestion-events/SKILL.md`'s own Load-bearing constraints documents both corrections directly for future callers.
  
  Neither correction changes this ADR's own Decision §1–§6 in substance (per-connector publishing, once-per-batch loading, post-commit ordering, best-effort catch, tenant-wide watchlist visibility, shared `runIngestionAttempt()` health-diff placement) — both are implementation-level fixes to *how* Decision §1/§3 are actually realized, found by the contract-first process working as intended.
