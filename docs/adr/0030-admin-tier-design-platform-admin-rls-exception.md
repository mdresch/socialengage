# ADR-0030: Admin-tier design — Platform Admin via a narrowly-scoped, audited `BYPASSRLS` role; Tenant-Admin via ordinary tenant-scoped RLS plus an application-layer role check

**Status:** Accepted (2026-08-03) — drafted by the AI Business & Requirements Analyst persona, revised in place at review per Menno's break-glass instruction (Amendment Log below), then accepted. Second of a seven-ADR batch; assumes ADR-0029's authentication shape (single Entra external tenant, `sub`-based identity resolution, Postgres as sole owner of tenant/role/license data).
**Acceptance note (2026-08-03):** Accepted by Menno after reading, with one direct instruction folded in before acceptance: *"I noted the break the glass procedure and that will be a minimum Tenant Admin User Password Reset. No other access to the clients data is permitted."* See §3's revised Decision text and the Amendment Log for the full change. All remaining Open Questions stay open at acceptance, including the three added by this same instruction (Graph API mechanics, notification requirement, zero-reachable-Tenant-Admin escalation gap).
**Source:** `docs/adr/README.md`'s 2026-07-30 brainstorm (three-tier Platform Admin → Tenant/Tenant-Admin → Tenant User model; Platform Admin "leans toward provisioning-only... zero tenant-data access — floated, not locked"); ADR-0015's already-Accepted Negative Consequences bullet ("Background/batch processes that legitimately need to operate across all tenants... need a deliberate, audited way to bypass or iterate through RLS per-tenant, rather than one implicit admin mode that could be misused"); ADR-0028's flagged, unresolved Open Question ("Whether Platform Admin ever gets an emergency/support-access override... not addressed by Menno's statement either way").

## Context

Two tiers of "admin" are named in this project's own documents and must not be conflated, because they need structurally different mechanisms:

- **Tenant-Admin** — `Stakeholder-Register.md`'s own persona entry: "manages that tenant's own users, connectors, and watchlists" *within one tenant*. ADR-0028 already names this role as the sole holder of tenant-wide credential-creation authority, without deciding its mechanics.
- **Platform Admin** — the brainstorm's provisioning-only role: create/suspend a SocialEngage tenant, set its license/seat count, with a boundary that "leans toward... zero tenant-data access" but was left "floated, not locked."

This project's own codebase already contains a real, working precedent for a database-level RLS exception, just not one built for live application traffic: every migration (`migrations/0002_enable_rls_social_posts.sql` and every RLS-enabling migration since) runs as the Postgres bootstrap/superuser role, and `credential-envelope-encryption`'s own `SKILL.md` states the underlying mechanic plainly — "superuser/table-owner RLS bypass." Postgres never applies RLS to a superuser (no override exists), and `docs/adr/README.md`'s own Story 5.4 contract test comment confirms this is understood and relied on today ("superusers and table owners bypass RLS unconditionally"). This is the "migration role's existing superuser bypass" `docs/adr/README.md`'s 2026-07-30 note names as the shape candidate ADR #2 should follow — but reusing the *migration* role directly for live Platform Admin traffic would be far broader than needed (full schema-alteration rights, not just a row-level bypass) and is rejected below.

Postgres exposes the narrower primitive this ADR actually needs: `BYPASSRLS` is a role attribute independently grantable to any role via `ALTER ROLE ... BYPASSRLS`, separate from superuser status — a role can bypass RLS without holding any of a superuser's other privileges. This project has not yet used that narrower form; only the bootstrap superuser's blanket bypass exists today.

## Decision

### 1. Two tiers, two different mechanisms — not one mechanism reused twice

- **Tenant-Admin requires no database-level RLS exception at all.** A Tenant-Admin's session is an ordinary tenant-scoped session — the same `app_user` Postgres role, the same `app.tenant_id` context (`withTenant()`, ADR-0015), the same `tenant_isolation` policies as any Tenant User. Tenant-Admin's elevated authority (creating tenant-wide credentials per ADR-0028 Tier 2; managing its own tenant's users/connectors/watchlists per `Stakeholder-Register.md`) is enforced entirely at the **application authorization layer** — a check against the caller's resolved `users.role` (candidate ADR #4) before permitting the specific action — never via a separate database bypass, because Tenant-Admin's authority never needs to cross a tenant boundary; ordinary RLS already scopes it correctly.
- **Platform Admin requires a real RLS exception**, because its legitimate operations (create/suspend a SocialEngage tenant; set/adjust its license seat count) act on rows that, by definition, exist outside any single tenant's own RLS-visible scope — there is no `app.tenant_id` value that could ever make the `tenants` table's own registry-of-all-tenants readable through the ordinary tenant-scoped path. Mechanism: a dedicated Postgres role (e.g. `platform_admin_role`), granted `BYPASSRLS` directly — the same underlying Postgres primitive the migration role already relies on today, deliberately narrowed to a purpose-built, non-superuser role used for scoped live-application traffic, rather than reusing the broad migration superuser.

### 2. Platform Admin's bypass scope is locked in, not left floating a second time

`platform_admin_role`'s session is granted read/write **only** on the `tenants` table (candidate ADR #3) and any dedicated Platform-Admin-only table (candidate ADR #4's own separate Platform Admin identity table) — **it is never granted, and must never be used to query, `users`, `watchlists`, `social_posts`, `platform_credentials`, or any other tenant-content table.** This resolves the brainstorm's "floated, not locked" language into a firm proposed Decision: Platform Admin's boundary is provisioning-only, zero tenant-data access, concretely enforced by which tables its own Postgres role is even granted against — not merely a documented intention.

### 3. Emergency/support-access override — resolves ADR-0028's flagged Open Question — **revised at review, 2026-08-03 (Amendment Log below)**

**A minimal break-glass mechanism is granted, scoped to exactly one action: Platform Admin may force a password/credential reset for a tenant's Tenant-Admin identity. No other tenant data — content, credentials, connector state, or anything else — is ever visible or writable through this or any other Platform Admin mechanism.** Menno's own framing, verbatim: *"the break the glass procedure... will be a minimum Tenant Admin User Password Reset. No other access to the clients data is permitted."*

This is deliberately the narrowest possible recovery path for the single most likely lockout scenario this ADR's own §2 boundary would otherwise leave with zero remedy: a tenant whose only Tenant-Admin loses access to their own credential, with no other Tenant-Admin in that tenant to re-invite them. It is **not** a general "view/edit tenant data" override, **not** an impersonation capability, and **does not extend to ordinary Tenant Users** — a locked-out Tenant User is that tenant's own Tenant-Admin's problem to solve (re-invite, per candidate ADR #4), not Platform Admin's.

**Mechanism — does not require widening `platform_admin_role`'s Postgres grants at all.** Per ADR-0029, the credential itself lives in Entra, not Postgres — this action is entirely an Entra-side operation (invalidating/forcing reset of the Tenant-Admin's own Entra credential for the specific `sub` linked to that `users` row), invoked through Platform Admin's own application-layer identity, not a database query against `users` or any tenant-content table. **§2's locked-in boundary (`platform_admin_role` granted only against `tenants` and its own identity table) is unaffected and unweakened by this addition.** This is a deliberate, narrow, named exception to ADR-0029 §2's "no Entra-specific SDK/Graph API call on the request-authorization path" principle — that principle governs ordinary per-request token validation; this is a rare, out-of-band, fully-audited administrative action, not part of the request path. **The exact Microsoft Graph API call and permission scope needed to trigger this from a Platform-Admin-owned service identity is not verified here** — flagged as an Open Question below, same evidentiary bar the rest of this ADR series holds itself to.

**Platform Admin never learns or sets the Tenant-Admin's actual new credential value** — this is a forced invalidation/reset trigger only; the Tenant-Admin completes their own password-reset flow directly with Entra afterward, the same as any self-service reset, just system-initiated rather than self-initiated.

Every invocation of this path is logged under §5's existing audit requirement — the acting Platform Admin's identity, the target tenant, the target Tenant-Admin's identity, and a timestamp — treated as at least as sensitive as Platform Admin's other bypassed writes, not an exception to that requirement.

### 4. A third legitimate bypass use, named here and concretized by candidate ADR #4: request-time identity resolution

Every authenticated request, before any tenant RLS context can be set at all, must resolve the validated token's `sub` claim (ADR-0029) to a SocialEngage `(tenant_id, user_id, role)` — a structural chicken-and-egg (a query cannot be scoped by `tenant_id` to discover what the `tenant_id` is). This is a legitimate, narrow, **SELECT-only** bypass use, distinct from Platform Admin's own provisioning actions above — named here as a **third** documented category of deliberate, audited RLS bypass (alongside the existing migration/`pg_cron` superuser use, and this ADR's own Platform Admin use). Its exact shape (which role executes it; exactly which columns of `users` it may read) is left to candidate ADR #4, which owns the `users` table this lookup queries — this ADR establishes only that such a bypass is an anticipated, legitimate category, not an ad hoc improvisation when #4 needs it.

### 5. Audit requirement

Every write performed through `platform_admin_role`'s bypass (tenant creation, suspension, license-seat-count changes) **must** be logged with the acting Platform Admin's resolved identity (ADR-0029), the operation, the target tenant, and a timestamp — a durable, queryable record, not an application log line alone. This is a restatement of ADR-0015's own already-Accepted requirement ("a deliberate, audited way to bypass... rather than one implicit admin mode"), not a new invention. The exact schema (a dedicated audit table, or a general mechanism) is left to candidate ADR #3, which owns the `tenants` table this auditing is most tightly coupled to.

### 6. Platform Admin's own identity is not a `users` row

Forward-referenced here so candidate ADR #4 isn't the first place this appears: Platform Admin does not belong to any SocialEngage tenant and does not fit the tenant-scoped shape `users` (candidate ADR #4) is built around. It is modeled in its own, separate table, decided concretely by ADR #4.

## Consequences

**Positive**
- Reuses a real, already-proven Postgres primitive (`BYPASSRLS`/superuser exemption) this project already depends on for migrations and `pg_cron`, rather than inventing a new bypass mechanism from scratch.
- Locks in a boundary the brainstorm explicitly left floating, and directly resolves ADR-0028's flagged Open Question rather than leaving it open a second time in this batch.
- Keeps Tenant-Admin's authorization model maximally simple: zero new database mechanism, reuses ADR-0015's existing RLS wholesale.
- **Added at review, 2026-08-03:** a real, narrowly-scoped recovery path now exists for the single most likely lockout scenario (a tenant's only Tenant-Admin losing their own credential) — without reintroducing any broader tenant-data access, and without widening `platform_admin_role`'s already-locked Postgres grant at all (§3).

**Negative**
- `BYPASSRLS` is an unconditional, row-level bypass for whatever tables a role holding it is granted access to. A future migration or code change that mistakenly grants `platform_admin_role` access to a tenant-content table (not just `tenants`) would silently defeat RLS for that table, with no additional guardrail beyond code review and the audit log catching it *after* the fact — not preventing it. This is a real, named risk of the chosen mechanism, not a costless one.
- **Revised at review, 2026-08-03 (was: "declining an emergency-access override... accepted gap"):** a break-glass path now exists, but only for the Tenant-Admin-credential-reset case. A tenant with **zero** remaining reachable Tenant-Admins and no other recovery contact still has no sanctioned path back in under this ADR — named as a real, remaining gap, not solved by this addition, and not addressed further here (Open Questions, below). The Graph API mechanism itself (§3) is also not yet verified against Microsoft's current documentation — a real, if narrow, implementation-readiness gap for whoever builds candidate ADR #4's story.

## Alternatives Considered

- **Application-level-only Platform Admin authority, no database bypass** (e.g. a sentinel `tenant_id` value the `tenants` table's own RLS policy special-cases as "visible to everyone") — rejected: invents a fragile sentinel-value hack instead of reusing this project's own proven `BYPASSRLS` precedent, and is harder to audit cleanly.
- **Grant Platform Admin the existing migration/bootstrap superuser role directly** — rejected: far broader than needed (schema-alteration rights, not just a row-level bypass), violates least-privilege, and the migration role's own bypass is acceptable today specifically because it is a rare, human-supervised action, not routine live-application traffic — reusing it directly would erase that distinction.

## Open Questions for decision

- **Exact audit-log schema** for Platform Admin's bypassed writes — deferred to candidate ADR #3.
- **Precisely which Postgres role executes the identity-resolution bypass (§4)** — the same `platform_admin_role`, or a fourth, even-narrower role — deferred to candidate ADR #4.
- **Whether Tenant-Admin ever needs a bypass of its own** for anything currently named in this project — this ADR's answer is no; revisit only if a real, specific need is later identified, not speculatively.
- **Added at review, 2026-08-03 — the exact Microsoft Graph API call and permission scope needed to trigger a forced credential reset for a specific Entra user from Platform Admin's own service identity** (§3) — not verified against Microsoft's current documentation; whoever builds this must confirm directly before implementing, same evidentiary bar as ADR-0029's own Entra claims.
- **Added at review, 2026-08-03 — whether the break-glass reset (§3) requires additional notification** (e.g. alerting the affected Tenant-Admin, or a secondary tenant contact, that a reset was triggered) — not decided, a real design question for whoever builds candidate ADR #4's story.
- **Added 2026-08-03 — a Platform Admin console design mockup now exists** (`docs/design/platform-admin-console-mockup-2026-08-03.html`), covering the tenant list, provisioning, break-glass confirmation flow, and audit log this ADR describes. A layout/flow reference only (plain HTML, not Next.js — see that folder's `README.md`); it does not resolve either of the two Open Questions immediately above, and its audit-log columns are illustrative, not a schema decision.
- **Added 2026-08-03 — infrastructure/operational metrics (server health, connectivity, storage size) are a real, named future capability for Platform Admin's own console, deliberately not designed by this ADR or the mockup above.** Menno's own words: *"lets place that into a future when the systems limitations and requirements are well known."* Deferred under this project's own "don't build ahead of a demonstrated need" discipline (ADR-0020's distributed rate-limit gate is the direct precedent for this kind of call) — revisit once this project's actual operational limitations and requirements are well enough understood to design real metrics/thresholds against, not speculatively now. See `docs/design/README.md`'s matching note.
- **Added 2026-08-03, same day — the basis (§2's "zero tenant-data access") is unchanged and extends to that future metrics capability too, not just to today's provisioning/break-glass screens.** Menno's own words, verbatim: *"the basis remains unchanged no tenant data to be viewable as admin. not the details of what a client sees as posts or could be refered to as user cata."* Whenever infrastructure metrics are eventually designed, they must stay aggregate/operational (e.g., storage consumed in bytes, connectivity/uptime status) — never a window into tenant content itself (posts, watchlists, or anything a client would recognize as their own user data). This is not a new rule; it is §2's existing boundary, restated here so the future metrics work doesn't quietly reopen it.
- **Added at review, 2026-08-03 — a tenant with zero remaining reachable Tenant-Admins** (this mechanism resets a credential, but presumes at least one valid Tenant-Admin identity to reset) — no escalation path is defined for this case; named as an explicit residual gap (Consequences, above), not resolved by this ADR.
