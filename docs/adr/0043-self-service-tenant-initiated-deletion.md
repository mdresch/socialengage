# ADR-0043: Self-service, Tenant-Admin-initiated tenant deletion — a narrow, additive supersession of ADR-0039 Decision §1's "cannot self-delete" prohibition

**Status:** Proposed — drafted by the AI Business & Requirements Analyst persona. This persona does not hold ADR-acceptance authority (`Stakeholder-Register.md` S-11: "no unilateral acceptance authority — Menno accepts every ADR"); Menno's own instructions that motivate this ADR (quoted verbatim below) were relayed through this session's orchestrating agent, not received as Menno's own direct message to this persona, so they are treated as the request to draft this decision, not as the acceptance of it. Awaiting Menno's own separate review and acceptance, the same treatment every other ADR in this series has received.
**Source:** Menno's own instruction, verbatim, relayed this session: *"could you check tenant admin can request tenant delete at which all connectors stop and no more data ingestion takes place for the tenant. a time period for download all available data in .csv or json format soft delete period then confirmation tenant delete is final."* When asked to clarify Platform Admin's role in this flow, Menno confirmed directly, via a structured choice: **"Fully self-service, Platform Admin only sees the audit trail."** Platform Admin's own separate, already-built Story 3.7 export/delete endpoints (ADR-0039) are confirmed unaffected, additive, for the Platform-Admin-initiated case.

## Context

ADR-0039 (Accepted 2026-08-06, hours before this ADR was drafted, same session) designed the tenant offboarding data lifecycle — export scope, per-table deletion treatment, async/bounded/partition-aware execution — and its own Decision §1 states, as a "deliberate, named limitation": **"A tenant cannot self-delete its own account via any self-service mechanism."** That same section named a possible future direction it explicitly declined to design: *"A future self-service deletion request could route to Platform Admin as a reviewed request (mirroring ADR-0030 §3's break-glass request/execute pattern) — named as a real possible future direction, not designed further here (Open Questions, below)."*

Menno has now resolved that Open Question directly — and resolved it *more aggressively* than the direction ADR-0039 §1 itself anticipated. ADR-0039's own aside assumed any future self-service path would still route through Platform Admin for review (the break-glass request/execute pattern, where a human Platform Admin picks up and executes a pending request). Menno's actual instruction removes that review step entirely: **"Fully self-service, Platform Admin only sees the audit trail"** — no Platform Admin approval gate anywhere in the request-export-wait-confirm flow.

This is a real reversal of ADR-0039 Decision §1's own stated prohibition and its own stated reasoning (*"an irreversible, cross-table deletion affecting every tenant-content table is not a self-service action at this project's current scale, consistent with ADR-0030 §3's own 'narrowest possible' framing"*) — not a parameter tweak, not an implicit-requirement clarification, and not merely resolving an Open Question in the direction that Open Question already assumed. `docs/adr/README.md`'s own governance table, row 1, is squarely on point: *"The underlying decision itself changes → New ADR, or a superseding ADR that says so explicitly."*

**Why a new ADR, not an in-place, dated revision to ADR-0039 itself, despite both being drafted the same session, hours apart:**

1. ADR-0039's own Acceptance note states, verbatim: *"Accepted by Menno, verbatim: 'Good news ADR 0039 is approved.' Accepted as drafted, no revisions."* That sentence is itself a specific, dated, quoted historical claim about what was decided and confirmed unrevised. Editing Decision §1's own text now would make that Acceptance note materially misleading to a future reader who trusts it — the whole reason this series' governance table treats an Accepted ADR's Decision/Consequences text as "a historical record [that] stays put" (table's own closing line).
2. The ADR-0030/ADR-0032 precedent this task explicitly asked to be weighed against is not, on inspection, the same situation: both of those were revised in place **before** Menno's acceptance action — while still Proposed, during their own first review round, per their own Amendment Log entries ("Revised at review, before acceptance... per this project's own convention, an in-place revision before acceptance is not a supersession — see ADR-0026/0027/0028/0029's own precedent," ADR-0030's Amendment Log, verbatim). ADR-0039's Decision §1 text, by contrast, was already Accepted, verbatim, no revisions, hours ago. Editing genuinely-Accepted Decision text is a different governance act than editing genuinely-Proposed draft text mid-review, however close in wall-clock time the two events are — using elapsed time as the deciding factor (rather than acceptance status) would create an undefined, indefensible boundary ("how many hours count as still-same-review-round?") that this series has never needed before and shouldn't invent now.
3. The reversal turns out not to be narrowly about "who may initiate deletion" at all — closing this gap for real (see Decision, below) surfaces a genuine, additional architectural boundary question ADR-0039 itself never touched: `tenants.status` is not merely policy-restricted to Platform Admin, it is **database-GRANT-restricted** to `platform_admin_role` (`migrations/0017_create_tenants.sql`: `GRANT UPDATE (status, license_seat_count) ON tenants TO platform_admin_role`; `app_user` — the role every Tenant-Admin session runs as — is granted only `UPDATE (active_seat_count)`). A self-service deletion flow either needs a new, narrow, explicitly-granted write path for a Tenant-Admin session, or a background executor that performs the eventual state transition under `platform_admin_role`'s own connection without a live Platform Admin's judgment call triggering it. That is a real "hard-to-reverse, real architectural boundary" decision by this series' own established ADR-worthiness bar (ADR-0027/0028/0030/0035/0036/0037's own bar, restated at ADR-0041's acceptance) — not a detail that belongs folded into a dated note on an already-Accepted ADR whose own Decision text never contemplated it.

**A "superseding ADR that says so explicitly" (the governance table's own named option in row 1) is the mechanism this ADR uses**, per the same pattern this file already uses for a still-Proposed ADR changing part of an Accepted one's decision (row 5's "Pending supersession note," e.g. ADR-0018 ← ADR-0039 itself) — see "Note on relation to ADR-0039," below.

## Decision

### 1. Supersedes ADR-0039 Decision §1's "cannot self-delete" prohibition specifically — nothing else in ADR-0039 is re-decided

A `tenant_admin`-authenticated caller (per ADR-0032's `role` column; **never** `tenant_user`) may request deletion of their own tenant, fully self-service: request, export, wait out a grace period, and confirm, with **no Platform Admin approval step anywhere in the path.** Platform Admin's role in this flow is limited to what Menno's own words specify — visibility via the audit trail, nothing more.

Platform Admin's own separately-triggered path (Story 3.7's `POST /v1/admin/tenants/:id/export` / `POST /v1/admin/tenants/:id/delete`, `platform_admin_role`-only) is **entirely unaffected** — this ADR adds a second, independent trigger onto the same underlying deletion mechanism (Decision §5, below); it does not replace, gate, or route through the first. ADR-0039 Decision §2 (export scope), §3 (per-table deletion treatment), §4 (asynchronous, bounded, partition-aware execution), and §5 (suspension stays distinct from deletion) are all reused as-is, unmodified, by this new path — this ADR decides *who else* may trigger the same already-decided mechanism and *how* that trigger reaches it, not what the mechanism itself does.

### 2. New tenant-lifecycle state, narrowly granted — mirrors `active_seat_count`'s existing precedent, does not touch the locked `status` column

Two new nullable `timestamptz` columns on `tenants`: `deletion_requested_at` and `deletion_confirmed_at`. Both are granted `UPDATE` to `app_user` — the same narrow, per-column-GRANT technique `migrations/0017_create_tenants.sql` already uses for `active_seat_count` (`GRANT UPDATE (active_seat_count) ON tenants TO app_user`), not a widening of `app_user`'s access to `status`, `license_seat_count`, or `domain`, all three of which stay exactly as locked to `platform_admin_role` by ADR-0030 §2/ADR-0031 §3 today. RLS enforcement needs no new policy — `tenants`' existing `id`-scoped `tenant_isolation` policy (ADR-0031 §2) already confines a Tenant-Admin's session to their own row; the application-layer role check (ADR-0030 §1's existing "Tenant-Admin requires no database-level RLS exception... enforced entirely at the application authorization layer" pattern) is what restricts the write to a `tenant_admin`-role caller specifically, not `tenant_user`.

`tenants.status` (`'active'`/`'suspended'`) is deliberately left untouched by the request/export/grace-period/cancel steps of this flow — only the final, irreversible execution step (Decision §5) ever causes the underlying `tenants` row itself to be removed, and that step runs under `platform_admin_role`'s existing, already-locked bypass, exactly as ADR-0039 already designed. This flow never needs `platform_admin_role`'s bypass for anything except that one, already-decided, final execution.

### 3. Ingestion halt — enforced at `runIngestionAttempt()`, the one real, shared choke point that already exists; no tenant-iterating scheduler exists yet to enforce it anywhere else

**Verified directly, not assumed:** no code in `social-listening-core` currently iterates "active tenants" and calls a connector's poll function in a loop — `pollGNewsSearch()` (`src/connectors/gnews/pollGNewsSearch.ts`) and `pollNewswireFeeds()` (`src/connectors/newswire/pollNewswireFeeds.ts`) are today invoked only by their own contract tests. A future scheduler (single loop, per-tenant queue, or something else) is not yet built and is out of this ADR's own scope to design.

What does already exist, and what every real ingestion attempt — however it is eventually triggered — already funnels through, is `runIngestionAttempt()` (`src/ingestion/runIngestionAttempt.ts`): both shipped connectors call it, and it is the single shared function that opens an `IngestionRun` and executes the connector's own `attempt()` closure. **The correct, forward-compatible enforcement point is a guard at the top of `runIngestionAttempt()`, before `startIngestionRun()` is called**: if the given `tenantId`'s `deletion_requested_at` is non-null, the attempt is refused immediately (a new, non-retryable classified outcome, e.g. `ClassifiableError('tenant_deletion_requested', ...)`, consistent with `ingestion/errorClassification.ts`'s existing pattern) rather than opening a run at all. This guarantees the halt takes effect regardless of which connector or future scheduler eventually calls it, without requiring a scheduler to exist first. **This is a real, named implementation change for whoever builds Story 3.8 — not built here** (documentation-only, per this persona's own scope boundary).

### 4. Export — reuses Story 3.7's own export logic, re-triggerable, caller's choice of CSV or JSON

A new `tenant_admin`-only endpoint (e.g. `POST /v1/tenants/self-service-deletion/export`) triggers an export of the same data ADR-0039 §2 already scopes (`social_posts` including archived `rawPayload` resolved via its blob pointer, `authors`, `watchlists`, `ingestion_runs` including archived rows) for the caller's own tenant only, reusing Story 3.7's own export service function directly rather than a second implementation of the same query/assembly logic — authorized differently (own-tenant, `tenant_admin` role, ordinary RLS scope) rather than via `platform_admin_role`. **Format is the caller's explicit choice, CSV or JSON** — this resolves, for this path specifically, the exact question ADR-0039 §2's own Open Questions left as "an implementation-time choice, not decided here." **Re-triggerable, not one-shot** — available any number of times from request until the final confirmation actually executes (Decision §5), not narrowly limited to a single download.

### 5. Grace period — 30 days, named as a real, explicit, revisable implementation default; cancellation available throughout

**30 days**, configurable, following this project's own established convention (ADR-0018's `rawPayload`/`IngestionRun` windows, ADR-0037's rate-limiting windows) of naming a real number rather than leaving it "TBD," explicitly revisable rather than treated as fixed. This ADR does not claim GDPR or any other regulation mandates this specific figure — it does not, for any deletion-grace-period length — 30 days is chosen as a defensible default that gives a tenant genuine time to complete a CSV/JSON export of potentially large data (`social_posts`, `authors`, `ingestion_runs`) without indefinitely delaying an explicit, deliberate deletion request the tenant themselves initiated.

**Cancellation is available at any point from request until the moment final confirmation is actually executed** — including after the 30-day grace period has technically elapsed but before the tenant has actually confirmed. Argued explicitly, not defaulted: a grace period with no way to change your mind is a confusing half-feature, not a real safety mechanism — a Tenant-Admin who requested deletion in error, or whose organization's circumstances changed, must have a real path back for as long as the deletion has not yet actually and irreversibly happened. Mechanism: a `tenant_admin`-only endpoint (e.g. `DELETE /v1/tenants/self-service-deletion`) nulls both `deletion_requested_at` and `deletion_confirmed_at`, which — via Decision §3's own guard — immediately resumes ingestion. There is no reason to forbid cancellation once 30 days have passed but before confirmation; the grace period is a floor on how soon deletion can be confirmed, not a ceiling on how long the tenant may still change their mind.

### 6. Final confirmation — only reachable once the grace period has genuinely elapsed; reuses, does not duplicate, Story 3.7's own execution mechanism

A `tenant_admin`-only confirmation endpoint (e.g. `POST /v1/tenants/self-service-deletion/confirm`) is rejected outright (HTTP 409, naming the remaining wait) if `now() < deletion_requested_at + 30 days` — an early attempt is rejected, never silently ignored or queued. Once eligible, confirmation sets `deletion_confirmed_at` and, in the same application-code action (no new Postgres role, no widened grant), invokes Story 3.7's own existing internal deletion-execution function directly — the same bounded, asynchronous, partition-aware job ADR-0039 §4 already designed and Story 3.7 already builds, running under `platform_admin_role`'s existing, already-locked bypass, called from application code the same way `adminTenantsRouter.ts`'s handlers already call `tenantStore.ts` functions that internally use `getPlatformAdminPool()` — not a second, parallel deletion pipeline. This mirrors Story 5.15's own precedent of a narrower, purpose-built role (`tenant_signup_role`) reaching an otherwise-privileged action through its own scoped path rather than widening `platform_admin_role` itself.

### 7. Audit — a real, named, deliberate extension of `platform_admin_audit_log`'s own scope, not a silent reinterpretation

Every step (request, each export, cancellation, confirmation) is logged via the existing `platform_admin_audit_log` table and `logPlatformAdminAction()` function (ADR-0030 §5), satisfying Menno's own "Platform Admin only sees the audit trail" requirement. **This is a real, named widening of that table's own original scope, argued explicitly rather than smoothed over**: ADR-0030 §5's original text describes this log as recording "every write performed through `platform_admin_role`'s bypass" — every row until now has corresponded to an actual `platform_admin_role`-executed write. Under this ADR, the request/export/cancel steps are ordinary `app_user`, tenant-scoped actions that never touch `platform_admin_role`'s bypass at all; they are logged to this table purely for Platform-Admin visibility, not because the write itself required the bypass. **This is not unprecedented** — Story 5.15 (ADR-0037 §2) already established exactly this pattern: `tenant_signup_role`, a role other than `platform_admin_role`, holds its own separate `INSERT` grant on `platform_admin_audit_log` (`migrations/0021_create_tenant_signup_role.sql`) so its own writes can be logged to the same shared table without borrowing `platform_admin_role`'s bypass. This ADR extends the identical mechanism to `app_user`: a new, narrow `GRANT INSERT ON platform_admin_audit_log TO app_user`, mirroring `migrations/0021`'s own precedent exactly, so a Tenant-Admin's own session can log these five lifecycle events directly.

**A second, related, real extension named explicitly:** `PlatformAdminAuditEntry.actorIdentity` has, until now, always been a Platform Admin's own resolved identity (`identity.adminId`, per every existing call site in `tenantStore.ts`). For this flow's request/export/cancel/confirm entries, `actorIdentity` instead records the requesting/confirming Tenant-Admin's own identity — the first time this field's value is not itself a Platform Admin. The field's own type (`string`) and the table's own schema (`actor_identity text not null`) already accommodate this without a schema change; only the *meaning* — "whoever performed this Platform-Admin-visible action," not "which Platform Admin performed this bypassed write" — is being named here as deliberately broadened, not silently assumed.

### 8. Explicit non-goal: this ADR does not decide whether a `requireTenantAdmin` middleware helper is added

`src/http/auth/requireTenantUser.ts` today exposes `requireTenantUserIdentity()` (returns `tenantId`/`userId`/`role`) and `requirePlatformAdmin()`, but no dedicated `requireTenantAdmin()` helper analogous to `requirePlatformAdmin()`'s shape — every route needing `tenant_admin` specifically (e.g. Story 5.16's `GET /v1/tenants/domain-signup-attempts`) checks `role === 'tenant_admin'` inline today. Whether this flow's five new endpoints add such a helper or follow that same inline-check precedent is an implementation choice for whoever builds Story 3.8, not decided here.

## Consequences

**Positive**
- Closes the exact gap ADR-0039 §1 named as a real possible future direction, resolved directly rather than left open a second time.
- Reuses every mechanism this project already has a real, working precedent for — `active_seat_count`'s narrow per-column `app_user` grant (ADR-0031 §1), `tenant_signup_role`'s own separate `INSERT` grant on `platform_admin_audit_log` (ADR-0037 §2/Story 5.15), and Story 3.7's own deletion-execution function (ADR-0039 §4) — rather than inventing a new bypass mechanism, a new deletion pipeline, or a new audit path.
- Gives a tenant a genuine, reversible-until-the-last-moment path to leave the platform entirely under their own control, addressing the general spirit of GDPR Article 17 (right to erasure) more directly than a Platform-Admin-only path could — the same caveat ADR-0039 §2 already names applies here too: this ADR does not itself certify legal compliance.
- Names, rather than silently produces, two real scope extensions to `platform_admin_audit_log` (a non-`platform_admin_role`-executed write category; a non-Platform-Admin `actorIdentity` value) so a future reader of ADR-0030 §5 alone isn't misled about what every row in that table now means.

**Negative**
- **A real, DB-level privilege widening for `app_user`, however narrow**: two new `UPDATE`-granted columns on `tenants`, and a new `INSERT` grant on `platform_admin_audit_log`. Both are scoped as narrowly as this project's own existing precedents (`active_seat_count`, `tenant_signup_role`'s audit-log grant) — but every `tenant_user` session shares the same Postgres role as every `tenant_admin` session (ADR-0030 §1's own "Tenant-Admin requires no database-level RLS exception... enforced entirely at the application authorization layer"), so the actual restriction to `tenant_admin` specifically is enforced only at the application layer for these two new writes, not the database layer, the same trade-off ADR-0030 §1 already accepted for every other Tenant-Admin-specific action.
- **`platform_admin_audit_log`'s own name and original framing (ADR-0030 §5) no longer precisely describes every row it contains** — a future reader must know this ADR exists to understand why some `actorIdentity` values are Tenant-Admins, not Platform Admins. Named explicitly (Decision §7) rather than left implicit, but a real, permanent documentation burden this ADR adds.
- **No self-service, Tenant-Admin-initiated deletion path existed at all until this ADR** — the operational risk ADR-0039 §1 originally named (an irreversible, cross-table deletion, self-triggered with no human-in-the-loop review) is real and does not disappear because export and a 30-day, cancellable grace period exist; those are real, meaningful controls, not a full substitute for the human review ADR-0039 §1's original reasoning relied on. This is a genuine, accepted trade-off this ADR makes on Menno's own explicit instruction, not a risk this ADR argues away.
- **A departed/deleted tenant's own audit trail (`platform_admin_audit_log` rows referencing it) survives the tenant's own deletion**, exactly as ADR-0039 §3 already decided for the Platform-Admin-initiated path — unchanged here, but worth restating since this path adds new row *kinds* (request/export/cancel/confirm) to that same surviving trail.

## Alternatives Considered

- **Route the self-service request through Platform Admin for review before execution** (the exact "future direction" ADR-0039 §1's own aside contemplated, mirroring ADR-0030 §3's break-glass request/execute pattern) — this was the more conservative option and the one ADR-0039 itself anticipated, but rejected here because Menno's own explicit, structured-choice answer ("Fully self-service, Platform Admin only sees the audit trail") directly forecloses it. Named, not silently dropped, because it was the design ADR-0039 itself expected and is worth recording as the road not taken.
- **Widen `platform_admin_role`'s own grant to cover the two new columns, instead of granting `app_user`** — rejected: this would require every ordinary tenant-scoped request in this flow to route through `platform_admin_role`'s connection, which ADR-0030 §2's own "locked-in, not left floating a second time" framing treats as reserved for genuinely cross-tenant operations; granting `app_user` a narrow, column-scoped write on its own row is the same technique this table already uses for `active_seat_count` and keeps this flow's ordinary steps inside the ordinary tenant-scoped RLS path.
- **A separate `tenant_deletion_requests` table instead of two columns on `tenants`** — considered; two nullable columns on `tenants` itself were chosen instead because the state being tracked (is deletion requested, is it confirmed) is a property of the tenant itself, not a repeated/multi-row event log the way `domain_signup_attempts` genuinely is (a tenant can have many sign-up attempts, but at most one live deletion request at a time) — a separate table would add machinery this ADR's own scope doesn't need. Revisit if a future requirement (e.g., a full request-history view beyond what the audit log already gives) makes a dedicated table genuinely necessary.

## Open Questions for decision

- **The exact wording and channel of any user-facing warning/reminder as the grace period nears its end** (e.g., "your data will become permanently unrecoverable in N days") — not designed here; a real UX question for whoever builds the `social-listening-admin` surface for this flow (out of this ADR's own backend scope).
- **Whether a `requireTenantAdmin()` middleware helper is added** (Decision §8) — left to implementation.
- **Whether this flow needs its own rate-limiting/abuse-prevention consideration** (e.g., a Tenant-Admin repeatedly requesting and cancelling) — not designed here; no evidence of a real problem exists yet to design against, consistent with this project's own "don't build ahead of a demonstrated need" discipline (ADR-0020's precedent).
- **The `social-listening-admin` UI surface for this flow** (a settings screen, confirmation modals, the export download UX) — not designed here; Epic 6 CRUD/UI-surface territory, not this ADR's backend-authorization scope.
