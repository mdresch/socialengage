# ADR-0061: Tier-3 (user-bound) poll scheduling — per-user enumeration, cross-user health/in-flight isolation, `pollUser()` as a new generic scheduler surface

**Status: Accepted (2026-08-18)** — drafted by the AI Business & Requirements Analyst persona, left Proposed per this persona's own charter boundary (it does not hold ADR-acceptance authority), then reviewed and approved by Menno (Sponsor) the same day, verbatim: *"ADR-0061 is complete, coherent, and ready for my acceptance. It cleanly bridges the gap between ADR-0060's data model and the background scheduling engine, resolving all implicit cross-user race conditions before they ever manifest in production. Excellent work and I approve ADR 0061"*. Accepted as drafted — no review-round amendments were requested; the review that came back confirmed the existing design rather than changing it. See Amendment Log.

**Source:** ADR-0052 (Accepted 2026-08-13) Decision §6 / Open Question 2 — explicitly named, without designing, the expected future shape of Tier-3 poll scheduling (a `poll(tenantId, userId)` signature and a `RequestGate` key of `(tenantId, userId, providerId)`), and explicitly deferred it: *"no such connector exists yet to design against."* One now does — ADR-0060 (Accepted 2026-08-18) gave Facebook a real, working Tier-3 poll function (`pollFacebook(tenantId, userId)`), but confirmed directly (grepped repo-wide) that this function has zero real call sites anywhere in the running server: its only references are its own definition and a comment in `bootstrapConnectors.ts` explaining why the scheduler's own wrapper `poll()` for Facebook throws rather than ever being reached. Menno confirmed via a structured choice (`AskUserQuestion`, not a freeform quote) that this gap gets its own ADR and story, kept separate from ADR-0060/Story 6.27's own storage/credential/UI scope.

---

## Context

### The real, current gap — confirmed directly, not assumed

- `pollFacebook(tenantId, userId)` (`pollFacebook.ts`) is never called by anything in the real running server. `bootstrapConnectors.ts`'s own Facebook registration gives it a `poll` property that unconditionally `throw`s, with a doc comment stating plainly: *"Real Facebook ingestion requires `pollFacebook(tenantId, userId)` invoked directly, or real Tier-3 scheduler support (ADR-0052 Decision §6's own named, not-yet-built gap)."* This is Story 2.15's own deliberately-honest design, not a bug — but it means a tenant connecting a Facebook Page today (single, per Story 2.15/6.23; multiple, once Story 6.27 ships) stores real, working credentials that are never actually polled by anything. No manual "poll now" endpoint exists either.
- ADR-0052 Decision §6 already named the expected future shape without designing it: a `poll(tenantId, userId)` signature and a `RequestGate` key of `(tenantId, userId, providerId)`, extending `socialConnectorKey`'s `tenantId:providerId` shape by one segment, the same pattern `aiModelKey`'s `tenantId:providerId:modelId` already established. This ADR is the first to actually design it, now that a real Tier-3 poll connector (Facebook) exists.

### A real bug confirmed by direct investigation, not hypothesized — Menno's own suspicion checked against the actual query

**Confirmed:** if `pollScheduler.ts`'s existing tenant-wide machinery were naively extended to Tier-3 pairs without change, two different users' own independent Facebook polls would incorrectly block/unblock and health-gate each other. Verified directly, not assumed:

- `getMostRecentRunStatus(tenantId, platformId)` (`ingestionRunStore.ts`, lines 55–66) — `SELECT status FROM ingestion_runs WHERE platform_id = $1 ORDER BY started_at DESC LIMIT 1`. **No `user_id` filter exists, and `ingestion_runs` has no `user_id` column at all today.** If this function were called as the Story 1.14 in-flight guard for a `(tenantId, userId, 'facebook')` tuple, it would return the single most recent run across **every** user's Pages for that tenant — User A's still-`running` run would incorrectly report the pair "not due yet" for User B too, and vice versa.
- `deriveConnectorHealth(tenantId, platformId)` (`connectorHealth.ts`) — its own `ingestion_runs` query is likewise `WHERE platform_id = $1`, no user scoping. `pollScheduler.ts`'s due-check reads `health.lastAttemptAt` from this same blended result (`runSchedulerTick()` line 91–92) — one user's recent poll would make the shared pair look "recently attempted" for every other user's own poll, delaying or skipping polls that are, for that specific user, genuinely overdue.
- **A second, adjacent bug found in the same function, not previously named anywhere:** `deriveConnectorHealth()`'s own `credentialStatus` sub-query (`SELECT status FROM platform_credentials WHERE platform_id = $1 ORDER BY created_at DESC LIMIT 1`) is *also* unscoped by `user_id` — once more than one tenant user holds their own Tier-3 Facebook credential, this field non-deterministically reflects whichever user's credential row happened to be created most recently, not the specific user the caller actually asked about.
- **A third, more consequential bug, in already-shipped code:** `shouldAttemptIngestion(tenantId, platformId, ownerType = 'tenant', userId?)` (`connectorHealth.ts`, Story 1.11) already correctly checks `isConnectorActive(tenantId, platformId, ownerType, userId)` — ADR-0051's own per-user activation scoping is right. But its *own* internal call, `const health = await deriveConnectorHealth(tenantId, platformId)`, passes neither `ownerType` nor `userId` through — the `failing`-status auto-disable circuit breaker this function gates on is computed **tenant-and-platform-wide, blended across every user**, not per the specific user being checked. Once two tenant users each hold their own Tier-3 Facebook connection, one user's badly-failing Pages would trip `shouldAttemptIngestion()`'s `failing` short-circuit for every *other* user's own healthy Pages too — a real, false-negative auto-disable bug, present in already-shipped Story 1.11/1.12 code, surfaced only now because Tier-3 scheduling is finally being designed against it.

**Confirmed: Menno's suspicion is correct, on all three counts (in-flight guard, due-check freshness, and the newly-found cross-user auto-disable blending), and the root cause is the same in each case** — every one of these functions is keyed by `(tenantId, platformId)` only, with no `user_id` anywhere in `ingestion_runs`' own schema to filter on.

### Composition with ADR-0060 — stated explicitly, since it's a real reason this design is simpler than it might first appear

**This ADR's own scope is exactly "when/how does the scheduler decide a `(tenant, user, Tier-3 connector)` tuple is due, and trigger it" — it is not a redesign of what happens once triggered.** ADR-0060 Decision §3 already fully owns `pollFacebook()`'s own per-Page fan-out (list this user's connected Pages, one sequential `runIngestionAttempt()` per Page, one Page's failure never blocking another's). This ADR's own scheduler enumerates and calls `connector.pollUser(tenantId, userId)` **once** per due tuple, with zero knowledge of "Pages" at all — the exact same relationship the existing tenant-wide scheduler already has with `pollGNewsSearch()`/`pollNewswireFeeds()`/`pollTenantOwnedFeed()` (the scheduler triggers; the connector's own function owns everything about what a single poll actually does). This ADR does not duplicate, re-decide, or touch ADR-0060 Decision §3's own fan-out logic in any way.

### What already exists and is directly reusable

- `connector_user_activations` (ADR-0051, Story 1.11) — the real Tier-3 activation table. `connectorActivationStore.ts`'s `isConnectorActive(tenantId, platformId, 'user', userId)`/`readUserActivation()` already read it correctly, per-target-user. **Confirmed: no function exists today to *list every user* with an active Tier-3 activation for a given `(tenantId, platformId)`** — every existing reader takes a specific `userId` as input, never enumerates. This is new, required enumeration work this ADR must decide the shape of.
- `RequestGate`/`acquireForProvider()` (`requestGate.ts`) — confirmed `socialConnectorKey(tenantId, connector) = ${tenantId}:${connector.providerId}`, a tenant-wide key. `pollFacebook()` (ADR-0060) already calls `gatedAcquire(tenantId)` → `acquireForProvider(tenantId, facebookConnector)` internally — **this key is fixed by `pollFacebook()`'s own existing implementation, not by the scheduler**, and stays exactly as ADR-0060 Decision §3/Consequences already named and deliberately left unresolved. See "Note on relation to ADR-0052" below for why ADR-0052 Decision §6's own `(tenantId, userId, providerId)` naming does not, in practice, become a scheduler-owned decision.
- `SocialConnector` (`types.ts`) — `poll?(tenantId): Promise<RunIngestionAttemptResult>` and `pollCadenceMs?: number` (ADR-0052 Decision §4, Story 1.13), both optional. Facebook's own current registration sets `pollCadenceMs: THIRTY_MINUTES_MS` on a throwing-placeholder `poll` — confirmed directly, `bootstrapConnectors.ts`.

## Decision

### 1. `ingestion_runs` gains a second new nullable column: `user_id UUID REFERENCES users(id)`

Alongside ADR-0060's already-decided `page_id` column, additive, following the exact same precedent (`is_credential_failure`, migration `0032`) both already followed — nullable, populated only by a Tier-3 connector's own poll path, `NULL` for every tenant-wide connector and every pre-existing row, zero behavior change to any existing query. **Populated directly on `ingestion_runs`, not derived via a join through a connector-specific table (e.g. `facebook_connected_pages`).** This is a deliberate choice: the scheduler must stay connector-agnostic (ADR-0048's own "no core pipeline change for new connector registration" guardrail) — a join through a Facebook-specific table would hardcode Facebook-shaped knowledge into what is meant to be a generic Tier-3 scheduling mechanism. A future Tier-3 connector (Reddit, the long-named candidate) populates this same column the same way, no scheduler change required.

### 2. New store functions, scoped to `(tenantId, platformId, userId)`

- **`listActiveUserActivations(tenantId, platformId): Promise<string[]>`** (`connectorActivationStore.ts`) — `SELECT user_id FROM connector_user_activations WHERE tenant_id = $1 AND platform_id = $2 AND is_active = true`, tenant-scoped via the existing `withTenant()` pattern every other function in this file already uses. This is the new enumeration work Context above names as missing — the per-user analogue of `listSocialConnectors()` for the tenant-wide path.
- **`getMostRecentRunStatusForUser(tenantId, platformId, userId): Promise<IngestionRunStatus | null>`** (`ingestionRunStore.ts`) — `SELECT status FROM ingestion_runs WHERE platform_id = $1 AND user_id = $2 ORDER BY started_at DESC LIMIT 1`. A new, additive sibling to the existing `getMostRecentRunStatus()`, which is left completely unchanged — every tenant-wide connector's existing in-flight guard (Story 1.14) keeps calling the original function, untouched.
- **`deriveConnectorHealth()` gains a fourth parameter, `userId?: string`**, filtering both of its internal queries (`ingestion_runs` and `platform_credentials`) by `user_id = $N` when supplied — fixing, as a direct and necessary consequence of this ADR's own due-check design (not a separate, unrelated fix bolted on), both the `lastAttemptAt`-blending bug and the adjacent `credentialStatus`-blending bug named in Context. Omitted, behavior is byte-for-byte unchanged for every existing caller (every tenant-wide connector, and ADR-0060's own `pageId`-scoped calls) — proven, at Story time, by re-running every existing `deriveConnectorHealth()` contract test unmodified.
  - **A real, named build-order coordination point, not a design flaw in either ADR:** ADR-0060 already specifies `deriveConnectorHealth(tenantId, platformId, pageId?)` — `pageId` as the third parameter — in Story 6.27's own already-written Acceptance Criteria. This ADR adds `userId` as a **fourth** parameter, preserving that reservation: `deriveConnectorHealth(tenantId, platformId, pageId?, userId?)`. If Story 1.15 (this ADR's own story, below) is implemented *before* Story 6.27, its own implementation must still insert `userId` in the fourth position (with `pageId` present but structurally unused, since the `page_id` column doesn't exist yet until Story 6.27 ships) rather than claiming the third position for itself — the two stories' own implementers must coordinate on final parameter order regardless of which lands first. Named explicitly here so neither implementation is surprised by a signature mismatch; this ADR does not edit ADR-0060's own Decision text or Story 6.27's own Acceptance Criteria to resolve it, per Menno's own explicit instruction to leave that story's ACs untouched.
- **`shouldAttemptIngestion(tenantId, platformId, ownerType, userId)`'s own internal `deriveConnectorHealth()` call is corrected** to pass `userId` through when `ownerType === 'user'`: `deriveConnectorHealth(tenantId, platformId, undefined, ownerType === 'user' ? userId : undefined)`. This is a real bug fix to already-shipped code (Story 1.11), not new scope invented by this ADR — named and fixed here because this ADR is the first thing that actually exercises the Tier-3 branch of this function's own already-existing `ownerType`/`userId` parameters in a live code path. Zero behavior change for the `ownerType: 'tenant'` default (every existing connector): `userId` stays `undefined`, so the new fourth argument is `undefined` either way, identical to today's two-argument call.

### 3. `SocialConnector` gains a new, distinct optional method — `pollUser?(tenantId, userId)` — not an overload of the existing `poll?(tenantId)`

```ts
/** Tier-3 (user-bound) poll entry point — present only on connectors with no
 *  tenant-wide poll() at all (ADR-0059 Decision §4's Tier-3-only rule for
 *  Facebook is the first real instance). A connector may have poll(),
 *  pollUser(), both, or neither — the scheduler enumerates each independently. */
pollUser?(tenantId: string, userId: string): Promise<RunIngestionAttemptResult>;
```

TypeScript cannot express two differently-shaped optional methods under one name, so a distinct name is required, not a design preference — `pollUser` was already the name this ADR's own sourcing task suggested and is adopted directly, since nothing about investigating the actual code surfaced a reason to prefer another. `pollCadenceMs` is **reused as-is**, unmodified — the same registered cadence value now serves either or both dispatch paths for a given connector; no second, Tier-3-specific cadence field is added.

**`bootstrapConnectors.ts`'s Facebook registration is revised: the throwing-placeholder `poll` is removed entirely (not replaced with a no-op), and `pollUser: pollFacebook` is added.** `poll` is already optional on `SocialConnector`; simply omitting it for Facebook is structurally self-documenting — "this connector has no tenant-wide poll path" is now a fact about the registered object's own shape (no `poll` property), not a runtime assertion that could theoretically be reached and would need to throw to say so. `runSchedulerTick()`'s own existing tenant-wide guard (`if (connector.poll && connector.pollCadenceMs !== undefined)`) already correctly skips a connector with no `poll` property — removing the placeholder is strictly safer than keeping it, not merely tidier, since it retires a defensive runtime check that a real, working generic Tier-3 dispatch path (this ADR) now makes genuinely unreachable rather than merely unlikely.

### 4. `runSchedulerTick()` gains a third, independent enumeration level for Tier-3 pairs — composed alongside, not instead of, the existing tenant-wide loop

For every tenant (existing `listTenants()`), for every registered connector with a `pollUser` method and a `pollCadenceMs` (a new filtered list, alongside — not replacing — the existing tenant-wide `listPollConnectors()`), for every `userId` returned by `listActiveUserActivations(tenant.id, platformId)` (Decision §2): apply the identical due-check shape the tenant-wide path already uses — `shouldAttemptIngestion(tenantId, platformId, 'user', userId)` (now correctly user-scoped per Decision §2's bug fix), the elapsed-time-plus-jitter comparison against that specific user's own most recent run (Decision §5 below), and the Story 1.14 in-flight guard via the new `getMostRecentRunStatusForUser()` — then call `connector.pollUser(tenant.id, userId)`.

**Failure isolation extends one level deeper, the same principle ADR-0060 Decision §3 already established one level down (one Page's failure doesn't block another's) applied here one level up (one user's failure doesn't block another user's, or another tenant's):** each `(tenant, user, connector)` tuple's own `try`/`catch` is independent — one user's `pollUser()` throwing does not prevent the next due user, or the next due tenant, from being attempted in the same tick. This reuses the exact same catch-and-log-via-`onPollError` pattern the existing tenant-wide loop already uses (`pollScheduler.ts` lines 87–109), extended one level, not redesigned.

### 5. `jitterFraction()` gains an optional third segment, `userId?`

```ts
export function jitterFraction(tenantId: string, platformId: string, userId?: string): number
```

Hashing `${tenantId}:${platformId}` when `userId` is omitted (byte-for-byte identical output to today, verified by construction — the existing two-argument call sites are entirely unaffected), or `${tenantId}:${platformId}:${userId}` when supplied. **A real, necessary addition, not a defensive extra:** without it, every one of a tenant's own users sharing one Tier-3 connector would receive the *identical* jitter offset (today's function ignores `userId` entirely), re-introducing exactly the simultaneous-due thundering-herd risk ADR-0052 Decision §5's own jitter design exists to prevent — just at per-user granularity within one tenant, rather than across tenants. Mirrors this codebase's own already-established "one more colon-segment, same pattern" precedent (`aiModelKey`'s `tenantId:providerId:modelId` over `socialConnectorKey`'s `tenantId:providerId`).

### 6. `RequestGate`'s own key shape is unaffected by this ADR — a clarifying correction to how ADR-0052 Decision §6's naming should be read, not a re-decision

See "Note on relation to ADR-0052" below.

## Consequences

**Positive**

- Closes the actual, live gap this session confirmed: a tenant with a real, working Facebook Page connection (single today, multiple once Story 6.27 ships) will actually be polled, on a real recurring cadence, without any manual trigger — the same "connector connected but never ingesting" class of gap ADR-0052 itself closed for tenant-wide connectors, now closed for Tier-3.
- Fixes three real, confirmed cross-user blending bugs as a direct, load-bearing consequence of this ADR's own design work, not as unrelated drive-by fixes: the in-flight-guard gap Menno specifically asked to be checked (confirmed real), an adjacent `credentialStatus`-blending gap found in the same function, and a `shouldAttemptIngestion()` cross-user auto-disable false-negative in already-shipped Story 1.11 code.
- No new database table — only two additive, nullable columns across two ADRs (`page_id` from ADR-0060, `user_id` from this ADR), both following the exact same precedent `is_credential_failure` already established.
- Retires a genuine runtime-assertion hack (Facebook's throwing-placeholder `poll`) in favor of a real, working, type-shape-enforced Tier-3 dispatch path — a structural improvement, not merely a cleanup.
- Composes cleanly with ADR-0060's own already-Accepted per-Page fan-out with zero duplication: the scheduler triggers `pollUser()` once per due tuple; everything about "which Pages, in what order, with what failure isolation" stays entirely inside `pollFacebook()` itself, exactly as designed there.

**Negative**

- **A real, named build-order coordination point** (Decision §2): `deriveConnectorHealth()`'s eventual four-parameter shape (`pageId?`, `userId?`) depends on which of Story 1.15 (this ADR) or Story 6.27 (ADR-0060) is implemented first — named explicitly, not silently left to be discovered as a merge conflict.
- **`ingestion_runs` gains a second nullable column in short succession** (this ADR's `user_id`, alongside ADR-0060's `page_id`) — each individually cheap and precedented, but the table's own schema is accumulating connector-specific optional columns two ADRs in a row; worth a future, non-urgent housekeeping look if a third one is ever proposed (not decided here, not invented as scope).
- **Enabling Tier-3 scheduling has the same real, immediate external-cost consequence ADR-0052 itself already named for tenant-wide polling, now extended to Facebook specifically:** the moment this ships, every tenant user with an active, connected Facebook Page starts consuming real Graph API quota continuously, not on-demand. No budget ceiling or cost-alerting mechanism is designed here, same unresolved gap ADR-0052 Open Question 4 already named — not re-solved, not re-invented, just newly applicable to a second connector.
- **`RequestGate`'s still-tenant-wide (not per-user) key for Facebook is unaffected and unimproved by this ADR** — see Decision §6/Note on relation to ADR-0052. Once Tier-3 scheduling actually runs continuously (rather than never running at all, today's status quo), this shared-budget risk ADR-0060's own Consequences already named becomes a live, not just theoretical, exposure. Not solved here — that decision belongs to `pollFacebook()`'s own implementation (ADR-0060's domain), not this scheduler-trigger ADR.
- Multi-instance distributed locking remains exactly as deferred as ADR-0052 Decision §7 already left it — this ADR adds a second, independent dimension (per-user, per-tenant, per-connector) to the same already-accepted single-instance assumption, without revisiting it.

## Alternatives Considered

| Alternative | Disposition |
|---|---|
| **Derive `user_id` for a Facebook `IngestionRun` via a join through `facebook_connected_pages` (ADR-0060) rather than a direct column** | Rejected. Would hardcode Facebook-specific schema knowledge into what is meant to be a generic, connector-agnostic scheduler mechanism (ADR-0048's own "no core pipeline change" guardrail) — a future Tier-3 connector with a different per-resource shape would need its own bespoke join, defeating the point of a generic `user_id` column every Tier-3 connector's own poll path populates the same way. |
| **Overload the existing `poll?(tenantId)` to also optionally accept a `userId`** | Rejected. TypeScript cannot express one optional method with two structurally different call signatures cleanly, and doing so would blur the real, meaningful distinction ADR-0059 Decision §4 already established — Facebook has *no* tenant-wide poll concept at all, not an optional extra argument on one that exists. A distinct `pollUser` method makes that absence a fact about the interface, not a runtime branch inside one method. |
| **Keep the throwing-placeholder `poll` on Facebook's registration, alongside the new `pollUser`, as defense-in-depth** | Considered, rejected. Once `pollUser` is real and the scheduler's own tenant-wide loop already structurally skips any connector lacking a `poll` property, the throwing placeholder guards against a code path that is now genuinely unreachable, not merely unlikely — keeping it would be an artifact of the old design, not a real safety net. |
| **Make `deriveConnectorHealth()`'s new `userId` filter a first-class options object (`{ pageId?, userId? }`) instead of stacked positional optional parameters, avoiding the build-order coordination risk entirely** | Considered, genuinely attractive, **not adopted** — Story 6.27's own Acceptance Criteria (ADR-0060, Accepted) already specify the positional `deriveConnectorHealth(tenantId, platformId, pageId?)` shape, and Menno's own instruction for this task is to add Story 6.27's dependency note without touching its Acceptance Criteria. Changing the parameter shape would require editing that story's already-written AC text to match, which is out of this ADR's own authorized scope. Named honestly as the cleaner design not taken, for a real, non-technical reason (a scope boundary), not because it's technically wrong. |
| **A cross-tenant `listActiveUserActivations(platformId)` (no `tenantId`), mirroring `listTenants()`'s own `platform_admin_role`-bypass shape** | Rejected. `connector_user_activations` is an ordinary tenant-scoped table under RLS — there is no existing precedent or demonstrated need for a cross-tenant bypass read here, unlike `listTenants()` (which must enumerate tenants themselves, a structurally different, already-Accepted case, ADR-0030). A tenant-scoped `listActiveUserActivations(tenantId, platformId)`, called inside the existing per-tenant loop, needs no new bypass role and fits the scheduler's already-established double-loop structure directly. |

## Note on relation to ADR-0052 (Accepted, 2026-08-13)

**This ADR fills in, rather than changes, ADR-0052 Decision §6 and Open Question 2 — both explicitly named the Tier-3 gap and explicitly declined to design it, pending a real Tier-3 poll connector existing.** One now does (ADR-0060). This ADR's own Decision §1–§5 is the design ADR-0052 itself named as future work, not a reversal of anything ADR-0052 already decided — the tenant-wide scheduling mechanism (Decision §1–§5, §7–§9 of ADR-0052) is entirely unchanged; this ADR adds a second, independent enumeration path alongside it.

**One real clarification to how ADR-0052 Decision §6's own naming should be read, not a re-decision of it:** ADR-0052 Decision §6 named a `RequestGate` key of `(tenantId, userId, providerId)` as part of the anticipated future shape. Investigated directly for this ADR: in practice, the scheduler itself never calls `RequestGate` — every existing poll connector (tenant-wide or, now, Tier-3) acquires its own `RequestGate` slot internally, inside its own poll function (`gatedAcquire()`/`acquireForProvider()`, confirmed directly in `pollFacebook.ts`, `pollGNewsSearch.ts`, etc.). The scheduler's own job (this ADR's actual scope) is purely "decide a tuple is due, then call `pollUser()`" — it has no `RequestGate` call site of its own to key one way or the other. **The re-keying decision ADR-0052 Decision §6 anticipated therefore belongs to each Tier-3 connector's own poll-function implementation, not to the scheduler** — for Facebook specifically, that is ADR-0060's own already-acknowledged, deliberately-deferred Open Question (`pollFacebook()`'s `gatedAcquire(tenantId)` call stays tenant-wide, not per-user, named as a real, unresolved risk there). This ADR does not change ADR-0052's own Decision text; it narrows how the already-named future `(tenantId, userId, providerId)` key should be understood — as a fact about where that decision actually lives, not a scheduler-level mechanism this ADR was expected to build.

## Note on relation to ADR-0060 (Accepted, 2026-08-18)

**This ADR triggers `pollFacebook()`; it does not redesign, duplicate, or reach inside what `pollFacebook()` itself does.** ADR-0060 Decision §3 fully owns the per-Page fan-out (listing a user's connected Pages, one sequential `IngestionRun` per Page, one Page's failure never blocking another's) — this ADR's own scheduler has zero knowledge of "Pages" at all, calling `connector.pollUser(tenantId, userId)` exactly once per due tuple, the same relationship the pre-existing tenant-wide scheduler already has with every other connector's own poll function. The one point of real interaction between the two ADRs — `deriveConnectorHealth()`'s eventual four-parameter shape (`pageId?` from ADR-0060, `userId?` from this ADR) — is named explicitly as a build-order coordination point in Decision §2, not a conflict between the two ADRs' own decisions. Neither ADR's Decision or Consequences text is edited by the other.
