# ADR-0036: Admin UI's own authentication/session mechanism — server-side (BFF) session, no bearer token in browser JS, role-gating sourced from a new core identity endpoint

**Status:** Proposed (drafted 2026-08-04 by the AI Business & Requirements Analyst persona) — **not accepted.** This persona does not hold ADR-acceptance authority (the same rule ADR-0026/0027/0028/0029–0035 followed); Menno reviews and accepts or rejects this separately, same as every other ADR in this series.
**Source:** Requested directly by Menno this session, drafting the admin UI's required user stories, after confirming `social-listening-admin` is still an empty shell (no Next.js scaffold, no pages, only `src/lib/core-client.ts` and Story 1.1's own contract — verified directly against the repo, not assumed). Grounded in ADR-0029 (authentication mechanism), ADR-0032 §5 (`resolveIdentity()`), ADR-0033 (bearer-token-only, `X-Tenant-Id` retired), ADR-0035 (one role-gated app), and this repo's own existing `src/lib/core-client.ts`/`.claude/skills/core-api-client/SKILL.md`.

## Context

Real backend authentication now exists and is fully wired: Story 5.6 (ADR-0029) validates an Entra External ID bearer token; Story 5.9 (ADR-0032 §5) resolves it via `resolveIdentity()` to `{ type: 'tenant_user', tenantId, userId, role }` or `{ type: 'platform_admin', adminId }`; Story 5.10 (ADR-0033) mounts both as `createTenantAuthMiddleware()`, the one seam every `/v1` route (except `/v1/health`) now requires. `social-listening-admin` has none of this — no Next.js scaffold exists at all (confirmed directly: `package.json` carries no `next`/`react` dependency; `src/` contains only `lib/core-client.ts`), so the admin UI's own sign-in flow, session mechanism, and how it attaches a bearer token to its calls into core are all still fully undecided.

Three things this project has already decided constrain, without fully answering, this question:

- **ADR-0029 §2** states the admin UI's sign-in flow "may reasonably use a standard OIDC client library, including Microsoft's, for the interactive redirect/PKCE dance itself — that is a UI-layer implementation choice, not an architectural dependency the core inherits." This settles that the *core* never depends on which library the UI picks; it does not settle what the UI itself should do, and is not itself an ADR for the UI's own mechanism.
- **ADR-0029 §2** also states, without qualification: tenant membership, role, and license status are "owned and enforced exclusively by SocialEngage's own Postgres tables... never inferred from any Entra-side group membership, organizational-role claim, or directory attribute." This has a direct, previously unstated consequence for the admin UI: **it cannot determine a signed-in caller's role (`tenant_admin` vs `tenant_user` vs Platform Admin) by decoding the Entra-issued token itself** — role isn't in the token's claims at all, by this project's own design. The UI must ask `social-listening-core` for the resolved identity. **No endpoint for this exists.** Checked directly: `src/identity/identityResolution.ts`'s `resolveIdentity()` is called only internally, inside `createTenantAuthMiddleware()`, and attached to `req.identity` for route handlers to read via `requireTenantUser()`/`requireTenantUserIdentity()` — nothing exposes the resolved identity itself over HTTP. This is a real, previously unnamed gap, not a hypothetical one.
- **`src/lib/core-client.ts`'s own existing design already implies an answer to where the bearer token must live.** It reads its base URL from `process.env.CORE_API_BASE_URL` — a bare environment variable, not a `NEXT_PUBLIC_`-prefixed one — which Next.js only ever inlines into server-side code, never into a browser bundle. This module, as it exists today (Story 1.1, unmodified since), can only run in a Node.js/server context (a Route Handler, Server Component, or Server Action), not in client-side JavaScript. Any admin-UI authentication design that requires the browser to hold and directly attach a bearer token to `core-client.ts`'s own calls would be incompatible with this already-shipped module without first rewriting it — a real, concrete piece of evidence, not a hypothetical preference, for where session state needs to live.

**Why this is architecturally significant enough for its own ADR, applying this series' own bar (ADR-0027/0028/0035's "one user story per ADR" default, departed from only for a stated, checked reason):** unlike Story 1.5's watchlist CRUD or Story 1.6/1.7's connect/disconnect endpoints — ordinary CRUD surface this project's own convention (`docs/implementation-plan.md`, `docs/user-stories/README.md`) already treats as not warranting an ADR — this decision is not a new field or endpoint shape. It is a hard-to-reverse choice with real security consequences (where a bearer token physically lives; whether it is ever reachable by an XSS payload in the browser), a real new cross-repo dependency this project did not previously know it needed (a core-side identity-exposure endpoint), and a real trade-off between a maintained third-party library and this project's own "thin, pluggable OIDC issuer" principle (ADR-0029 §2) that a future maintainer would have to re-derive from scratch if it weren't written down now. It is the direct UI-side analogue of Story 5.6 being "the root; nothing else in this phase can be built first" for the backend — every other admin-UI story (connect flow, watchlist management, connector status, Platform Admin console) needs this decided first.

## Decision

### 1. Server-side session only — no bearer token, access token, or refresh token is ever placed in browser-reachable storage or JavaScript

The admin UI's interactive sign-in (Authorization Code + PKCE against the single Entra external tenant ADR-0029 §1 already established) is performed and terminated **server-side** — inside a Next.js Route Handler, never a Client Component. The resulting tokens are held in an **encrypted, `httpOnly`, `Secure`, `SameSite=Lax` session cookie** (a reference/session-ID pattern, or an encrypted-cookie session store such as `iron-session`'s own approach — the exact library is left to whoever builds Story 6.1, not decided here) — never in `localStorage`, `sessionStorage`, or any value a Client Component's own JavaScript can read. This is the standard "Backend-for-Frontend" (BFF) token-handling pattern, chosen for two independent, both load-bearing reasons: it is the only design consistent with `core-client.ts`'s own existing server-only environment-variable shape (Context, above) without first rewriting that module, and it bounds the blast radius of an XSS vulnerability anywhere else in the admin UI to "no token to steal," rather than "steal the token from `localStorage`."

### 2. `core-client.ts` remains the single choke point for attaching the bearer token, exactly as its own `SKILL.md` already requires for every other call

Extend `core-client.ts` so that every call it makes to `social-listening-core` reads the caller's session (via Next.js's server-side cookie/session APIs) and attaches `Authorization: Bearer <token>` itself — no other file in `social-listening-admin` constructs this header directly. This is not a new principle; it is `core-api-client/SKILL.md`'s own already-stated "Keep this the single choke point: if a second ad hoc `fetch` call to core appears elsewhere in `src/`, fold it into this module instead" constraint, applied to the one new thing (the bearer token) this ADR adds to every call.

### 3. Client library: no third-party auth framework (e.g. NextAuth.js/Auth.js) adopted at v1 — a standard, minimal Authorization Code + PKCE flow instead, using a generic OIDC/JWT library

**Checked, not assumed:** Auth.js (NextAuth.js's current name) ships a documented `microsoft-entra-id` provider for ordinary (workforce) Microsoft Entra ID (`authjs.dev/getting-started/providers/microsoft-entra-id`). Its support for **Entra *External* ID specifically** (the CIAM product ADR-0029 selected, distinct from workforce Entra ID) is **not confirmed to this project's own primary-source evidentiary bar** — a live `nextauthjs/next-auth` GitHub discussion titled "Microsoft Entra Customer Tenant" (`github.com/nextauthjs/next-auth/discussions/8872`) and a web search summary both indicate this combination is community-reported as difficult/under-documented, not a confirmed, supported path the way the workforce provider is. This was checked via web search only, not by directly reading Auth.js's own source or opening a real External ID sign-in against it — a real limit on this ADR's own verification, named honestly rather than glossed over, the same way ADR-0029 named its own unresolved `oid`-vs-`sub` question.

Given that gap, and given ADR-0029 §2's own already-Accepted principle — Entra is "a pluggable OIDC token issuer only," and the core deliberately avoids any Entra-specific SDK dependency to bound a future provider swap's blast radius — the more consistent choice for v1 is a **standard, minimal Authorization Code + PKCE implementation using a generic OIDC/JWT library** (e.g. `openid-client`, or the same `jose` library `entra-authentication/SKILL.md` already uses on the core side for JWKS/signature verification) rather than a Next.js-specific auth framework whose support for this project's actual chosen provider variant is unverified. This is deliberately the **narrower**, not the more feature-rich, choice — it accepts writing more of the PKCE/redirect/token-exchange mechanics by hand, a real cost for a solo developer (Consequences, below), in exchange for not taking on an unverified dependency for the one piece (External ID/CIAM support) this project actually needs.

**This is not a permanent rejection of NextAuth.js/Auth.js.** If whoever builds Story 6.1 verifies Auth.js's Entra External ID support directly (against Auth.js's own current documentation and a real sign-in attempt, the same bar ADR-0029 held its own Entra claims to) and finds it solid, adopting it instead is a legitimate, lower-maintenance alternative — named here as an Open Question, not foreclosed.

**Redirect URI is a decided security control, not deployment trivia — corrected 2026-08-04 (Amendment Log below).** The authorization request's `redirect_uri` parameter must be an **exact-match value pre-registered on `social-listening-admin`'s own Entra app registration — never a wildcard or pattern-matched URI.** Entra rejects an authorization request whose `redirect_uri` doesn't exactly match a registered value, which is what actually constrains where an authorization response can be delivered — a distinct, complementary control to PKCE, not a redundant one: PKCE stops a stolen authorization code from being redeemed by anyone other than the instance that initiated the flow; exact redirect-URI matching stops the code from being delivered anywhere other than an explicitly pre-approved destination in the first place. A wildcard or broadly-pattern-matched redirect URI is a well-documented real-world source of OAuth authorization-code interception (e.g. via an open redirector elsewhere on a wildcarded origin) and would materially weaken this design regardless of how well PKCE and the BFF session pattern (§1) are otherwise implemented. Each real environment (local dev, and whatever real host this project eventually deploys to) registers its own distinct, exact redirect URI — never a shared pattern across environments.

### 4. Role-gating is layered, and is UX only — never the actual security boundary

Two layers, mirroring the backend's own already-established layered pattern (`createTenantAuthMiddleware()`'s "one seam" plus each route's own `requireTenantUser()`/`requireTenantUserIdentity()` check) rather than inventing a different shape for the UI:

- **Coarse-grained, edge Middleware:** an unauthenticated request to any route other than the sign-in page itself is redirected to sign-in. This is fast but cannot safely hold a full resolved identity (Middleware runs at the edge, before a full Node.js request context), so it decides only "signed in or not," not "which role."
- **Server-side, per-request check** (a Server Component/layout or Route Handler reading the session): decides which of the two structurally different route trees (tenant-facing vs. Platform-Admin-facing, per ADR-0035's own already-Accepted "role-gated routing" decision) a given request may render, and whether a `tenant_admin`-only affordance (e.g. offering `ownerType: 'tenant'` on the connect flow, Story 1.7) is shown at all.

**Named explicitly so it is never mistaken for the real boundary:** exactly like the backend's own `deleteCredential()`/connect-disconnect authorization (Story 1.7), the UI's role-gating is a usability convenience — hiding an action a caller isn't allowed to take — never the actual enforcement. `social-listening-core`'s own RLS and application-layer role checks (ADR-0028/ADR-0034) remain the sole real security boundary; a UI bug that mistakenly renders a `tenant_admin`-only button for a `tenant_user` would be a real bug to fix, but not a security incident, precisely because the server-side 403 (Story 1.7) still holds regardless of what the UI renders.

### 5. A new core-side endpoint is required, and does not yet exist — named here as a hard dependency, not designed here

Per §3's Context finding: the admin UI cannot determine a signed-in caller's role or tenant/Platform-Admin identity without asking `social-listening-core` — Entra's own token carries no such claim, by ADR-0029 §2's own design. **`social-listening-core` needs a new, authenticated `GET /v1/me`-shaped endpoint** (exact path/shape left open, not decided here) that returns `resolveIdentity()`'s already-computed result — `{ type: 'tenant_user', tenantId, userId, role }` or `{ type: 'platform_admin', adminId }` — to the caller whose own token it resolved. This is additive, read-only, and exposes data `resolveIdentity()` already computes internally on every request; it is ordinary CRUD-adjacent surface in the same sense Story 1.5's watchlist CRUD was (no new architectural decision of its own), **not** something this ADR itself designs or builds — named here as a concrete, blocking prerequisite for Story 6.1 (below), to be built in `social-listening-core` following that project's own contract-first discipline, by the AI Delivery Agent or Menno, not by this drafting pass.

**Clarification, 2026-08-04 (Security & Architecture Reviewer finding, pre-acceptance revision):** this endpoint must derive the returned identity *exclusively* from `req.identity` — the value `createTenantAuthMiddleware()` already attaches from the caller's own validated bearer token via `resolveIdentity()`, the same mechanism every other authenticated `/v1` route already uses (Story 5.10). It must never accept a `tenantId`, `userId`, or any other identity-shaped value from a query parameter, request body, or header and let it influence the response — there is no legitimate reason for this endpoint to accept one at all. This closes a real, concretely-named spoofing/disclosure risk a reviewer raised against this ADR's own text (which left the endpoint's authorization behavior implicit): without this constraint stated explicitly, a careless implementation could accidentally accept a client-supplied override (e.g. a debug parameter never removed) and leak another caller's role/tenant/user id. Story 6.1's own Acceptance Criteria states this as a testable requirement, not just prose here.

### 6. Session lifetime backstop — a decided minimum, not left fully open — **added at review, 2026-08-04 (Amendment Log below)**

The session cookie (§1) carries a **hard, absolute maximum lifetime of 8 hours from sign-in, enforced server-side regardless of activity** — after which the session is invalid and the caller must sign in again, full stop, no silent renewal past this ceiling. This is a deliberate, decided backstop, not a placeholder: a Security & Architecture Reviewer finding correctly identified that leaving session lifetime itself as an Open Question (as this ADR originally did, conflating it with the separate *rotation/refresh* question) meant a hijacked session cookie could remain valid indefinitely, with no architectural bound at all. 8 hours is a template default — chosen as "one working day," not derived from a deeper analysis of this project's actual risk tolerance — and is explicitly revisable via this Amendment Log, the same way ADR-0017's deprecation window and ADR-0018's retention windows started as template defaults and were tuned in place.

**What stays genuinely open (see Open Questions below), now narrowed:** whether an additional *idle* timeout (expiring a session after N minutes of inactivity, shorter than the 8-hour absolute ceiling) is worth the added complexity at solo-project/single-operator scale, and the exact *rotation* mechanism (silent refresh vs. forced re-auth). Both are UX/complexity trade-offs layered on top of the now-decided absolute ceiling, not a gap in whether any bound exists at all.

## Consequences

**Positive**
- Reuses ADR-0029/ADR-0032's identity model exactly — no second, UI-side notion of "role" is invented; the UI is a consumer of the same resolved identity the backend already computes, not a second source of truth for it (consistent with ADR-0029 §3's own "exactly one source of truth per field" principle).
- Bounds the admin UI's own XSS blast radius concretely: no bearer/refresh token is ever placed anywhere a browser-side script could read it, regardless of what other client-side code this UI eventually ships.
- No rework required to `core-client.ts`'s already-shipped, Story-1.1-contract-verified environment-variable design — the server-side-session decision is the one consistent with what already exists, not a competing design that would force a change to already-tested code.
- Role-gating's two-layer shape mirrors the backend's own already-proven pattern (one seam plus a per-route check) rather than introducing an unrelated design for the UI half of this project — less conceptual drift for whoever maintains both repos (today, only Menno).

**Negative**
- **A real, new, previously-unnamed cross-repo dependency:** `GET /v1/me` (or equivalent) does not exist in `social-listening-core` today — confirmed directly, not assumed. Story 6.1 (below) cannot be built end-to-end until it exists. `docs/implementation-plan.md`'s existing Phase 1/Phase 3 "also build, not storied" framing did not previously name this gap.
- **Rejecting NextAuth.js/Auth.js at v1 is a real cost, not a costless caution.** It means hand-building and maintaining PKCE/redirect/token-exchange/refresh logic that a maintained library would otherwise absorb — genuine, ongoing solo-developer maintenance burden, accepted here specifically because the one piece this project actually needs (Entra External ID/CIAM support) is not confirmed solid in that library, not because bespoke auth code is preferred in general. If Story 6.1's own implementation-time verification finds Auth.js's CIAM support solid after all, this trade-off should be revisited, not treated as permanently settled by this ADR.
- **This ADR's own verification of Auth.js's Entra External ID support is a web-search-level check, not the primary-source depth ADR-0029 held its own Entra claims to** (reading Microsoft's or Auth.js's own documentation directly, or attempting a real sign-in). Named honestly as a real limit on this Decision's own evidentiary basis, not glossed over — Open Questions, below.
- The BFF/session-cookie pattern requires the admin UI's screens to be built consistently against Next.js's server-side data-fetching model (Server Components/Route Handlers/Server Actions calling `core-client.ts`), not a client-side-fetch-heavy SPA style — a real constraint on every future admin-UI story's own implementation approach, not just Story 6.1's.

## Alternatives Considered

- **NextAuth.js/Auth.js with its Microsoft Entra ID provider** — the maintained, lower-maintenance-burden option; rejected for v1 only because its support for this project's actual chosen provider variant (Entra External ID/CIAM, not workforce Entra ID) is not confirmed to this project's own evidentiary bar (§3). Not rejected as architecturally incompatible — revisit once verified.
- **Client-side token storage** (the browser holds the access token in `localStorage`/`sessionStorage` and attaches it directly to calls) — rejected: reintroduces the exact XSS-token-theft risk the BFF pattern exists to avoid, and is structurally incompatible with `core-client.ts`'s own current server-only environment-variable design without first rewriting that already-shipped, contract-verified module (Context, above).
- **Decoding the Entra-issued token's own claims for role/tenant information, skipping a call to core entirely** — rejected outright: contradicts ADR-0029 §2's own already-Accepted "never inferred from any Entra-side... attribute" principle; role and tenant membership are Postgres-owned facts that do not exist in the token at all.
- **No UI-side role-gating at all, relying solely on the backend's own 403s** — considered; rejected as materially worse UX (a `tenant_user` would see and attempt an action that always fails on submit) while conceding the backend's 403 remains the real boundary regardless — named in Decision §4 rather than silently assumed away.

## Open Questions for decision

- **Whether Auth.js/NextAuth.js's Entra External ID (CIAM) support is actually solid enough to adopt after all** — this ADR's own web-search-level check is not sufficient to decide it either way; whoever builds Story 6.1 should verify directly (Auth.js's own current documentation, or a real attempted sign-in) before committing to the bespoke PKCE flow this ADR otherwise specifies.
- **The exact path, response shape, and name of the new core-side identity-exposure endpoint** (`GET /v1/me`, `GET /v1/identity`, or otherwise) — named as required in Decision §5, not designed here; left to whoever builds it in `social-listening-core`.
- **Which specific encrypted-session-cookie mechanism/library** (e.g. `iron-session`, a hand-rolled JWE via `jose`, or Next.js's own newer built-in session primitives if available at implementation time) — left to Story 6.1's own implementation, not decided here; the requirement is the property (httpOnly, encrypted, never client-JS-readable), not a specific library.
- **Whether a shorter *idle* timeout on top of §6's decided 8-hour absolute ceiling is worth the added complexity**, and the exact rotation/refresh mechanism within that ceiling (silent refresh vs. forced re-auth-on-401) — not decided here; a real UX/complexity trade-off at solo-project scale, deferred to Story 6.1's own implementation with a note to revisit if session-expiry friction proves the simpler choice wrong. (Narrowed 2026-08-04 — whether *any* absolute bound exists at all is no longer open, see §6.)
- ~~**Whether `social-listening-admin`'s own Entra app registration needs additional redirect-URI configuration once a real (non-`localhost`) hosting environment exists** — not designed here; a deployment-time configuration detail, not an architectural one.~~ — **corrected 2026-08-04:** this was mischaracterized. Exact-match (never wildcard) redirect-URI registration is now a decided security control (§3, added at review) — what remains genuinely open is only the mechanical detail of *how many* environments need their own registered URI and *when* each is added (e.g. a real deployed host doesn't exist yet), not *whether* exact matching is required.
