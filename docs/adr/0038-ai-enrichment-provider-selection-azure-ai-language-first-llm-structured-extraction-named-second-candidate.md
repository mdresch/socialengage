# ADR-0038: AI enrichment provider selection — Azure AI Language as the first concrete `AIProviderConnector`, general-purpose-LLM structured extraction named as the deliberate second-provider swappability candidate

**Status:** Proposed — drafted by the AI Business & Requirements Analyst persona. This persona does not hold ADR-acceptance authority (the same rule ADR-0026/0027/0028/0029–0037 followed); awaiting Menno's own review and acceptance before Story 2.8 can move to Ready.
**Source:** Requested directly by Menno as part of a 16-item story-drafting batch, closing the gap named by `docs/implementation-plan.md` Phase 2 ("the first `AIProviderConnector` implementation") and confirmed directly against the codebase: Stories 4.1, 4.2, and 5.1 all assume `enrichment.entities`/`keyPhrases`/`sentiment` are already populated, but no story in Epics 1–6 implements `AIProviderConnector.analyze()` against a real provider. Menno separately, and directly, instructed that this selection be held to "the same primary-source rigor ADR-0024/0026 used for connector selection" — not assumed correct just because Azure AI Language is the design spec's own illustrative example — and, in two follow-up messages during this drafting pass, specifically directed that a general-purpose LLM (GPT-4o/4.1-class, Claude, Gemini) be given a genuinely fair, verified comparison against a dedicated NLP service, including the real efficiency argument that an LLM can extract all four fields (language, sentiment, key phrases, entities) in a single call where a dedicated service is often called per-capability.

## Context

`docs/project docs/2026-07-28-social-listening-ingestion-design.md` §2/§3.1 names Azure AI Language as this project's own illustrative AI-enrichment provider (Azure-native tech stack, "Azure AI Language today; OpenAI, Claude, or others later"), and `SocialPost.enrichment`'s own shipped shape (`sentiment: 'positive' | 'neutral' | 'negative' | 'mixed'`, `sentimentScores: { positive, neutral, negative }`, `keyPhrases: string[]`, `entities: { text, category, confidenceScore }[]`) is modeled directly on Azure AI Language's actual Text Analytics response shape — this is a materially stronger degree of prior specificity than existed for RSS/News before ADR-0026 (where only the *category* — poll-only, API-key, no paid tier — had been decided, no concrete provider). ADR-0028 (Accepted) separately resolved the credential-ownership/billing question specifically for this provider: `AIProviderConnector` credentials are tenant-owned, tier-2 (Tenant-Admin-created), cost settled directly between the tenant and Microsoft/Azure, no SocialEngage-operated shared subscription (ADR-0028 §1's "Resolved 2026-08-03" note; `Project Management Plans/Cost-Management-Plan.md` C-14).

Two things nonetheless make this a genuine, undecided ADR-level question rather than a settled implementation detail this story can build against silently:

1. **The design spec's own illustrative choice predates the current maturity of general-purpose-LLM structured output.** OpenAI's `strict: true` JSON-schema-constrained output (verified directly below) and comparable tool-use-based structured output from Anthropic's Claude models did not exist in a form mature enough to treat as a production-reliable alternative when the spec's worked example was written. Menno's own instruction is that this maturity shift is real and must be weighed now, not assumed away by the spec's original illustrative pick.
2. **A real, verified efficiency argument favors an LLM approach that nothing in this project's existing documents has weighed:** a single LLM call can plausibly return all four `enrichment` fields at once, where Azure AI Language's action-specific endpoints (the ones its own SDK guidance recommends for anything short of large/batch documents — see Decision §1 below) are typically called once per capability. This changes the real per-post latency and cost profile in a way worth a primary-source-grounded comparison, not a default assumption either way.

This is squarely the kind of decision this series reserves an ADR for: hard to reverse (`SocialPost.enrichment`'s shipped shape, and every downstream story that reads it — 4.1, 4.2, 5.1 — already assumes a specific field shape), a real vendor/data-flow/cost consequence, and — per Menno's own direct instruction — not to be settled by defaulting to the spec's illustrative example without a genuine comparison.

## Research performed this session (primary-source verification, the same bar ADR-0024/0026 held themselves to)

**Azure AI Language:**
- Free tier: 5,000 free text records/month, shared across sentiment analysis, key phrase extraction, language detection, and named entity recognition (`azure.microsoft.com/en-us/pricing/details/language/`, fetched directly this session). A text record is up to 1,000 characters; a document over 1,000 characters counts as more than one record for whichever action processes it.
- Standard (S) tier beyond the free allowance: confirmed to exist and be volume-tiered (0.5M–2.5M / 2.5M–10M / 10M+ text records), but the exact per-record dollar rate could not be pinned to a directly-fetched number this session — the live pricing page rendered its rate cells as placeholders in this tool's fetch, and a secondary source (not Microsoft's own page) estimated "around 1/10th of a cent per record" (~$1/1,000 records) beyond the free tier. **Named honestly as an unresolved verification gap, not invented** — the same treatment ADR-0026 gave NewsData.io's unreachable terms pages, rather than asserting a number this session could not confirm to its own bar.
- **Call shape, corrected from this ADR's own first-drafted assumption:** Azure AI Language does have a combined multi-action endpoint (`begin_analyze_actions` in its SDKs) capable of running sentiment, key phrases, entities, and language detection together in one submitted request — not strictly one call per capability, as this ADR's drafting initially assumed before checking. **However, Microsoft's own SDK guidance (confirmed via `learn.microsoft.com`, fetched this session) recommends the combined/batched endpoint specifically for larger documents and/or genuinely batched multi-action analysis, and recommends the action-specific (per-capability) endpoints otherwise** — meaning for this project's actual workload (one social/news post at a time, well under the size that motivates batching), the more naturally-fitting call shape is still closer to one call per capability than a single combined call, even though the combined endpoint technically exists. This is a real, materially different latency/round-trip profile from a genuinely single-call LLM extraction, even after correcting the initial overstatement.
- No production/commercial-use restriction on the free tier was found for Azure AI Language specifically (unlike the TTS-specific "Free tier output has no commercial license" ambiguity this session's search also surfaced — that restriction is scoped to Azure AI **Speech**'s text-to-speech *audio output licensing*, a different product with different IP considerations around generated audio, and does not appear to apply to Language's structured-analysis output).
- ADR-0028's already-Accepted tenant-owned/tier-2 credential resolution already covers this provider by name; no new credential-authority decision is needed if Azure AI Language is the chosen provider.

**General-purpose LLMs (OpenAI, Anthropic, comparably Google Gemini):**
- **Structured output reliability:** OpenAI's `response_format` with `strict: true` and a supplied JSON Schema is documented (`openai.com`, `developers.openai.com`, fetched/searched this session) to guarantee schema-conformant output — every required field present, every type correct, every enum value valid — a materially stronger guarantee than plain "JSON mode," which only guarantees syntactic validity, not schema adherence. Anthropic's Claude models support an equivalent pattern via tool use (a JSON-schema-defined tool the model is directed to call), the same general mechanism, verified against Anthropic's own current pricing/docs page (`platform.claude.com/docs`, fetched directly this session).
- **Pricing, verified directly against Anthropic's own current pricing page (`platform.claude.com/docs/en/about-claude/pricing`, fetched this session, 2026-08-05):** Claude Haiku 4.5 — $1/MTok input, $5/MTok output (Batch API: $0.50/$2.50). GPT-4o-mini pricing (searched, not directly fetched from `openai.com` this session — a real, named residual verification gap, not asserted to the same primary-source bar as the Claude figures above) is reported consistently across several aggregator sources at approximately $0.15/MTok input, $0.60/MTok output.
- **Rough per-post cost estimate, worked explicitly rather than left implicit:** for a typical ingested post (~500–700 input tokens including the extraction prompt/schema, ~100–150 output tokens for the structured result), GPT-4o-mini costs on the order of $0.0002/post; Claude Haiku 4.5 costs on the order of $0.001–0.0015/post. Azure AI Language's own per-record cost beyond the free tier could not be pinned to the same confidence (gap named above), so a direct, fully-apples-to-apples dollar comparison at volume is **not** asserted here as settled — named as a real open item for whoever accepts or revises this ADR to close before committing capital-P production traffic to either path.
- **A real, new data-flow/vendor consideration this ADR's Alternatives Considered section returns to:** using OpenAI's or Anthropic's own first-party API directly would introduce a new third-party vendor relationship *outside* this project's existing Azure-native stack (ADR-0014, ADR-0015, ADR-0016, ADR-0029 are all Azure-anchored), with its own ToS/DPA this project has not verified to the ADR-0024/0026 bar (whether Anthropic's or OpenAI's standard commercial API terms permit this project's specific automated, third-party, per-tenant-credential usage pattern was not checked this session — a real, named gap, not asserted either way).
- **A materially better-fitting variant exists and is named here rather than left undiscovered:** both OpenAI-family and Anthropic-family models are available *through Azure* — Azure OpenAI Service and Claude in Microsoft Foundry (the latter confirmed directly in this session's own Anthropic pricing fetch, which documents "Claude in Microsoft Foundry pricing," billed through the Azure Marketplace) — which would let an LLM-based `AIProviderConnector` stay inside this project's existing Azure-native, tenant-owned-Azure-subscription pattern (ADR-0028's tier-2 resolution, Key Vault credential storage, the same billing relationship already designed for Azure AI Language) rather than opening a wholly new, unverified vendor relationship. This variant was not independently priced this session (a further, named residual gap) but is the natural candidate if this project ever builds an LLM-based enrichment provider, not a same-cost-different-vendor swap of the direct-API options costed above.

## Decision

### 1. Azure AI Language is the first concrete `AIProviderConnector` implementation — Story 2.8's own scope

Building the first real `AIProviderConnector` against Azure AI Language is the lower-risk, better-grounded choice for the *first* implementation, for reasons independent of, not merely defaulting to, the spec's own illustrative pick:

- `SocialPost.enrichment`'s already-shipped shape (four-way sentiment including `'mixed'`, three-way `sentimentScores`, `entities` with a per-entity `confidenceScore`) is a direct match for Azure AI Language's actual output shape — building the first connector against a materially different extraction paradigm (LLM prompting, whose `sentimentScores` would be self-reported model confidence, not a calibrated classifier probability) would mean either reshaping an already-shipped, already-depended-on (Stories 4.1/4.2/5.1) data shape, or accepting a real fidelity gap in a field type this project has not yet decided it's willing to accept. Building the already-shape-matched provider first avoids deciding that trade-off under the pressure of also being the *first* provider ever wired in.
- This project's technology stack is Azure-native throughout (ADR-0014/0015/0016/0029) — Azure AI Language keeps AI enrichment inside the same operational/credential/observability surface the rest of this project already uses, rather than introducing a first non-Azure vendor relationship for the very first `AIProviderConnector` this project ever ships.
- No production/commercial-use restriction analogous to the ones that disqualified RTPR, NewsAPI.org, or Currents API (ADR-0024/0026) was found for Azure AI Language's free tier during this session's research (see Research section above) — it is a clean, verified-eligible candidate for this project's actual per-tenant, tier-2 usage pattern (ADR-0028).
- ADR-0028 has already resolved the one genuinely hard-to-reverse question this provider raised (credential ownership/billing) — nothing about *selecting* this provider now reopens that.

### 2. General-purpose-LLM structured extraction is named as the deliberate, real candidate for the second `AIProviderConnector` — not rejected, not silently deferred

`docs/implementation-plan.md` Phase 2 already recommends, as its own "Recommended validation" line, standing up a second `AIProviderConnector` specifically to prove AI-provider swappability needs zero core pipeline changes — mirroring how Reddit validated the social-connector side in Phase 1. **This ADR decides that recommendation's natural fit is an LLM-based extractor, preferably via Azure OpenAI Service or Claude in Microsoft Foundry (Research section above) to stay inside this project's already-decided Azure-native, tenant-owned-credential pattern rather than opening an unverified direct vendor relationship** — not a generic placeholder "any second provider will do." The real efficiency case Menno raised (a single call returning all four fields, vs. Azure AI Language's own SDK-recommended per-capability call shape for a single small document — Research section above, corrected from this ADR's own first-drafted overstatement) is a genuine, primary-source-grounded reason to expect a real latency/cost win from this specific second provider, not an arbitrary pick for symmetry's sake.

This is a deliberate, reasoned sequencing choice, not a downgrade of Menno's own suggestion: proving the `AIProviderConnector` abstraction generalizes to a structurally different extraction paradigm (prompted, schema-constrained LLM output vs. a purpose-built classifier) is exactly the kind of test Phase 1's own two-connector proof already established as this project's own standard for validating an abstraction, and doing it second — once the shape-matched, lower-risk provider already exists and the pipeline is proven — is lower-risk than making the first-ever `AIProviderConnector` also the first test of a materially different output-fidelity trade-off (calibrated classifier scores vs. self-reported LLM confidence).

### 3. Explicit reconfirmation, not an inherited assumption: SocialEngage is never a billing intermediary or contracting party for either candidate provider

**Stated here explicitly, in this ADR's own Decision text, rather than left as something a future reader must infer by chasing cross-references** — per Menno's own direct instruction during this drafting pass: whichever provider this ADR's own Decision §§1–2 name (Azure AI Language as the first `AIProviderConnector`; an Azure-hosted LLM as the named second candidate), **the tenant directly activates and holds their own account/credential/contract with that provider. SocialEngage stores and uses that credential only as a technical pass-through** — the same envelope-encrypted, Key-Vault-backed storage mechanism ADR-0014 already applies to every other tier-2 credential, no different handling for an AI-enrichment credential than for a GNews or Newswire one. **No SocialEngage-operated shared subscription exists for either candidate, no SocialEngage-to-provider billing relationship exists, and SocialEngage never accepts payment from the tenant on the provider's behalf or pays the provider on the tenant's behalf** — the cost of using the chosen AI provider is incurred and settled directly between the tenant and that provider (Microsoft, or whichever LLM vendor a future second-provider story specifies), full stop.

**This is not new policy this ADR originates — it is ADR-0027's already-Accepted "technical intermediary only... no pooling or sharing... no intermediary in billing or pricing" principle, and it is ADR-0028's own Amendment Log, which already resolved this exact question specifically for Azure AI Language** ("the client tenant will own this connector and enrichment should be cost incurred and settled between the connecting vendor and the end users" — Menno, quoted directly in ADR-0028's Context/Amendment Log; "no SocialEngage-operated shared subscription... cost settled directly between the tenant and the vendor"). **This ADR's own contribution is confirming that resolution explicitly reaches whichever provider this ADR actually selects, rather than letting the prior resolution's Azure-AI-Language-specific wording leave ambiguity if a different provider (an LLM vendor) is ever chosen as the second `AIProviderConnector`** — ADR-0028's tier-1/tier-2 framework and ADR-0027's billing-intermediary prohibition are provider-agnostic by their own Decision text; this section makes that explicit for this ADR's own two named candidates rather than relying on a future reader to re-derive it. **This applies identically regardless of whether the second `AIProviderConnector` ends up being Azure OpenAI Service, Claude in Microsoft Foundry, or a direct (non-Azure) vendor API** — Decision §2's own preference for the Azure-hosted path is a data-flow/consistency choice, not a precondition for this billing-intermediary prohibition, which holds unconditionally either way.

### 4. What this ADR does not decide

- **The exact dollar-per-post cost comparison at production volume** — Azure AI Language's own per-record S-tier rate was not pinned to this project's own primary-source bar this session (Research section above); whoever builds Story 2.8 (or specs the second provider) should verify it directly against `azure.microsoft.com/en-us/pricing/details/language/`'s live rate table before any capacity/cost planning depends on it.
- **Whether OpenAI's or Anthropic's own first-party API terms (as opposed to their Azure-hosted equivalents) would even be eligible under ADR-0027's "source eligibility" bar** for this project's automated, per-tenant usage pattern — not checked this session, named as a real gap for whoever specs the second provider if a direct (non-Azure) LLM API is ever chosen instead of the Azure-hosted variants this ADR names as preferred.
- **The exact model** within either family (e.g., which Azure AI Language pricing tier; which specific LLM model/version) — an implementation-time choice for whoever builds each story, the same treatment ADR-0024/0026 gave their own exact-endpoint details.
- **Whether enrichment happens synchronously inline during ingestion or as an asynchronous follow-up step** — the design spec's own pipeline diagram places enrichment inline between normalization and persistence, and Phase 2's plan describes "wiring enrichment into the ingestion pipeline after normalization" the same way; this ADR treats that as already-decided by the spec, not reopened here.
- **A data-processing/GDPR-adjacent question this ADR surfaces but does not resolve, named honestly rather than silently built past:** enrichment necessarily sends already-ingested post content (potentially including public individuals' names, opinions, or other personal data appearing in third-party social/news posts) to a third-party processor — Microsoft (Azure AI Language) or an LLM vendor, Azure-hosted or otherwise. This is the same category of gap `docs/open-items-and-deferred-work.md` §C already names for tenant offboarding/GDPR Article 17 ("not addressed anywhere in this subsystem yet") — not a new, Story-2.8-specific problem, but this story is the first place it becomes concretely live rather than hypothetical. Not resolved by this ADR; named here so it isn't discovered as a surprise, the same discipline ADR-0018 already applied to the adjacent tenant-offboarding gap.

### 5. Capability-and-cost proportionality, made explicit — neither axis decided in isolation

**Stated directly, per Menno's own instruction:** both of this ADR's named candidates are chosen for being genuinely capable of the actual task (structured sentiment/entity/key-phrase extraction at production-usable accuracy) *and* proportionate in cost for a solo, self-funded project's real per-tenant economics — the same two-axis discipline this series already applied to ADR-0026 (GNews chosen over pricier alternatives, but not over a free option that couldn't actually do the job) and ADR-0024 (RTPR rejected on real pricing grounds, not merely "some option existed").

- **Azure AI Language** is not chosen for being cheapest in isolation (a free tier exists, but so would a free tier of a materially worse classifier) — it is chosen because it is a purpose-built, production-grade NLP classifier (real confidence scores, real entity categories, the exact shape `SocialPost.enrichment` already assumes) available at genuinely low cost for this project's own expected per-tenant volume (5,000 free text records/month, and — per the Research section's own honestly-flagged verification gap — an S-tier rate reported around $1/1,000 records beyond that, not a premium enterprise-only price point).
- **The LLM candidate is deliberately named as the small/cheap tier of each model family (GPT-4o-mini-class, Claude Haiku-class), not a flagship model (GPT-4o, Claude Opus/Sonnet).** This is a direct, reasoned choice, not an oversight: a bulk, per-post, structured-extraction classification task does not need frontier-model reasoning capability, and a flagship model's per-token price (Claude Sonnet 5's $2–3/MTok input and $10–15/MTok output vs. Haiku 4.5's $1/$5, both verified directly against Anthropic's own pricing page this session — Research section, above) would be a disproportionate cost for this specific job, the same "don't pay for capability the task doesn't need" reasoning ADR-0024 already applied when rejecting RTPR's $139/month paid-only tier for a job GlobeNewswire's/PR Newswire's free direct feeds could do just as well. Whoever builds the second `AIProviderConnector` should verify the small-tier model's own accuracy at this specific task before committing to it in production (Open Questions, below) — naming the cheap tier as the *starting* candidate is not the same as asserting its accuracy is already proven sufficient.
- **Neither candidate was chosen by defaulting to "most capable" or "cheapest" alone** — Azure AI Language beats a hypothetically cheaper-but-inadequate classifier on capability; the small-tier LLM models beat their own flagship siblings on cost-proportionality for a task that doesn't need flagship-level capability. Both choices are named explicitly here, on both axes, rather than left for a future reader to infer from the pricing figures alone.

## Consequences

**Positive**
- Closes the single largest functional gap in the product (no story anywhere implements `AIProviderConnector.analyze()` against a real provider) with a provider already shape-matched to shipped code, avoiding a costly reshape of `SocialPost.enrichment` under first-implementation pressure.
- Gives Menno's own LLM-based suggestion a real, primary-source-grounded evaluation and a concrete, reasoned place in this project's own roadmap (the second-provider swappability proof Phase 2 already calls for) rather than either adopting it uncritically or dismissing it.
- Keeps the credential/billing model exactly as ADR-0028 already resolved it — no new authorization or ownership-tier decision required for either candidate, provided the LLM candidate is pursued via its Azure-hosted form as recommended.

**Negative**
- **This ADR does not fully close the cost comparison Menno asked for** — Azure AI Language's own S-tier per-record price was not verified to this project's own primary-source bar this session; a real, material number is still missing before a confident production cost projection exists for either candidate.
- **Sequencing the LLM-based candidate second, not first, means the real efficiency win Menno identified (fewer round trips, likely lower cost) is not realized by Story 2.8 itself** — it is deliberately deferred to whichever future story builds the second `AIProviderConnector`, a real, named trade-off (lower first-implementation risk, later realized efficiency gain) rather than a costless sequencing choice.
- **The GDPR-adjacent third-party-data-processing question (Decision §4) is left open by this ADR**, the same way ADR-0018 already left tenant offboarding open — a real, accepted gap, not silently resolved by naming a provider.
- Building against Azure AI Language's per-capability call shape (rather than a single combined call) for a single small document, per Microsoft's own SDK guidance, means Story 2.8's own real per-post latency will be closer to several round trips than the single-call shape an LLM-based approach would offer — a real, accepted cost of sequencing the lower-risk provider first.

## Alternatives Considered

- **Build the LLM-based extractor first, Azure AI Language second (or not at all)** — considered directly, per Menno's own instruction to take this seriously; not chosen for the first implementation because it would require reshaping or accepting reduced fidelity in `SocialPost.enrichment`'s already-shipped, already-depended-on shape (`sentimentScores`' calibrated-probability framing in particular) as its very first real-world test, a bigger, less-verified first step than proving the already-shape-matched provider first. Not rejected outright — named directly in Decision §2 as the deliberate second-provider candidate.
- **A direct (non-Azure-hosted) OpenAI or Anthropic API integration** — considered; not recommended as the default path because it would open a first non-Azure vendor relationship for AI enrichment with its own unverified ToS/DPA fit (Decision §4), when an Azure-hosted equivalent (Azure OpenAI Service, Claude in Microsoft Foundry) achieves the same structured-extraction benefit while staying inside this project's already-verified, already-Azure-native operational and billing model.
- **Google Cloud Natural Language / AWS Comprehend as the dedicated-service candidate instead of Azure AI Language** — considered via a comparative search this session (feature parity is roughly similar across all three: sentiment, entities, key phrases, language detection); not chosen, because switching away from Azure for the very first `AIProviderConnector` would abandon this project's own Azure-native consistency (ADR-0016's own precedent) without a demonstrated, verified reason to do so — no red flag was found for Azure AI Language's own eligibility, and no comparative pricing/ToS advantage for AWS or Google Cloud's equivalents was verified this session to justify the switch.

## Open Questions for decision

- Azure AI Language's exact S-tier per-record price beyond the free tier — not verified to this project's own primary-source bar this session; verify directly against `azure.microsoft.com/en-us/pricing/details/language/`'s live rate table before production cost planning.
- GPT-4o-mini's exact current pricing — sourced from aggregator sites, not fetched directly from `openai.com`'s own pricing page this session; verify directly before choosing a specific LLM model for the second `AIProviderConnector`.
- Azure OpenAI Service's and Claude-in-Microsoft-Foundry's own current pricing and model availability — not independently priced this session; needed before specifying the second `AIProviderConnector`'s exact provider.
- Whether OpenAI's or Anthropic's own first-party (non-Azure) API terms would satisfy ADR-0027's source-eligibility bar for this project's automated, per-tenant usage pattern — not checked this session; only relevant if the Azure-hosted path (this ADR's own recommendation) is ever abandoned in favor of a direct vendor relationship.
- The GDPR-adjacent third-party-data-processing question named in Decision §4 — not resolved here; whoever eventually resolves the tenant-offboarding/right-to-erasure gap (`docs/open-items-and-deferred-work.md` §C, and Story 3.7/ADR-0039 in this same drafting batch) should check whether it also needs to name AI-enrichment data flows explicitly.
- Whether an LLM-based extractor's self-reported sentiment/entity confidence is fit-for-purpose against `SocialPost.enrichment.sentimentScores`'/`entities[].confidenceScore`'s own implied "calibrated probability" semantics, or whether that field's own documentation/contract needs a dated clarification once a second, structurally different provider exists — a real question for whoever builds the second `AIProviderConnector`, not decided here.
- **Whether the small/cheap-tier model named in Decision §5 (GPT-4o-mini-class or Claude Haiku-class) is actually accurate enough at this specific extraction task in practice** — this ADR names the cheap tier as the right *starting* candidate on cost-proportionality grounds, but does not itself run or verify an accuracy benchmark; whoever builds the second `AIProviderConnector` should validate this directly (e.g. against a sample of real ingested posts, compared to Azure AI Language's own output) before committing to it in production, and escalate to a stronger (costlier) model only if a real, demonstrated accuracy gap is found — the same "demonstrated need, not speculative" discipline this series applies elsewhere (ADR-0020).
