# ADR-0053: A canonical Markdown post-body representation — computed once at ingestion, stored on `social_posts`, decoupling N ingestion sources from M future consumers

**Status:** Accepted (2026-08-13)
**Source:** Not specified in the design spec or any prior ADR. Originated by Menno directly this session, while debugging why AI enrichment results were "not that great" — a real, live investigation (verified independently below, not assumed from the request) found that two of the three RSS/Atom-based connectors feed `enrichPost()` **title text only**, because their own parsers never extract the source's body content at all, and no column anywhere on `social_posts` could hold it even if they did. This ADR originates the fix; it does not document a decision any prior ADR made.

**Acceptance note (2026-08-13):** Accepted by Menno (Sponsor), verbatim: *"The last finding where sufficient I would like to approve ADR 0053."* Accepted as revised — twelve in-place revisions were made during live review before acceptance (see the Amendment Log below for the full record of each: the §8 consumer contract naming `body_markdown` as source-not-display-text plus its render-time sanitization requirement; the required pre-conversion `sanitize-html` pass ahead of `turndown`, argued directly from `turndown`'s own security documentation; the exact `<script>`/`<img>`/tracking-parameter sanitization configuration; the explicit, version-pinned `allowedTags`/`nonTextTags` enumeration replacing an implicit dependency on library defaults; the pre-conversion `MAX_BODY_SOURCE_LENGTH` length guard; the `exclusiveFilter` fix for tracking-stripped links reduced to bare, dead domains; the explicit statement of the pre-existing `raw_payload` spread mechanism that automatically propagates new parser fields; the explicitly-untested-assumption framing for raw Markdown syntax reaching enrichment, with Open Question 9 naming a future ADR as the correct home for closing it, not this one; the documented, un-fixed `enrichPost()`/`insertSocialPost()` write-ordering exposure; `turndown-plugin-gfm` for GFM table conversion, closing a real data-loss gap the `allowedTags` decision had itself newly exposed; the GNews truncation-marker regex trim, with its exact literal format honestly left unconfirmed; and, following a critical review of an independent Copilot review of this same ADR, `body_markdown_version` and `rawXml` as two accepted findings out of eight assessed). **Story 3.10** (`docs/user-stories/epic-3-data-model-storage-and-archival.md`) is added at this acceptance, per this series' own "no story until acceptance" precedent (ADR-0024/0026).

## Context

### The gap, verified directly this session

- **`social-listening-core/src/connectors/newswire/rssFeedParser.ts`** — read in full. `ParsedRssItem` (lines 11–20) captures exactly `guid`, `link`, `title`, `pubDate`, `issuer`. There is no `description` or `content:encoded` field anywhere on the type, and `parseRssItems()` (lines 57–80) never calls `extractTag(block, 'description')` or `extractTag(block, 'content:encoded')` — it only ever extracts `guid`, `link`, `title`, `pubDate`, `dc:contributor`. This is a real gap against the file's **own doc comment** (lines 1–9), which explicitly names `<description>` as one of "the two real differences observed between them" (GlobeNewswire's and PR Newswire's feeds) that motivated this parser's design — the comment documents the field's existence and CDATA-wrapping, but the parser never actually captures it.
- **`social-listening-core/src/connectors/newswire/pollNewswireFeeds.ts`** line 62 — `const enrichment = await enrichPost(tenantId, item.title);`. Title only, directly because title is the only prose field `ParsedRssItem` ever populates.
- **`social-listening-core/src/connectors/tenantOwnedFeed/feedItemParser.ts`** — read in full. `ParsedFeedItem` (lines 11–18) has the identical gap: `id`, `link`, `title`, `publishedAt` only. Its own doc comment (lines 1–10) states it "covers both RSS and Atom 'via the same poll/parse mechanism' per ADR-0050's own Context section" — confirmed against `docs/adr/0050-tenant-owned-domain-rss-content-feed-connector.md` line 52, which does say exactly that — but neither RSS's `<description>`/`<content:encoded>` nor Atom's `<summary>`/`<content>` is extracted anywhere in `parseBlocks()` (lines 61–82).
- **`social-listening-core/src/connectors/tenantOwnedFeed/pollTenantOwnedFeed.ts`** line 58 — `const enrichment = await enrichPost(tenantId, item.title);`. Same title-only pattern, same root cause.
- **`social-listening-core/src/connectors/gnews/gnewsConnector.ts`** — `GNewsArticle` (lines 9–19) already has both `description` **and** a separate `content` field, verified directly against the type. **`social-listening-core/src/connectors/gnews/pollGNewsSearch.ts` line 83** — `const enrichmentText = [article.title, article.description].filter(Boolean).join('. ');` — already enriches on title+description, but never includes `content`.
  - **GNews's `content` truncation on the free tier is confirmed, not assumed** — fetched directly from GNews's own documentation (`docs.gnews.io/endpoints/search-endpoint`, fetched this session): *"For users on the free plan, the content attribute is automatically truncated."* Untruncated content requires a paid plan upgrade. This is real, sourced, and load-bearing for Decision §5 below: `content` is a real, sourced field, but its value for a free-tier tenant will often be a truncated fragment, not full article text — Menno's own framing ("even a truncated snippet is more signal than title+description alone") is accepted as the working assumption, not treated as risk-free.
- **No `content`/`body` column exists anywhere on `social_posts`, verified against every migration that touches that table.** `migrations/0001_create_social_posts.sql` creates the table with exactly `id`, `tenant_id`, `raw_payload`, `created_at` (lines 6–11). `migrations/0010_add_social_posts_enrichment_fields.sql` adds `published_at` and `enrichment` (JSONB). No migration from `0001` through the current highest, `0029_grant_platform_admin_name_update.sql`, adds a body/content column of any kind. Everything content-related today lives only inside `raw_payload` JSONB — and, per the finding immediately below, for two of the three connectors, not even fully there.

### A second, previously-unnamed finding: `raw_payload` itself has already been silently under-capturing content for two connectors

`raw_payload` for Newswire and tenant-owned-feed posts is not the source's raw XML — it is `{ providerId, externalId, ...item }`, where `item` is the already-parsed `ParsedRssItem`/`ParsedFeedItem` object (`pollNewswireFeeds.ts` line 68, `pollTenantOwnedFeed.ts` line 64). Because those parser types never captured `description`/`content:encoded`/`summary`/`content` in the first place, **that data was never present in `raw_payload` either** — not archived, not queryable, not recoverable. This sits in tension with this project's own stated guarantee for `raw_payload`: ADR-0018's Context describes it as *"the full original platform JSON, explicitly 'never discarded.'"* For these two connectors, in practice, it was never "the full original" to begin with — a real field the source actually returned has been silently dropped on the floor since these connectors shipped, not merely deferred. Widening the two RSS/Atom parsers (Decision §4) closes this gap as a direct side effect, independent of anything this ADR decides about a new Markdown column — it is reason enough on its own, and is treated here as load-bearing, not incidental.

### What this ADR leaves completely unchanged

`raw_payload`'s "store exactly what the source returned, immutable" discipline — ADR-0016 (JSONB as the column type backing it, Decision: *"JSONB gives `rawPayload` a queryable, indexable column type... directly addressing the schema variance across platforms"*) and ADR-0018 (retention/tiering: `rawPayload` retained hot for 90 days, then moved to Blob Storage with the JSONB column replaced by a pointer, never hard-deleted) — is **completely unchanged** by this ADR. Nothing here alters how `raw_payload` is populated (beyond the parser-widening in §4, which only adds fields the source already sent, per the finding above) or how it's tiered/archived. This ADR is purely additive: a new, separate column, populated from the same already-fetched source data, computed once.

### The `ConnectorHealth`-derived vs. `enrichment`-stored precedent — and why this is `enrichment`, argued explicitly, not assumed

ADR-0009's Decision is that `ConnectorHealth` is **not** separately stored mutable state — `status`/`lastSuccessfulFetchAt`/`lastAttemptAt`/`consecutiveFailures` are derived at read time from `IngestionRun` history, specifically because storing them separately "would need to be kept in sync with every ingestion attempt's outcome — a second place that can drift from the actual run history." That reasoning does not transfer to a Markdown body column, for two independent reasons, not one:

1. **The `enrichment` precedent this ADR is following instead.** `social_posts.enrichment` (`migrations/0010`) is computed exactly once, at ingestion, by `enrichPost()` (called from all three `ingestX()` functions), and persisted — never recomputed from `raw_payload` on every read. `enrichment` could, in principle, be re-derived from `raw_payload`'s title/description on every read the same way `ConnectorHealth` re-derives from `IngestionRun` — but it isn't, because the actual computation is an external, billed Azure AI Language call (ADR-0038), and re-running it on every read would be wasteful and non-idempotent-in-cost. This ADR's new `body_markdown` column follows the same shape: computed once at ingestion by the shared `htmlToMarkdown()` utility (Decision §3), stored, never recomputed at read time.
2. **A second, independent, and arguably stronger reason `body_markdown` cannot safely be a `ConnectorHealth`-style read-time derivation from `raw_payload`: `raw_payload` is not permanently live-queryable.** ADR-0018's own Decision states that after 90 days (configurable), `rawPayload`'s hot JSONB content is replaced with "a pointer/reference" to Blob Storage — quoted directly: *"move to cheaper archival storage (Azure Blob Storage, keyed by post ID) and replace the JSONB column's content with a pointer/reference."* `ConnectorHealth`'s derivation source, `IngestionRun`, has its own, separate 18-month archival window (ADR-0018), but the point stands generally: unlike `ConnectorHealth`'s always-live aggregation source, a naive "derive Markdown from `raw_payload` at read time" design would silently stop working for any post older than 90 days, the exact moment `raw_payload`'s JSONB content is replaced by a blob pointer — breaking display (or a future enrichment re-run) for aged posts with no error, just empty or wrong output. Storing `body_markdown` once, at ingestion, while `raw_payload` is still the live original, avoids this failure mode entirely and is not merely a style preference — it is required by ADR-0018's own already-Accepted archival design.

Both reasons point the same direction: `body_markdown` is `enrichment`-shaped (compute once, persist, never silently re-derive), not `ConnectorHealth`-shaped (derive fresh, trust the source of truth to always be there). `ConnectorHealth`'s source of truth (`IngestionRun` at read time, within its own retention window) is always live when queried; `raw_payload` is deliberately *not* always live past 90 days, which is disqualifying for a "derive on every read" design here even before considering the `enrichment`-precedent argument.

### The N×M value proposition — stated explicitly, as its own load-bearing rationale

Today, and for the foreseeable future, this project has **N ingestion sources**, each returning body content in a different shape: GNews's own possibly-truncated `content` field (JSON, plain-text-ish per GNews's docs), GlobeNewswire's and PR Newswire's CDATA-wrapped HTML `<description>`/`<content:encoded>` (which differ from each other in markup conventions, per `rssFeedParser.ts`'s own doc comment), an arbitrary tenant's own blog/CMS HTML via the tenant-owned-feed connector (which could be WordPress, Squarespace, HubSpot, or a hand-rolled feed — ADR-0050 Open Question 3 already names this variability without resolving it), and whatever shape any future connector returns (Wikipedia/Story 2.13's wikitext-derived HTML, a future Reddit connector's Markdown-flavored comment bodies, etc.).

Separately, this project has, or will have, **M output/consumption needs** for that content: the admin UI's post feed display (today, plain text/title only per Story 6.11), a plausible future HTML render, a plausible future Word export, a plausible future PDF export, and enrichment's own text input (which already exists, today, per `enrichPost()`'s callers).

**Without a canonical intermediate representation, every new connector requires new parsing logic in every consumer that wants to understand its content, and every new consumer requires new parsing logic for every connector's shape — an N×M problem that grows by one row or one column, respectively, with every future addition on either axis.** Storing one normalized Markdown field once, at ingestion, means every future consumer converts *from* Markdown — a single, stable, well-understood format with mature libraries on every side (Markdown→HTML, Markdown→DOCX via Pandoc-family tooling, Markdown→PDF via any of several established toolchains) — and no future consumer ever needs its own bespoke logic to understand GNews's JSON shape, GlobeNewswire's CDATA HTML, a tenant's arbitrary CMS HTML, or a future connector's own shape. This collapses the problem from N×M conversion pairs to N (ingestion → Markdown) + M (Markdown → output), which is the actual, load-bearing reason this ADR chooses a stored canonical intermediate over letting each future consumer parse `raw_payload` directly.

### Author-rights standing check (per this role's charter)

This ADR touches ingested content that has an author — for all three affected connectors, an issuing-organization/publication `Author` under ADR-0004's organization-as-Author clause (ADR-0024 Newswire, ADR-0026 GNews, ADR-0050 tenant-owned-feed), not an individual. Checked explicitly: this ADR does not touch `Author`, `authorId`, or any attribution mechanism — `body_markdown` is additive content storage, keyed to the same `SocialPost` row that already carries `author_id` (ADR-0004) and, where applicable, `author_follower_count_at_publish` (ADR-0049). No redistribution, enrichment-provider disclosure, or export feature is being built or changed by this ADR (enrichment's *input* text changes; ADR-0038's enrichment-provider processing relationship does not). Ownership is never reassigned, and nothing here strips or obscures who authored the content — the same `Author` upsert, keyed by the same `externalAuthorId` (issuer, source publication, or verified domain), runs unchanged. This check applies narrowly and finds no gap to close; it is recorded because the check is a standing obligation, not because it surfaced a new issue.

## Decision

**The durable decision — this is what would need superseding, not just amending:**

### 1. `raw_payload` discipline: unchanged

Reaffirmed, not re-decided: `raw_payload`'s "store exactly what the source returned, immutable" property (ADR-0016, ADR-0018) is untouched. This ADR adds a new column and widens two parsers to capture fields the source already sends (closing the gap named in Context) — it does not change how `raw_payload` is written, tiered, or archived.

### 2. A new column, `social_posts.body_markdown` — computed once at ingestion, stored, `enrichment`-shaped not `ConnectorHealth`-shaped

A new, nullable `TEXT` column on `social_posts`, added by a new migration (exact number assigned at Story time, per this project's own "added by a later migration, not speculated here" convention — `migrations/0001`'s own header text). Populated exactly once, at ingestion time, by each connector's `ingestX()` function, and never recomputed on read. Argued explicitly in Context above (the `enrichment` precedent, and — independently and more concretely — `raw_payload`'s own 90-day archival tiering under ADR-0018, which disqualifies a `ConnectorHealth`-style "derive fresh from `raw_payload` on every read" design outright for any post older than the hot-storage window).

Nullable for the same reason `enrichment` and `published_at` are nullable (`migrations/0010`'s own stated rationale): only posts with body content resolve to a non-null value; a source item with neither a body field nor extractable text yields `NULL`, not an empty string, so a caller can distinguish "no body was ever provided" from "the body converted to an empty string."

**No database transaction wraps `enrichPost()` and `insertSocialPost()` together — verified directly this session, not assumed.** A repo-wide grep of `socialPostStore.ts` and all three ingest functions for `BEGIN`/`COMMIT`/`transaction` found none. `insertSocialPost()` (`socialPostStore.ts`) is a single `INSERT INTO social_posts (...) VALUES (...) RETURNING id` statement — `enrichment` today, and `body_markdown` once this ADR ships, are both **values passed into that one atomic INSERT**, never a follow-up `UPDATE`. The real failure mode this implies, stated explicitly rather than left for a reader to work out independently: `enrichPost()` (a real, billed, external Azure AI Language/Azure OpenAI call, ADR-0038) runs and returns *before* `insertSocialPost()` is ever called. If `enrichPost()` succeeds but the subsequent `insertSocialPost()` call then fails (a dropped connection, a constraint violation, any exception), the entire row — `raw_payload`, `enrichment`, and `body_markdown` alike — is never created; the computed `enrichment` result, held only in a local variable, is discarded when the exception propagates, and the AI cost already incurred is not recoverable. If `runIngestionAttempt()` retries the attempt (a retryable error), the ingest loop re-runs from the start; `findSocialPostByExternalId()`'s own dedup check correctly skips posts already committed earlier in the same loop, but the one post whose insert failed has no persisted row yet, so `enrichPost()` runs again for it on retry — a second billed AI call for that specific post. The exposure is real but narrow: bounded to at most one post per failure, not the whole batch, since every other post in the loop either already committed (skipped on retry) or hasn't been attempted yet.

**A second new column, `social_posts.body_markdown_version` — a nullable `SMALLINT`, populated alongside `body_markdown` at ingestion, tracking which conversion pipeline produced it.** Decision §3/§5/§7 already treat the conversion pipeline's own library versions and configuration (`allowedTags`, `nonTextTags`, the tracking-parameter denylist, the GNews truncation regex, and so on) as revisable implementation defaults, changeable without superseding this ADR — which means two posts ingested on either side of such a change could hold differently-produced Markdown for identical source content, with nothing in the row itself recording which ruleset produced it. `body_markdown_version` closes that: this ADR's own pipeline (as fully specified in Decision §3/§5) is version `1`; a future change to the pipeline that could plausibly alter output for real content — a library version bump, or a configuration change to any of the above — increments it. Judging whether a specific future change is output-altering enough to warrant a bump is left to whoever makes that change (e.g. a dependency patch release fixing an unrelated bug is unlikely to need one; changing the `allowedTags` list or the tracking-parameter denylist clearly would) — not mechanically triggered by every dependency update, which this Decision does not attempt to enumerate in advance. `NULL` exactly when `body_markdown` is `NULL`, mirroring that column's own nullability semantics — there is no meaningful pipeline version for content that was never produced. Directly useful for a future backfill (Open Question 1): it lets that later Story selectively target only outdated-version rows rather than uniformly re-processing everything.

**This exposure is not new, not introduced by this ADR, and not worsened by it.** `enrichment` has carried this exact same shape since Story 2.8/2.9 (ADR-0038) — this ADR changes what text is *fed into* `enrichPost()` (Decision §6), not when it's called relative to the database write. `body_markdown` itself introduces no comparable risk of its own: `htmlToMarkdown()` (Decision §3) is a synchronous, in-process, non-billed, non-network computation — a failed insert after it runs wastes negligible local CPU, nothing metered or rate-limited, unlike `enrichPost()`'s real external cost. Per this project's own scope discipline, and per direct instruction this session, this ADR documents the existing stance rather than designing a fix (e.g. wrapping both calls in a transaction, or restructuring to insert-then-update) — that remains a real, pre-existing, unaddressed gap belonging to `enrichPost()`'s own call-site pattern, not something Decision §2/§6 take on.

### 3. A new shared utility, `htmlToMarkdown()` — one implementation, called identically by all three connectors' ingest functions

A single function, in a new shared module (not owned by any one connector — none of `rssFeedParser.ts`, `feedItemParser.ts`, or `gnewsConnector.ts` is the right home, since all three call it identically), converts a raw body string (HTML or plain text) to normalized Markdown. Called from `ingestNewswireItems()`, `ingestTenantOwnedFeedItems()`, and `ingestGNewsArticles()` — not reimplemented per-connector, not folded into any connector's own RSS/JSON parser (parsers extract raw field values only; conversion is a separate, shared concern).

**Must be a safe pass-through for text that's already plain** — GNews's `description`/`content` fields are not guaranteed to contain HTML markup (verified: `GNewsArticle`'s doc comment cites `docs.gnews.io/json-response` but does not claim HTML-formatted fields; GNews is a news-aggregation API, not a CMS export). A library whose HTML-to-Markdown conversion degrades gracefully on plain input (no tags to convert, output ≈ input) satisfies this; the one caveat, named honestly rather than glossed over: a text-node-escaping library (see Alternatives Considered) will backslash-escape Markdown-significant characters (`*`, `_`, `[`, `]`, etc.) that appear naturally in already-plain source text, so `body_markdown` for a plain-text GNews snippet will not be byte-identical to the original — it will be Markdown-safe (round-trips correctly through a Markdown renderer) but not literally unchanged. This is expected, correct behavior for a Markdown-producing function, not a defect, and is named here so it isn't mistaken for a bug at implementation time.

**A pre-conversion length guard truncates the raw source string before anything else runs — before sanitization, before conversion.** `htmlToMarkdown()`'s first step, ahead of both `sanitize-html` and `turndown`, is `rawSource.slice(0, MAX_BODY_SOURCE_LENGTH)` on whichever field Decision §4/§5's own precedence rule already selected — the precedence logic itself is unchanged, this only bounds the string handed to the conversion pipeline. Two independent reasons, not one: **(1) parser exposure.** Every one of this ADR's three sources is untrusted third-party content (Context, N×M section), and the tenant-owned-feed connector is the weakest trust boundary of the three — a tenant supplies the feed URL directly, so an unusually large or adversarially-crafted response is not a hypothetical. Bounding input size before `sanitize-html`/`htmlparser2` and `turndown`/`domino` ever parse it limits how much untrusted content either library's parser is exposed to per post, the same "smallest exposure for the actual requirement" reasoning already used elsewhere in this ADR. **(2) enrichment cost.** `enrichmentText` (Decision §6) is built from `body_markdown` and sent to a real, billed Azure AI Language/Azure OpenAI call (ADR-0038) — an unbounded body inflates enrichment cost per post. This is a narrow, per-post mitigation only, explicitly **not** a substitute for ADR-0052's own already-named, still-unresolved Open Question 4 (no aggregate cost/quota ceiling across a tenant's continuous polling) — it bounds one post's own contribution, not total spend.

A truncated string handed to a malformed-markup-tolerant parser (Decision §3's own already-established reason for choosing `sanitize-html`/`turndown` in the first place) is not a new class of problem — mid-tag truncation produces exactly the kind of incomplete markup these libraries' HTML5-style error recovery already exists to handle gracefully, not a scenario this guard introduces.

**`MAX_BODY_SOURCE_LENGTH`, a named, revisable implementation default, not a durable ceiling** (same "real number, marked adjustable" convention as ADR-0052's tick interval and jitter bound): **100,000 characters (~100KB)** of the selected raw source field, measured as JavaScript string length (UTF-16 code units) via a plain `.slice()`, not a precise byte count — for predominantly-ASCII/Latin-1 HTML source this is a close-enough approximation for a soft safety bound, not a guarantee, and is named here so that imprecision isn't silently assumed away. Chosen as a generous multiple of what a genuine press release, blog post, or news article's own body realistically runs (typically low single-digit KB to a few tens of KB) — truncation is expected to be rare in practice, not a routine occurrence. No truncation indicator (e.g. an appended "…[truncated]" marker) is mandated by this Decision — a reasonable implementation-time nicety, not required (Open Questions).

**A pre-conversion sanitization step is required, not optional — confirmed directly against `turndown`'s own security guidance, not asserted as independent best practice.** `turndown`'s own `SECURITY.md` (fetched this session) states explicitly that a string input's DOM parser "depends on the environment... malicious string inputs can lead to undesired effects in the DOM parser before Turndown processes the document," and recommends: *"either sanitize the input using a dedicated HTML sanitizer library or opt for a DOM parser that aligns with your security requirements."* Turndown 7+ (the current major version) already mitigates the worst of this at the parser level — it moved off `jsdom` (which has script-execution capability) onto a bundled `domino` parser that does not support script execution or external resource downloads — but the maintainers still name sanitizing untrusted input as the primary defense, not the parser swap alone. Every one of this ADR's three input sources is untrusted third-party content (Context, N×M section), so `htmlToMarkdown()`'s actual pipeline is **sanitize, then convert**: the raw source string passes through `sanitize-html` (an allowlist-based sanitizer — strips disallowed tags/attributes rather than merely escaping them) before being handed to `turndown`. This has a second, independent benefit directly relevant to real-world RSS/Atom content, raised directly by Menno: `sanitize-html` is built on `htmlparser2`, a lenient, forgiving HTML/XML parser (not a strict spec validator), which tolerates the malformed markup RSS/Atom feeds are well known to contain — unclosed `<p>` tags, mismatched `<div>`/`<span>` nesting, vendor-specific quirks — producing well-formed output for `turndown` to convert, rather than handing `turndown` potentially-broken markup directly. Accepted as a required pipeline step.

**Library choice — `turndown` for conversion, `sanitize-html` for the required pre-conversion sanitization pass; both named as real, revisable defaults**, with Microsoft's own MarkItDown explicitly weighed and rejected as a fit for this narrow use — see Alternatives Considered. `social-listening-core/package.json` was checked directly this session: no HTML-parsing, HTML-sanitizing, or HTML-to-Markdown dependency of any kind currently exists (`turndown`, `sanitize-html`, `marked`, `html-to-text`, `cheerio`, `jsdom`, and near-variants all absent from both `dependencies` and `devDependencies`), so both are genuinely new dependencies, not a reuse of something already present.

**A real data-loss gap, found directly, not hypothetical: `allowedTags` (above) permits full table markup through sanitization, but vanilla `turndown` has no rule to convert it.** Verified directly against both libraries' own source this session: `turndown`'s complete built-in rule set (`commonmark-rules.js`, `mixmark-io/turndown`) contains zero table-related rules — CommonMark itself has no table syntax, so `turndown` never needed one. A `<table>` that survives sanitization (its tags are all in the explicit `allowedTags` list above) is handed to a converter with no rule for `table`/`tr`/`td`/`th`, and `turndown`'s default fallback for an unrecognized element just walks its children and concatenates their text — a real financial table, pricing grid, or comparison table in a press release collapses into an unstructured run of cell text with every row/column boundary gone, unreconstructable after the fact. This is not a corner case invented for completeness; it is the direct, verified consequence of Decision §3's own explicit table-tag allowlist paired with a converter that was never going to honor it.

**Decided: add `turndown-plugin-gfm`, applied via `turndown`'s own documented plugin API (`turndownService.use(...)`), to add real GFM table conversion.** Verified directly, not assumed: its `tables.js` module (`mixmark-io/turndown-plugin-gfm`) implements genuine `tableCell`/`tableRow` rules producing proper `| cell | cell |` / `|---|---|` GFM Markdown table syntax, closing the exact gap above. **One correction to how this option was first framed, worth stating precisely rather than silently accepting:** it is real and does live under the `mixmark-io` org — confirmed directly via the GitHub API (`gh api repos/mixmark-io/turndown-plugin-gfm`), even though the published npm package's own `package.json` `repository` field still points at the project's old pre-org-move URL (`domchristie/turndown-plugin-gfm`, which GitHub now transparently redirects) — but calling it "maintained" overstates its current activity: its last npm release (`1.0.2`) shipped in **2018**, and its last GitHub commit was **2023** (`pushed_at`, checked this session), with 21 open issues. Not archived, and the table-conversion feature itself is small and stable enough that a multi-year gap doesn't necessarily indicate a real defect — but this is accepted as a real, if lower-recency, third dependency, not represented as actively maintained. The judged trade-off: the confirmed data-loss gap above is worse than depending on a stable-but-quiet package from the right org for a narrow, self-contained conversion rule.

**Concrete sanitization configuration — decided explicitly, as literal values this project's own code passes to `sanitize-html`, never inherited implicitly from whatever the library's own defaults happen to be at install time.** The distinction matters and is deliberate: relying on `sanitizeHtml.defaults.allowedTags` (or any other un-passed default) means a future `sanitize-html` version bump could silently widen or narrow what's permitted with no corresponding change to this project's own code or tests to catch it. Pinning the actual values here, verified directly against the library's real current source rather than assumed from its documentation prose, closes that gap.

- **`allowedTags` — a literal array in this project's own code, copied from `sanitize-html@2.17.6`'s own current default set (fetched directly from `apostrophecms/sanitize-html`'s `index.js` on its `main` branch this session, not assumed) and not independently re-curated by this ADR beyond the `img` exclusion already decided below:**
  `address, article, aside, footer, header, h1, h2, h3, h4, h5, h6, hgroup, main, nav, section, blockquote, dd, div, dl, dt, figcaption, figure, hr, li, menu, ol, p, pre, ul, a, abbr, b, bdi, bdo, br, cite, code, data, dfn, em, i, kbd, mark, q, rb, rp, rt, rtc, ruby, s, samp, small, span, strong, sub, sup, time, u, var, wbr, caption, col, colgroup, table, tbody, td, tfoot, th, thead, tr`
- **`nonTextTags` — likewise pinned explicitly, not inherited implicitly, for the identical reason:** `script, style, textarea, option` (copied from the library's own current default this session). This is what makes `<script>`/`<style>` content fully discarded, not merely unwrapped — both the tag and its inner text are dropped together. Explicitly pinning this option closes the same "silent future drift" gap `allowedTags` above closes, for the one other option this ADR's security argument depends on.
- **Images are deliberately not included in the explicit `allowedTags` array above.** Stated as a deliberate decision, not an accidental side effect of "whatever the default happens to be": `body_markdown`'s actual purpose (Context) is enrichment-quality text and a future text-oriented render, not image-preserving display, so `img` is left out rather than added. This has the direct, useful side effect of also excluding tracking pixels — raised directly by Menno — without this ADR needing to design any tracking-pixel-specific heuristic (dimension checks, domain denylists, etc.), which would be inherently imperfect. If a future story wants to preserve legitimate content images, *that* story inherits the harder problem of distinguishing a tracking pixel from real content — named here so it isn't silently assumed solved by this one (Open Questions).
- **`<a href>` tracking-parameter stripping is a required, separate step — `sanitize-html` does not do this by default, and this is a real gap this ADR must decide, not one already closed by the library's own defaults.** `<a>` is in the explicit `allowedTags` list above (links are core content — a press release or blog post routinely links out), and `sanitize-html` has no built-in concept of "strip known tracking query parameters from an otherwise-safe URL," since that's a data-hygiene concern, not a security one. Decided: a `transformTags` function (`sanitize-html`'s own documented mechanism for rewriting a tag's attributes during sanitization) strips a fixed, named set of known tracking parameters from every `<a href>`'s query string before the value is retained — `utm_source`, `utm_medium`, `utm_campaign`, `utm_term`, `utm_content`, `fbclid`, `gclid`, `mc_cid`, `mc_eid` — a real, named, revisable list (same "implementation default, not durable decision" convention as the cadence numbers in ADR-0052), not an unbounded or unspecified "clean the URL somehow." A tracking parameter's *presence* triggers stripping of that parameter only; the link itself (and any of its own legitimate query parameters) is preserved.

**A real failure mode of the stripping above, found directly, not hypothetical: if a URL's entire query string is tracking parameters, stripping them can leave a bare tracking domain with no meaningful destination.** Email-marketing click-redirect links are the concrete case — `https://clicks.example.com/?mc_cid=abc&mc_eid=xyz`, where the destination is resolved by the tracking service from those exact parameters, becomes `https://clicks.example.com/` after stripping: a syntactically valid but functionally dead link, and the denylist above names `mc_cid`/`mc_eid` specifically (Mailchimp's own click-tracking parameters) as parameters this pipeline already strips. Left unspecified, this is a worse outcome than doing nothing — a link that looks legitimate but goes nowhere useful.

**Decided: an `exclusiveFilter` step, run after `transformTags`, drops the `<a>` wrapper (keeping its inner text as plain content) when the post-stripping `href` has no path (or only `/`), no remaining query string, and no fragment.** Verified directly against `sanitize-html`'s own source (`index.js`, `onclosetag`) that `exclusiveFilter` executes after `transformTags` has already run and sees the already-transformed `frame.attribs` — the ordering this fix depends on is real, not assumed. Returning the string `'excludeTag'` (not bare `true`) from `exclusiveFilter` is required specifically because it unwraps the tag while preserving inner text; bare `true` discards the text too, per the library's own documented distinction, and would silently lose real prose content over a merely-broken link. The bareness check parses `frame.attribs.href` (e.g. via the WHATWG `URL` API) and tests `pathname` is empty or `/`, `search` is empty, and `hash` is empty; an `href` that fails to parse as an absolute URL is treated conservatively — kept, not excluded, since incorrectly dropping a link over a parsing edge case is worse than leaving a possibly-imperfect one, the same "fail toward keeping content" bias already used elsewhere in this Decision (e.g. GNews's free-tier truncation is accepted rather than discarded). **A relative `href` whose entire content is a now-stripped tracking parameter (e.g. `?utm_source=foo`, reduced to `?` or empty after stripping) already falls into this same conservative-keep path** — the WHATWG `URL` constructor requires a base to resolve a relative reference and throws without one, so this case is caught by the existing "fails to parse as absolute → keep" fallback, not a separate gap; named explicitly here so it isn't mistaken for an overlooked case at implementation time.
- **All three dependency versions are pinned to an exact version at Story time, not a semver range, with a code comment tying the pin back to this ADR.** `package.json` entries for `turndown`, `sanitize-html`, and `turndown-plugin-gfm` must be exact (e.g. `"turndown": "7.2.4"`, not `"^7.2.4"`), and the actual `htmlToMarkdown()` call site must carry a comment naming ADR-0053 explicitly (e.g. *"turndown/sanitize-html/turndown-plugin-gfm versions pinned exactly — see ADR-0053 before bumping any of them; the allowedTags/nonTextTags lists and table-conversion behavior above were verified against these specific versions and a version bump could silently change any library's own internal behavior even with our own config unchanged"*). Verified this session, real and current, not placeholders: `turndown@7.2.4`, `sanitize-html@2.17.6`, `turndown-plugin-gfm@1.0.2` (`npm view <pkg> version`, all fetched live). `sanitize-html@2.17.6` requires Node `>=22.12.0` (`npm view sanitize-html engines`) — confirmed compatible, since `social-listening-core/package.json` declares no `engines` constraint of its own and the actual running Node version this session is v26.6.0.

### 4. The two RSS/Atom parsers widened to actually capture body content

**`rssFeedParser.ts` (Newswire):** `ParsedRssItem` gains two new nullable fields — `description` (from `<description>`) and `contentEncoded` (from `<content:encoded>`) — extracted via the same `extractTag()` helper already used for every other field (its CDATA-stripping and entity-decoding already handle exactly the shape the file's own doc comment names: "CDATA-wrapped values... GlobeNewswire's `<description>`"). `extractTag()`'s tag-name interpolation (`` `<${tagName}(?:\s[^>]*)?>...` ``) works unchanged for a colon-containing tag name like `content:encoded` — colons are not regex metacharacters, verified by reading the existing implementation directly; no change to `extractTag()` itself is required.

**`feedItemParser.ts` (tenant-owned-feed):** `ParsedFeedItem` gains the RSS/Atom-unified body fields the file's own doc comment already claims to support but doesn't yet extract. Because this connector "covers both RSS and Atom via the same poll/parse mechanism" (ADR-0050 Context, confirmed directly against that ADR), the widened parser must extract **both** shapes: RSS's `<description>`/`<content:encoded>` and Atom's `<summary>`/`<content>`. `parseBlocks()`'s existing `dateTags: string[]`-and-`.find()` pattern (already used to try `pubDate` for RSS and `updated`/`published` for Atom in one pass) is the direct model for the same "try each format's own tag name, take the first that resolves" approach for body fields — not designing the exact implementation here, but naming that the existing function already has the right shape to extend, so this is a widening of an established pattern, not a new one.

**Both parsers also gain a `rawXml` field, holding the item's entire raw inner XML block verbatim — closing the Context "second finding" gap completely, not just narrowing it.** Decision §4's own named-field widening (`description`/`contentEncoded`/`summary`/`content`) still only extracts a fixed, enumerated set of fields; any element a source sends that no `extractTag()` call knows to ask for — a custom namespace element, an enclosure/media tag, metadata this ADR didn't anticipate — would still be silently dropped, the same category of gap this ADR exists to close, just on a narrower remaining surface. Verified directly this session, not assumed: both `rssFeedParser.ts`'s `parseRssItems()` and `feedItemParser.ts`'s `parseBlocks()` already capture each item's entire raw inner XML as a local variable (`const block = match[1]`, from `ITEM_RE`/`ENTRY_RE`) before extracting any named field from it — currently discarded once the named fields are pulled out. Retaining it as `rawXml: block` on `ParsedRssItem`/`ParsedFeedItem` costs zero additional parsing logic, since the value is already in hand mid-loop. It flows into `raw_payload` automatically via the exact same spread mechanism this Decision already documents below (`{ providerId, externalId, ...item }`) — no additional `insertSocialPost()` call-site change needed for this specific field either. This is deliberately `raw_payload`-only: `rawXml` is never read as a `body_markdown` source (the precedence rule below is unchanged) — it exists purely to make this ADR's own "closes the under-capture gap" claim actually true, matching the completeness GNews's own `rawPayload: {...article}` full-object spread already has (GNews needs no equivalent change — its `rawPayload` already spreads the entire API response object, so this gap never existed there).

**The parser widening above automatically closes the Context "second finding" `raw_payload` under-capture gap, with no additional code change to either ingest function's own `insertSocialPost()` call required for that specific effect — re-verified directly this session, not assumed stale from the original draft.** `pollNewswireFeeds.ts` line 68 and `pollTenantOwnedFeed.ts` line 64 were re-read this session and confirmed unchanged: both still construct `rawPayload` as `{ providerId, externalId, ...item }`, spreading the entire parsed object. Because this is a spread of `item` itself, not an enumerated subset of its fields, any field this Decision adds to `ParsedRssItem`/`ParsedFeedItem` — `description`, `contentEncoded`, and the Atom equivalents — flows into `raw_payload` automatically the moment the parser populates it, purely as a consequence of widening the parser's own return type. This is the actual mechanism that closes the Context finding; it is not a separate piece of work this Decision still owes. (Decision §6 below does still require its own, separate edit to each of these same two call sites — composing `enrichmentText` — but that is a different change to different lines, not a second instance of this one.) If a future implementer finds these line numbers have drifted by Story time, re-confirm the spread pattern itself still holds before relying on this paragraph's claim — the pattern, not the exact line number, is what this Decision depends on.

**Precedence rule, stated explicitly so no ambiguity is left for an implementer to resolve independently, per this project's own `ADR-0052 Decision §5` standard:** for each item, the body source is the *richest* available field, in this fixed order — **`content:encoded` (RSS) or `content` (Atom), if present and non-empty; else `description` (RSS) or `summary` (Atom), if present and non-empty; else `null`.** This mirrors the real-world shape both formats already establish (a full-content field when present, a shorter summary/excerpt field as the fallback) rather than inventing a new rule.

**What GlobeNewswire's and PR Newswire's real `<description>` content typically contains could not be confirmed this session.** No fixture or test file in `social-listening-core/contracts` (checked directly — a repo-wide grep for `description`, `CDATA`, and `content:encoded` under `contracts/` returns only two unrelated files, `story-6.16` and `story-3.9`, neither a Newswire fixture) captures a real sample of either wire's `<description>` payload. `rssFeedParser.ts`'s own doc comment confirms the field exists and is CDATA-wrapped on GlobeNewswire's feed, but not its typical length or whether it's a full press release or an excerpt. **Stated honestly as unconfirmed, not guessed at** — this is exactly the kind of claim this ADR's own house discipline requires not fabricating. Whoever implements this Decision should verify against a live feed fetch before assuming either wire always returns full-text content.

### 5. GNews enrichment input widened to include `content`

`GNewsArticle.content` is added to the enrichment input's source material alongside the already-used `title`/`description`, per Menno's own explicit direction this session ("include it too... even a truncated snippet is more signal than title+description alone") — accepted as the working call, with the free-tier truncation caveat (Context, confirmed via `docs.gnews.io`) named plainly rather than hidden. `content`'s value flows into `body_markdown` (§2) via the same `htmlToMarkdown()` pass (§3) as every other connector's body field — GNews gets no special-cased enrichment path; it goes through the identical `body_markdown` → enrichment-input pipeline described in §6 below.

**Precedence for GNews's own `body_markdown` source, stated explicitly:** `content`, if present and non-empty; else `description`, if present and non-empty; else `null` — same "richest field first" rule as §4, applied to GNews's two-field shape.

**A real, distinct pollution gap, not the same thing as this ADR's own `MAX_BODY_SOURCE_LENGTH` truncation (Open Question 10 below): GNews's own free-tier truncation of `content` (Context, confirmed via `docs.gnews.io`) appends a literal marker to the field's own plain-text value before this system ever receives it — commonly reported in the form `[+N chars]` (e.g. "...announced a new funding round [+1,842 chars]"), though the exact string is not spelled out in GNews's own documentation (checked directly this session — their docs confirm truncation occurs but not its literal format).** Because this is plain text, not HTML markup, `sanitize-html` has nothing to strip it (there is no tag to disallow), `turndown` passes plain text through unchanged, and the marker lands verbatim inside both `body_markdown` and `enrichmentText` — visible AI-analysis noise and a real, if minor, content-quality defect, unrelated to and not addressed by this ADR's own length-guard truncation (Decision §3).

**Decided: a regex trim removes a trailing GNews-style truncation marker from `content` before it reaches `htmlToMarkdown()`** — e.g. `content.replace(/\s*\[\+\d+ chars\]$/, '')` — named as a real, revisable implementation default (same convention as the tracking-parameter denylist and `MAX_BODY_SOURCE_LENGTH`), **not asserted as confirmed against GNews's real output.** The pattern is this ADR's best current understanding, not a verified fact the way `turndown('')`'s behavior (Decision §6) now is — whoever implements this Decision should confirm the exact literal format against a real truncated GNews response (a free-tier tenant with a long article is sufficient to observe it) before finalizing the regex, the same "verify against a live feed fetch" standard Open Question 4 already sets for Newswire's own unconfirmed content shape.

### 6. Enrichment's input text — the exact composition rule, stated with no ambiguity left to an implementer

**Timing/transaction note: see Decision §2 for the write-ordering exposure this composition inherits — `enrichPost()` (below) runs before, and independently of, the `insertSocialPost()` call that persists its result; no transaction ties the two together, an existing exposure this ADR documents rather than changes.**

**All three connectors compose enrichment input identically, at ingestion time, as:**

```
enrichmentText = [title, body_markdown].filter(Boolean).join('. ')
```

This is the *same* join pattern already live in `pollGNewsSearch.ts` line 83 (`[article.title, article.description].filter(Boolean).join('. ')`), generalized to use the new `body_markdown` value in place of the raw `description` field, and now applied uniformly to Newswire and tenant-owned-feed as well (both currently pass `item.title` alone). Concretely, per connector:

- **Newswire** (`pollNewswireFeeds.ts` line 62): replace `enrichPost(tenantId, item.title)` with `enrichPost(tenantId, [item.title, bodyMarkdown].filter(Boolean).join('. '))`, where `bodyMarkdown = htmlToMarkdown(item.contentEncoded ?? item.description ?? '')` — **empty string in, empty string out, verified directly this session, not assumed:** `turndown@7.2.4`'s own `turndown('')` returns `''`, and `turndown('   ')` (whitespace-only) also returns `''` (confirmed by installing the exact pinned version in an isolated scratch environment and running both calls directly). `filter(Boolean)` correctly drops the falsy empty string, matching the existing "no description available" degrade-to-title-only behavior for items with no body at all — this is now a confirmed behavior this Decision relies on, not an assumption about how the library "probably" behaves.
- **Tenant-owned-feed** (`pollTenantOwnedFeed.ts` line 58): identical shape, using the widened `ParsedFeedItem`'s own body field (§4).
- **GNews** (`pollGNewsSearch.ts` line 83): `enrichmentText` becomes `[article.title, htmlToMarkdown(article.content ?? article.description ?? '')].filter(Boolean).join('. ')` — `description` is no longer joined directly; it is folded into `body_markdown`'s own §5 precedence rule instead, so the same title+body shape applies uniformly across all three connectors rather than GNews alone keeping a bespoke two-and-a-half-field join.

**`enrichmentText` carries `body_markdown`'s literal Markdown syntax through to the AI provider unmodified — a deliberate, but explicitly untested, decision for this ADR, not a settled conclusion.** No Markdown-stripping or plain-text-rendering step runs between `body_markdown` and `enrichPost()`; `**bold**`, `# heading`, `[text](url)`, and list markers reach Azure AI Language/Azure OpenAI embedded in the text exactly as stored. The working assumption — Markdown syntax is low-noise for sentiment/entity/key-phrase extraction, and meaningfully less disruptive than the raw HTML this ADR replaces would have been — is accepted as this ADR's own starting position, **not verified against real enrichment output this session** (Open Questions). If real usage shows Markdown syntax measurably degrading enrichment accuracy, closing that gap is explicitly **out of this ADR's own scope** — a separate future ADR would design a Markdown-to-plain-text (or otherwise-cleaned) conversion step applied only at the `enrichmentText` composition point, leaving `body_markdown` itself (the stored column, Decision §2/§8's own canonical-Markdown contract) completely unchanged. This ADR is not blocked on that future work and does not preempt it.

`body_markdown` (the *stored* column) and `enrichmentText` (the *ephemeral* string passed to `enrichPost()`) are related but distinct: `body_markdown` holds the body alone (so a future consumer wanting just the body — an HTML render, an export — isn't stuck with the title prepended into it); `enrichmentText` is `title` + `body_markdown` joined at the point of the `enrichPost()` call, exactly mirroring the existing GNews pattern rather than inventing a new one. This composition may optionally be factored into a second small shared helper alongside `htmlToMarkdown()` for consistency across the three call sites — a reasonable implementation-time nicety, not mandated by this Decision the way `htmlToMarkdown()` itself is.

### 7. Scope: backend only (`social-listening-core`)

No admin UI change is decided here. Nothing in `social-listening-admin` consumes `body_markdown` for display today — that is explicitly future, out-of-scope work for whoever eventually builds a rendering story (see Open Questions).

**Implementation defaults (adjustable — does not require superseding this ADR on its own):**

- **HTML-to-Markdown pipeline:** `sanitize-html@2.17.6` (required pre-conversion sanitization pass, exact-pinned, explicit `allowedTags`/`nonTextTags` — see the concrete configuration above) → `turndown@7.2.4` + `turndown-plugin-gfm@1.0.2` (conversion, GFM table support, both exact-pinned) — see Alternatives Considered for the full comparison, including Microsoft's MarkItDown, weighed and rejected for this specific narrow use.
- **Pre-conversion length guard:** `MAX_BODY_SOURCE_LENGTH = 100,000` characters, truncating the raw source string (a plain `.slice()`) before it reaches `sanitize-html`/`turndown` — see the concrete rationale above.
- **New column names/types:** `body_markdown` (nullable `TEXT`) and `body_markdown_version` (nullable `SMALLINT`, starting at `1`). Real, revisable names — no other candidates were seriously considered, since both directly state what they hold.
- **Migration number:** left to the Story that implements this, per `migrations/0001`'s own "added by a later migration, not speculated here" convention.

### 8. Consumer contract: `body_markdown` is source, not display text — must be rendered, never shown raw, and never rendered without sanitizing

Stated explicitly now, before a second implementer could get it wrong independently, the same category of durable invariant ADR-0052 Decision §8 already established for this project's own `ClassifiableError`-propagation rule: **`body_markdown` holds Markdown *source*, not display-ready text.** Any future consumer — an admin UI post-body render, a Word export, a PDF export, or any other surface — **must convert it to that surface's own native formatting (e.g. Markdown → HTML) before showing it to a human.** Displaying the raw column value directly (literal `**bold**`, `# heading`, `[text](url)` syntax visible to an end user) is a defect in that future consumer, not a valid reading of this column — this ADR decides the field's own meaning now, even though no consumer exists yet (§7) and the rendering mechanism itself is explicitly not designed here (Open Question 2).

**A second, security-relevant half of the same contract, not a separate concern:** `body_markdown` ultimately originates from third-party, untrusted external content — an arbitrary news API, an arbitrary press-release wire, or, in the tenant-owned-feed connector's case, literally any domain a tenant chooses to verify and point at any feed URL they control. Converting it to HTML for display is a real, standard cross-site-scripting surface if done naively (Markdown source can itself carry raw inline HTML, and a naive or misconfigured Markdown→HTML renderer can pass that through unescaped). **Any future Markdown→HTML rendering step must sanitize its output** (e.g. via a well-established HTML sanitizer applied to the rendered result, or a renderer configured to disable raw-HTML passthrough) before insertion into the DOM — this project's own general security discipline (no XSS-vulnerable code) applies to this column exactly as it would to any other untrusted-content render path, and is named here so it is decided policy by the time a future rendering story is built, not an afterthought discovered during that story's own security review.

**This is a second, distinct sanitization boundary from Decision §3's pre-conversion `sanitize-html` pass — not a duplicate of it.** §3's pass sanitizes the *source* HTML before it ever becomes `body_markdown`, at ingestion time. This §8 requirement sanitizes the *rendered* HTML a future consumer produces *from* `body_markdown`, at display time — necessary in addition to §3, not instead of it, because Markdown itself can carry raw inline HTML that an allowlist-sanitized-but-still-Markdown-legal source could still contain (e.g. an allowlisted `<a href>` surviving §3 intact), and because a future consumer might not be the only path that ever populates or edits `body_markdown`. Two independent layers, each guarding a different point in the pipeline.

## Consequences

**Positive**
- Directly closes the root cause of the "enrichment results not that great" complaint that started this investigation: Newswire and tenant-owned-feed posts currently enrich on title text alone (a few words), not the actual press-release/blog-post body — the single biggest quality gap this ADR closes.
- Closes a real, previously-unnamed, silent `raw_payload` under-capture for two connectors (Context, second finding) — a side effect of widening the parsers for `body_markdown`'s sake, but independently valuable against ADR-0018's own "full original platform JSON, never discarded" framing.
- The N×M value proposition (Context) is real, not decorative: every future connector (Reddit, Wikipedia/Story 2.13) and every future consumption format (HTML render, Word export, PDF export) is decoupled from every other connector's/consumer's own shape, once each side only has to convert to/from the one canonical Markdown representation.
- `enrichment`-shaped storage (computed once, persisted) avoids the correctness trap a naive `ConnectorHealth`-style derivation would hit once `raw_payload` ages past its 90-day hot-storage window (ADR-0018) and is replaced by a blob pointer — `body_markdown` keeps working for old posts because it was captured while `raw_payload` was still live, independent of `raw_payload`'s own archival state.
- GNews's enrichment input gains real signal (`content`, even truncated on the free tier) it did not have before, per Menno's own explicit direction.
- The required pre-conversion `sanitize-html` pass (Decision §3) closes a real risk `turndown`'s own security documentation names directly, and — independently — improves conversion robustness against the malformed markup RSS/Atom feeds are known to contain (unclosed tags, mismatched nesting, vendor quirks), a genuine functional upside alongside the security one.
- `<script>`/`<style>` content, tracking pixels, and known link-tracking query parameters (UTM and equivalents) are all excluded from `body_markdown` by the decided sanitization configuration — real, previously-unaddressed data-quality/privacy concerns Menno raised directly, closed as part of the same pipeline rather than deferred.
- The pre-conversion length guard bounds both parser exposure to untrusted content (the tenant-owned-feed connector's own weaker trust boundary in particular) and per-post enrichment cost, without waiting on ADR-0052 Open Question 4's own broader, still-unresolved aggregate cost-ceiling design.
- Tracking-parameter stripping (Decision §3) no longer leaves behind dead, bare-domain links when a redirect service (e.g. Mailchimp click-tracking, `mc_cid`/`mc_eid`) encoded the destination entirely in the parameters being stripped — a real, concrete failure mode Menno identified directly, closed via `exclusiveFilter` rather than left unspecified.
- Real tabular content (a press release's own pricing/comparison/financial table) survives conversion with its row/column structure intact via `turndown-plugin-gfm`, rather than silently collapsing into unstructured, unreconstructable text — a real data-loss gap found and closed directly, not left as a side effect of the broader `allowedTags` decision.
- `body_markdown_version` means a future pipeline change (a library bump, a config change to `allowedTags`/the tracking-parameter denylist/etc.) never leaves the database silently ambiguous about which ruleset produced a given row — and lets a future backfill (Open Question 1) selectively target only outdated rows.
- The Context "second finding" `raw_payload` under-capture gap is now genuinely closed, not just narrowed — `rawXml` retains each item's entire raw inner XML block (already captured mid-parse, discarded before this addition), matching the same "never discarded" completeness GNews's own full-object `rawPayload` spread already had.

**Negative**
- **Two new dependencies are added to `social-listening-core`** (`turndown` and `sanitize-html` — neither previously existed) — a real, if small, new supply-chain surface for a solo-developer project that has otherwise kept its dependency list deliberately minimal (`package.json`'s current seven runtime dependencies, checked directly this session).
- **`body_markdown` for already-ingested historical rows is not backfilled by this ADR.** Existing Newswire/tenant-owned-feed/GNews posts will have `body_markdown = NULL` until re-ingested or a separate backfill job is run — named as an Open Question, not designed here.
- **GNews's `content` field is confirmed truncated on the free tier** (`docs.gnews.io`, fetched this session) — enrichment quality improves over title+description-only, but is not "full article text" for a free-tier tenant; a false expectation of completeness should not be set.
- **What GlobeNewswire's/PR Newswire's `<description>` typically contains (excerpt vs. full text) could not be confirmed this session** — the parser widening (§4) captures whatever is there, but its practical value for enrichment quality is not independently verified against a real sample, only asserted as plausible.
- **`htmlToMarkdown()` applied to already-plain text (GNews) will backslash-escape Markdown-significant characters** that occur naturally in the source (`*`, `_`, `[`, `]`, etc.) — correct, round-trip-safe Markdown behavior, but means `body_markdown` is not always byte-identical to the pre-conversion text even when no HTML was present, a subtlety worth knowing before assuming "no-op for plain text" means "untouched."
- **No admin UI consumer exists for `body_markdown` yet** — this ADR ships storage and enrichment-input improvements with no user-visible display change; the value is enrichment quality only until a future rendering story is built.
- **Images are dropped entirely, not filtered for legitimacy** — a real press release's own genuine photo or an org's logo is excluded exactly the same way a tracking pixel is, since this ADR does not attempt to distinguish the two. Accepted as the simpler, safer default for this ADR's actual (text-oriented) scope, not a nuanced content-preservation decision — named honestly rather than implied to be more sophisticated than it is.
- **The tracking-parameter denylist (Decision §3) is a fixed, named list, not exhaustive** — a tracking parameter this ADR doesn't name (a platform-specific or newly-invented one) will pass through unstripped until the list is revised; this is an implementation default, deliberately left revisable, not a claim of completeness.
- **An unusually long genuine post (rare, but real) is silently truncated at 100,000 characters, with no indicator in `body_markdown` itself by default** — a caller cannot distinguish "this post's real body was short" from "this post's body was truncated" without a future implementation adding a marker, which this Decision names as optional, not required.
- **`turndown-plugin-gfm` is a third dependency with real, if lower-recency, maintenance activity — last npm release 2018, last GitHub commit 2023.** Named honestly rather than described as actively maintained; accepted because the alternative (silent table-structure data loss) was judged worse, not because the recency gap is dismissed as unimportant.

## Alternatives Considered

| Alternative | Disposition |
|---|---|
| **Store the Markdown body, `enrichment`-shaped (computed once at ingestion, persisted)** | **Chosen.** Argued explicitly in Context/Decision §2: mirrors the already-established `enrichment` precedent, and is independently required (not merely stylistically preferred) by ADR-0018's own `raw_payload` 90-day archival tiering, which would silently break a `ConnectorHealth`-style read-time derivation for any post older than the hot-storage window. |

## Open Questions

1. **Backfilling `body_markdown` for already-ingested historical rows — explicitly out of scope for this ADR's own Decision (§1–§8 authorize new ingestion only), does not need its own future ADR, and is a real, standing quality gap for historical data if never done, not a cosmetic omission.**
   - **Out of scope, precisely:** no migration, script, or job that populates `body_markdown` for an existing row is decided or authorized here. A future implementer runs one only as a separate, later Story.
   - **No future ADR is required to design it — verified directly, not assumed.** The read-back mechanism a backfill would need already exists and is already contract-tested: `downloadArchiveBlob()` (`src/archival/blobArchiveClient.ts`) rehydrates a `raw_payload` whose JSONB content was already replaced by a blob pointer (ADR-0018's 90-day tiering), and `resolveSocialPostsForExport()` (`src/tenants/tenantDeletion.ts`) is a real, already-shipped caller of it (Story 3.8's tenant-export flow). A backfill job needs no new architectural mechanism — it would read each row via the same tiering-aware path Story 3.8 already established, run it through this ADR's own already-decided `sanitize-html` → `turndown` pipeline (§3), and `UPDATE` the row. This is squarely Story-level "apply an already-decided policy to existing data," the same no-new-ADR category Story 6.16/6.17 already used in this project.
   - **Not required for this ADR's own stated goal, but its absence is a real, standing, non-self-healing gap, stated plainly rather than softened:** every post ingested *after* this ADR ships gets the enrichment-quality improvement immediately, without backfill. Every post ingested *before* it ships keeps `body_markdown = NULL` and its original, degraded enrichment (title-only for Newswire/tenant-owned-feed) **forever, unless a backfill is run** — it does not improve on its own, and re-running `enrichPost()` alone (without a body-content backfill first) would not close the gap, since the input text is what's missing, not just the analysis. Whether that permanent inconsistency is acceptable is a product decision for whoever prioritizes the future backfill Story, not resolved here.
2. **Any future Markdown-to-HTML/Word/PDF renderer.** Explicitly out of scope — a future consumer's own job, once `body_markdown` exists to convert *from*. No rendering library, format, or story is named or implied here.
3. **The exact HTML→Markdown library choice** — `turndown` is named as a real, revisable implementation default (Decision §7, Alternatives Considered), not a mandate; `node-html-markdown` is named as a credible, considered alternative. Whoever implements this Decision may revisit at Story time without needing to supersede this ADR, per this project's own "implementation default, not durable decision" convention.
4. **What GlobeNewswire's and PR Newswire's real `<description>` content typically contains** — could not be confirmed this session (no fixture data exists in `contracts/`, and no live fetch was performed). Should be verified against a real feed sample before or during implementation, since it affects whether the enrichment-quality improvement this ADR targets for Newswire actually materializes as expected.
5. **Atom `<content>`'s `type` attribute (`text`/`html`/`xhtml`) is not addressed.** The RSS 2.0 spec's `<description>`/`<content:encoded>` are effectively always HTML-ish text; Atom's `<content>` can formally carry plain text, escaped HTML, or inline XHTML depending on its `type` attribute (RFC 4287) — which shape a given tenant's feed actually uses is not verified here, and `htmlToMarkdown()`'s pass-through behavior for plain-text `type="text"` content vs. its HTML-conversion behavior for `type="html"`/`type="xhtml"` content is not distinguished by this Decision. Left to implementation time to verify against real Atom feeds, if a tenant configures one.
6. **TXT-record-style precedence tie-breaks when a field exists but is whitespace-only or malformed CDATA.** §4/§5's precedence rules say "present and non-empty" — the exact definition of "non-empty" (trimmed-empty-string counts as absent?) is left as an implementation-time detail, not a durable decision.
7. **Whether `body_markdown` should ever preserve images.** Not decided here — the current default (`sanitize-html`'s own unmodified `allowedTags`) excludes all `<img>` tags, tracking pixels and legitimate content images alike. A future story wanting to preserve real content images would need to solve distinguishing them from tracking pixels (dimension heuristics, domain reputation, or some other signal) — a genuinely harder problem this ADR deliberately does not attempt, not a gap it overlooked.
8. **The tracking-query-parameter denylist's exact membership.** Decision §3 names nine parameters (`utm_source`/`utm_medium`/`utm_campaign`/`utm_term`/`utm_content`/`fbclid`/`gclid`/`mc_cid`/`mc_eid`) as a real, revisable implementation default — extending it (or building a more systematic detection approach) does not require superseding this ADR.
9. **Whether raw Markdown syntax in `enrichmentText` measurably degrades enrichment accuracy — explicitly untested, a real trigger condition for a future ADR, not designed here.** Decision §6 accepts, as an unverified working assumption, that passing `**bold**`/`# heading`/`[text](url)` syntax directly to Azure AI Language/Azure OpenAI is low-noise. If real enrichment output (once this ADR ships and real posts flow through it) shows meaningful sentiment/entity/key-phrase degradation attributable to Markdown syntax noise, a separate future ADR — not an amendment to this one — would design a Markdown-to-plain-text (or otherwise-cleaned) conversion step for `enrichmentText`'s own composition only, leaving `body_markdown` itself unchanged. Named here specifically so this is a recognized, watched-for trigger, not a silent assumption nobody planned to revisit.
10. **Whether truncation should leave any visible marker in `body_markdown`** (e.g. an appended "…[truncated]" note) — not mandated by Decision §3, left as an implementation-time nicety. Also open: whether `MAX_BODY_SOURCE_LENGTH`'s 100,000-character default is right long-term, or should be revisited once real ingested-content length data exists (revisable without superseding this ADR, per the same convention as the tracking-parameter list above). **This is this ADR's own length-guard truncation only — distinct from GNews's own free-tier `content` truncation marker (Open Question 11 below), which is a source-side artifact this ADR removes rather than marks.**
11. **The exact literal format of GNews's free-tier truncation marker on `content` is not confirmed against a real response.** Decision §5's regex trim (`/\s*\[\+\d+ chars\]$/` as the current best-understanding pattern) is based on commonly-reported GNews behavior, not GNews's own documentation (checked directly this session — their docs confirm truncation occurs but not its literal string format) and not a live API response (no GNews credential was available this session to observe one directly). Must be verified against a real truncated response — a free-tier tenant with a sufficiently long article is enough to produce one — before or during implementation; the regex is revisable without superseding this ADR if the real format differs.
