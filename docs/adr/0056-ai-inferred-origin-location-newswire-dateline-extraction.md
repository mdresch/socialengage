# ADR-0056: AI-provider-inferred origin location from a Newswire post's own dateline text — feasibility, architecture, and v1-scope recommendation

**Status:** Accepted (2026-08-17)

**Source:** Not specified in the design spec or any prior ADR. Requested directly by Menno, 2026-08-17, the same day as ADR-0054/ADR-0055, as a follow-up to ADR-0055's Amendment Log — after approving ADR-0055's Language half ("yes please extend the language field"), Menno raised a genuinely different question ADR-0055's own Location research never considered: could the enrichment AI *provider itself* (Azure OpenAI's generative completion model, `azureOpenAiConnector.ts` — explicitly **not** Azure AI Language's structured NER/entity-recognition capability) be asked to infer a Newswire post's likely origin location from its own body text — a wire-service "dateline" — as prep work toward eventually revisiting the Location tab. Scoped narrowly by Menno at the outset: "just one source, the newswire, mostly starts with the location where it's written."

**Acceptance note:** Accepted by Menno 2026-08-17, verbatim: *"ADR 0056 is approved as well."* Accepted as drafted, no revisions — Decision §5's own recommendation ("name it, don't build it now") stands as accepted policy, not overridden by acceptance. **No story is drafted at this acceptance** — matching this ADR's own Decision §5 and ADR-0054's identical precedent for its Location tab: a "name it, don't build it" verdict has nothing yet for a contract test to target. Revisit only per Decision §5's own named trigger (a real, prioritized Location-tab decision, or a real tenant request).

## Context

### What a wire-service dateline is, and why it might be extractable

Both PR Newswire and GlobeNewswire — the two wires this project's Newswire connector polls (`newswireConnector.ts`, ADR-0024) — follow a decades-old print-journalism convention: a press release's body text opens with a "dateline" naming the city (and state/country) it was issued from, e.g. `"GAYLORD, Mich., Aug. 17, 2026 /PRNewswire/ --"`. If present in a post's own ingested text, this is a real, textually-grounded signal an LLM-class model could plausibly extract — categorically different from fabricating a location, since it would be reading something the source itself actually wrote.

### Independently re-verified this session — the premise holds only for part of Newswire's real feed roster, and the dateline is not always at position zero

The orchestrating session had already verified this live before requesting this ADR (real `curl` output against both of Newswire's default feed URLs, `DEFAULT_NEWSWIRE_FEED_URLS` in `newswireConnector.ts`). This role's own standing discipline is to re-verify, not take a prior summary on trust — re-verification here was partial, honestly reported as such:

- **PR Newswire — re-verified independently via `WebFetch` against `https://www.prnewswire.com/rss/news-releases-list.rss`, live, this session.** Two real, current items were fetched. Both carry a real dateline, but **the dateline is not always the literal first line of body content** — a real, previously-unstated nuance this session's own re-verification adds: one item opened with a lead sentence ("The article explains how ductless mini-splits...") before the dateline appeared mid-paragraph ("HERMISTON, Ore., Aug. 17, 2026 Is a ductless mini-split..." — no `/PRNewswire/` marker on this one either); the other opened with a lead line before `"GAYLORD, Mich., Aug. 17, 2026 /PRNewswire/ -- What does it actually cost..."`. **Implication for Decision §1 below:** any structural pre-check or extraction prompt must search the text for a dateline-shaped pattern, not assume it anchors at position zero, and must tolerate the `/PRNewswire/` marker being absent even on a genuine dateline.
- **GlobeNewswire — re-verification attempted three times this session via `WebFetch` against the same energy-category feed URL the orchestrating session's own live `curl` already checked; all three attempts timed out.** This ADR's GlobeNewswire finding therefore rests on the orchestrating session's own already-reported live evidence (short, headline-only `<description>` text with no dateline structure, and `grep -c "content:encoded"` returning `0` on the full feed body), not this session's own independent reproduction — named honestly rather than presented as independently re-confirmed. It is corroborated structurally, though, by this codebase's own `rssFeedParser.ts`, confirmed directly this session: `ParsedRssItem` only ever captures `description` and `content:encoded` as possible body sources (`extractTag(block, 'description')` / `extractTag(block, 'content:encoded')`), and `ingestNewswireItems()`'s own body-source precedence (`item.contentEncoded ?? item.description ?? null`) means a GlobeNewswire item with a `content:encoded`-less, headline-only `description` — as the orchestrating session found live — would have essentially no body text at all for a dateline (or anything else) to appear in.
- **No existing field distinguishes which wire a given `ParsedRssItem` came from.** Confirmed directly: `ParsedRssItem` (`rssFeedParser.ts`) carries `guid`, `issuer` (from `<dc:contributor>`), `description`, `contentEncoded`, and the item's own tag fields — no `feedUrl`, `wireId`, or equivalent. `pollNewswireFeeds()` does process one feed URL's items at a time (looping over `DEFAULT_NEWSWIRE_FEED_URLS` and calling `ingestNewswireItems()` once per feed before moving to the next), so the wire *could* be known at ingestion time if threaded through — but nothing does that today. Whether `issuer`/`dc:contributor` content itself reliably differs by wire in a way that could serve as a cheaper, non-AI signal was not verified this session (Open Questions).

**Conclusion, reaffirmed rather than merely repeated:** the premise is real for PR Newswire-sourced items, structurally absent for GlobeNewswire-sourced items (at least via this connector's current RSS-only capture — not verified across every possible GlobeNewswire feed category), and — new finding this session — even where present, a dateline cannot be assumed to sit at a fixed position in the text.

### Where this would live technically — `enrichPost()` has zero connector-awareness today, confirmed directly

`enrichPost(tenantId: string, text: string): Promise<AnalyzeResult | undefined>` (`social-listening-core/src/connectors/azureAiLanguage/enrichPost.ts`) is called identically, with no connector/provider-source argument of any kind, from all four real call sites: `pollGNewsSearch.ts`, `pollNewswireFeeds.ts`'s `ingestNewswireItems()`, `pollTenantOwnedFeed.ts`, and Story 6.16's manual re-enrichment route (`postsRouter.ts`). It internally iterates a fixed `PROVIDERS` list (`azureAiLanguageConnector`, `azureOpenAiConnector`, in that priority order) and returns whichever one succeeds first for the tenant — the caller never learns, and never influences, which provider actually ran, beyond inspecting the returned `AnalyzeResult.modelUsed` string after the fact. **There is no existing concept of "connector-aware enrichment" anywhere in this pipeline.** Any design proposing to gate a step by `providerId === 'newswire'` is proposing a genuinely new pattern, not extending an existing one — worth stating plainly, not minimized.

There is, however, an existing and directly relevant precedent one level up: each connector's own ingest loop (`ingestNewswireItems()`, `pollGNewsSearch.ts`'s equivalent) already composes its own `enrichmentText` inline (title + `bodyMarkdown`, per ADR-0053) before calling the shared `enrichPost()` — i.e., connector-specific composition already happens at the ingest-loop level, just not inside `enrichPost()` itself. A new, connector-specific enrichment step is architecturally consistent with this existing pattern if it is added at the same level (inside `ingestNewswireItems()`), not inside the shared, provider-agnostic `enrichPost()`/`ENRICHMENT_SCHEMA`.

### `AnalyzeResult`/`ENRICHMENT_SCHEMA` — confirmed shape, and why bolting this on there is the wrong fit

`ENRICHMENT_SCHEMA` (`azureOpenAiConnector.ts`) is a single JSON Schema requested on **every** `analyze()` call, `required` covering all five fields (`sentiment`, `sentimentScores`, `entities`, `keyPhrases`, `detectedLanguage`) plus `overallConfidence` — confirmed directly, this is the "single-call efficiency" design ADR-0038 Decision §2 named as the whole reason a second, LLM-based provider was wanted, and the `entities[].category` enum is explicitly constrained "so this provider invent[s] its own vocabulary... which would undermine genuine cross-provider comparability, the entire point of Story 2.9's swappability proof" (the schema's own code comment). Adding an origin-location field to this schema would mean requesting it on **every** Azure OpenAI call regardless of connector — GNews and tenant-owned-feed posts included, where it would almost always resolve to nothing — the exact "wasted cost/tokens for non-Newswire posts" outcome this ADR was explicitly asked to weigh, not default into.

There is a real, already-shipped precedent for a provider-asymmetric field on the *shared* `AnalyzeResult` interface: `overallConfidence` is documented as "Never populated by `azureAiLanguageConnector.ts`" — an LLM-only field on an otherwise-shared contract. That precedent shows the codebase already tolerates optional, provider-specific fields on `AnalyzeResult`. But `overallConfidence` is a meta-property of *every* analysis (how confident was the model in this answer), always relevant, always requested. An origin-location inference is different in kind: it is relevant to at most one connector's content convention, and should be requested rarely, not on every call — a fundamentally different invocation shape, not a smaller version of the same one.

### Author-rights standing check (per this role's charter)

This ADR touches ingested Newswire content whose `Author` is the issuing wire service/company — an organization, not an individual, under ADR-0004's organization-as-Author clause (ADR-0024). Checked explicitly: inferring an origin location from a post's own already-ingested body text introduces no new attribution mechanism (the `Author` upsert and `SocialPost.url`/provenance fields are unchanged), reassigns no ownership, and is not a new redistribution path beyond what enrichment already does today for every post (deriving `sentiment`/`entities`/`keyPhrases` from the same already-legitimately-ingested text, unchanged by this ADR). **One real, inherited-not-new concern:** ADR-0054's own Open Question 3 (whether a future per-widget CSV/JSON export of aggregate dashboard data needs its own consent/disclosure treatment, separate from ADR-0039's tenant-export mechanism) remains undecided — if an inferred-location field is ever surfaced on such a widget, it inherits that same open question; this ADR does not resolve it and does not need to, since Decision §5 below declines to build the consuming feature yet.

## Decision

### 1. Architecture: a new, optional `AIProviderConnector` method, invoked conditionally at the Newswire ingest-loop level — not a new field on the shared, every-call structured-output schema

**Decided, if this is ever built:** do **not** add an origin-location field to `ENRICHMENT_SCHEMA`/`AnalyzeResult`'s always-on, every-call contract. Instead: add a new, optional `AIProviderConnector` interface member —

```
inferOriginLocation?(text: string, credential?: string): Promise<{ text: string; confidence: number } | null>
```

— implemented only by `azureOpenAiConnector` (Azure AI Language's structured NER capability cannot perform this kind of free-text generative inference and would correctly leave the method undefined, the same asymmetric-capability shape `overallConfidence` already establishes for `AnalyzeResult`). It is invoked **only** from `ingestNewswireItems()` (`pollNewswireFeeds.ts`) — never from `enrichPost()` itself, never from `pollGNewsSearch.ts` or `pollTenantOwnedFeed.ts` — matching the existing precedent of connector-specific composition happening at the ingest-loop level (Context, above), and matching Menno's own explicit scoping to Newswire only.

**Two gates, not one, before a real API call is ever spent:**
1. A cheap, local, non-AI structural pre-check on the composed `enrichmentText` for a dateline-shaped pattern (a `CITY[, STATE/COUNTRY], Month Day, Year` structure, optionally followed by a wire marker like `/PRNewswire/`) — searched within the text, **not** anchored to position zero, per this session's own re-verification finding above. This is a real, load-bearing cost control: it is what lets this design skip GlobeNewswire-shaped items (and any Newswire item with no dateline at all) without a hardcoded per-wire allowlist. The exact pattern is left to the sourced story's own implementation-time judgment, not fixed here, per this project's own "durable decision vs. adjustable implementation default" convention (ADR-0053's identical treatment of its own unconfirmed literal-format details).
2. `enrichment?.modelUsed` (already returned by `enrichPost()`) is checked to confirm the tenant's active/credentialed provider for this call was actually Azure OpenAI, not Azure AI Language — reusing the same signal already available, no new field required to detect this.

Only if both gates pass does `ingestNewswireItems()` re-resolve the tenant's Azure OpenAI credential (the same `isConnectorActive`/`getLatestCredentialId`/`readCredential` calls `tryProvider()` in `enrichPost.ts` already makes, scoped to `providerId: 'azure-openai'`) and call the new method. This is a genuine **second** real HTTP round trip to Azure OpenAI for any post that passes both gates — not folded into the existing single structured-output call — and must be counted against the tenant's own `RequestGate` budget for that provider (`getRateLimitConfig()`'s existing 500-requests/30-day placeholder default), the same `gatedAcquire()` discipline every other AI call in this pipeline already follows.

**Why not a broader, connector-agnostic design (e.g., attempt this for every connector, gated only by the structural pre-check):** rejected. A dateline is a wire-service journalistic convention, not a property of general news prose (GNews) or an arbitrary tenant's own blog content (tenant-owned-feed) — extending the call site beyond Newswire would be scope neither Menno requested nor this session verified any evidence for, and would silently spend real AI calls checking a pattern that has no reason to appear outside wire-service content.

### 2. Stored field: confirmed no migration and no `SocialPostSummary` widening required — a materially different situation from ADR-0054's `post_geo_location` blocker

**Verified directly, not assumed, against `social-listening-core/src/posts/socialPostStore.ts`:** `social_posts.enrichment` is stored and read as an unfiltered `JSONB`/`Record<string, unknown>` blob — the column's own doc comment already states "additive keys in one JSONB blob, not separate columns." Critically, and unlike `post_geo_location`: **`SocialPostSummary` (the shape `GET /v1/posts` actually returns, line 208–213) already includes `enrichment: unknown` in full, unfiltered.** ADR-0054 Decision §4's disqualifying finding for `post_geo_location` — real column, but invisible to `SocialPostSummary`, only reachable via the single-post `SocialPostFull` fetch — **does not apply here.** A new `inferredOriginLocation` key merged into the same `enrichment` object at insert time (`insertSocialPost()`'s existing `enrichment` parameter, no signature change) would already be wire-visible via the exact same paginated `GET /v1/posts` fetch loop Epic 8's client-side aggregation already uses, with **zero migration, zero new column, zero `SocialPostSummary` schema change.** This is the single cleanest finding in this ADR's whole investigation, and it should not be understated: the hard blocker ADR-0054 named for Location does not reproduce here.

### 3. Honesty/labeling: a distinctly-named, never-conflated field, carrying its own confidence signal

**Decided, if built:** the inferred result is stored as `enrichment.inferredOriginLocation: { text: string; confidence: number } | null` — never as `post_geo_location`, never presented as equivalent to a real, structured geo-coordinate. The `confidence` component is required (not optional), following `overallConfidence`'s own already-established discipline ("this score is used to decide whether to trust or discard your answer... do not default to a high number") — a real, self-reported LLM confidence, not a calibrated probability, and should be documented as such wherever it's read, the same distinction `AnalyzeResult.overallConfidence`'s own doc comment already draws.

**UI/copy obligation this creates, named as a real follow-up requirement for whoever eventually builds the consuming feature (not designed or implemented here — outside this role's scope):** any future rendering of this field must always carry an explicit "AI-inferred" qualifier (e.g., "Likely origin (AI-inferred): Providence, RI") and must never be plotted with the same visual affordance (e.g., an undifferentiated map pin) that would imply the same evidentiary weight as a real, structured `post_geo_location` value, if that ever exists. This is not the same failure mode ADR-0054's Alternatives Considered table rejected for fabricated placeholder data (this data would be real, textually grounded) — but a real signal presented with false precision is still a distinct, real risk this project's own established anti-fabrication discipline (`Business-Case-v6.0.md` §8/§4, this role's own charter) requires naming explicitly, not smoothing over.

### 4. v1 scope: a confidence-and-structural-pre-check approach, not a hardcoded PRNewswire-only gate

**Decided, if built:** do not hardcode a `feedUrl === PRNewswire`-style allowlist. Reasoning, argued explicitly: (a) no field in this codebase currently distinguishes which wire an item came from (Context) — building one only to hardcode against it would be more invasive than the structural pre-check already described in Decision §1; (b) a structural, content-based gate degrades honestly and automatically for GlobeNewswire-sourced items (no dateline pattern found → the pre-check fails → no API call spent, `inferredOriginLocation` stays `null`) without any wire-specific code branch; (c) it is more robust to a future roster change (a new PRNewswire regional feed, or a GlobeNewswire category that does carry datelines, which this session's investigation did not rule out for every category) without a code edit, in the same spirit as ADR-0048's "no core pipeline change for new connector registration" discipline, generalized here to "no per-wire hardcoding." The call site itself (Decision §1) still stays gated to Newswire only — that part is a deliberate, connector-level scope boundary, not left to a content heuristic.

### 5. Whether this is worth building now — recommended: name it, do not build it yet

**Recommendation: do not build this now.** Reasoned explicitly, not defaulted to "yes" because it was asked about:

- **No consuming feature exists or is committed.** ADR-0054 Decision §4 and ADR-0055 Decision §2 both already declined to build a Location tab — for lack of demonstrated tenant need — even for the *structurally simpler* candidates each investigated (a full `post_geo_location` connector build-out; a free, already-captured GNews `source.country` widget). This ADR's own finding is that the AI-inferred path is real and technically closer to shippable than either of those (Decision §2's finding), but "closer to shippable" is not the same as "a consumer exists" — and Menno's own framing of this request ("prep work toward eventually revisiting") already names it as precursor work, not the trigger itself.
- **Real, non-zero added cost.** A genuine second Azure OpenAI HTTP call for every post that passes the structural pre-check (Decision §1) — tenant-borne under ADR-0028's tenant-owned-credential model, not a SocialEngage cost line, but still a real per-tenant cost this project has repeatedly treated as worth weighing explicitly (ADR-0038's own "small/cheap tier, not a flagship model" reasoning; `Project Management Plans/Cost-Management-Plan.md`'s own tenant-cost framing for AI enrichment).
- **This project's own repeatedly-applied "don't build ahead of a demonstrated need" discipline** (ADR-0020's precedent, explicitly reused by ADR-0054 and ADR-0055 for this exact category of question — a data capability with no committed consuming UI) applies here with no less force than it did for either of those two ADRs' own declined options.
- **A real, if smaller, version of the same risk ADR-0054 already flagged for `mockData.ts`/`types.ts`** — building a data capability that then sits unused in `enrichment` with no reader is its own standing-confusion risk for a future reader, however honestly labeled.

**Named, concrete trigger for revisiting** (not designed further here): either (a) the Location tab itself becomes a real, prioritized decision (its own future ADR/decision, not this one), at which point this ADR's Decision §1–§4 shape is ready to build against directly; or (b) a real tenant with meaningful PRNewswire-sourced post volume asks for this specifically. Neither condition exists today.

## Consequences

**Positive**
- Fully specifies a real, technically sound, buildable design (Decision §1–§4) so that if/when the trigger in Decision §5 occurs, no re-investigation is needed — the architecture placement, storage shape, honesty/labeling requirement, and scoping mechanism are all already decided.
- Confirms directly (Decision §2) that this data-storage path carries none of ADR-0054's `post_geo_location`/`SocialPostSummary` structural blocker — a genuinely easier path than the one ADR-0054/ADR-0055 already declined, named honestly rather than conflated with it.
- Keeps this project's "don't build ahead of a demonstrated need" discipline applied consistently, matching ADR-0054/ADR-0055's own posture for the exact same category of question, rather than treating "Menno asked about it" as itself sufficient grounds to build.
- Independently re-verifies (not merely re-cites) the PR Newswire premise, and surfaces a real refinement (dateline position is not fixed at line zero) the original live-`curl` check did not have — a genuine, if small, improvement on the evidence this ADR would otherwise have just repeated.

**Negative**
- **Nothing ships from this ADR.** If Menno judges the value of having this ready outweighs the "don't build ahead of demonstrated need" discipline, that is a real, visible tension this ADR does not pre-resolve in either direction — named, not smoothed over, per this role's charter.
- **GlobeNewswire-sourced posts get no inferred location, permanently, under this design** — not a temporary v1 gap but a structural consequence of the wire's own real content shape (Context), unless a future GlobeNewswire feed category is found to behave differently (not ruled out, Open Questions).
- **Coverage is further narrowed to tenants with Azure OpenAI specifically active and credentialed** — a tenant using only Azure AI Language (which cannot perform this kind of inference at all) gets no inferred location regardless of connector or content, a real, named asymmetry between the two otherwise-swappable providers.
- **This session's own GlobeNewswire re-verification could not be completed independently** (three `WebFetch` timeouts) — this ADR's GlobeNewswire finding rests on the orchestrating session's prior live evidence, honestly flagged as such rather than presented as freshly reproduced.

## Alternatives Considered

| Alternative | Disposition |
|---|---|
| **A new, optional `AIProviderConnector.inferOriginLocation?()` method, invoked conditionally only from `ingestNewswireItems()`, gated by a structural dateline pre-check plus `modelUsed` provider confirmation** | **Recommended design, if built.** Keeps the shared, every-call `ENRICHMENT_SCHEMA`/`AnalyzeResult` contract untouched; reuses existing credential/activation/rate-limit plumbing; degrades honestly for GlobeNewswire without a hardcoded wire allowlist. |
| **Add the field directly to `ENRICHMENT_SCHEMA`, requested on every Azure OpenAI call** | Rejected. Requests it on 100% of GNews/tenant-owned-feed posts and a meaningful share of GlobeNewswire-sourced Newswire posts, where it would almost always resolve to nothing — the exact wasted-cost outcome this ADR was asked to weigh explicitly, not default into. |
| **A hardcoded `feedUrl`/wire-name allowlist (PRNewswire-only) as the v1 gate** | Rejected in favor of the structural pre-check (Decision §4) — no existing field cleanly distinguishes the two wires per item today, and a content-based gate is more robust to a future roster change without a code edit. |
| **Build it now, alongside this ADR's acceptance, per Menno's own "prep work" framing** | Rejected for now (Decision §5) — no consuming Location feature exists or is committed; reaffirms ADR-0020's/ADR-0054's/ADR-0055's own identical discipline for this same category of question. Named as ready-to-build, not built. |
| **Extend the call site beyond Newswire, gated purely by the structural pre-check** | Rejected — a dateline is a wire-service-specific convention with no verified reason to appear in GNews or tenant-owned-feed content; broadening the call site is unrequested, unverified scope. |

## Open Questions

1. **Whether `ParsedRssItem.issuer` (`<dc:contributor>`) reliably differs between GlobeNewswire and PR Newswire items** — not verified this session. If it does, it could serve as a cheaper, non-AI, per-item wire signal alongside (not instead of) the structural pre-check. Left for whoever eventually implements this.
2. **Whether any GlobeNewswire feed category other than the one energy-category feed this connector currently polls carries dateline-shaped body content** — named by the orchestrating session's own original investigation as worth checking, still not checked, either by that session or this one (this session's own re-verification attempt timed out three times).
3. **The exact dateline structural-pattern definition (Decision §1)** — left to implementation-time judgment, not fixed here, per this project's own durable-decision-vs-adjustable-default convention.
4. **Whether this design should eventually generalize beyond Newswire, if a future connector is added whose content also carries a structured, extractable origin signal** — not evaluated here; Decision §1's Newswire-only call-site gate is deliberately narrow to today's real, verified roster.
5. **Relationship to a future Location tab's own eventual data-source decision** — if and when that ADR/decision is made, it should decide explicitly whether this AI-inferred signal, the GNews-only `source.country` signal ADR-0055 already named and declined, both, or neither, feed it — not pre-decided here.
