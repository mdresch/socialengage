# ADR-0052: Live ingestion-polling scheduler — connector registry bootstrap, generic per-connector `poll()` invocation, in-process interval loop with derived (not stored) cadence

**Status:** Accepted (2026-08-13)
**Source:** Not specified in the design spec or any prior ADR. Raised by Menno directly this session ("could you write up the required either ADR r use te existing ADR as approvval for storeis to schedule incomming blog posts?"), after a real, live investigation this same session found that a self-service-verified `tenant-owned-feed` connector (Story 6.12/ADR-0050) and an active, credentialed GNews connector both produced zero ingested posts in the running application, while 66 incidental Newswire rows (all ingested during earlier contract-test runs, not live polling) were the only `SocialPost` rows the tenant's own export (Story 6.13) actually showed. Root-caused directly, not assumed: `social-listening-core` has no code path anywhere that invokes `pollGNewsSearch()`, `pollNewswireFeeds()`, or `pollTenantOwnedFeed()` outside their own Jest contract tests. This ADR originates the scheduling design; it does not document a decision any prior ADR made — every ADR that touches the topic (ADR-0043 §3, ADR-0051 Open Question 1) explicitly names the gap and explicitly declines to design it.

**Acceptance note (2026-08-13):** Accepted by Menno (Sponsor), verbatim: *"Excellent ADR very strong seems to get better each time we create a new ADR. The ADR 0052 is hereby Approved!!"* Accepted as revised — four in-place revisions were made during live review before acceptance (Decision §5's eligibility comparison stated explicitly, with a matching `pollCadenceMs?: number` member added to Decision §4's `SocialConnector` extension; Decision §8 gained the explicit inverse of the scheduler's catch obligation — a `poll()` implementation must let `ClassifiableError` propagate uncaught, never swallow it locally; Decision §5 gained a deterministic ±5% per-`(tenantId, platformId)` `jitterFraction`, closing a real thundering-herd risk on server restart / across tenants with similar poll history, with the stale "no jitter is designed here" Negative Consequences bullet corrected in place to describe only the smaller residual risk left open; Decision §6 now names, without designing, the expected future Tier-3 shape — `poll(tenantId, userId)` and a `RequestGate` key of `(tenantId, userId, providerId)`, verified directly against `requestGate.ts` before being written) — see the Amendment Log below for the full record of each. **Story 1.13** (`docs/user-stories/epic-1-repository-and-api-foundation.md`) is added at this acceptance, per this series' own "no story until acceptance" precedent (ADR-0024/0026).

## Context

### The gap, verified independently this session

- `social-listening-core/src/http/server.ts` — read directly, full file (26 lines). `main()` waits for Postgres readiness and starts the Express app; there is no `setInterval`, no cron invocation, no background loop of any kind.
- Grepped `setInterval|cron|scheduler|setTimeout` (case-insensitive) across the entire `social-listening-core/src` tree: the six matches (`enrichPost.ts`, `connectorHealth.ts`, `postgresReadiness.ts`, `breakGlassCredentialReset.ts`, `runIngestionAttempt.ts`, `requestGate.ts`) are all retry/backoff/readiness-polling `setTimeout` calls internal to a single request's own execution, not a scheduler that iterates tenants and triggers ingestion.
- Grepped every call site of `pollGNewsSearch`, `pollNewswireFeeds`, `pollTenantOwnedFeed` repo-wide: each is called only from its own contract test file, plus one doc-comment reference in `tenantOwnedFeedRouter.ts` explaining *why* the router itself never calls it — not an actual invocation.
- This matches, and independently confirms, ADR-0043 §3's own verbatim finding: *"no code in `social-listening-core` currently iterates 'active tenants' and calls a connector's poll function in a loop... A future scheduler... is not yet built and is out of this ADR's own scope to design."* ADR-0051 Open Question 1 restates the same gap: *"No scheduler/cron and no quota-consumption tracking exist yet anywhere in this project to design a trigger against."* `docs/implementation-plan.md`'s 2026-08-12 dated note (Story 1.11/1.12/2.12/6.15 batch) restates it a third time, verbatim: *"auto-deactivation has no scheduler or quota-tracking mechanism anywhere in this project yet to build against."* Three separate, already-Accepted sources name this exact gap and none design it — this ADR is the first to.

### Two further gaps found independently this session, not previously named anywhere

These were not part of the original investigation reported to this persona; they surfaced while designing this ADR's own mechanism, and they are load-bearing preconditions for any scheduler design, so this ADR must decide them too rather than assume them solved elsewhere.

**1. The shared connector registry (`src/connectors/registry.ts`) is never populated outside test setup.** `registerSocialConnector()` and `registerAIProviderConnector()` are called only from Jest contract test files (verified by a repo-wide grep of every call site — ten matches, all under `contracts/` or `.claude/skills/*/SKILL.md` documentation, zero under `src/`). `src/http/app.ts` and `src/http/server.ts` import no connector module, directly or indirectly. This means `getSocialConnector(providerId)` and `listSocialConnectors()` return `undefined`/`[]` in the actual running server today — a real, previously-unnamed gap with an already-live side effect: `connectorsRouter.ts`'s `authModeForbidsUserScope()` (lines 150–161) resolves `getSocialConnector(platformId)?.authMode` to `undefined` for every real request, so its `authMode === 'none'` check silently never matches and the Tier-3-forbidden-for-`authMode: 'none'` rule ADR-0051 Decision §1 states is not actually enforced in the live server right now. Any scheduler design that enumerates connectors via this registry inherits this gap and would silently do nothing unless it is also closed.

**2. `SocialConnector` (`src/connectors/types.ts`) has no generic, registry-visible poll-invocation method.** Each real connector's actual poll entry point — `pollGNewsSearch(tenantId, query?)`, `pollNewswireFeeds(tenantId)`, `pollTenantOwnedFeed(tenantId, ...)` — is a standalone exported function outside the `SocialConnector` interface (`normalize()`, `translateWatchlistQuery()`, `supportedQueryFeatures`, etc. — no `poll()`). A scheduler that hardcodes a per-`providerId` switch/map to these functions would need editing every time a new poll connector is added (Wikipedia/Story 2.13 is already Ready, not yet built) — a direct violation of ADR-0048's already-Accepted Decision: *"Any edit to core ingestion orchestration for registration purposes is out of policy unless accompanied by a separately approved ADR superseding this rule."* A scheduler is squarely "core ingestion orchestration."

### What already exists and is directly reusable (verified directly, not assumed)

- **`listTenants()`** (`src/tenants/tenantStore.ts:157`, Story 5.12) — already lists every tenant under `platform_admin_role`'s existing, already-Accepted (ADR-0030) bypass scope. No new bypass role is needed to enumerate tenants for scheduling.
- **`shouldAttemptIngestion(tenantId, platformId, ownerType?, userId?)`** (`src/connectors/connectorHealth.ts:131`) — already combines ADR-0010/0023's health-based auto-disable logic with ADR-0051's activation-state check, and its own doc comment states, verbatim: *"so a future scheduler consults the same derived health this module already computes, rather than a separate 'disabled' flag anyone could write independently."* This function was already built, by name, for exactly this ADR's purpose — it has simply never been called by anything except its own tests.
- **`runIngestionAttempt()`'s tenant-deletion halt guard** (ADR-0043 §3) — already enforced automatically inside every poll call, regardless of caller. A scheduler needs no separate check for this.
- **`RequestGate`/`acquireForProvider()`** (ADR-0003/ADR-0020) — already enforced automatically inside every existing `pollX()` function via its own `gatedAcquire()` wrapper. A scheduler needs no separate rate-limit handling.
- **`ingestion_runs`** (ADR-0005's immutable audit anchor) — already records `started_at` per `(tenantId, platformId)` attempt, reusable as the "when did we last actually poll this pair" source of truth without inventing a new stored field.

## Decision

**The durable decision — this is what would need superseding, not just amending:**

### 1. Mechanism: an in-process interval loop inside `social-listening-core`'s own Node process — not `pg_cron`, not a separate scheduling service

**ADR-0022's `pg_cron` precedent does not generalize to this job, and the distinction is argued explicitly, not assumed:**

ADR-0022 chose `pg_cron` for `AuthorTopicSignal` refresh because that job is a pure in-database aggregate recomputation — `pg_cron` schedules a SQL function that reads and writes Postgres tables, nothing else. This job is categorically different: it must make outbound HTTPS calls to third-party APIs (GNews, GlobeNewswire/PR Newswire, a tenant's own RSS host), decrypt Key Vault-stored credentials (`readCredential()`), acquire an in-process `RequestGate` slot, and run through `runIngestionAttempt()`'s full Node-side retry/classification logic. None of that is expressible inside Postgres — `pg_cron` can only invoke SQL, and this project's own provisioned Postgres image (ADR-0025) is confirmed to include the `pg_cron` extension but is not confirmed to include `pg_net` or any other outbound-HTTP extension; no such extension is named anywhere in this project's ADRs, migrations, or `docs/architecture/`. Even if one were added, the actual work (credential decryption, `RequestGate` state, connector-specific parsing) already lives in the Node application layer, so `pg_cron` would still need to shell out to that same process — at which point `pg_cron` is only re-adding a network hop to trigger the same in-process work an in-process timer can trigger directly, with no benefit and a new, unverified dependency. **Rejected.**

An in-process `setInterval`-driven loop, started from `server.ts`'s existing `main()` alongside the HTTP listener, is the smallest mechanism that satisfies the actual requirement: it already runs inside the one process that has `RequestGate` state, Key Vault credential access, and every connector's poll function. This mirrors ADR-0022's own underlying reasoning — *"keeps the refresh logic in the [layer] rather than requiring a separate scheduling service to run and monitor"* — just realized at the application layer instead of the database layer, because that is where this job's actual dependencies already live. It also mirrors this project's own solo-developer discipline (ADR-0020's Redis deferral, `docs/implementation-plan.md`'s "lightweight CI, no team-scale process" framing): no new deployable, no new component to provision, run, or monitor.

### 2. Enumeration: `listTenants()` × `listSocialConnectors().filter(deliveryMode === 'poll')` × `shouldAttemptIngestion()`

Each scheduler tick: for every tenant (`listTenants()`) × every registered poll-mode connector (`listSocialConnectors().filter(c => c.deliveryMode === 'poll')`), call `shouldAttemptIngestion(tenantId, platformId)` (defaulting `ownerType: 'tenant'` — see §7 below) as the eligibility filter before invoking anything. This reuses, rather than reinvents, the health/activation gate ADR-0051's own code comment already named as the intended consumer.

### 3. Registry bootstrap — a required precondition this ADR must decide, not assume solved

`server.ts`'s `main()` must call a new bootstrap step (e.g. `bootstrapConnectors()`) that calls `registerSocialConnector()`/`registerAIProviderConnector()` for every real connector module, before the scheduler's first tick and before the HTTP listener starts accepting traffic — mirroring exactly what each contract test's own `beforeAll()` already does, just moved to the one place that has never done it: the real running server. Without this, §2's enumeration returns an empty connector list and the scheduler silently does nothing, regardless of how correctly everything else in this ADR is built. This closes the `authModeForbidsUserScope()` live gap named in Context as a direct byproduct, not as a redesign of ADR-0051 — no change to that ADR's own Decision text follows from this.

### 4. Generic poll invocation — extend `SocialConnector` with an optional `poll()` method, never a hardcoded per-`providerId` switch

`SocialConnector` (`src/connectors/types.ts`) gains two optional members:

```ts
poll?(tenantId: string): Promise<RunIngestionAttemptResult>;
pollCadenceMs?: number;
```

Present only on connectors with `deliveryMode: 'poll'`. Each already-shipped poll connector (GNews, Newswire, tenant-owned-feed) gets a thin wrapper registered alongside its existing `SocialConnector` object, delegating to its already-existing, already-contract-verified `pollX()` function unchanged — no rewrite of `pollGNewsSearch()`/`pollNewswireFeeds()`/`pollTenantOwnedFeed()` themselves. `pollCadenceMs` carries that same connector's own Implementation-default cadence number (§5 below) as a real, registry-visible value — not a second, separately-maintained lookup table inside the scheduler itself, which would drift the moment a connector's own registration changed its cadence without a matching scheduler edit. The scheduler calls `connector.poll(tenantId)` generically through the registry (`getSocialConnector(platformId)?.poll?.(tenantId)`), never a hardcoded map of `providerId` to function — this is the mechanism that keeps ADR-0048's "no core pipeline change" guarantee intact as Wikipedia (Story 2.13) or any future poll connector is added: registering the new connector with its own `poll()`/`pollCadenceMs` is sufficient, no scheduler edit required.

### 5. Cadence — derived from `ingestion_runs` history, never a new stored "next poll at" field

Before calling `connector.poll(tenantId)` for an eligible pair, the scheduler checks whether enough time has elapsed since that pair's most recent `ingestion_runs.started_at` (a cheap, already-indexed-by-necessity query against an existing table). No new column, no new table. **The exact comparison, stated explicitly so a future implementer has no ambiguity to resolve on their own:**

```
now - last_started_at >= connector.pollCadenceMs * (1 + jitterFraction(tenantId, platformId))
```

— where `last_started_at` is that `(tenantId, platformId)` pair's most recent `ingestion_runs.started_at` (or, if no run has ever started for that pair, treated as unconditionally due — `-Infinity`, never a special-cased "first run" branch), and `connector.pollCadenceMs` is the value named on the connector's own registration (§4 above). This deliberately extends the same "derived, not stored" discipline ADR-0009 established for `ConnectorHealth` and ADR-0022 reaffirmed for its own cache — a scheduler restart loses no state and can never double-track a "next poll time" independently of the audit trail that already exists.

**`jitterFraction(tenantId, platformId)` — a deterministic, ±5% per-pair offset, not a random re-roll each tick.** Every pair going simultaneously due is a real, structural risk this formula alone would otherwise have: on every server (re)start, every `(tenantId, platformId)` pair whose cadence has elapsed looks equally "due" at once, and two tenants who happen to share a similar `last_started_at` history (e.g. onboarded the same day, or both last polled during the same earlier contract-test burst) would otherwise re-synchronize onto the same tick indefinitely, since a fixed cadence with no jitter has no mechanism to ever drift them apart. `jitterFraction` is computed once per pair, deterministically, from a stable hash of `tenantId` and `platformId` (e.g. `(hash(tenantId + ':' + platformId) % 1000) / 1000 * 0.1 - 0.05`, yielding a value uniformly in `[-0.05, +0.05]`) — never `Math.random()` and never recomputed per tick. Determinism matters for two concrete reasons: (1) a contract test can compute the identical offset and assert exact scheduling behavior, rather than asserting against a moving target; (2) once a pair's elapsed time genuinely exceeds its jittered threshold, it stays past it regardless of which tick observes it — the monotonic nature of `now - last_started_at` means jitter only ever shifts *when* a pair first becomes eligible, never whether it does, so a per-tick re-roll would add pure noise without doing anything a one-time-per-pair offset doesn't already do. This is a correctness/load-distribution property, not a traffic-tuned optimization — it costs nothing to design now and closes a real thundering-herd risk that would otherwise exist from the very first deploy, not just "once real usage data exists."

### 6. Scope: tenant-wide (`ownerType: 'tenant'`) poll connectors only, v1

Every real poll connector today (GNews, Newswire, tenant-owned-feed) is `authMode: 'none'` or a tenant-wide `authMode: 'api_key'` credential — none uses `connector_user_activations`' Tier-3 (per-user) scope. `pollGNewsSearch()` et al. take only `tenantId`, never `userId`; `RequestGate`'s keys (`socialConnectorKey`) are `tenantId:providerId`, never per-user. Extending this scheduler to Tier-3 poll connectors (the clearest future case: a per-user Reddit OAuth grant) is deliberately out of this ADR's scope — no such connector exists yet to design against, and doing so now would mean inventing both the connector shape and its scheduling need speculatively, the same premature-design risk ADR-0051 itself named and declined for auto-deactivation. Named as Open Question 2.

**The future shape, named so a later ADR doesn't have to reinvent it, without designing it now:** a Tier-3 poll connector will need a `poll(tenantId, userId)` signature (one level more granular than §4's tenant-wide `poll(tenantId)`) and a `RequestGate` key of `(tenantId, userId, providerId)` — extending `socialConnectorKey`'s existing `tenantId:providerId` shape by exactly the same one additional segment `aiModelKey`'s own `tenantId:providerId:modelId` already demonstrates this codebase's established pattern for. Enumeration would similarly need a per-user activation source analogous to §2's `listSocialConnectors()`, reading `connector_user_activations` rather than `connector_activations`. None of this is designed further here — no real Tier-3 poll connector exists yet, and `pollGNewsSearch()`/`pollNewswireFeeds()`/`pollTenantOwnedFeed()`'s own current `(tenantId)`-only signatures would need no change to keep working under `ownerType: 'tenant'` regardless of when this is eventually built.

### 7. Single-instance, no distributed coordination — mirrors ADR-0020's own precedent exactly

This scheduler assumes exactly one `social-listening-core` instance runs at a time, matching this project's actual current deployment shape (confirmed by ADR-0020's own Amendment Log: "confirmed this is a solo-developer personal project"). No distributed lock, no Redis coordination is built now. If a second concurrent instance is ever deployed, two independent in-process loops would double-poll every eligible pair — a real, named correctness gap, deliberately deferred with the same reasoning and the same trigger condition ADR-0020 already used for its own Redis-backed `RequestGate` state ("build when a second concurrent instance is actually deployed, not built speculatively"). A Postgres advisory lock (`pg_try_advisory_lock`) per `(tenantId, platformId)` around each poll invocation is named as the likely future mechanism — cheap, already available in the provisioned Postgres image, no new infrastructure — but not designed here.

### 8. Failure isolation

An unexpected (non-`ClassifiableError`) exception from one pair's `poll()` call must be caught and logged at the scheduler level, never allowed to crash the process or halt the loop for every other pair. `runIngestionAttempt()` already converts every classified connector failure into a recorded `IngestionRun`; this catch is only for a genuine programming-error escape, the same category `runIngestionAttempt()` itself already re-throws rather than swallows (see its own `if (!(err instanceof ClassifiableError)) throw err;`).

**The inverse, stated explicitly so it is a documented invariant and not just an accident of the current implementation:** a `poll()` implementation must let `ClassifiableError` propagate to `runIngestionAttempt()` uncaught — it must never wrap its own connector-level failures (rate limits, auth failures, malformed responses, etc.) in a local `try`/`catch` that swallows or downgrades them before `runIngestionAttempt()` sees them. Every real connector already behaves this way today (that's the only reason `deriveConnectorHealth()`/`shouldAttemptIngestion()` work at all), but this ADR states it as a durable contract, not an accident of the current implementations — a future connector author "helpfully" catching everything inside their own `poll()` would silently break `ConnectorHealth` derivation (ADR-0009) and the `failing`/auto-disable threshold (ADR-0010/0023) for that connector, with no error and no test failure to catch it, since `runIngestionAttempt()` would simply see an artificially healthy run. §8's own scheduler-level catch exists *because* of this contract, not instead of it — the scheduler catches what a compliant `poll()` was never supposed to catch itself.

### 9. Test isolation

The scheduler must start only from `server.ts`'s `main()`, never from `createApp()` — the same test/production seam `app.ts` already uses for auth middleware selection (`process.env.NODE_ENV === 'test'`). Every contract test constructs the app via `createApp()` directly and never calls `main()`, so this placement alone is sufficient to guarantee no background timer polls real external APIs during `npm test` — no new env flag is strictly required, though one (e.g. `SCHEDULER_ENABLED`) is a cheap, explicit safety net named as an implementation default below.

**Implementation defaults (adjustable — Amendment Log; does not require superseding this ADR on its own):**

- **Tick interval:** the loop wakes every **60 seconds** and re-evaluates every eligible pair's derived cadence — a guess, not derived from real traffic, same "name a real number, mark it revisable" convention ADR-0018/ADR-0037 already established.
- **Per-connector poll cadence:** GNews **15 minutes**, Newswire **15 minutes** — new defaults, since neither ADR-0024 nor ADR-0026 named a cadence (they named rate limits, a related but distinct concept). Tenant-owned-feed keeps **30 minutes**, ADR-0050's own already-decided number — not re-litigated here.
- **Per-pair jitter bound:** **±5%** of `pollCadenceMs` (§5) — a real, named, revisable number, same convention as the cadence numbers above.
- **`SCHEDULER_ENABLED`:** defaults to the inverse of `NODE_ENV === 'test'` (on outside test mode), an explicit belt-and-suspenders flag alongside §9's structural placement.
- **Bootstrap failure handling:** if a single connector module fails to register at startup, the exact behavior (crash the server vs. log and continue with a reduced connector set) is left to the Story that implements this.

## Consequences

**Positive**
- Closes the actual, live, core-value-proposition gap this session found: connectors can be connected, verified, activated, and still never ingest anything — this ADR's Decision, once built, is the first design that makes that gap closeable rather than a described-but-unaddressed limitation.
- No new database table or migration is required for the scheduler mechanism itself (§5's derived-cadence decision) — the only schema-adjacent change is none; the only new persisted state anywhere in this Decision is nothing beyond what `ingestion_runs` and `connector_activations` already store.
- §4's generic `poll()` interface addition is enforced, not just requested, by ADR-0048's own already-Accepted CI guardrail (Story 2.10) — a future connector cannot silently reintroduce a hardcoded scheduler switch without that guardrail flagging it, the same protection every other connector-registration surface already has.
- §3's registry-bootstrap fix has a genuinely useful side effect found only while drafting this ADR: it closes the live, previously-unnamed `authModeForbidsUserScope()` no-op gap in `connectorsRouter.ts`, at zero additional design cost.
- §5's derived-cadence choice means a scheduler process restart loses no state and can never desynchronize from the audit trail — consistent with, not a departure from, this project's existing `ConnectorHealth`/`AuthorTopicSignal` "single source of truth, nothing else to reconcile" discipline (ADR-0009, ADR-0022).

**Negative**
- **Real, immediate external cost begins the moment this ships.** Every tenant with an active, credentialed connector (GNews's paid/free-tier API calls in particular) starts consuming real quota continuously, not on-demand — this is the first mechanism in this project that turns "connected" into "actually costing something, repeatedly, without a human clicking anything." No budget ceiling, rate cap, or cost-alerting mechanism is decided by this ADR — named as a real, unresolved gap for Menno (see Open Question 4), not fabricated a number here.
- Single point of failure while single-instance: if the one `social-listening-core` process is down, ingestion stops entirely for every tenant, with no distributed fallback — an accepted, named trade-off (§7), not an oversight.
- Distributed correctness (double-polling under a hypothetical second concurrent instance) is deliberately deferred, same as ADR-0020's own Redis deferral — a real gap if that condition is ever hit, not designed against now.
- §5's own ±5% per-pair jitter spreads *cross-tenant* and *cross-restart* synchronization, but a single tenant with several active poll connectors that all happen to become eligible on the same tick still dispatches them concurrently within that tick — bounded only by `RequestGate`'s own per-key queueing, not by any explicit stagger across a tenant's own connectors. A real, smaller residual risk than the one §5 closes, deliberately left as-is rather than over-designed against a burst width (at most a handful of connectors per tenant today) that `RequestGate` already absorbs.
- This ADR makes a separate, already-existing gap newly *visible* rather than closing it: `pollGNewsSearch()`'s query defaults to a hardcoded `'technology'` string, not each tenant's actual watchlist terms (verified directly, `pollGNewsSearch.ts` line 10 and its call site). Once polling actually runs continuously, tenants will start seeing real posts matched against that hardcoded query, not their own watchlists — a real, adjacent, "what to poll for" gap, deliberately out of this "when/how to trigger polling" ADR's own scope (Open Question 5).

## Alternatives Considered

| Alternative | Disposition |
|---|---|
| **`pg_cron`, generalizing ADR-0022's precedent** | Rejected — argued explicitly in Decision §1: this job needs outbound HTTP, credential decryption, and in-process `RequestGate`/retry logic that live only in the Node application layer, none of which `pg_cron` can do without shelling back out to that same process anyway. |
| **A separate scheduling service/worker** (BullMQ + Redis, Azure Functions Timer trigger, a standalone cron container) | Rejected as premature operational complexity for a solo-developer, single-instance project — a new deployable to provision, monitor, and keep available, for a job an in-process loop already satisfies. Revisit if/when a genuine multi-instance or queue-depth need materializes, the same "don't build ahead of a demonstrated need" discipline ADR-0020 already applied to its own Redis-backed gate. |
| **A hardcoded per-`providerId` switch/map from the scheduler to each connector's poll function** | Rejected — directly violates ADR-0048's already-Accepted "no core pipeline change for new connector registration" Decision. Every future poll connector would require a scheduler edit. |
| **A new persisted `next_poll_at` column/table per `(tenantId, platformId)`** | Rejected in favor of deriving cadence from `ingestion_runs.started_at` — a second, independently-updatable "when to poll" fact would reintroduce exactly the drift risk ADR-0009 designed `ConnectorHealth` to avoid, generalized to a new mechanism. |
| **Defer this ADR entirely, let the gap stand until a real tenant complains** | Considered and rejected on the evidence: this is not a hypothetical — it was found live, against Menno's own real, DNS-verified tenant connector, verified via a real self-service export. The core "social listening" value proposition is not met without it, and three already-Accepted ADRs (0043, 0051, and this session's own implementation-plan note) have already named the gap three separate times without designing it — a fourth deferral is not a neutral choice, it is choosing to keep a shipped, user-visible false-positive ("connector: active") standing. |

## Open Questions

1. **Exact tick interval and per-connector cadence numbers** — real guesses (60s tick; 15 min GNews/Newswire; 30 min tenant-owned-feed inherited from ADR-0050), not derived from real traffic data, same as every numeric default ADR-0020/ADR-0022 named and left revisable at acceptance.
2. **User-bound (Tier 3) poll connector scheduling** — deliberately out of scope (Decision §6). No real Tier-3 poll connector exists yet (Reddit is unbuilt); revisit when one is designed. Decision §6 names, without designing, the expected future shape (`poll(tenantId, userId)`, `RequestGate` key `(tenantId, userId, providerId)`) so a later ADR isn't left reinventing it from scratch.
3. **Multi-instance distributed locking** — deliberately deferred (Decision §7), mirroring ADR-0020's own Redis-deferral precedent exactly. A per-pair Postgres advisory lock is named as the likely future mechanism, not designed here.
4. **Cost/quota budget ceiling for continuous polling.** This ADR decides *that* and *how* polling runs, not *how much it may cost*. No per-tenant or platform-wide spend ceiling, alerting threshold, or circuit-breaker-on-cost mechanism is designed here — a real, unresolved gap this ADR's own Negative Consequences names but does not close. Flagged for Menno directly, and for `Project Management Plans/Cost-Management-Plan.md` to be checked against once this ships (that document's existing gaps around AI-enrichment cost, per ADR-0028's footnote 10, are the closest existing precedent for this same class of open item).
5. **Watchlist-driven query construction for poll connectors that need one (GNews).** `pollGNewsSearch()`'s hardcoded `DEFAULT_QUERY = 'technology'` is a real, separate, already-existing gap this ADR's scheduler will make newly user-visible once ingestion actually runs continuously. Explicitly out of scope: this ADR decides *when/how* to trigger a poll, not *what query* a poll should run. Named so it is not discovered as a surprise once the scheduler ships.
6. **Bootstrap failure handling** (Decision §3/Implementation defaults) — whether one connector module's registration failure should crash the whole server or degrade gracefully with a reduced connector set. Left to the implementing Story.
