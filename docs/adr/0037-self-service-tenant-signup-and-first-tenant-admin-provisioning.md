# ADR-0037: Self-service tenant sign-up — authorization mechanism for unauthenticated tenant creation, domain-match handling, and public-email-provider exclusion

**Status:** Accepted (2026-08-04) — drafted by the AI Business & Requirements Analyst persona (left Proposed, per its own charter boundary; this persona does not hold ADR-acceptance authority, the same rule ADR-0026/0027/0028/0029–0036 followed), revised in place twice at review (a Security & Architecture Reviewer finding on domain-match information disclosure, then Menno's own direct instruction on domain-match visibility/escalation), then accepted by Menno. Story 6.7 moves to **Ready** (still practically gated on the same not-yet-built cross-repo endpoint named throughout this ADR).
**Acceptance note (2026-08-04):** Accepted by Menno, verbatim: *"ADR 0037 is approved as well."* Accepted together with a direct instruction, verbatim: *"the domain disclosure should not be sillent but should create sufficient noise to allow for users to regain access to their tenant and signal repeatable requests as noisy escalations"* — folded into this same acceptance as new Decision §8 (a durable, tenant-visible record of every domain-match rejection, with escalating visibility for repeated attempts), not deferred as a separate future amendment. §3's own outright-rejection decision and its vague, non-org-naming rejection message (added at the prior review pass) both stand unchanged — §8 decides how the rejection is *recorded and surfaced*, not whether it happens. All other Open Questions below remain open at acceptance, including §7's still-undesigned rate-limiting mechanism, which §8's new attempt record now gives real data to eventually work from.
**Source:** Requested directly by Menno this session ("a user sign up screen for tenant admins" — a brand-new, not-yet-tenant-linked user signing up and becoming the first Tenant-Admin of a newly-created tenant). Grounded in a direct read of ADR-0031 §5 (which names this exact event — "whichever user's sign-up actually provisions a tenant" — but explicitly declines to design the rerouting UX or the public-email-provider exclusion mechanism, leaving both to "whoever builds candidate ADR #4's own story"), ADR-0032 §6 (which designs only the *invite* flow — an already-existing Tenant-Admin inviting a colleague into their own already-existing tenant — not first-tenant creation), ADR-0029 §4 (invite-only onboarding as the default, with Entra's own self-service sign-up user flow confirmed to exist and be usable, but not yet pointed at any SocialEngage-side authorization decision), ADR-0030 §2 (Platform Admin's locked, narrow `platform_admin_role` grant, which this ADR does not widen), `docs/adr/README.md`'s no-story-ADR convention and ADR-0027/0028/0035/0036's own bar for what counts as architecturally significant enough to need an ADR at all, and a direct read of `social-listening-core/src/tenants/tenantStore.ts` and `migrations/0017_create_tenants.sql`/`0018_create_users_and_platform_admins.sql` confirming `createTenant()` is callable only through `platform_admin_role`'s own Postgres grant today.

## Context

**This is a real, currently undesigned gap, confirmed directly against the corpus rather than assumed:**

- ADR-0031 §5 (Accepted, `domain` column) *names* self-service sign-up as a real, expected event but explicitly states: "The exact 'rerouting' behavior on a domain match is also not decided here... is a sign-up/invite-flow UX decision for whoever builds candidate ADR #4's own story, not designed by this schema-level ADR," and separately names, as its own unresolved Open Question, "the public/free-email-provider exclusion mechanism for `domain` matching."
- ADR-0032 §6 (Accepted, "Invite/link flow") designs only the case where an *already-existing* Tenant-Admin creates an `invited` row for a *new colleague* inside their *own already-existing* tenant. It does not touch who creates the very first tenant, or its first Tenant-Admin — this table's own schema has no `INSERT`-then-immediately-`tenant_admin` path for a caller who arrives with no `tenant_id` at all.
- ADR-0029 §4 (Accepted) confirms Entra External ID's own "user flows" support self-service sign-up at the identity-provider level, and states the general rule that "an authenticated Entra sign-in with no matching invitation is rejected at the application layer (401/403)." It does not carve out any exception to that rule — because at the time it was drafted, no candidate feature needed one. This ADR is the first to need one.
- `tenantStore.ts`'s `createTenant()` (Story 5.8, ADR-0031) is callable only through `platform_admin_role` — confirmed directly: `migrations/0017_create_tenants.sql` grants `SELECT, INSERT` on `tenants` only to `platform_admin_role`, nothing to `app_user`, and no third role exists yet with any grant on this table. A self-service sign-up caller is, by definition, unauthenticated-until-that-moment and nowhere near a Platform Admin identity. **Widening `platform_admin_role`'s own grant to accommodate this would directly violate ADR-0030 §2's already-locked boundary** ("Platform Admin's bypass scope is locked in, not left floating a second time... it is never granted, and must never be used to query... any other tenant-content table" — and, by the same logic, must never be reachable by an arbitrary, unauthenticated-until-the-instant-before caller either).
- `docs/user-stories/epic-6-admin-ui.md` (Stories 6.1–6.6, drafted 2026-08-04) covers sign-*in* only (Story 6.1) — it assumes either an already-linked identity or a pre-existing `invited` row created by someone else. It does not cover initial sign-up.
- ADR-0036 (Proposed, same drafting pass as this one) designs the admin UI's session/BFF mechanism and names, but does not build, `GET /v1/me`. This ADR's own required backend surface (§5, below) composes with that mechanism rather than duplicating it.

**Why this needs its own ADR, applying this series' own established bar (ADR-0027/0028/0035/0036's "ordinary CRUD/UI surface doesn't need one; a hard-to-reverse authorization/abuse/security decision does"):** this is not a new field or a new screen. It requires resolving, before any code can be written safely:

1. **How an unauthenticated-until-that-instant caller gets tenant-creation authority** without widening `platform_admin_role`'s own locked boundary (ADR-0030 §2) or inventing an ungoverned second bypass.
2. **Abuse/rate-limiting** — nothing today stops one person, or one script, from creating unlimited tenants; `createTenant()`'s own doc comment says plainly "this function only proves the mechanics, it does not check who's calling."
3. **The domain-match "rerouting" UX** ADR-0031 §5 explicitly named and explicitly declined to design.
4. **The public-email-provider exclusion mechanism** ADR-0031 §5 explicitly named as its own open gap.
5. **A narrow, explicit exception to ADR-0029 §4's own general rule** ("an authenticated Entra sign-in with no matching invitation is rejected") — this is the one case where that rejection must not apply.

Every one of these is a hard-to-reverse authorization or abuse-surface decision, not a copy or layout question — squarely the kind of decision this series reserves an ADR for.

## Decision

### 1. A new, narrower Postgres role — `tenant_signup_role` — never a widening of `platform_admin_role`

A fifth Postgres role (after `app_user`, `platform_admin_role`, the migration/bootstrap role, and `identity_resolver_role`), following the exact precedent ADR-0032 §5 already established for `identity_resolver_role`: **a fourth (now fifth), even-narrower, purpose-built role, so that a compromise of one bypass role does not imply a compromise of another.**

- `BYPASSRLS`, granted **`INSERT` only on `tenants`** — no `SELECT`, no `UPDATE`, nothing else. This is deliberately narrower than `platform_admin_role`'s own `tenants` grant (`SELECT, INSERT` plus column-scoped `UPDATE(status, license_seat_count)`).
- **No `SELECT` grant is needed for domain-collision detection.** The existing partial unique index (`uq_tenants_domain`, migration `0017`) already enforces "one tenant per captured domain" at the database layer — an `INSERT` that would violate it fails with a unique-constraint violation, which the application layer catches and turns into the domain-match handling in §3 below. This avoids a check-then-insert race condition entirely (a TOCTOU gap a separate `SELECT` step would otherwise reopen) and keeps this role's grant to the minimum literally required.
- The **first `users` row** (the new tenant's first Tenant-Admin) is **not** created by this new role at all. Once the `tenants` INSERT succeeds, the tenant's `id` now exists, so the application immediately opens an ordinary tenant-scoped session (`withTenant(newTenantId, ...)`, ADR-0015, exactly as every other tenant-scoped write in this codebase already does) and inserts the `users` row as `app_user` — reusing `migrations/0018`'s already-existing `GRANT SELECT, INSERT, UPDATE ON users TO app_user`, no new grant required. This keeps the new bypass role's blast radius confined to exactly the one structurally-necessary bypass (creating the tenant row itself, which cannot be scoped by a `tenant_id` that doesn't exist yet) and nothing else.

**A Security & Architecture Reviewer pass, post-acceptance, asked how this role's own database credential is protected — not a new, `tenant_signup_role`-specific gap, the same already-disclosed project-wide one.** This project has no decided real-production secrets-management strategy for *any* application-level or database credential today (Entra client secret, the admin UI's session-cookie key, and every Postgres role's own connection credential, `tenant_signup_role` included) — named honestly in ADR-0036 §1 and `docs/open-items-and-deferred-work.md`'s own "Security / authentication" section, not solved narrowly for this one role in isolation. `tenant_signup_role` carries exactly the same, already-accepted exposure `platform_admin_role` and `identity_resolver_role` already carry — nothing about it is newly or differently at risk.

### 2. Every `tenant_signup_role` write is durably audited — reusing, not duplicating, the existing mechanism

Per ADR-0030 §5's underlying principle ("every write performed through [a bypass role] must be logged... a durable, queryable record, not an application log line alone") and ADR-0032 §9's own "don't invent a fourth, parallel audit path" discipline: every `tenants` INSERT performed through `tenant_signup_role` is logged via the **same `platform_admin_audit_log` table and `logPlatformAdminAction()` call** `createTenant()` already uses (`platformAdminAuditLog.ts`) — with `actorIdentity` set to a clearly self-service-labeled value (e.g. `self-service-signup:<validated Entra sub>`), never conflated with an actual human Platform Admin's own identity. This requires extending that table's own `INSERT` grant to `tenant_signup_role` (a small, explicit, auditable grant addition — not a `platform_admin_role` grant change) — named here as required migration work, not designed further (exact SQL is implementation-time detail).

### 3. Domain-match handling — decided, not deferred a second time

ADR-0031 §5 left this as "a sign-up/invite-flow UX decision for whoever builds candidate ADR #4's own story." This ADR is that decision point, and decides it plainly:

**A sign-up whose captured, non-excluded (§4, below) email domain already matches an existing tenant's `domain` is rejected — no new tenant is created, and no automatic join to the existing tenant happens either.** The caller is shown a specific, distinguishable message directing them to ask their own organization's existing Tenant-Admin for an invite, rather than a generic failure. Mechanically, this is simply the existing partial unique index's constraint violation (§1) caught and translated into that specific response — no new schema.

**The rejection message never names the matched organization — decided at review, 2026-08-04 (Security & Architecture Reviewer finding, Amendment Log below).** The response is deliberately generic: it states that an account for this email domain already exists and directs the caller to request an invite from their own organization's admin, but never discloses the existing tenant's name, ID, seat count, or any other identifying detail. **Why this is the right call, not the more informative alternative:** the caller at this point is an unauthenticated-until-that-instant identity — validated only to the extent of controlling the mailbox, not vetted as actually belonging to that organization in any SocialEngage-recognized sense. Naming the matched organization would let anyone with a plausible-looking corporate email address enumerate which organizations have already onboarded (a real information-disclosure/reconnaissance surface, e.g. systematically probing competitor or target-company domains) in exchange for a marginal UX improvement a genuine employee doesn't need — they already know their own employer's name. This closes what §3's own prior text had left as an open, undecided question (see the struck item in Open Questions, below) rather than leaving a plausible attack surface unresolved a second time.

**Why this is the right call, not a compromise between two options:** the 2026-07-30 brainstorm already locked in "invite-only onboarding... no request-then-approve queue" as this project's onboarding philosophy (ADR-0029 §4 restates it). Auto-joining the existing tenant on a bare domain match would be a real security regression — a validated corporate email address proves the person controls that mailbox, not that the existing tenant's own Tenant-Admin has vetted or authorized them for access to that tenant's data. Building a new "join request" approval queue for this one case would be new, unbudgeted machinery contradicting the already-decided "no queue" philosophy. **Rejecting outright and pointing at the existing invite flow is the only option that adds zero new authorization machinery and never grants unvetted access** — self-service sign-up is the mechanism for a domain's *first* arrival only; every subsequent person from an already-onboarded domain goes through ADR-0032 §6's existing, already-designed invite flow, never a second self-service entry point.

**A real, accepted limitation, named plainly, not hidden:** a legitimate second employee from an already-onboarded domain, who is not yet invited, has **no self-service path at all** under this decision — they must wait for or request an invite through an out-of-band channel (e.g. asking a colleague). This is a direct, foreseeable consequence of the decision above, not an oversight. ADR-0031 §5's own separately-named limitation (a legitimate multi-tenant single-domain organization, e.g. distinct subsidiaries, is not supported by the domain-uniqueness constraint at all) is inherited unchanged, not reopened or re-litigated here.

### 4. Public/free-email-provider exclusion — a maintained, static denylist, checked before domain capture

ADR-0031 §5's own named gap ("two unrelated organizations both signing up with personal `@gmail.com` addresses must never be matched... exact exclusion mechanism not designed here") is resolved as follows, consistent with this project's own repeatedly-stated minimal-machinery pragmatism (ADR-0031 §3's own precedent — application-layer enforcement over a database trigger; `docs/open-items-and-deferred-work.md` §E's "no ORM, no migration/query-builder framework"):

- A **static, maintained list, held in application code** (not a database table, not a third-party domain-classification lookup service) of common public/free email providers (starter set, not exhaustive: `gmail.com`, `googlemail.com`, `outlook.com`, `hotmail.com`, `live.com`, `yahoo.com`, `yahoo.co.uk`, `icloud.com`, `aol.com`, `protonmail.com`, `gmx.com`, `mail.com`).
- If the sign-up email's domain matches this list, `domain` is left `null` on the created tenant — exactly ADR-0031 §5's own already-designed "nullable" escape hatch, not a new mechanism. A `null` domain never participates in the uniqueness index or any future matching; two unrelated `@gmail.com` sign-ups each get their own, entirely independent tenant, exactly as they do today informally.
- **Named honestly as a real, accepted, permanent gap, not a false completeness claim:** a static list requires ongoing manual maintenance and will never be exhaustive — a public-email domain not yet added to the list would incorrectly participate in domain-matching until the list is updated. This is the same class of accepted limitation ADR-0031 §5's own Consequences already flagged ("only as safe as its public-email-provider exclusion list... risks incorrectly linking unrelated tenants"), now given a concrete (if imperfect) mechanism rather than left fully unaddressed.
- **Rejected alternative:** a third-party domain-classification/verification service (e.g. a disposable/free-email-detection API) — would be more complete, but is new external-vendor machinery this solo project has not needed anywhere else and is not justified by current scale; revisit only if the static list's false-negative rate proves to be a real, demonstrated problem (the same "revisit if demonstrated, not speculative" discipline as ADR-0020's deferred distributed rate-limit gate).
- **Considered and explicitly declined, 2026-08-04 (Menno, post-acceptance): DNS TXT-record domain-ownership verification.** Raised directly in response to a Security & Architecture Reviewer finding on this section's own permanently-incomplete-denylist limitation (an unlisted public domain gets captured as if it were a real organization's, then blocks a second, unrelated legitimate signer-upper from the same public provider). The standard mechanism for this class of problem is a DNS **TXT** record carrying a SocialEngage-issued token (the same pattern Microsoft 365, Google Workspace, and Slack use for domain claiming — never an A record, which serves a different, unrelated purpose; a WHOIS lookup was also considered and rejected outright, since it proves domain *registration*, not the signer-upper's authorization to act for the organization, and is frequently privacy-redacted). **Declined for this endpoint, Menno's own words verbatim:** *"Do Not Change anything at the moment activating a TXT on a domain whilst not being able to continue would take to long for a signup."* DNS propagation (minutes to 48 hours) and the real-world need to route through a client's own IT/ops team would turn this endpoint's entire reason to exist — instant, zero-touch self-service, Story 6.7's own stated "so that I can start using SocialEngage without waiting for anyone" — into an indeterminate wait for every legitimate sign-up, to guard against a comparatively low-severity edge case (a false-positive domain match is an availability/UX bug, not a data breach or unauthorized access). Not reopened without a demonstrated, forcing need, the same "named gap, don't invent the fix speculatively" discipline this series uses elsewhere (ADR-0031 §3, ADR-0020). **A distinct, separately-named idea, not designed or committed to here:** Menno separately floated turning self-service sign-up into a fuller onboarding journey (collecting stated intent, the organization's current social-listening maturity, and which platforms/credentials it already holds) rather than a single instant form — a real, possible future product direction, not a domain-ownership-verification mechanism and not decided or built by this ADR (Open Questions, below).

### 5. A narrow, explicitly-scoped exception to ADR-0029 §4 — one endpoint only

ADR-0029 §4 states, without qualification: "An authenticated Entra sign-in with no matching invitation is rejected at the application layer (401/403)." **This ADR adds exactly one named, narrow exception to that rule, for exactly one endpoint:** a new, dedicated self-service tenant-provisioning endpoint (exact path left open — `POST /v1/tenants/self-service-signup` or equivalent, per this series' own convention of not pre-deciding exact route shape, e.g. ADR-0036 §5's identical treatment of `GET /v1/me`) is the **one** place in this project where a validated-but-unmatched Entra token (no `users` row, no `platform_admins` row for its `sub`, and — per §6 below — no `invited` row for its `email` either) is accepted rather than rejected, specifically to let that caller provision their own first tenant. **Every other route in this project continues to reject an unmatched caller exactly as ADR-0029 §4 already specifies, unchanged.** Once this endpoint succeeds, the same token resolves normally on the very next request (`resolveIdentity()` now finds the freshly-created `users` row) — no new session or token-issuance mechanism is introduced.

**A real, named tension with ADR-0029's own still-open Open Question, surfaced honestly rather than hidden:** ADR-0029 §"Open Questions for decision" separately asks "whether Entra's own user-flow sign-up should additionally be restricted at the IdP configuration level, on top of the application-layer invite check — a defense-in-depth question, not decided here." **If that question is ever resolved toward "yes, restrict,"** it would directly disable the Entra-side self-service sign-up this feature depends on to even reach SocialEngage's application layer at all. This is a genuine conflict between two different domains' priorities — security hardening (defense-in-depth, restrict self-service sign-up at the IdP) versus the business requirement this ADR exists to satisfy (a real, working self-service sign-up flow) — **not pre-resolved here.** Whoever accepts this ADR must also, at minimum, confirm ADR-0029's own Open Question stays resolved "no" (or unrestricted) for as long as self-service sign-up remains a live feature; flagged for Menno (Sponsor) to reconcile explicitly, not silently assumed.

### 6. Must-check-first: an existing, unlinked `invited` row for the same email takes precedence over creating a new tenant

A real correctness requirement, not previously named anywhere: before this endpoint attempts any tenant/user creation, it must first check — via the same `identity_resolver_role`/email-lookup mechanism ADR-0032 §6's link flow already uses internally — whether an `invited`, unlinked `users` row already exists for this exact validated email, in **any** tenant. If one exists, this is not a first-time sign-up at all; the request must be routed through ADR-0032 §6's already-designed invite-link flow (link `external_subject`, activate) instead, **never** creating a second, unrelated tenant for someone who was already invited into an existing one. This endpoint's own tenant-creation path (§1–§4 above) fires only when no such row exists anywhere for that email.

### 7. Abuse and rate-limiting — one concrete floor decided; the rest named, not designed

**Decided:** a validated Entra identity (`sub`) that already resolves to an existing `users` or `platform_admins` row is rejected outright by this endpoint (400/409, "you already belong to a tenant") — it never reaches the tenant-creation path a second time. This is a cheap, mechanical guard, not the harder problem below.

**Not designed here, named as a real, open gap:** nothing in this Decision bounds how many *distinct* new identities (e.g. a script creating many disposable Entra accounts) can each successfully create one new tenant in rapid succession. `createTenant()`'s own doc comment already states plainly that it "does not check who's calling" — this ADR's new endpoint inherits that same gap unless a rate limit is added at the application or edge layer (e.g. per-IP, per-time-window). This project's existing `RequestGate` (ADR-0003) is keyed by `(tenantId, providerId)` — neither exists yet at the moment this endpoint is invoked, so it cannot be reused as-is; a **new**, differently-keyed limiting mechanism would be required. Following this series' own repeatedly-used discipline (name the gap, don't invent the fix speculatively — ADR-0031 §3's seat-count race condition, ADR-0020's deferred distributed gate), **the exact mechanism and numeric threshold are left as an Open Question below**, not designed here. **Narrowed, not closed, by §8a's email-OTP-verification precondition (added at acceptance):** a distinct-identities attack here means distinct, real, *verified* mailboxes, not freely-fabricated email strings — meaningfully raising the cost of the exact scripted-abuse scenario this paragraph names, though not eliminating it (an attacker who genuinely controls many real mailboxes, e.g. across many domains they own, is unaffected).

**The actual blast radius of a successfully-abused tenant, stated explicitly, added post-acceptance 2026-08-04 (Menno):** even a tenant created through this gap is worth restating what it *doesn't* get an attacker, not just what it costs this project (junk rows, storage — Consequences, below). A freshly-provisioned tenant is an empty shell (no connectors, no data — see §8's own discussion) that grants **zero ambient access to any external system.** Every connector this project has, or will ever have, requires its own separate, vendor-issued end-user credential — a contract between the data source and the connecting party's own end user, never brokered, pooled, or granted by SocialEngage itself (ADR-0027's already-Accepted "technical intermediary only" principle; ADR-0028's ownership-tier credential model, tier 2/3 credentials created only by an actual Tenant-Admin or activated by an actual user, never system-wide). Creating a tenant, by itself, is not a key to anything — it's an empty container that only becomes valuable once its own Tenant-Admin independently authenticates with a real external vendor using their own credentials, exactly the same as any other tenant's connector setup. This bounds §7's own severity (a real, still-open gap, not dismissed by this) to resource consumption and operational nuisance, not unauthorized access to any real system or data.

### 8. Domain-match rejections are not silent — decided at acceptance, three directly-given instructions folded in together (Menno, Sponsor, 2026-08-04)

Three direct instructions from Menno, given at this ADR's acceptance in immediate succession, all folded in here rather than deferred separately: verbatim, *"the domain disclosure should not be sillent but should create sufficient noise to allow for users to regain access to their tenant and signal repeatable requests as noisy escalations"*; verbatim, *"in our auth flow we should have confirmation of email address of the user then validate the domain to either propose to the admin of a new user or atleast do something nice for the user that legimatly tries to sign up to existing tenant but was not issued an invite"*; and verbatim, *"repeating domain requests should trigger security alertts."* **§3's own outright-rejection decision stands completely unchanged — no auto-join, no new tenant on a domain match.** This section decides four things downstream of that rejection: how the caller's email is verified before it's trusted for domain-matching at all (§8a); how the rejection is recorded and proposed to the matched tenant's own Tenant-Admin (§8b); how repeated attempts also become a Platform-Admin-visible security signal (§8c); and how the rejected caller's own experience is improved without over-promising infrastructure this project hasn't built (§8d).

**8a. Email verification is a stated precondition of domain-matching, not an assumed one — confirmed directly against Microsoft's own current documentation, not assumed.** Checked directly (`learn.microsoft.com/en-us/entra/external-id/customers/concept-authentication-methods-customers`, retrieved 2026-08-04): for **Email with password** (the default local-account sign-in method for a sign-up/sign-in user flow), Microsoft's own text states plainly, "Users are prompted for an email address, which is verified at sign-up with a one-time passcode" — before the account is even created. For the alternative **Email one-time passcode** method, the OTP itself *is* the sign-up step. Both of this project's realistically-available local-account methods verify email ownership via OTP before a token is ever issued — this ADR decides that confirming this is actually enabled on `social-listening-admin`'s own configured user flow (not merely assumed default) is a precondition this endpoint's trust in a token's `email` claim depends on, before that claim is ever used for §3/§4's domain-matching or denylist logic. Named as a required verification step for whoever builds Story 6.7, not new machinery this ADR itself builds — Entra already does the verification; this project must confirm its own user-flow configuration actually has it turned on.

**A real config-drift gap a Security & Architecture Reviewer pass correctly flagged, post-acceptance: a one-time manual check at build time doesn't guard against the user flow's configuration silently changing later.** If `social-listening-admin`'s Entra user flow were ever misconfigured to skip email verification (accidentally or otherwise), this endpoint would have no way to know and would trust an unverified `email` claim for domain-matching. **Decided:** a deployment-pipeline/startup check that confirms the configured user flow still has email verification enabled is the required minimum (Gemini's own suggested control) — named as required, not built here. **Left genuinely open, not asserted as fact:** whether Entra also emits a runtime, per-token `email_verified` claim for local (Email-with-password/Email-OTP) accounts that this endpoint could check directly on every request, as cheaper defense-in-depth than a deployment-time check alone — checked against Microsoft's own general ID-token claims reference (`learn.microsoft.com/en-us/entra/identity-platform/id-token-claims-reference`), which does **not** list `email_verified` among its documented claims, but that reference covers workforce Entra ID, not confirmed to also describe External ID/CIAM local-account tokens specifically. Not resolved to this project's own primary-source bar this session — a real Open Question (below), not decided either way.

**A real, favorable security consequence of 8a, raised directly by Menno and worth stating explicitly: this closes off cheap domain enumeration, not just cheap tenant creation.** Because email ownership is verified *before* SocialEngage's own domain-matching logic ever runs, nobody can reach §3's rejection path — or trigger §8b/§8c's own visibility/escalation signal — for a domain they don't control at least one real, working mailbox on. An attacker cannot cheaply spray guessed addresses at `@target-domain.com` to probe whether that organization is already onboarded (the exact reconnaissance risk the earlier Security & Architecture Reviewer finding raised, §3's own dated note) without first proving they can receive mail there. It similarly narrows §7's own still-open volumetric-abuse concern from "fabricate arbitrary emails at any domain" down to "control many real, distinct mailboxes" — a meaningfully higher bar, though not zero (a single real mailbox, e.g. a shared/role account like `info@acme.com`, is still enough to probe or repeatedly trigger one domain's own signal) — named honestly as a real mitigation, not a complete close of either gap.

**A second, related point Menno raised: even a single mailbox can't cheaply repeat the attempt, at least under one of Entra's two local-account methods.** Which method `social-listening-admin`'s own user flow configures — **Email with password** or **Email one-time passcode** (§8a) — is not yet decided by any ADR. If it's the latter, Entra's own sign-in mechanism issues a fresh OTP challenge on *every* sign-in, not only the first — meaning even a retry from the exact same, already-existing, already-verified Entra account still has to pass a new human-interactive Entra challenge each time, further raising the cost of scripting §8c's own escalation trigger. Under **Email with password**, this specific friction doesn't recur past the first sign-up (a stored password is reusable) — the exact choice between the two is left to whoever builds Story 6.7, not decided here, but is now a real, named factor in that choice, not a detail without downstream consequence.

**8b. Every domain-match rejection is written to a new, tenant-scoped, RLS-visible record — surfaced to the Tenant-Admin as a proposal, not a passive count.** A new table (working name `domain_signup_attempts`: `tenant_id`, `email`, `attempted_at`), RLS-scoped exactly like every other tenant-content table (ADR-0015's ordinary `tenant_isolation` policy — never a bypass role, deliberately the opposite of §2's Platform-Admin-only audit log), `INSERT`-only via `tenant_signup_role` (a second, narrow grant addition alongside §2's, same minimum-required discipline). Whoever builds the admin UI's own Tenant-Admin-facing screens (Story 6.2's dashboard or equivalent) surfaces this as a real, hard-to-miss indicator — not a quiet log line requiring someone to go looking — **with a direct, one-click "invite this person" affordance that pre-fills ADR-0032 §6's already-existing invite-creation flow with the attempted email — named here as its own thing, the Same-Domain Invite Assist, per Menno's own framing at acceptance ("the helpful tenant admin and invite creation for user in same domain is a service") rather than left as unnamed prose buried inside this endpoint's description.** This remains entirely the Tenant-Admin's own decision and action: this ADR introduces no automatic invite, no auto-join, no approval-queue state machine — it only removes the friction of acting on a request that is now visible and pre-filled, instead of requiring the Tenant-Admin to first hear about it out-of-band and then separately create an ordinary invite from scratch. **This directly softens, without fully closing, §3's own already-named limitation** (a legitimate not-yet-invited colleague has no self-service path): they still cannot self-provision access, but their attempt is no longer invisible to the one person who can actually invite them. A domain crossing a template default of 3 attempts within a rolling 30-day window (both revisable via this Amendment Log, not deeply analyzed defaults) is surfaced with materially more prominence than a first attempt — an explicit, decided escalation in visual treatment, not just a bigger number in the same UI element.

**The Tenant-Admin-facing surface aggregates by domain, one item per domain, never one row per individual attempt — decided post-acceptance, 2026-08-04, closing a real gap a Security & Architecture Reviewer pass found.** An actor controlling several distinct, individually-verified mailboxes at the same already-onboarded domain (e.g. `sales@target.com`, `marketing@target.com`) could otherwise generate many separate `domain_signup_attempts` rows, each surfacing as its own separate proposal — flooding the Tenant-Admin's dashboard and burying the one legitimate request among noise, a real operational-nuisance/attention-DoS risk distinct from anything §7 already names. The underlying table still records every individual attempt (needed for §8c's own escalation logic and any future rate-limiting work, §7), but the Same-Domain Invite Assist itself shows exactly one entry per domain, with the distinct-email count and escalation state folded into that single item, not one entry per email.

**A summary count alone would under-serve the Tenant-Admin's own decision, a real gap a further Security & Architecture Reviewer pass correctly caught: the one-click invite action (above) needs a specific email to target, so the individual list can't just disappear behind an aggregate count.** Decided: the summary item (one per domain, the escalation/flood protection above, unchanged) expands on demand to the full list of distinct verified email addresses behind it — the Tenant-Admin sees a count at a glance, and the actual addresses (to recognize a known colleague, spot something odd, or simply pick which one to invite) on request, not buried or lost. This is the same underlying `domain_signup_attempts` data (§8b) surfaced two ways, not a second mechanism.

**8c. Repeated attempts against the same domain also become a Platform-Admin-visible security signal — reusing, not duplicating, the existing audit mechanism.** When §8b's escalation threshold is crossed, the same event is also written to the existing `platform_admin_audit_log` (§2's already-established table and `logPlatformAdminAction()` call), distinguishably labeled as a repeated-domain-match escalation rather than an ordinary signup — giving Platform Admin real operational visibility into a potential abuse pattern (many attempts against one domain, or one domain matched by many structurally different identities) without inventing a second, parallel audit path. **Named honestly as a real, deliberate scope limit:** this decides what gets *recorded and made reviewable*, not real-time paging — an automatic Slack/email/on-call alert firing the moment this threshold is crossed would require an outbound-alerting capability this project has not designed or built anywhere (no ADR, story, or shipped code sends any outbound notification today). That remains a real, concrete future enhancement (Open Questions, below), not committed to now; §7's own still-undesigned rate-limiting mechanism is the more natural home for deciding whether/how this eventually becomes a true real-time alert.

**The escalation entry carries the verified email addresses behind it, not just a domain and a count — decided post-acceptance, 2026-08-04 (Menno).** Menno's own point, worth recording plainly: triggering this escalation is not something that happens by accident — §8a's OTP-verification precondition means it requires an attacker (or, just as plausibly, a cluster of legitimate colleagues) to control *multiple, real, individually-verified* mailboxes at the target domain. That's a meaningfully attributable signal, not anonymous noise, and this project already has the data — `domain_signup_attempts` (§8b) stores each attempt's own verified email. **Decided:** the `platform_admin_audit_log` escalation entry includes the list of verified email addresses that crossed the threshold, not merely the domain and a count. This arms §9's own manual recovery process with real, ready-to-use contact information the moment Platform Admin investigates — deliberately **not** automated outreach (no email is sent by the system itself; that would require this project's first outbound-email capability, not built anywhere today, and raises its own design questions about what such a message would say and whether it could itself become a spam/abuse vector) — a small, no-new-infrastructure change, not a new communication channel.

**8d. The rejected caller's own experience: reassurance, without over-promising infrastructure this project hasn't built.** The rejection message (§3, already decided as vague and non-org-naming) is extended to state plainly that the request has been shared with the caller's own organization's admin — without confirming that organization's identity, preserving §3's own anti-enumeration decision — and that they should expect access if it's legitimate, rather than a cold "ask your admin" instruction with no sense that anything actually happened. **Named honestly as a real, deliberate scope limit, not silently promised beyond what's true:** actually notifying the rejected caller later, once they're invited (e.g. an outbound email, or a "come back and try again" prompt), would require an outbound-notification/email-sending capability this project has not designed or built anywhere — the existing invite flow (ADR-0032 §6) is entirely in-app; an invited person discovers their invite only by attempting to sign in again. This ADR does not invent that capability speculatively to satisfy one screen's copy — named as a real future enhancement (Open Questions, below), not decided or built here.

**A secondary, genuinely useful side effect of §8b/§8c, not their primary purpose:** the same durable per-domain attempt record is real data for whoever eventually designs §7's still-deferred rate-limiting/abuse mechanism — an unusually high attempt count from one domain, or a pattern spanning many structurally-different identities, is exactly the signal a future anomaly-detection pass would want, and it now exists to look at rather than being invented from nothing. §7's own Open Question is not resolved by this — it only gives it real data to eventually work from.

### 9. Platform Admin gains a real, audited recovery path for a wrong `domain` value — decided post-acceptance (Menno, 2026-08-04)

Verifying §4's own already-named denylist false-negative gap surfaced a materially more serious, previously-unraised problem: **nothing in this project, not even Platform Admin's own bypass role, could ever correct a wrong `domain` value on an existing tenant row.** Not the ordinary false-negative case (§4, an unlisted public domain incorrectly captured), and not a deliberately squatted real corporate domain — an attacker with a single real mailbox at a target company (per §8a's own precondition, they need at least one) signing up first, permanently blocking that company's own future employees' self-service path toward an "admin" who will never invite them, with §3's own outright-rejection design giving them no other route in. `platform_admin_role`'s existing grant on `tenants` (ADR-0031 §3) covers only `status` and `license_seat_count` — never `domain`.

**Decided:** `platform_admin_role`'s grant is extended by exactly one additional column: `UPDATE(domain)` on `tenants`. Clearing or reassigning a wrong or disputed `domain` value is now a real, possible, audited Platform Admin action — the same "administrative metadata, not tenant-content" category ADR-0031 §3 already established for `status`/`license_seat_count` (a domain string is an administrative/identity attribute of the tenant record itself, not tenant-owned content, the same distinction that already justified those two existing writes). **This does not widen Platform Admin's boundary in the sense ADR-0030 §2 locked** — no `SELECT`/`UPDATE` access to any tenant-content table is added; Platform Admin still cannot read or alter `users`, `platform_credentials`, or anything tenant-scoped. It's one additional column on the one table Platform Admin already administers.

**Every such write is audited, reusing the existing mechanism, not a fourth parallel path:** logged via `platform_admin_audit_log`/`logPlatformAdminAction()` (§2), the same table and call every other Platform Admin action in this project already uses.

**Named as required, not designed here:** the exact operational trigger for using this grant (a support request from the legitimate organization, a manually-investigated abuse report) is not designed — this decides the grant exists and is fully audited, not a self-service dispute/reclaim workflow (considered and explicitly not chosen — Alternatives Considered, below). §8c's own escalation entry (above) now carries the verified email addresses behind a repeated-attempt pattern — real, ready-to-use contact information for whoever investigates, rather than a domain and a count alone. **This updates ADR-0031 §3's own already-Accepted grant description** — see that ADR's own new "Supersession update" note; ADR-0031's own Decision/Consequences text stays unedited, per this file's own governance-table convention.

## Consequences

**Positive**
- Resolves ADR-0031 §5's own explicitly-named "not decided here" gap (rerouting UX) and its own named Open Question (public-email exclusion mechanism) directly, rather than leaving both open a second time.
- **Added at acceptance (§8):** §3's own previously-named UX cost (a legitimate not-yet-invited colleague has zero visible path) is materially softened, not left as a pure dead-end — the Tenant-Admin gets a proposed, one-click-actionable signal instead of relying purely on out-of-band word-of-mouth, and repeated attempts are durably reviewable by Platform Admin rather than invisible.
- Reuses every mechanism this project has already built wherever possible — the existing partial unique index (domain-match detection), the existing `platform_admin_audit_log`/`logPlatformAdminAction()` (audit trail), the existing `app_user`/`withTenant()` path (first-user insert), and ADR-0032 §6's existing invite-link flow (§6, must-check-first) — introducing exactly one new thing (`tenant_signup_role`) rather than a parallel set of new mechanisms.
- `tenant_signup_role`'s grant is even narrower than `platform_admin_role`'s own (`INSERT`-only, no `SELECT`, no `UPDATE`) — a compromise of this role cannot read or alter any existing tenant, only ever attempt to create a new one, and even that is fully audited.
- Names, rather than silently defers a second time, the one real remaining abuse gap (bulk/scripted tenant creation) — visible for a future decision instead of hidden.
- **Added post-acceptance (§9):** a wrong or squatted `domain` value is now recoverable — a real gap this ADR itself would otherwise have introduced with no way out is closed, via a minimally-scoped, fully-audited Platform Admin grant extension rather than new machinery.

**Negative**
- **A real, new Postgres role and grant to provision and keep correctly scoped** — genuine, if small, operational surface, the same trade-off ADR-0032 §5 already accepted for `identity_resolver_role` and named honestly there ("a small but genuine increase in the database's own role-management complexity").
- **The domain-match rejection (§3) has a real, accepted UX cost, now partially but not fully mitigated:** a legitimate not-yet-invited colleague at an already-onboarded organization still has zero *self-service* path — §8b's Same-Domain Invite Assist makes their attempt visible and actionable to the Tenant-Admin, but access still depends entirely on that Tenant-Admin choosing to act; this is a deliberate trade-off against reopening the "no request-then-approve queue" philosophy, not a costless choice, and not a full fix.
- **§8's new tenant-scoped `domain_signup_attempts` table (§8b) is a real, new, if small, schema/migration surface**, and its escalation thresholds (30 days / 3 attempts) are unanalyzed template defaults needing eventual tuning against real usage — the same trade-off every other numeric default in this series accepted (ADR-0017–0019's own precedent).
- **§8c's escalation signal is durably logged, not actually alerted on in real time** — a Platform Admin must still go look at `platform_admin_audit_log` to see it; this is a real, named gap versus true "trigger security alerts" until an outbound-alerting capability is built (Open Questions, below).
- **The public-email-provider denylist (§4) is permanently incomplete by construction** — a real, ongoing maintenance burden and a real, if bounded, false-negative risk, accepted rather than solved.
- **The bulk/scripted-abuse gap (§7) is a genuine, currently-unresolved risk**, not a hypothetical one — this ADR decides the authorization *shape* but does not close the volumetric abuse surface; whoever builds this story must treat §7's Open Question as a precondition for exposing this endpoint publicly, not an optional hardening pass. **Its severity is bounded, not eliminated, by §7's own added note (post-acceptance):** a successfully-abused tenant is an empty shell with zero ambient access to any external system — every connector requires its own separate, vendor-issued end-user credential (ADR-0027, ADR-0028) — so the real cost of this gap is resource consumption/operational nuisance, not unauthorized data or system access.
- **§9's Platform Admin recovery path is manual, not instant** — a legitimate organization blocked by a squatted or misclassified domain must still reach Menno (or a future support process) and wait for a Platform Admin action; not a self-service fix, an accepted trade-off against building heavier automated dispute-resolution machinery this problem's current, low likelihood doesn't yet justify.
- **A real, named tension with ADR-0029's own still-open Open Question (§5)** — this feature's continued existence depends on that question never being resolved toward IdP-level self-service restriction; a future security-hardening decision could silently break this feature if that dependency isn't checked at the time.

## Alternatives Considered

- **Reuse `platform_admin_role` directly for this endpoint** (e.g. treat every self-service sign-up as an automated "Platform Admin" action) — rejected outright: directly violates ADR-0030 §2's own already-locked boundary, and conflates a genuinely different actor (an anonymous-until-that-instant member of the public) with a trusted, singular, human Platform Admin identity — a materially larger blast radius if this endpoint or its credential were ever compromised.
- **Auto-join on domain match, no rejection** — rejected (§3): grants unvetted tenant access on the strength of a verified mailbox alone, contradicting this project's own already-decided "invite-only, no queue" philosophy and Platform Admin's own "zero tenant-data access" boundary's underlying spirit (data should be reachable only by people the tenant's own admin actually decided should have it).
- **A new request-then-approve queue for domain-matched sign-ups** — considered as the more feature-complete option; rejected as unbudgeted new machinery this ADR does not need to introduce to satisfy the actual requirement, and a direct reopening of the already-decided "no queue" philosophy without a demonstrated need forcing that reopening. **Not reopened by §8's new Same-Domain Invite Assist, added at acceptance:** §8 is a notification-plus-proposal, not a queue — no accept/reject state machine, no gating action, no automatic anything; the Tenant-Admin's own ordinary act of creating an invite (ADR-0032 §6, unchanged) remains the only thing that actually grants access. Menno decided this directly, distinct from and lighter-weight than the queue considered and rejected here.
- **A third-party domain-classification/disposable-email-detection service** for public-provider exclusion — rejected for v1 (§4): real new external-vendor dependency, not justified by current scale, revisit only if the static list proves demonstrably insufficient.
- **Skip the `INSERT`-only `tenant_signup_role` and instead have `identity_resolver_role` also perform the tenant `INSERT`** — rejected: `identity_resolver_role` is deliberately SELECT-only by ADR-0032 §5's own explicit design ("never any write grant... a compromise of this role must not imply a compromise of [`platform_admin_role`]"); adding a write grant to it would weaken an already-shipped, narrowly-scoped role rather than introducing a new one purpose-built for this one job.
- **A self-service, DNS-TXT-verified domain-reclaim workflow** (§9) — the real organization proves ownership itself and the system reassigns the domain automatically, no Platform Admin involved — considered as the more automated, no-human-intervention option; rejected for now as heavier machinery than this problem's current, low (if nonzero) likelihood justifies. §8a's own OTP-verification precondition already meaningfully raises the bar for a deliberate squat (needs a real mailbox at the target domain); a manual, fully-audited Platform Admin action is judged the right-sized fix at this project's current solo/support-desk scale — revisit if this is ever actually hit at a frequency that makes manual handling impractical, the same "demonstrated need, not speculative" discipline this series uses throughout.
