# ADR-0054: Tenant-facing Analytics Dashboard — v1 scope, client-side data-source strategy, and a scoped, narrow supersession of ADR-0008's charting deferral

**Status:** Accepted (2026-08-17)
**Source:** Not specified in the design spec or any prior ADR. Requested directly by Menno, 2026-08-17, to bring a Tenant-facing Analytics Dashboard into formal scope for `social-listening-admin` — previously out of scope per `docs/design/frontend-design-specification.md` §10 ("Rich Analytics & Charting Dashboards: deferred to dedicated analytics/reporting subsystems (Design Spec §9, ADR-0008)").

**Acceptance note (2026-08-17).** Accepted by Menno, via a structured approval decision in the orchestrating session — not a freeform verbatim chat message, named honestly here rather than fabricated as a quote in his own words: the orchestrating assistant presented a summary of this ADR's scope (the four-tab v1, the client-side data-source strategy, the ADR-0008 relationship, and the Location-tab feasibility finding), and Menno selected "Approve as summarized." Accepted as drafted, no revisions. **Story 8.1, Story 8.2, and Story 8.3** (`docs/user-stories/epic-8-analytics-dashboard.md`) move from Blocked to **Ready** — see that file's own dated note. `docs/adr/0008-defer-topic-time-series-and-charting.md`'s 2026-08-17 "Pending supersession note" now gains its matching "Supersession update" note, per `docs/adr/README.md`'s own governance-table convention — ADR-0008's own Decision/Consequences text remains untouched.

## Context

### The gap, verified directly this session

`social-listening-admin` has no analytics/dashboard route today. `docs/design/frontend-design-specification.md` (the Approved, dated 2026-08-14 implementation baseline) §5 Screen Inventory and §9 Route Table list 16 routes, none of them analytics. §10 "Deferred Items & Non-Goals" explicitly names "Rich Analytics & Charting Dashboards" as out of scope, citing this project's own ADR-0008 and Design Spec §9. §11 lists `docs/design/Gemini Designs/` (Vite/React/Tailwind, AI Studio) as covering exactly this deferred surface — "Overview, Sentiment, Conversations, Location, Sources" — and states plainly: "Not to be ported as code."

**Prior, uncommitted prototype work already exists and was reviewed in full before drafting this ADR.** Five untracked component files sit at `social-listening-admin/src/app/tenant/analytics/` (`SentimentDashboardTab.tsx`, `LocationDashboardTab.tsx`, `ConversationsDashboardTab.tsx`, `GlobalDateRangePicker.tsx`, `AnimatedChartTooltip.tsx`) — not wired into any route, nav entry, or contract test. They already use this project's real conventions (`ad-`-prefixed custom CSS classes, not Tailwind; Recharts for charting) rather than the Google AI Studio reference's Tailwind markup, which is the right instinct — but three concrete, verified problems mean none of them can be treated as implementation-ready:

1. **They import a `FlatPost` type from `./types`, a file that does not exist anywhere in the repository** (confirmed via `Glob` — no `social-listening-admin/src/app/tenant/analytics/types.ts` on disk). All three data-consuming components (`SentimentDashboardTab.tsx`, `ConversationsDashboardTab.tsx`, `LocationDashboardTab.tsx`) fail to compile as-is.
2. **Every `ad-*` CSS class they reference (`ad-tab-grid`, `ad-widget`, `ad-col-left`, dozens more) is undefined.** `social-listening-admin/src/app/globals.css` was grepped directly for `\.ad-` and returned zero matches, despite `AnimatedChartTooltip.tsx`'s own code comment claiming its `.ad-tooltip` class is "defined in globals.css ad-\* block." No such block exists yet.
3. **Fabricated data is mixed with real, computed data in a way that would mislead a reviewer skimming the code, not just in the widgets that are obviously placeholders.** `SentimentDashboardTab.tsx`'s `topFans`/`topCritics` derive genuinely from `filteredPosts` (real `FlatPost[]`) — but silently fall back to a hardcoded `TOP_FANS`/`TOP_CRITICS` array when the real derivation yields zero results (`dynamic.length > 0 ? dynamic : TOP_FANS`), meaning a tenant with too little real positive/negative sentiment data would see fabricated names (`kiefferphilippe`, `Philippe Kieffer`, etc.) rendered with no visual distinction from genuine data. `SENTIMENT_HISTORY` (the sentiment-over-time chart) is 100% static, entirely disconnected from `filteredPosts`, despite sitting in the same component as the genuinely-computed donut. `ConversationsDashboardTab.tsx`'s `INTENTIONS` and `TAGS` widgets (`information_request`/`purchase`/`support_request`/`complaint`; `announcement`/`advocate`/`mse_today`) are entirely static and have **no corresponding field anywhere in this project's real enrichment schema** — confirmed directly against `social-listening-admin/src/app/tenant/posts/postDisplay.ts`'s `PostEnrichmentSummary` interface, which carries exactly `sentiment`, `sentimentScores`, `entities`, `keyPhrases`, `modelUsed` and nothing resembling an "intention" or "tag" classification. `LocationDashboardTab.tsx` is **entirely** static (`REGIONS`, `LANGUAGES`, `COVERAGE_SLICES`, a hand-drawn SVG world map with hardcoded region paths) — it derives nothing from `filteredPosts` beyond a single cosmetic "matched posts" count.

This ADR exists to replace that ad hoc, partially-fabricated prototype with a decided, honestly-scoped v1: real data only, no silent fallback to fake data, and an explicit Open Question rather than an invented answer wherever real data doesn't exist yet.

**Separately, `src/lib/mockData.ts` and `src/lib/types.ts` already exist in the tracked codebase** (confirmed: neither appears in this session's starting `git status`, meaning both are already committed, not part of the currently-uncommitted work) with fully generic social-platform demo data — `Twitter/X`, `LinkedIn`, `Forums`, `YouTube` fan/post/author fixtures bearing no relationship to this project's actual three-connector roster (`gnews`, `newswire`, `tenant-owned-feed`). These are not consumed by anything in `social-listening-admin/src/app/**` today (confirmed: neither file is imported by any of the five analytics prototype components, which import from a non-existent local `./types` instead) — a dead, already-committed artifact from an earlier design-reference pass. Named here as a real, standing cleanup item for whoever picks up Story 8.1 (see Open Questions) — not fixed by this ADR, which is documentation only.

### What this subsystem's real data can support today, verified directly, not assumed

- **`GET /v1/posts`** (Story 6.11, ADR-0011 cursor pagination) returns `SocialPostSummary[]`: `id`, `createdAt`, `rawPayload`, `publishedAt`, `enrichment` — confirmed directly against `social-listening-core/src/posts/socialPostStore.ts`. Default page size 20, max 100 (`DEFAULT_PAGE_LIMIT`/`MAX_PAGE_LIMIT`); `social-listening-admin/src/lib/core-client.ts`'s `listPosts()` doesn't currently even expose a `limit` parameter to its caller.
- **`enrichment`** (`postDisplay.ts`'s `extractEnrichmentSummary()`) yields `sentiment`, `sentimentScores`, `entities`, `keyPhrases`, `modelUsed` — real fields, real data, once Story 2.8/2.9's AI providers have run. No `intention`, `tag`, or topic-cluster field exists anywhere.
- **`rawPayload.providerId`** (`extractProviderBadge()`, `postDisplay.ts`) identifies which of exactly three real content connectors ingested a post: `gnews`, `newswire`, `tenant-owned-feed` (confirmed via `PROVIDER_ID` exports in `gnewsConnector.ts`, `newswireConnector.ts`, `tenantOwnedFeedConnector.ts` — `azure-ai-language`/`azure-openai` are enrichment providers, not content sources, and never appear as a post's own `providerId`). This project's real "Sources" breakdown is these three, not the generic X/Twitter/LinkedIn/Facebook/Instagram/YouTube/Blogs roster the Google AI Studio reference assumes.
- **No `TopicDailyCount` or any other stored aggregation exists** — confirmed via `Grep` for `TopicDailyCount`/`aggregat`/`timeseries` across `social-listening-core/src`, which returns no aggregation-table matches (only unrelated hits: `runIngestionAttempt.ts`, `domainSignupAttempts.ts`, `authorTopicSignalStore.ts`). This is exactly what ADR-0008 decided not to build.
- **Post geo-location: a column exists, but is real only in the schema, not in practice.** `social_posts.post_geo_location` (surfaced as `postGeoLocation: unknown` on `InsertSocialPostInput` and `SocialPostFull`, `socialPostStore.ts`) is a real, nullable column — but **no connector populates it.** Confirmed directly: `pollGNewsSearch.ts`'s `insertSocialPost()` call passes `tenantId`, `authorId`, `acquisitionId`, `rawPayload`, `publishedAt`, `enrichment`, `bodyMarkdown`, `bodyMarkdownVersion` — no `postGeoLocation` key at all; the same is true structurally for Newswire and tenant-owned-feed (neither RSS/Atom parser extracts anything geo-shaped, confirmed against `rssFeedParser.ts`/`feedItemParser.ts`'s own field lists, most recently re-verified by ADR-0053). **Independently, and more decisively for this dashboard specifically: even if it were populated, `SocialPostSummary` — the shape `GET /v1/posts` actually returns, the endpoint any client-side aggregation would page through — does not include `postGeoLocation` at all.** Only `getSocialPostById()`'s single-post `SocialPostFull` fetch carries it. A dashboard aggregating "posts by region" from paginated list results has no geo field to read even for the small fraction of rows that might someday carry one.

### Author-rights standing check (per this role's charter)

This ADR touches ingested content that has an `Author` — for all three real connectors (GNews, Newswire, tenant-owned-feed), an issuing-organization/publication `Author` under ADR-0004's organization-as-Author clause (ADR-0026, ADR-0024, ADR-0050), not an individual. Checked explicitly: the Sentiment tab's "Top Fans"/"Top Critics" widgets display `p.author` (the already-normalized Author name `postDisplay.ts`'s `extractAuthor()` already surfaces on the existing, shipped post feed, Story 6.11) grouped by sentiment count — this is a read of already-displayed attribution data, not a new attribution mechanism, and this ADR's Decision does not reassign ownership, alter the `Author` upsert, or introduce any new redistribution path. **One real gap this check does surface, named as an Open Question rather than silently built in:** the prototype's per-widget "download" buttons (`onExportWidgetData`) would export author-identified aggregate data (e.g. a CSV/JSON of "Top Critics" handles and counts) outside the tenant-level export mechanism ADR-0039/Story 6.13 already built and governs. This ADR does not decide whether that's an acceptable redistribution path or needs its own consent/disclosure treatment — Decision §2 scopes it out of v1 explicitly (Open Questions) rather than assume it inherits ADR-0039's export contract by default.

## Decision

### 1. Relationship to ADR-0008: a narrow, scoped supersession, not a wholesale reversal

ADR-0008 (Accepted 2026-07-28) decided two distinct things under one Decision sentence: (a) do not build a `TopicDailyCount` aggregation table or endpoint in `social-listening-core`, and (b) do not build "any charting UI" in "this subsystem." Its own Negative Consequences named the exact cost of deferral explicitly: *"Any consumer wanting topic-volume-over-time today must aggregate `GET /posts` results client-side... acceptable for now since no such consumer exists yet in scope."* That is precisely the situation this ADR now resolves — a consumer (this same subsystem's own admin UI) now exists in scope, at Menno's direct request.

**Decided: ADR-0008 Decision clause (a) — no `TopicDailyCount` table, no new backend aggregation endpoint — is fully reaffirmed, unchanged, and not touched by this ADR.** Nothing in this Decision adds a stored aggregate, a new `social-listening-core` endpoint, or commits to any aggregation grain (daily/hourly/per-tenant-timezone). Decision §3 below is explicit that this dashboard computes everything client-side from data `GET /v1/posts` already returns.

**Decided: ADR-0008 Decision clause (b) — "any charting UI in this subsystem" — is superseded in part, narrowly, to the exact scope Decision §2/§3 below name: client-side-computed charting inside `social-listening-admin`, using only data already available via `GET /v1/posts` + `enrichment`, with zero new backend aggregation.** Everything beyond that narrow scope — a stored `TopicDailyCount`-shaped aggregation, a dedicated analytics/reporting subsystem or service, server-side pre-computed rollups — remains exactly as deferred as ADR-0008 originally decided. `docs/adr/0008-defer-topic-time-series-and-charting.md` gains a dated "Pending supersession note" pointing to this ADR, per `docs/adr/README.md`'s own governance-table convention (row 5) — it does not edit ADR-0008's own Decision/Consequences text, and only takes effect if and when this ADR is accepted.

**`docs/design/frontend-design-specification.md` §10/§11 will need a corresponding update once this ADR is accepted — not made by this ADR.** §10's "Rich Analytics & Charting Dashboards... deferred" bullet needs narrowing to match the scope Decision §2 below actually ships; §11's "Not to be ported as code" framing for `docs/design/Gemini Designs/` stays correct (this ADR treats it as UX/layout reference only, per Decision §5) but its "covers screens explicitly deferred in §10" sentence will be stale once §10 is narrowed. Named here as required follow-up, not performed — per this task's own explicit instruction, this ADR does not edit that file.

### 2. Scope: which tabs and widgets ship in v1

**In scope for v1**, all computed from real data, no fabricated fallback of any kind:

- **Tab shell + global date-range filter**, reusing the already-drafted `GlobalDateRangePicker.tsx` (reviewed directly: a complete, non-fabricated component — real preset ranges, a real calendar, no static demo data anywhere in it). Filters the underlying `GET /v1/posts` query by `publishedAt`.
- **Overview tab** — a minimal KPI summary (total matched post count, sentiment split at a glance, source breakdown at a glance) reusing the same computed aggregates Decision §3 below defines once, not a novel widget of its own.
- **Sentiment tab** — sentiment donut split (positive/neutral/negative counts from real `enrichment.sentiment`), a real sentiment-over-time chart (bucketed by day from real `publishedAt` + `enrichment.sentiment`, replacing the prototype's fully-static `SENTIMENT_HISTORY`), Top Fans/Top Critics (real `author` + `enrichment.sentiment` aggregation, **no fallback to a hardcoded array when the real result set is small or empty — an empty state is required instead**, closing the exact defect named in Context), and positive/negative key-phrase clouds (real `enrichment.keyPhrases`, bucketed by the sentiment of the posts they appear on).
- **Conversations tab** — key-phrase word cloud and phrase-frequency-over-time chart, both from real `enrichment.keyPhrases` (replacing the prototype's fabricated `MAIN_PHRASES` fallback and fully-static `PHRASES_HISTORY` sine-wave data). **The prototype's `INTENTIONS` and `TAGS` widgets are explicitly excluded from v1** — no field in this project's real enrichment schema backs either concept (Context), and building them as static or fabricated placeholders would repeat the exact defect this ADR exists to close.
- **Sources tab** — post-volume and sentiment breakdown per real `providerId` (`gnews`, `newswire`, `tenant-owned-feed` — this project's actual three content connectors, not the generic social-platform roster the Google AI Studio reference assumes).

**Explicitly out of scope for v1, named rather than silently dropped:**

- **Location tab — deferred entirely, not built with fabricated or placeholder geo data.** See Decision §4.
- **"Explain the Spike" AI storytelling/root-cause narrative panels, live predictive forecasting/early-warning indicators, an interactive D3 topic-cluster/co-occurrence network graph, a real-time pulse-map/heatmap upgrade to Location, and 1-click executive PDF/slide export or automated action workflows (support-ticket creation, etc.)** — all five are speculative brainstorm content from `docs/design/frontend-design-future-devs.md`, an untracked file with no product decision behind it (confirmed: it opens with "Here is a strategic brainstorm... Recommended Next Step... Which of these directions resonates"). None of the five is decided, designed, or implied as future work by this ADR — they are named here only so a future reader doesn't mistake their presence in that file for existing scope.
- **Per-widget CSV/JSON export of aggregate data** (the prototype's `onExportWidgetData` affordance) — see the Author-rights standing check above and Open Questions.

### 3. Data source strategy: 100% client-side aggregation from existing `GET /v1/posts` + `enrichment`, no new backend work now

Every widget in scope (Decision §2) is computed in `social-listening-admin` from `SocialPostSummary[]` (`GET /v1/posts`, paginated) and its `enrichment`/`rawPayload.providerId` fields — the same data Story 6.11's post feed already fetches, just aggregated rather than listed. **No new `social-listening-core` endpoint, no new stored column, no new migration is authorized or required by this Decision.**

**This has a real, named cost, inherited directly from ADR-0008's own already-accepted trade-off, not newly discovered here:** accurately computing a tenant-wide aggregate (e.g. "sentiment split across all posts matching the current date range") requires paging through every matching post via `GET /v1/posts`'s cursor pagination — `MAX_PAGE_LIMIT = 100` per page, `listPosts()` in `core-client.ts` doesn't currently expose a caller-supplied page-size parameter at all. For a tenant with a large post volume, this means either many sequential round trips to compute one accurate aggregate, or accepting an approximation over only the most recent N pages within the selected range — a real scale ceiling this ADR does not resolve (Open Questions), the same one ADR-0008's Negative Consequences already named as the accepted cost of deferring server-side aggregation.

### 4. Location tab: not feasible for v1 — a named Open Question, not a narrow decision

**Decided: the Location tab does not ship in v1.** Two independent, both-disqualifying findings (Context): (1) no connector populates `post_geo_location` today — the column is schema-real but data-empty in practice; (2) even a populated column would not be visible to this dashboard's own data source, because `SocialPostSummary` (what `GET /v1/posts` returns) does not include `postGeoLocation` at all — only the single-post `SocialPostFull` fetch does. Building a Location tab against this would mean either fabricating geo data (the exact defect the current prototype already commits, `LocationDashboardTab.tsx`'s entirely-static `REGIONS`/`LANGUAGES`/hand-drawn world map) or silently showing an empty/misleading view. Neither is acceptable. This is left as Open Question 1, not designed further — revisit only once a real geo-data source exists (a future connector that actually carries location data, or a deliberate decision to widen `SocialPostSummary` and populate the column), per this project's own "don't build ahead of a demonstrated need" discipline (ADR-0020's precedent).

### 5. Styling and dependencies

**Vanilla CSS design tokens (`globals.css`, per frontend spec §3), not Tailwind — reaffirmed, not re-decided.** `docs/design/Gemini Designs/`/`Google AI Studio` remain UX/layout reference only, exactly as `frontend-design-specification.md` §11 already states — screens/tabs/widgets worth learning from, Tailwind markup not to be ported as code. The prototype components under `social-listening-admin/src/app/tenant/analytics/` already made the right styling choice (custom `ad-`-prefixed classes) but **no CSS backing those classes exists yet anywhere in `globals.css`** (Context, finding 2) — building that CSS block is real, non-trivial implementation work Story 8.1 inherits, not a rewiring exercise.

**Recharts is confirmed already a real dependency, not a new one.** `social-listening-admin/package.json` lists `"recharts": "^3.10.1"` under `dependencies` (checked directly this session) — no new charting library needs to be added for this ADR's scope. **`tailwindcss` (`^4.3.3`) and `autoprefixer`/`postcss` also already sit in `devDependencies`**, apparently left over from tooling used to browse/adapt the Google AI Studio reference — genuinely unused by the production app (which uses vanilla CSS per spec §3) and not removed by this ADR; named as a minor, low-priority cleanup item (Open Questions), not fixed here.

## Consequences

**Positive**
- Closes a real, previously-deferred gap at Menno's own direct request, using data this subsystem already captures — no new backend surface, no new stored aggregation, keeping ADR-0008's core cost-avoidance rationale (don't commit to an aggregation grain before a real consumer's requirements are known) fully intact.
- Replaces an already-started but broken/partially-fabricated prototype (non-existent `./types` import, undefined CSS classes, silent fake-data fallbacks, and two widgets — Intentions, Tags — with no real backing field at all) with an honestly-scoped v1 that has none of those defects.
- The three-connector "Sources" scope (`gnews`/`newswire`/`tenant-owned-feed`) matches this project's actual roster rather than inheriting the Google AI Studio reference's generic social-platform assumption, avoiding a dashboard that implies coverage this project doesn't have.
- `GlobalDateRangePicker.tsx` is confirmed reusable as-is — a real, complete component with no fabricated data, closing one of Story 8.1's pieces before it starts.

**Negative**
- **Client-side aggregation over paginated `GET /v1/posts` does not scale gracefully** — a tenant with a large post volume faces either many sequential page fetches to compute one accurate aggregate or an accepted approximation; this ADR does not resolve that ceiling, only names it (Decision §3, Open Questions).
- **The Location tab ships nothing in v1** — a real, visible gap against the Google AI Studio reference's own screen inventory, with no committed timeline to close it (Decision §4).
- **The Intentions/Tags widgets from the reference design are dropped entirely**, not adapted — a tenant familiar with the Microsoft Social Engagement-style reference mockup will not find an equivalent in this project's dashboard, because no underlying data supports one.
- **`src/lib/mockData.ts`/`types.ts` remain dead, already-committed, generically-themed code** this ADR does not clean up (Open Questions) — a real, if minor, standing confusion risk for a future reader who finds it and assumes it's live.
- **Per-widget CSV/JSON export (the prototype's `onExportWidgetData` affordance) is explicitly scoped out of v1** without this ADR deciding whether or how a future version should reconcile it with ADR-0039's already-governed tenant-level export mechanism — named, not resolved (Open Questions).

## Alternatives Considered

| Alternative | Disposition |
|---|---|
| **Client-side aggregation from existing `GET /v1/posts` + `enrichment`, zero new backend work** | **Chosen.** Matches ADR-0008's own explicitly-accepted deferral cost, ships fastest, requires no new `social-listening-core` contract, and keeps the "don't commit to an aggregation grain before real requirements exist" discipline intact. Real scale cost named honestly (Decision §3), not hidden. |
| **Build a `TopicDailyCount`-shaped server-side aggregation now, to remove the client-side scale ceiling** | Rejected for v1 — this is exactly what ADR-0008 declined to do speculatively, and nothing about this dashboard's real, current tenant scale (a solo-developer, pre-production project, per `CLAUDE.md`) demonstrates the need yet. Revisit if real usage shows the client-side approach is actually too slow in practice — a concrete, observable trigger, not a preemptive build. |
| **Ship the Location tab with the prototype's fabricated region/language/world-map data, clearly labeled as illustrative** | Rejected. This project's own established discipline (`Business-Case-v6.0.md` §8, cited in this role's own charter) never presents a fabricated figure as if real, even labeled — and a "sample data" watermark on a production tenant-facing screen is a worse experience than not shipping the tab at all. |
| **Widen `SocialPostSummary`/`GET /v1/posts` now to carry `postGeoLocation`, and add geo-population to at least one connector, to make Location shippable in v1** | Rejected for v1 — this is real, non-trivial `social-listening-core` scope (a backend API contract change plus new connector logic) with no demonstrated tenant need yet, and no connector in this project's real roster (news/wire/RSS sources) is an obvious geo-data carrier in the first place. Named as the real path to closing Open Question 1, not built speculatively now. |
| **Include the Intentions/Tags widgets as static or "coming soon" placeholders, matching the reference design's screen count** | Rejected. Directly repeats the exact defect (fabricated data with no visual distinction from real data) this ADR exists to close in the existing prototype. An honest "not available" is not the same failure mode as a fake number. |

## Open Questions

1. **Location tab's real data source and timeline — not designed here.** Decision §4 defers it entirely. Whoever eventually revisits this needs, at minimum: a real geo-data-carrying source (no connector in today's roster obviously has one), a `SocialPostSummary`/`GET /v1/posts` schema widening (a `social-listening-core` change, its own contract-first story), and a decision on whether that's worth building before a real tenant demonstrates the need.

   **Clarification (2026-08-17, ADR-0055).** [ADR-0055](0055-analytics-language-and-location-enrichment-feasibility.md) re-investigated this Open Question independently the same day, at Menno's own direct request, rather than assuming this ADR's conclusion still held. It reconfirms both disqualifying findings above unchanged, and surfaces one genuine new detail this ADR's own Context did not have: `GNewsArticle.source.country` is a real field, already spread unmodified into `rawPayload`, and therefore already wire-visible via `SocialPostSummary.rawPayload` with zero backend change. ADR-0055 names this and explicitly declines to treat it as a Location substitute — it covers only one of three real connectors, and reports the publisher's own declared country, not per-post or per-conversation geography. This is a Clarification, not a supersession: nothing in this ADR's Decision §4 or Consequences text changes as a result — see `docs/adr/README.md`'s own governance-table row 4.
2. **The client-side aggregation scale ceiling (Decision §3) is named, not resolved.** No specific tenant post-volume threshold is decided here as "the point where this stops being acceptable" — left to real usage to surface, per this project's own "don't build ahead of a demonstrated need" discipline.
3. **Per-widget export (`onExportWidgetData` in the existing prototype) — explicitly not decided.** Whether a future version of this dashboard should offer aggregate-data export at all, and if so, whether it reuses ADR-0039/Story 6.13's existing tenant-export mechanism or needs its own consent/disclosure treatment (per this role's standing author-rights check, Context), is left open. Not built in v1.
4. **`src/lib/mockData.ts`/`src/lib/types.ts` cleanup** — real, dead, already-committed code with generic (non-project) demo data. Named as a real follow-up for whoever picks up Story 8.1 or a future documentation/cleanup pass — not designed or actioned here (documentation-only ADR, no code changes).
5. **`tailwindcss`/`autoprefixer`/`postcss` in `social-listening-admin`'s `devDependencies`** — apparently unused leftover tooling from browsing the Google AI Studio reference. Removing them is a real, low-priority cleanup item, not decided or actioned here.
6. **`docs/design/frontend-design-specification.md` §5/§9/§10/§11 all need updates once this ADR is accepted** (a new Screen Inventory entry, a new Route Table row, §10's deferral bullet narrowed, §11's relationship note updated) — named as required follow-up, not performed by this ADR per explicit task scope.
7. **Exact date-bucket granularity for the sentiment-history and phrase-history time-series charts (Decision §2)** — daily is assumed as the natural default (matching ADR-0008's own original "mentions of X per day" framing), but the exact bucket size, timezone handling, and behavior for a date range spanning many months is left to Story 8.2/8.3's own implementation-time judgment, not fixed here as a durable decision.
