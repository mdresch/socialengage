# ADR-0059: Facebook connector — narrowed to a tenant's own connected Page (Standard/Advanced Access), organization-as-Author modeling; genuine public-content social listening found not viable

**Status: Accepted (2026-08-18)** — drafted by the AI Business & Requirements Analyst persona, left Proposed per this persona's own charter boundary (it does not hold ADR-acceptance authority), then reviewed and approved by Menno (Sponsor) the same day, verbatim: *"Approved ADR 0059 Facebook Connector is approved."* Accepted as revised — both review-round amendments (the Tier 3 credential-tier correction and the three review-round additions: App Review discretionary-rejection risk, the hard "Facebook Page (Owned Feed)" naming constraint, and the "reconnect required" silent-failure health state) are in effect. See Amendment Log.
**Source:** `docs/open-decisions.md`'s 2026-08-06 connector-comparison entry (the Meta bullet), which left two propositions explicitly unequally verified: Standard Access for a tenant's own Page ("confirmed easy, free, no-App-Review") versus genuine public-content social listening ("not yet confirmed either way... typically gated behind a separate Marketing Partner relationship, not ordinary app review"). This ADR's job, per that entry's own framing and per this project's established connector-ADR discipline (ADR-0024, ADR-0026, ADR-0042), is to verify both propositions directly against Meta's own current developer documentation before drafting a decision — not to draft from the prior entry's own secondary-sourced language. **One correction results: the "no-App-Review" half of the prior claim does not survive verification for a real multi-tenant SaaS product — see Decision §3.**

## Context

Every connector this project has shipped or drafted so far (Newswire, GNews, Wikipedia, tenant-owned-domain feed) shares one property: a tenant (or the connector itself, for Newswire/Wikipedia's keyless access) independently obtains a credential or needs none at all, with no gate operated by SocialEngage itself in between. ADR-0027 formalizes this as a durable rule — SocialEngage is a technical intermediary, never a contracting party. ADR-0028 names a Company Page / multi-admin Group as its own worked example of a Tier 2, tenant-wide credential, without having verified Meta's actual access model at the time it was drafted (2026-08-03) — that verification is this ADR's job, not something ADR-0028 itself performed.

`docs/open-decisions.md`'s 2026-08-06 connector-comparison entry researched Reddit, X, YouTube, Meta, and Wikipedia against this project's own evaluation discipline. Its Meta bullet, verbatim: *"confirmed easy, free, no-App-Review access exists for managing a tenant's own Page/account ('Standard Access'). Not yet confirmed either way: whether Meta's API supports the actual social-listening use case (searching/monitoring other people's public posts) at all... typically gated behind a separate Marketing Partner relationship, not ordinary app review."* Wikipedia was drafted first (ADR-0042) because it was better-grounded at the time; Meta was left as real, sourced groundwork, not yet a decision.

This ADR performs that verification directly against `developers.facebook.com` (Meta's own developer documentation — Graph API reference, Page Public Content Access / Page Public Metadata Access feature pages, Permissions Reference, Business Verification requirements, Webhooks for Pages, Access Token Guide, Rate Limiting overview) and `developers.facebook.com/terms` (Meta Platform Terms), fetched directly in this drafting pass, 2026-08-18 — the same primary-source bar ADR-0024/0026/0042 held themselves to after RTPR's, Currents API's, and (initially) Reddit's own claims failed to survive direct verification.

## Decision

**The durable decision — this is what would need superseding, not just amending:**

### 1. Feasibility finding — genuine public-content social listening is not buildable against Meta's current API for a project at this scale

Verified directly, 2026-08-18:

- **Page Public Content Access (PPCA)** — the Graph API feature closest to "read public content on Pages you don't administer" (`developers.facebook.com/docs/features-reference/page-public-content-access`) — requires, per its own stated text: (a) *"successful completion of the App Review process before your app can access live data"*; (b) *"only available with business verification. You may also need to sign additional contracts before your app can access data"*; and (c) during development, testing is restricted to *"a Page for which... the person who holds the admin role for the Page also holds an admin, developer, or tester role on the app"* — i.e., an app cannot even be tested against a Page it doesn't already have a relationship with, before App Review is cleared. The allowed-usage statement is *"analyze and/or display posts and engagement on Pages"* — the doc names no explicit prohibition on monitoring pages a requester doesn't own, but names no explicit permission for it either, and the "additional contracts" language is Meta's own signal that self-service alone may not be the actual path even after App Review.
- **No general keyword-search/discovery surface exists.** PPCA is a per-Page content-retrieval feature — it returns data for specific Pages an app already identifies by ID, not a search across the platform's public Page/post corpus. Meta's own current Graph API reference and "Using Graph API" overview pages, fetched directly, describe no keyword-search-across-public-content capability. This is corroborated (secondary-sourced, named as such, not primary-verified further than this) across multiple independent, current (2026) third-party developer guides and community threads: Facebook's original Graph Search and its `/search?type=page` public-content search surface are consistently reported as deprecated since the platform's 2018–2019 lockdown, with no live replacement documented anywhere in Meta's own current reference pages this pass could find. **This is the load-bearing fact, independent of approval odds:** even a hypothetically-approved app has no endpoint to run a watchlist's "find public posts matching this query" against — the mechanism every other connector in this project's roster (Newswire, GNews, Wikipedia) is built around does not exist on Facebook's current API surface at all.
- **Corroborating context (secondary-sourced, named as such).** Meta discontinued its own free social-monitoring tool, CrowdTangle, in August 2024. Multiple independent reports (Nieman Lab, CJR, Mozilla Foundation's own open letter, Meta's own public communications) describe Meta directing commercial monitoring use cases toward established, already-contracted third-party paid platforms — Meltwater, Hootsuite, Sprout Social, Cision, NewsWhip — rather than toward ordinary App-Review-gated self-service access, while its direct first-party academic successor, the Meta Content Library, is documented as restricted to nonprofit researchers and explicitly excludes for-profit companies. This does not, by itself, prove PPCA is closed to a project like this one, but it sharpens `docs/open-decisions.md`'s own prior "typically gated behind a Marketing Partner relationship" flag from plausible to well-corroborated: the platform's own behavior since 2018 has been to concentrate general public-content monitoring in a small set of established, contracted vendors, not to leave it as an ordinary self-service App Review outcome.

**Conclusion:** genuine social listening — a watchlist discovering public Facebook posts about a topic from accounts/Pages a tenant does not own — is not buildable today against Meta's ordinarily-accessible API surface for a self-funded, solo-operated project. This is the same category of finding as ADR-0024's RTPR reversal (a real, verified access wall, not an assumption) and ADR-0042's Reddit de-prioritization (real friction found, addressed by scoping down or elsewhere, not forced through).

### 2. Scope decision — narrow the connector to the tenant's own connected Page, posts only, at v1

Per this project's own precedent for exactly this situation (ADR-0024 dropped RTPR for a narrower, verified-viable path; ADR-0042 deprioritized Reddit in favor of a better-grounded alternative), **do not build a "Facebook connector" in the sense the rest of this project's roster uses that phrase.** Recommend instead a materially narrower connector, scoped to what Meta's own Standard/Advanced Access model actually and confirmedly supports: a tenant's own connected Facebook Page's **own posts**.

- **v1 scope:** ingest the tenant's connected Page's own published posts (`GET /{page-id}/feed` or `/posts`) as `SocialPost` rows, including whatever engagement counts (reactions, comments, shares) the Page-feed response returns. No comment ingestion, no mention/tag discovery at v1 — see the explicit, named reason in Decision §5.
- **Value proposition, stated honestly, not oversold:** this does not discover anything new about a tenant from outside sources the way Newswire/GNews/Wikipedia do. It gives a tenant a consolidated, single-pane record of their own Facebook Page's own published content and its engagement metrics, alongside every other connector's genuinely-discovered content — closer in kind to an owned-channel content mirror than to this project's other connectors' discovery function. Any story or UI copy built against this ADR must say "your own connected Facebook Page," never an unqualified "Facebook," to avoid misrepresenting what ships — the same "name it honestly, don't force a mismatched label" discipline ADR-0026 applied to "RSS/News" naming a category, not a literal RSS feed.
- **This naming discipline is a hard implementation constraint, not a stylistic suggestion — strengthened at review.** The connector-selection UI, the connected-connector list, and any settings screen referencing it must never render the bare platform name "Facebook" as this connector's label — the recommended default display name is **"Facebook Page (Owned Feed)"**, or an equivalent that names both the platform and the owned-content-only scope in the same label, not just in a tooltip or a details page a tenant might not read. This default is adjustable (logged in this ADR's own Amendment Log, doesn't require superseding), but the *principle* — the label itself, not just the surrounding copy, must disclose the scope — is binding on whichever story implements Story 6.3-equivalent UI work for this connector, per Decision §3's own "add a standard, consistent disclosure pattern" open question in `docs/open-decisions.md`.

### 3. Access-gate finding — App Review + Business Verification are required even for this narrowed scope; corrects `docs/open-decisions.md`'s prior claim

**This is a real correction, not a refinement, of `docs/open-decisions.md`'s 2026-08-06 claim that Standard Access is "no-App-Review."** Verified directly, `developers.facebook.com/docs/development/release/business-verification`: *"Apps that request advanced access for permissions and apps that allow other Businesses to access their own data must be connected to a Business that has completed Business Verification"* — with one named exception: *"If your app will only be used by app users who have a role on the app itself you do not need to complete verification."*

A real tenant connecting their own Facebook Page is, by definition, **not** a person holding a role on SocialEngage's own registered Meta App — they are an unaffiliated third party. That means SocialEngage's own Meta App (a single, project-level app registration this ADR's connector would require, distinct from anything any prior connector needed) must obtain **Advanced Access** for whatever Page permissions it needs (`pages_show_list`, `pages_read_engagement`, and — if the future push-webhook path in Decision §4 is ever built — `pages_manage_metadata`), which requires: (a) SocialEngage's own App being connected to a Business that has completed Meta's Business Verification, and (b) App Review, permission-by-permission, each justified with a working demo. **The prior "no-App-Review" framing was accurate only for the degenerate case Meta itself names — a Page administered by the app's own developers/testers** (i.e., Menno's own test Page) — not for onboarding any real, unaffiliated tenant, which is this connector's actual purpose. `docs/open-decisions.md`'s Meta bullet is corrected in place with a dated note pointing here (see that file).

**A further, real precondition named honestly rather than assumed satisfied:** Meta's own Business Verification process (verified via multiple current third-party guides, not Meta's own formal terms directly in this pass — flagged as secondary-sourced) requires documentation showing "the business as the account holder... not an individual's name," even for a sole proprietorship. Whether this project — described in `CLAUDE.md` as a solo-developer, self-funded personal project — has, or can readily obtain, whatever business documentation Meta's process actually requires is **not confirmed by this ADR** and is named as a real, concrete precondition to check before committing to build this connector at all, not after.

**A second, distinct risk beyond documentation alone, raised at review and worth naming explicitly rather than folding into the paragraph above: App Review approval is a discretionary human judgment call, not a mechanical documentation check.** Clearing Business Verification does not itself guarantee `pages_read_engagement`/`pages_show_list` get approved — Meta's own App Review process for these permissions typically requires a screencast demonstrating a real user authenticating and real data being retrieved by a live, production-grade use of the app, and reviewer practice (secondary-sourced, not verified to this project's own primary-source bar in this pass) is reported to weigh an app's track record and apparent production-readiness, not just whether its stated use case is technically permitted. A solo-developer project with no existing user base or commercial track record carries real, unquantified rejection risk at this step — distinct from, and additional to, the Business Verification documentation question above. Not confirmed either way by this ADR; named as a second concrete precondition to weigh before committing engineering time, not a formality nested inside the first.

**This is a materially different shape from every prior connector.** GNews (each tenant's own API key, registered directly with GNews, no SocialEngage-level registration), Newswire and Wikipedia (no account of any kind, for anyone) all needed zero involvement from SocialEngage itself as an entity known to the data source. This connector requires SocialEngage to register itself as a Meta developer/App, complete Business Verification, and pass App Review — a one-time, project-level administrative step, not a recurring or per-tenant one, and not a paid one, but a real gate this ADR names plainly rather than smoothing into "same as the others, just OAuth instead of an API key." See the Note on relation to ADR-0027/ADR-0028 below for why this does not, however, make SocialEngage a contracting party in the tenant's own relationship with Meta.

### 4. authMode / deliveryMode / credential tier — Tier 3 (user-bound) only, no Tier 2 path

**Revised 2026-08-18, during review, before acceptance.** Menno's direct instruction, verbatim: *"only the user accounts please"* — clarified on follow-up as: restrict this connector's `platform_credentials` ownership to **Tier 3 (user-activated, user-bound) only, per ADR-0028 §3 — no Tier 2 tenant-wide credential path at all.** The rest of this Decision (§4 below) is revised accordingly; the content scope decided in §2 (a Page's own posts) is unaffected — see the explicit reasoning below for why.

- `authMode: 'oauth'` — Facebook Login for Business, exchanged for a long-lived Page access token. Verified directly (`developers.facebook.com`'s Access Token Guide): a long-lived Page access token, generated from a long-lived user token, *"can be set to never expire"* — simpler rotation than a typical 60-day OAuth refresh cycle, though a documented re-consent path is still needed for the real cases that can invalidate it (password change, permission revocation, Page-admin change, the connecting individual revoking the grant, or the Page removing SocialEngage's App) — an implementation-time concern, not designed here. **If built, this would be the first connector in this project's shipped roster to actually exercise `authMode: 'oauth'`** — Newswire and Wikipedia use `'none'`, GNews uses `'apiKey'`, and Reddit (the only other OAuth-shaped candidate on record) remains unbuilt — closing a real, still-open gap in ADR-0002's "the abstraction generalizes across every auth mode" claim.
  - **A named consequence of that invalidation list, strengthened at review: every one of those triggers produces a silent failure state, not a loud one, unless the connector design explicitly accounts for it.** None of password change, Page-admin removal, or grant revocation notify SocialEngage synchronously — the poller's next call simply starts receiving Meta API authorization errors (or, per this section's own Tier 3 finding above, stops having anyone able to re-authorize on the tenant's behalf at all). Without an explicit check, this degrades identically to `ConnectorHealth`'s (ADR-0009) ordinary derived-failure signal — but a tenant seeing "connector unhealthy" for a rate-limit blip and a tenant seeing it because their own Page admin revoked access are different problems needing different tenant-facing language. **This ADR recommends the connector's health-derivation surface a distinct, named state (e.g. "Facebook connection expired — reconnect required") for this specific failure class, not just the generic unhealthy/failing state every other connector already reports** — an implementation-time addition to `deriveConnectorHealth()` (ADR-0009), not a new ADR-level decision, since ADR-0009 already establishes health as fully derived from `IngestionRun` history and this is a refinement of what gets derived, not a new storage or architecture decision.
- **Credential tier: Tier 3, user-bound, activated only by the connecting individual's own act — never created by Tenant-Admin, per ADR-0028 §3.** This is not a mechanical relabeling of this ADR's original Tier 2 draft — it is checked directly against Meta's own OAuth grant mechanics, and holds up structurally, not merely as Menno's stated preference (see the reasoning immediately below and the "Note on relation to ADR-0028" for the full argument):
  - **Meta's Graph API has no organizational/app-only grant for ordinary Page access, unlike Reddit's.** Every Page access token this connector could use is *derived from* a specific individual's own long-lived User access token (verified directly, `developers.facebook.com`'s Access Token Guide) — there is no equivalent of Reddit's `client_credentials`/`installed_client` "userless" grant (ADR-0028's own corrected Reddit worked example) for a standard Page-connect flow. A separate "System User" token does exist, but only inside a Meta Business Manager, requiring the connecting Business to already operate one and SocialEngage's own App to be installed there with Ads-Management-API-tier access or above (verified directly, `developers.facebook.com`'s Business Management APIs docs) — a materially heavier, Marketing-API-adjacent onboarding path, not an ordinary self-service Page connect; considered and rejected as the alternative "make it Tier-2-shaped after all" path — see Alternatives Considered. **Structural consequence:** at the mechanical credential level, a Facebook Page connection was always going to authenticate through one specific person's own OAuth grant — classifying it as Tier 2 in this ADR's original draft mechanically reused ADR-0028's own worked example (*"company pages, groups with multiple admins"*) without checking it against Meta's actual grant shape, the same category of error ADR-0028's own first-drafted Reddit example made in the opposite direction (assumed Tier 3, corrected to Tier 2 once Reddit's real app-only grant was found). Here the correction runs the other way: assumed Tier 2, corrected to Tier 3 once Meta's lack of an app-only grant was checked.
  - **This does not force a pivot to monitoring the connecting individual's own personal profile instead of the Page — checked explicitly, not assumed.** ADR-0028 §3's own worked example for Tier 3 is "an individually-issued account... personal pages, which remain private to the users," which could be read as implying Tier-3-only pushes this connector toward an individual's personal timeline. It does not, for two independent reasons: (1) Meta's own OAuth-then-Page-token flow lets one person's User access token request access to Pages *that person administers* (`/me/accounts`) without that access itself being "personal" content — the credential is personally held, but what it grants access to is still the Page, an organizational asset; (2) direct third-party personal-timeline read access was itself heavily restricted after 2018 (`publish_actions` and broad personal-post read scopes deprecated), so pivoting to an individual's own profile posts would not even be a more-open path than the Page. **Conclusion: the content scope from Decision §2 (a Page's own posts) is unchanged — only who may create and hold the connecting credential changes.**
  - **A real, new operational consequence this correction introduces, named plainly:** because only Tier 3 is permitted, only the specific individual within a tenant who personally administers the target Page on Facebook can activate this connector — per ADR-0028 §3, *"neither Tenant-Admin nor Platform Admin may create or activate a user-bound credential on a user's behalf."* If that individual leaves the tenant, is removed as a Page admin on Facebook, or revokes the OAuth grant, ingestion stops with no tenant-wide credential to fall back on, and re-activation requires another individual who also administers the Page to personally connect it again — Tenant-Admin has no path to do this on the team's behalf. This is a real trade-off Tier 2 would have avoided; accepted here as the cost of Menno's instruction, named rather than hidden — see Consequences.
  - **Harvested content stays ordinary tenant-wide data despite the personally-held credential — reusing an already-established precedent, not inventing a new rule.** ADR-0028's own 2026-08-03 Clarification, drafted for Reddit's structurally identical situation, states this exactly: *"credential tier governs credential ownership, not harvested-data visibility... public [posts] polled via one user's personal, self-activated... connection (tier 3) are intended to come into the tenant-wide watchlist review, the same as every other connector's harvested content."* This connector's Page posts, once ingested via ADR-0004/0005/0015, are ordinary tenant-scoped `SocialPost` rows like any other connector's output — the Tier-3 credential does not narrow visibility to only the activating user.
- `deliveryMode`: recommend **`'poll'` for v1**, matching every other connector's shape and simpler to build first. **A real, confirmed-feasible `'push'` path exists as a named v2 enhancement, not designed here:** Meta's Page Webhooks (verified directly, `developers.facebook.com`'s Webhooks-for-Pages doc) let a Page's own app receive real-time `feed` updates, requiring `pages_manage_metadata` + `pages_show_list`, a Page access token from someone holding `CREATE_CONTENT`/`MANAGE`/`MODERATE` on the Page, and the Page itself installing the app via its `subscribed_apps` edge — restricted to pages the app administers, consistent with this connector's narrowed scope, and unaffected by the Tier 3 correction (the same individually-held Page token that would poll is also the one that would authorize a webhook subscription). Would be this project's first genuine push-mode connector if ever built (ADR-0023's own still-open "does failure-threshold behavior vary by `deliveryMode`" question would finally get a real second data point).
- `getRateLimitConfig()`: verified directly (`developers.facebook.com`'s Rate Limiting overview) — the Pages API ceiling is **4,800 × the Page's own Engaged Users, per rolling 24-hour window** — a real, confirmed, published ceiling (unlike Newswire's/Wikipedia's unconfirmed placeholders), but relative to the Page's own engagement rather than a flat number, unlike every other connector's ceiling, and unaffected by which credential tier authenticates the calls. Needs its own `getRateLimitConfig()` shape at implementation time, not a drop-in reuse of GNews's/Newswire's pattern.

### 5. Author modeling — the tenant's own Page, a fourth instance of ADR-0004's already-generalized organization-as-Author clause; comments/mentions explicitly deferred over a real, unresolved author-rights question

**Argued explicitly, per this ADR's own task, not assumed identical to prior instances or dismissed as obviously different (the way ADR-0042 argued Wikipedia's distinct case):** a Facebook Page is squarely the shape ADR-0004's 2026-08-11 "Organization-as-Author clause" already generalizes — *"organization, publication, or verified domain... the party responsible for producing the content, not a person who authored it in the ordinary sense."* Graph API's own Page-post `from` field returns the Page, not whichever individual admin clicked "post" — organization-as-Author is Facebook's own data model here, not an interpretation imposed on it. `Author.externalAuthorId` = the Page's own `id`; `Author.handle`/`displayName` = the Page's name. **Per the existing clause's own stated purpose — "a future connector with this shape may cite this clause directly... rather than adding its own one-off Pending-supersession note to [ADR-0004]" — no new note on ADR-0004 is needed.**

**One real, minor divergence from every prior organization-as-Author instance, named rather than silently matched:** Newswire, GNews, Wikipedia, and the tenant-owned-domain connector all leave `Author.followerCount` unpopulated ("not a meaningful attribute for a non-individual entity"). A Facebook Page genuinely has a follower/fan count Meta's own API returns — this connector is the first organization-as-Author instance where populating `followerCount` is both possible and meaningful. This doesn't change the clause; it's a data-availability difference worth recording so a future reader doesn't assume every organization-as-Author connector leaves the field null as a rule rather than as a per-connector fact about what the source returns.

**Comments/mentions are a structurally different case, deliberately not included at v1 — this is the standing author-rights check this role applies to every connector touching authored content, applied here explicitly.** A public comment on a tenant's own Page post is authored by an identifiable individual Facebook user — Graph API's comment objects return that person's own `id`/`name`. That is not an instance of the organization-as-Author clause at all; it would be the first real production case of ADR-0004's *original*, individual-account default, and the first connector in this project to ingest identifiable personal data of a genuine third party who has no relationship with the tenant or with SocialEngage and did not consent to being tracked by a monitoring product. Meta's own Platform Terms §3.a.viii (verified directly, `developers.facebook.com/terms`) prohibit *"processing Platform Data for purposes other than the applicable permitted purposes"* Meta's own documentation specifies — whether "ingest into a tenant's social-listening watchlist" is a permitted purpose for comment-level personal data has not been checked. **This ADR does not decide that question and does not include comment ingestion in v1 because of it.** Per this role's standing charter, name what the design should provide if this is ever built (attribution preserved — the commenter's own name/handle, never reassigned to the tenant or SocialEngage; a consent-checkpoint analysis before ingestion, not after) without certifying legal sufficiency, which stays outside an ADR's own competence — flagged for a dedicated `docs/legal/legal-compliance-register.md` pass before any v2 comment/mention design, not decided here.

### 6. Watchlist matching, and Meta's Platform Terms on retention/reselling

Per Decision §1, no native search/query surface exists — `supportedQueryFeatures` (ADR-0021) is empty. Matching is 100% ADR-0006 post-fetch fallback against the Page's own post text, structurally identical to Newswire's and Wikipedia's own minimal-native-support treatment, not a new pattern.

Meta Platform Terms, verified directly (`developers.facebook.com/terms`):
- §3.a.iv: *"Selling, licensing, or purchasing Platform Data"* is prohibited — consistent with, not in tension with, ADR-0027's already-Accepted "no reselling" posture.
- §3.d.i: developers must delete Platform Data *"as soon as reasonably possible"* when, among other triggers, *"a User requests their Platform Data be deleted or no longer has an account with you,"* and must give users *"an easily accessible and clearly marked way to ask for their Platform Data to be modified or deleted."* This is the same category of tension with ADR-0018's tiered-retention design that Reddit's own 48-hour deletion-propagation rule creates (`docs/open-decisions.md`'s 2026-08-06 Reddit finding) — softer-worded here ("as soon as reasonably possible" vs. a fixed 48-hour window) but real, and not resolved by this ADR.

## Consequences

**Positive**
- Closes `docs/open-decisions.md`'s Meta bullet with a real, primary-source-verified answer instead of leaving it as unconfirmed groundwork — the same rigor bar ADR-0024/0026/0042 already established for this project's connector ADRs.
- Gives ADR-0028's own worked example (Company Page / multi-admin Group) a real, verified, buildable connector instead of only a hypothetical illustration — and corrects, in the process, two claims ADR-0028's own drafting never checked: whether onboarding a real tenant's Page needs App Review at all (Decision §3), and whether the example actually grants at Tier 2 once Meta's real OAuth mechanics are checked (Decision §4 — it doesn't; see the revised "Note on relation to ADR-0028" below).
- If built, would be this project's first connector to actually exercise `authMode: 'oauth'`, and names a real, confirmed-feasible first `deliveryMode: 'push'` candidate (deferred to v2) — both close named gaps in ADR-0002's own "the abstraction generalizes across every mode" claim.
- Reuses ADR-0004's already-generalized organization-as-Author clause with zero new Pending-supersession note required — a real, low-friction confirmation that the 2026-08-11 generalization is working as intended for a fourth instance.
- Honestly narrows scope rather than forcing an unqualified "Facebook connector" through that cannot do what a listening product needs — the same discipline as ADR-0024's RTPR reversal and ADR-0042's Reddit de-prioritization, applied here for the first time to a case where the *narrower* alternative is still worth building, not abandoned outright.

**Negative**
- **Does not deliver genuine social listening — the headline trade-off, not a footnote.** Nothing about this connector lets a tenant discover what the broader public is saying about them on Facebook, the actual product need "Facebook connector" implies elsewhere in this project's roster and design spec. Any story or UI copy built from this ADR must say "your own connected Page," not "Facebook," or it misrepresents what ships.
- **A real, one-time, project-level App Review + Business Verification gate applies even to this narrowed scope** (Decision §3) — a materially higher up-front bar than any prior connector, and one whose feasibility for this specific project (documentation, business-entity status) is not confirmed by this ADR. **Beyond documentation, App Review approval itself is a discretionary human review, not a mechanical check** — a solo-developer project with no production track record carries real, unquantified rejection risk distinct from the Business Verification question, named in Decision §3 and Open Questions.
- **Every credential-invalidation trigger named in Decision §4 (password change, Page-admin removal, grant revocation) produces a silent failure by default** — the connector needs an explicit, distinctly-labeled "reconnect required" health state (Decision §4), not just the generic unhealthy signal every other connector already reports, or a tenant has no way to tell a revoked Facebook grant apart from an ordinary rate-limit blip.
- The public-content-monitoring-is-effectively-closed finding rests partly on secondary-sourced corroboration (CrowdTangle's shutdown, Meta's own vendor pointers), not a single first-party policy statement saying "closed to projects this size" — a narrow possibility remains that a direct approach to Meta's Marketing API Partner program could change this; not pursued further in this pass.
- Comment/mention ingestion — the part of "own-Page monitoring" that would actually resemble listening (what people say in reply) — is deliberately deferred, not designed, because of the real, unresolved third-party personal-data/author-rights question in Decision §5.
- The Page-engagement-relative rate-limit shape (4,800 × Engaged Users) needs its own `getRateLimitConfig()` design, not a drop-in reuse of any existing connector's pattern.
- OAuth token lifecycle/re-consent handling is new, first-of-its-kind build work for this project — every shipped connector to date uses `'none'` or `'apiKey'`.
- Meta's Platform Terms retention language creates the same category of tension with ADR-0018 that Reddit's 48-hour rule does, though softer-worded — named, not resolved.

## Alternatives Considered

- **Build the full "search/monitor any public Facebook content" connector as the roster's "Facebook connector" entry originally implied** — rejected. Per Decision §1's primary-source verification, no such API surface is available to a general-purpose app today; building toward it would misrepresent what ships and cannot be built regardless.
- **Defer Facebook entirely, the same treatment ADR-0042 gave Reddit** — considered, rejected. Unlike Reddit (where even the narrower Standard-Access-shaped path carries real, still-unverified commercial-use/approval-process risk per ADR-0028's own flagged open question), Meta's Page-management access for a tenant's own Page is confirmed, verified, and viable, modulo the App Review/Business Verification gate named in Decision §3 — a real, if narrower-than-hoped, connector is worth building here, not nothing.
- **Include comment/mention ingestion in v1** — rejected. The third-party personal-data/author-rights question in Decision §5 is real and unresolved; shipping it without that analysis would risk silently ingesting an unconsenting third party's identifiable data, the exact failure mode this role's standing author-rights check exists to catch.
- **Model `Author` as the individual admin who published the post, rather than the Page** — rejected. Graph API's own Page-post data model attributes posts to the Page (the `from` field returns the Page), not to whichever admin clicked "post" — organization-as-Author is the natural fit Facebook's own API already provides, not an interpretation this ADR imposes.
- **Pursue Meta's Marketing API Partner program directly, to unlock genuine public-content monitoring** — not pursued in this pass; named in Open questions as a real, unexplored option, distinct from and more involved than ordinary App Review.

## Note on relation to ADR-0027 (Accepted, 2026-08-01)

**This connector's OAuth model does not make SocialEngage a party to, reseller of, or intermediary in any tenant's own relationship with Meta — the same conclusion ADR-0024's and ADR-0042's own relation notes reached for their respective keyless models, argued explicitly here rather than assumed, because this connector's shape is genuinely different from theirs in one respect worth naming precisely.** Each Page access token remains the connecting individual's own credential (Tier 3, ADR-0028, per Decision §4) — not pooled, not shared, not something SocialEngage holds on their behalf; that individual's own act of clicking "Authorize" is their own acceptance of whatever Meta requires of them as a Page administrator, exactly as ADR-0027 requires. ADR-0027's "no pooling" rule is agnostic to which tier the credential lands in — it constrains SocialEngage's own conduct toward whoever holds the credential, not the tier classification itself.

**What is genuinely different here, and worth stating precisely rather than glossing over:** unlike GNews (each tenant registers their own account and key directly with GNews, with zero involvement from any SocialEngage-registered entity) or Newswire/Wikipedia (no account, for anyone), this connector requires SocialEngage itself to register one Meta Developer App, complete Business Verification for it, and pass App Review — a real, direct, project-level relationship between SocialEngage and Meta, binding SocialEngage to Meta's Platform Terms as the App's own operator. **This is not a violation of ADR-0027.** ADR-0027 prohibits SocialEngage becoming a party to *the connecting party's own relationship with a data source* (their credential, their billing, their liability for their own terms violations) — it does not, and could not, prohibit the ordinary technical fact that any OAuth-based connector requires the software itself to be registered with the platform it speaks to, the same way any "Sign in with X"-style integration anywhere requires a registered OAuth client. SocialEngage registering its own App is SocialEngage operating its own technical infrastructure (the same category ADR-0028 §1 already places Postgres/Key Vault/Service Bus in, not the connecting party's own external relationship) — it is not billing, reselling, or holding liability on any tenant's behalf, and each tenant still independently authorizes, and remains solely responsible for, their own Page's own use of that access. **Named explicitly here because it is a real, first-of-its-kind degree of project-level commitment this connector requires that no prior connector did — not because it changes ADR-0027's own Decision, which it does not.**

## Note on relation to ADR-0028 (Accepted, 2026-08-03)

ADR-0028 names *"company pages, groups with multiple admins"* as its own worked example of a Tier 2, tenant-wide credential, without having verified Meta's actual access requirements at the time — that verification was never ADR-0028's own job, and this note does not fault it for not performing one. **This ADR's own verification finds that example does not hold for Facebook specifically, once Meta's actual OAuth grant mechanics are checked (Decision §4):** every Page access token is derived from one specific individual's own long-lived User access token; no app-only/organizational grant exists for an ordinary Page-connect flow (a separate Business Manager "System User" path exists but requires a materially heavier onboarding this ADR does not recommend — see Decision §4 and Alternatives Considered). Mechanically, this connector was always going to authenticate through one person's own OAuth grant — Tier 3, not Tier 2, per ADR-0028 §3's own operative test (who creates/activates the credential), not per its illustrative Page/Group example. **Also revised 2026-08-18, during review, before acceptance:** Menno directly instructed this connector be restricted to Tier 3 only ("only the user accounts please") — this note's finding above independently supports that instruction on structural grounds, not merely deference to it; see Decision §4 for the full argument, including why this does not push the connector's *content* scope toward an individual's personal profile (it still ingests the Page's own posts). **This does not change ADR-0028's own Decision or Consequences text.** It does correct, for the record, the assumption implicit in ADR-0028's own Page/Group worked example — the same category of in-place correction ADR-0028's own Amendment Log already made once for its first-drafted Reddit example (assumed Tier 3, corrected to Tier 2 once Reddit's real app-only grant was found); here the correction runs the other way (assumed Tier 2 by association with the example, corrected to Tier 3 once Facebook's actual grant shape was checked). Per this project's own governance table (`docs/adr/README.md`), this is a genuine "Note on relation" — it doesn't reopen or supersede ADR-0028's own Tier 2/Tier 3 framework, only records that this specific connector, once checked, lands in Tier 3 rather than illustrating Tier 2 as its own drafting first assumed.
