# ADR-0042: Wikipedia connector — MediaWiki API, revision re-poll cadence, article-as-Author modeling

**Status:** Proposed — drafted 2026-08-06 by the AI Business & Requirements Analyst persona. Left Proposed per this persona's own charter boundary; only Menno, as Sponsor, holds ADR-acceptance authority (same rule ADR-0024/0026/0027/0028 followed).
**Source:** Not specified in the design spec — spec §10's platform roster does not name Wikipedia at all. This ADR originates from `docs/open-decisions.md`'s 2026-08-06 dated connector-comparison entry (prompted by Reddit's own real access friction, found the same day — see that entry and its Reddit sub-bullet), which found Wikipedia the best-grounded of four researched alternatives (X, YouTube, Meta, Wikipedia). It also resolves, as its own Decision, an ingestion-cadence question the Knowledge-Graph & Semantic Data Modeling Reviewer explicitly declined to resolve on 2026-08-06 (`docs/architecture/knowledge-graph-register.md`, "Wikipedia connector authorship" entry) — see Context and Decision below.

## Context

`docs/open-decisions.md`'s 2026-08-06 connector-comparison entry vetted Reddit, X, YouTube, Meta, and Wikipedia against this project's own established evaluation discipline (ADR-0024/0026's primary-source verification bar, ADR-0027's technical-intermediary-only posture). Reddit — the informally "next" connector per `docs/implementation-plan.md`'s Phase 1 note — was found to have closed self-service registration since late 2025 (approval-gated, "slow and often silent" for commercial use per community reporting) and a 48-hour content-deletion-propagation obligation that does not fit ADR-0018's/ADR-0039's current retention design. X requires a paid tier with no free path at all. Meta's actual social-listening capability (monitoring *other* accounts' public posts, not a tenant's own Page) is unconfirmed either way. Wikipedia came back clean on every axis this project actually screens for.

**Verified directly against Wikimedia's own primary sources, 2026-08-06** (not secondhand — every claim below was fetched from `foundation.wikimedia.org`, `meta.wikimedia.org`, or `mediawiki.org` directly, the same discipline ADR-0024/0026 held themselves to after RTPR's and Currents API's claims failed to survive direct verification):

- **Self-service, no approval gate.** The Wikimedia Foundation's own API Usage Guidelines (`foundation.wikimedia.org/wiki/Policy:Wikimedia_Foundation_API_Usage_Guidelines`) state directly: *"the existence of this policy does not require members of the Wikimedia community to get prior permission from the Wikimedia Foundation before using the APIs in a manner consistent with this policy."* No account, no API key, no developer application review — a materially different posture from Reddit's now-closed registration.
- **Commercial reuse explicitly permitted.** The Foundation's Terms of Use §7 ("Licensing of Content"), fetched directly: contributed text is dual-licensed CC BY-SA 4.0 and GFDL, and *"these licenses do allow commercial uses of your contributions, as long as such uses are compliant with the terms of the respective licenses."* No commercial/non-commercial split exists in the API Usage Guidelines either — unlike GNews's free tier (ADR-0026), which is explicitly non-commercial-only.
- **Attribution mechanism, stated by Wikimedia itself.** Terms of Use §7 names three acceptable attribution methods; the first, verbatim: *"Through hyperlink (where possible) or URL to the article to which you contributed (since each article has a history page that lists all contributors, authors and editors)."* This is the mechanism this ADR's Decision adopts below — see the "Attribution mechanism" implementation default.
- **Only real restriction: no sublicensing/reselling/white-labeling of the API itself**, not a restriction on using it. The API Usage Guidelines, fetched directly: *"Operators (or those acting on their behalf) may not sublicense, lease, assign, or guarantee the availability or functionality of a Wikimedia Foundation-managed API to any third party,"* and *"It is not permissible to implement an API client that white labels in a manner that obscures the identity of the ultimate service provider of the APIs (the Wikimedia Foundation)."* This restricts reselling Wikimedia's own API access to a third party while hiding that it's Wikimedia's — it does not restrict SocialEngage from using the API internally to power its own ingestion pipeline, the same posture ADR-0027 already establishes for every connector: SocialEngage is a technical consumer of the source, never a reseller of it.
- **ShareAlike triggers on modification-and-redistribution, not passive storage.** CC BY-SA 4.0's own legal text (`creativecommons.org/licenses/by-sa/4.0/legalcode.en`), fetched directly: the ShareAlike obligation (§3(b)) applies only when a licensee *"Share[s] Adapted Material,"* where "Adapted Material" (§1) requires the licensed material to be *"translated, altered, arranged, transformed, or otherwise modified."* Reproducing, storing, or displaying the unmodified text — which is all this connector's v1 scope does — does not trigger it. Named explicitly here, per this ADR's own task, so a future contributor does not assume SocialEngage's own database storage of raw article text is itself a "modification."

This is the same rigor bar ADR-0024 (Newswire) and ADR-0026 (GNews) already established for a connector-selection ADR — this ADR follows their structure directly, not a lighter-weight decision.

**The entity-modeling question this ADR must resolve, not defer a third time.** The Knowledge-Graph & Semantic Data Modeling Reviewer reviewed this exact question on 2026-08-06 (`docs/architecture/knowledge-graph-register.md`) and found: relational storage remains sufficient (no graph-shaped traversal or dense many-to-many pattern is implied by anything proposed); but the floated framing — "`Author` = the article's own contributor-history page, a dynamic reference, not one fixed organization" — does **not** cleanly extend ADR-0024's/ADR-0026's issuer-as-Author pattern the way it first looked like it might. A per-article history-page reference is 1:1 with the `SocialPost` being ingested, which collapses `Author` normalization to exactly the "embed author fields per post" alternative ADR-0004's own Alternatives Considered section already rejected — **unless** a real many-post-to-one-`Author` reuse pattern exists. The reviewer named the open question directly: does this connector re-poll/re-ingest an article as it gets edited over time (producing multiple `SocialPost` rows over time, all pointing at the same `Author`), or is each article ingested once as a static snapshot? This ADR's Decision, below, makes that call.

## Decision

**The durable decision — this is what would need superseding, not just amending:**

### 1. Provider and mechanism

Target the **MediaWiki Action API** (`en.wikipedia.org/w/api.php`, and the equivalent per-language-edition endpoint) directly — no aggregator, no third-party wrapper, no account, matching Newswire's (ADR-0024) `authMode: 'none'` shape more closely than GNews's (ADR-0026) `apiKey` shape, since Wikipedia's own self-service model requires neither an account nor a key. `deliveryMode: 'poll'` — MediaWiki has no push/webhook mechanism for arbitrary external consumers. `authMode: 'none'`, gated only by a compliant `User-Agent` header per the Foundation's own User-Agent Policy (`foundation.wikimedia.org/wiki/Special:MyLanguage/Policy:User-Agent_policy`, verified directly): the header must identify the client and include contact information (e.g. `SocialEngage/1.0 (https://socialengage.example; contact@example.org)`); non-compliant requests "may be blocked without notice" (HTTP 403). This is a connector-operational configuration requirement, not a credential — see the ADR-0027 relation note below for why this does not implicate ADR-0027's "no pooling" rule.

### 2. Ingestion cadence — re-poll on edit, not one-shot snapshot

**The connector re-ingests an article as it is edited, producing a new `SocialPost` for each qualifying revision, not a single static snapshot at first discovery.** This is a deliberate design choice, not the reviewer's "leave it open" default, for three concrete reasons:

1. **It is the actual product value this source offers that GNews/Newswire do not.** GNews and Newswire both ingest content that is published once and effectively immutable (a news article, a press release) — "new item since last poll" is the entire signal. A Wikipedia article about a tenant's own brand or topic is, by contrast, a living document that gets revised, sometimes adversarially (a reputation-relevant edit war, vandalism, a disputed factual change). A reputation-monitoring watchlist that only ever sees the article once, at first discovery, misses the actual event a tenant would want to know about — that their Wikipedia article just changed.
2. **Wikipedia's own API is built around this use case.** The `recentchanges` API (`mediawiki.org/wiki/API:RecentChanges`, verified directly) is explicitly a polling primitive for "what changed since I last checked," filterable by page (`rctitle`) and time range (`rcstart`/`rcend`). This is not an ad hoc repurposing of a static-content API — it is the native mechanism the platform provides for exactly this monitoring pattern, the same way GNews's `q` parameter is the native mechanism for its own use case.
3. **It resolves the reviewer's own named open question in the direction that preserves `Author`'s purpose, not just its cardinality.** See §3 below.

`recentchanges` carries one confirmed, hard constraint worth naming directly: timestamps "may not be more than [`$wgRCMaxAge`] into the past, which on Wikimedia wikis is 30 days" (verified directly against `mediawiki.org/wiki/API:RecentChanges`) — a rolling-window enumeration limit, not a limit on the underlying revision history itself (a page's own `revisions` API can be walked arbitrarily far back). A tenant connecting a watchlist today cannot use `recentchanges` alone to retroactively discover edits to an already-known article from more than 30 days ago; a **newly discovered** article (one that matches a watchlist's query for the first time) can still have its full current content ingested as of discovery, and its prior revision history is separately walkable if a deeper backfill is ever wanted — left as an implementation-time volume-control choice, not mandated by this ADR, the same way ADR-0024/0026 left their own feed-subset and de-duplication choices to implementation time.

### 3. `Author` modeling — the article, not the platform, not the contributor list

For this connector, `Author` represents **the specific Wikipedia article being tracked** — keyed by the page's stable `pageid` (not its title, which can change on a page move), with `handle`/`displayName` set to the article's current title. `Author.followerCount` is left unpopulated, as with Newswire and GNews. `Author.firstSeenAt`/`lastSeenAt` track when the connector first and most recently ingested a qualifying revision of that article — a genuinely meaningful signal here (edit-velocity/attention on a topic), not a vestigial field, unlike a naive reading of "the article" as a static one-off container might suggest.

**This is a real, if structurally distinct, third instance of ADR-0024's/ADR-0026's issuer-as-Author departure — argued explicitly, not assumed:**

- Under the re-poll cadence decided in §2, many `SocialPost` rows (one per qualifying revision) point back to the same `Author` row over the article's lifetime. This is genuine many-post-to-one-`Author` reuse, not the 1:1 collapse the reviewer flagged as the real risk in the static-snapshot framing.
- It preserves `Author`'s functional purpose from ADR-0004's own Context — "the same author will post repeatedly within a watchlist's matching window" and supports reasoning "about an author's behavior over time... rather than about any single post" — because `firstSeenAt`/`lastSeenAt` and future `AuthorTopicSignal` aggregation against this `Author` genuinely describe something real: how actively this specific Wikipedia article is being edited in relation to a tracked topic.
- **It is not, however, identical in shape to Newswire's or GNews's departure, and this ADR does not claim it is.** Newswire's and GNews's `Author` represents a real-world **organization** that exists independently of the platform (GlobeNewswire's issuer, GNews's source publication) and that produces genuinely distinct works (many different press releases, many different articles). Wikipedia's `Author`, under this Decision, represents **the persistent identity of a single platform-native document** — it has no existence outside Wikipedia, and every "post" it produces is a revision of the *same* work, not a distinct one. The reused property (many posts, one `Author`, not embedded per-post duplication) holds; the "is a real-world issuing organization" property does not.

**This ADR explicitly does not adopt the reviewer's other named fallback** (a single, arbitrary representative `Author` value — e.g., a constant "Wikipedia" row reused across every article — with attribution routed entirely through a separate field). That alternative was seriously considered (see Alternatives Considered) and rejected: it would satisfy the FK's structural requirement but would be informationally empty (every Wikipedia-sourced post for every topic would share one `Author`, telling `AuthorTopicSignal`/the expert-finder query nothing), whereas the per-article model above genuinely reuses a meaningful entity.

### 4. Attribution — a separate field from `Author`, per this ADR's own task framing

The CC BY-SA/GFDL attribution obligation (§7's stated mechanism: a hyperlink to the article, since it has a history page) is satisfied through **`SocialPost.url`** (the field already defined in Design Spec §4.2, reused here rather than inventing a new one) — set to the specific revision's own permalink (`https://en.wikipedia.org/w/index.php?title=<Title>&oldid=<revid>`), which is itself one click from the article's full contributor-history page. **`Author`-the-entity does not carry the attribution obligation and is not read as satisfying it** — `Author` here answers "which article is this a revision of," a data-modeling/reuse question; `SocialPost.url` answers "how do we comply with Wikimedia's stated attribution mechanism," a legal-compliance question. Per this ADR's own task instruction, these are deliberately kept as two different fields serving two different purposes, not forced into one.

### 5. Watchlist matching

Primary use case is watchlist/reputation-monitoring — keyword/hashtag/boolean matching against whole-article content, matching ADR-0024's/ADR-0026's own precedent. MediaWiki's CirrusSearch-backed `search` API supports quoted-phrase matching, `-`/`!` exclusion, and field-scoped operators (`intitle:`, `insource:`) per `mediawiki.org/wiki/Help:CirrusSearch`, verified directly — a real native query surface, though this pass did not confirm the exact parameter-level availability of every operator through the standard `action=query&list=search` endpoint specifically (as opposed to the CirrusSearch extension UI it documents). Per ADR-0021's capability matrix and ADR-0006's connector-side-with-fallback pattern: whatever subset proves reachable natively is pushed down; the rest falls back to whole-article post-fetch matching, the same as every connector to date. Exact AST-to-CirrusSearch-syntax translation is an implementation-time task, not fixed by this ADR — the same treatment ADR-0026 gave GNews's own query translation.

**Implementation defaults (adjustable — logged in this ADR's own Amendment Log going forward; does not require superseding this ADR on its own):**

- `authMode: 'none'`, gated by a compliant, connector-identifying `User-Agent` header (not a per-tenant credential — see ADR-0027 relation note).
- `deliveryMode: 'poll'` — no push mechanism exists.
- `getRateLimitConfig()`: Wikimedia publishes a dedicated rate-limits policy (`mediawiki.org/wiki/Wikimedia_APIs/Rate_limits`, referenced but not fetched to an exact numeric ceiling in this pass) — an unconfirmed placeholder until verified, the same honest treatment ADR-0024 gave Newswire's own unpublished limit. Do not invent a number; verify before `RequestGate` is sized against it.
- `Author.externalAuthorId` = the article's `pageid`; `Author.handle`/`displayName` = current title; `Author.followerCount` unpopulated.
- `SocialPost.url` = the specific ingested revision's own permalink (`?oldid=<revid>`), not the bare article URL — the attribution mechanism, per §4.
- New-article discovery (a page matching a watchlist's query for the first time) is polled separately from `recentchanges`-driven re-ingestion of already-tracked pages — via the `search` API for newly matching content, not designed further here.
- **No cross-source de-duplication concern of the Newswire/GNews kind** (the same story appearing on multiple wires) applies here — but a related, new one does: multiple tenants independently tracking the same public Wikipedia article each ingest their own tenant-scoped copy of the same revision under RLS (ADR-0015), by design, consistent with how every other connector already works; not a new gap.
- Volume/retention consequence, named not resolved: a single actively-edited article can generate many `SocialPost` rows over its lifetime (unlike GNews/Newswire's one-shot items), each potentially carrying the article's full text — a real, cumulative storage driver against ADR-0018's existing tiered-retention policy, worth a deliberate look once real Wikipedia-connector volume exists, not before.

## Consequences

**Positive**

- The best-grounded connector candidate this project has vetted since GNews/Newswire — self-service with no approval gate (unlike Reddit's now-closed registration), commercial reuse explicitly permitted (unlike GNews's non-commercial-only free tier), every material claim verified directly against Wikimedia's own primary sources rather than secondhand summaries.
- Resolves, with reasoning rather than a third deferral, the entity-modeling open question the Knowledge-Graph reviewer explicitly declined to answer — a genuine, if structurally distinct, third instance of the issuer-as-Author pattern, giving `docs/adr/README.md`'s and ADR-0004's own "rule of three" trigger a real third data point (see the accompanying Pending supersession note on ADR-0004).
- Cleanly separates the entity-reuse question (`Author` = the article) from the legal-attribution question (`SocialPost.url` = the specific revision permalink) — avoids conflating two different concerns into one field, per this ADR's own explicit task framing.
- Storing whole, unchunked article text in `SocialPost.text` at each qualifying revision keeps the future RAG/embedding direction Menno has already named as anticipated (not designed here — see Open questions) structurally open rather than foreclosed: a later chunking/indexing pass can operate on the stored raw text without this ADR having pre-committed to any particular chunk boundary.
- `recentchanges`-driven re-polling is a genuinely novel monitoring signal none of this project's other connectors offer — "your own Wikipedia article just changed" — closer to the actual reputation-monitoring use case than a one-shot article snapshot would be.

**Negative**

- **`Author`'s reused shape here is not identical to Newswire's/GNews's**, and treating it as a mechanical "third instance, therefore generalize ADR-0004 without further thought" would overstate the similarity — see the Pending supersession note on ADR-0004 for the narrower, honestly-scoped generalization this ADR actually recommends.
- **A re-poll-per-revision cadence can generate real per-tenant volume** for an actively-edited article, a cumulative storage/retention driver ADR-0018's existing tiers were not sized against; named here, not yet resolved.
- **No confirmed, published rate limit** at the exact numeric level — same honest gap ADR-0024 disclosed for Newswire; the connector must poll conservatively by default until verified.
- **CirrusSearch's exact native-query-parameter surface through the standard API endpoint was not fully confirmed** in this pass — a real verification gap before `supportedQueryFeatures` can be finalized, named rather than glossed over.
- **`recentchanges`'s 30-day rolling window** means an already-tracked article's edit history beyond 30 days back is not retroactively discoverable through that endpoint alone — a real, if partial (revision-history walking can go further), limitation.
- Every qualifying revision re-ingests the article's current full text, not a diff — Wikipedia's own API does not expose a plain "what changed" field suitable for direct ingestion (per-diff attribution isn't cleanly available either, confirmed by the Knowledge-Graph reviewer's own finding) — meaning a large, mostly-unrelated edit to an otherwise-matching article still produces a full-text re-ingestion, a real noise/volume trade-off left for implementation-time tuning (e.g., a materiality threshold), not resolved here.

## Alternatives Considered

- **Static snapshot, ingested once per article at first discovery** — rejected as the primary cadence. This is the reviewer's own "degenerate" branch: `Author` collapses to 1:1 with the `SocialPost`, functionally identical to the "embed author fields per post" alternative ADR-0004 already rejected, and it discards the actual reputation-monitoring signal (an article changing) that distinguishes Wikipedia from GNews/Newswire in the first place. Not rejected because it's technically impossible — a leaner v0 could plausibly ship this way — but because it would misrepresent the connector's real value and would need to be revisited almost immediately once "did my Wikipedia page just change" turned out to be the actual ask.
- **`Author` as a single, constant, connector-wide representative value (e.g., one "Wikipedia" row reused for every article and every tenant), with attribution carried entirely by a separate field** — the reviewer's own named fallback for the static-snapshot branch. Considered seriously, including under the re-poll cadence this ADR actually adopts, and rejected: it does achieve real N:1 reuse, but the reused entity carries no distinguishing information — `AuthorTopicSignal`/the expert-finder query would return "Wikipedia" as the sole author for every topic ever matched, which is worse than uninformative, it's actively misleading about what the aggregate represents. The per-article model in Decision §3 achieves the same structural goal (real reuse, no per-post duplication) while keeping the aggregate meaningful.
- **Modeling `Author` as the article's own contributor-history page or contributor list** (the framing the Knowledge-Graph reviewer was originally asked to assess) — rejected for the reason the reviewer itself gave: a history page is inherently 1:1 with the article, not an independently reusable entity, and per-diff/per-revision attribution to a specific contributor is not a plain field Wikipedia's API exposes. This framing is retained, correctly, as the *attribution mechanism* (Decision §4), just not as the `Author` entity.
- **Graph-shaped storage for contributor/article relationships** — not pursued; the Knowledge-Graph & Semantic Data Modeling Reviewer found relational storage sufficient, no deep/variable-length traversal or dense many-to-many pattern implied by anything this connector needs (`docs/architecture/knowledge-graph-register.md`, 2026-08-06 entry).
- **Designing chunked/RAG-oriented ingestion granularity as part of this ADR** — explicitly rejected, per Menno's own stated direction ("its more the question when then if" on RAG/embedding retrieval drawing on Wikipedia/Wolfram Alpha) and the Knowledge-Graph reviewer's own finding that chunk-granularity is a source-agnostic indexing-strategy decision, not specific to Wikipedia. Named as a real, anticipated future direction in Open questions below, not designed here.
- **A third-party Wikipedia API wrapper/SDK instead of the MediaWiki Action API directly** — not pursued; no reason surfaced to add an intermediary layer to a self-service, well-documented first-party API, consistent with ADR-0024's/ADR-0026's own "direct to the source, no aggregator" preference where the source's own access is already open.

## Open questions for decision

- **The rule-of-three generalization question for ADR-0004** — this ADR's own position (yes, a real third instance, but structurally narrower than a mechanical "organization-as-Author" restatement) is argued in Decision §3 and carried to ADR-0004 as a Pending supersession note (see that file). Recommend Menno decide the exact generalized wording at this ADR's own acceptance, not defer a fourth time.
- **CirrusSearch's exact native-query surface through the standard API endpoint** — needs implementation-time confirmation before `supportedQueryFeatures` is finalized; not confirmed to this project's own primary-source bar in this pass.
- **Exact rate-limit ceiling** — Wikimedia publishes a rate-limits policy; not fetched to a specific number in this pass. Verify before sizing `RequestGate`.
- **Materiality threshold for re-ingestion** — should every qualifying `recentchanges` entry for a tracked article produce a new `SocialPost`, or only ones crossing some materiality bar (size delta, non-minor-edit flag, which is self-reported and not fully reliable)? Left as an implementation-time tuning choice, named so it isn't discovered mid-build, the same way ADR-0024/0026 left their own feed-subset and de-duplication choices open.
- **How far to backfill a newly discovered article's prior revision history**, given `recentchanges`'s 30-day window doesn't cap the underlying `revisions` API — an implementation-time volume/cost trade-off, not fixed here.
- **RAG/embedding-oriented chunked ingestion** — a real, anticipated future direction (Menno's own words: "its more the question when then if," drawing on Wikipedia and/or Wolfram Alpha as grounding sources) that this ADR deliberately does not design. Named here so a future ingestion-granularity ADR knows this connector's whole-article `SocialPost.text` storage was chosen partly to keep that door open, not to close it.
- **Whether an AI-enrichment pass (ADR-0038) that transforms stored Wikipedia text and then re-exposes the transformed output externally would itself constitute "sharing Adapted Material"** under CC BY-SA §3(b) — flagged as a genuine, not yet analyzed, edge case surfaced by this ADR's own attribution research; today's enrichment output (`enrichment.entities`, a flat category/confidence list) plausibly does not rise to "Adapted Material" of the licensed text itself, but this has not been checked against CC BY-SA 4.0's own definition to this project's usual bar, and should be before any future feature redistributes enrichment output derived from Wikipedia text outside the tenant's own account.

## Note on relation to ADR-0027 (Accepted, 2026-08-01)

This connector's self-service, keyless access model means there is no per-tenant credential or account relationship for ADR-0027's "no pooling, no contracting on anyone's behalf" rule to apply to — the same structural position ADR-0024's own relation note reached for Newswire's `authMode: 'none'` shape, not a new gap this ADR introduces. The one element that is shared across every tenant — the connector's own `User-Agent` string, identifying SocialEngage itself as the API client per Wikimedia's own policy — is not a credential, not an account, and not a business relationship any tenant is a party to; it identifies the software making the request, not a connecting party's own relationship with Wikimedia, the same way a browser's User-Agent string doesn't make the browser vendor a party to every website a user visits. **This ADR needs no scope change against ADR-0027** — its Decision text already satisfies the principle without requiring one.

On the one real, confirmed restriction (no sublicensing/reselling/white-labeling Wikimedia's own API — see Context): this restricts reselling *access to Wikimedia's API itself* to a third party while obscuring Wikimedia as the source. SocialEngage's use here is as an internal data consumer powering its own ingestion pipeline, not a reseller of Wikimedia's API to anyone — the same "technical intermediary only" posture ADR-0027 already establishes for every connector, not a new obstacle this connector introduces.
