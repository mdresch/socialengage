ADRs derived from [`2026-07-28-social-listening-ingestion-design.md`](../project%20docs/2026-07-28-social-listening-ingestion-design.md) (Status: Approved for implementation). Each record captures one architecturally significant decision from that spec, with the context and alternatives that motivated it.

Each ADR feeds a [user story](../user-stories/README.md); each story is built per [`docs/implementation-methodology.md`](../implementation-methodology.md) (contract-first, component `SKILL.md`s, permanent regression suite) — so an ADR's decision stays enforced in code, not just recorded in prose.

## Conventions for changing an existing ADR

Four situations, four different responses — don't default to editing the original Decision/Consequences text in place:

| Situation | Response |
|---|---|
| The underlying decision itself changes | New ADR, or a superseding ADR that says so explicitly |
| The decision stands, but *why* it was made needs more explanation | Add a "Note on provenance" or similar, without altering the original text (e.g. ADR-0002, ADR-0016) |
| An adjustable parameter changes (a window length, a threshold) | Log it in that ADR's "Amendment Log" (e.g. ADR-0017–0019) — doesn't need superseding |
| Implementation surfaces a constraint that was already logically required by the decision, just not stated | Add a dated "Clarification" section (e.g. ADR-0013) — not a new decision, just making an implicit requirement explicit |
| A still-Proposed ADR would change part of this (Accepted) ADR's decision, if accepted | Add a dated "Pending supersession note" pointing to it, naming exactly which part would change (e.g. ADR-0009/0010 → ADR-0023) — not an edit to the original text, and not a full supersession unless the whole decision is affected |
| A "Pending supersession note" above becomes real because the other ADR gets accepted | Add a dated "Supersession update" note confirming it, without editing the original Pending supersession note or Decision text (e.g. ADR-0009/0010, once ADR-0023 was accepted) — and don't assume already-shipped code changes automatically; it only changes when the superseding ADR's own story is actually built |
| A new ADR formalizes, as an explicit and durable principle, something a prior Accepted ADR's Decision text already assumed but never stated as project-wide policy — without changing that prior ADR's own Decision at all | Add a dated "Note on relation to ADR-XXXX" section on the prior ADR, naming what it already satisfies and why no scope change follows — not a supersession (nothing changes), not a provenance note (this isn't explaining *why* the prior decision was made), not a parameter change, not a clarification of an implicit requirement (e.g. ADR-0024/0026 → ADR-0027) |

The common thread: the original Decision and Consequences text is a historical record and stays put. Everything learned later is appended, dated, and labeled by which of the five categories it is.

## Audit mechanism - emerging pattern across multiple per-table designs (added 2026-08-08)

A review of a non-series draft (`_stale-drafts/0045-audit-trail-from-other-project.md`, see below) on 2026-08-08 surfaced that this project's audit-mechanism question is being answered **incrementally per concern**, not by a single global "Audit Trail Architecture" ADR - and that the per-table pattern is the right shape, not a missed unified decision. The current per-concern design:

- **`platform_admin_audit_log`** - Platform-Admin-bypassed writes (tenant creation, suspension, license changes, break-glass). Decided by ADR-0030 §5, migration `0015`. RLS-bypassed for the acting role, granted only to `platform_admin_role` / `tenant_signup_role` (ADR-0037 §8b's INSERT-only grant). Not a tenant-content table.
- **`domain_signup_attempts`** - self-service sign-up domain-match attempts and escalations. Decided by ADR-0037 §8b, migration `0022`. Tenant-content-shaped (RLS-scoped to the calling tenant), but written by `tenant_signup_role` during a structurally-unscoped-to-tenant signup, the same chicken-and-egg pattern ADR-0037 §1 already explains.
- **`user_access_audit_log`** - `access_ends_at` writes (offboarding, reactivation). Designed by Story 5.17 (Ready), transactionally paired with the `users` update per its Acceptance Criteria. Story 5.17 itself explicitly notes "no new ADR needed" - this is an implementation-time mechanics question, not a fresh architectural one, since the underlying principle (every `access_ends_at` write is auditable) is already decided by ADR-0032 §9.
- **General tenant-content mutation audit** (e.g., who changed this watchlist's `terms`?) - **not designed, deliberately deferred.** ADR-0044 §6 (the redline on this same date) explicitly leaves this as an Open Question: "Whether a real compliance need will eventually surface for tenant-mutation audit history... if yes, a separate ADR for an `activity_logs` table naming is the right place; this ADR deliberately doesn't pre-decide the schema for a need that hasn't materialized." No story has surfaced a concrete need for a general tenant-content audit table yet - every existing audit need has been scope-specific enough to live on its own table - so this remains deferred under the rule-of-three discipline.

**This is the project's actual emerging pattern** - one audit table per distinct actor / action class, each designed at the table's own ADR or story, not a single monolithic audit schema retrofitted onto all of them. **No unifying ADR is warranted.** Anyone reviewing a future story that asks "do we have an audit table for this?" should answer by extending the per-concern pattern above, not by inventing a new global table - same as ADR-0037 §8b already did for `domain_signup_attempts` rather than reusing `platform_admin_audit_log`.
