**A note specific to this register:** this role's own domain pull is data minimization — does a field or flow actually need to be retained/transmitted for the platform's stated listening/insights purpose, or is it kept by default. Findings here name the specific field/flow, the concern, and the minimization change (plus, where applicable, an architecture mitigation) that would close it — per the charter's own current Output Format. Distinct from `data-sovereignty-register.md` (S-23's own register): that role argues jurisdictional residency/encryption/redundancy tensions; this one argues minimization and unnecessary third-party exposure. The two roles share adjacent territory on purpose (ADR-0004-style, not yet formally reconciled) — don't assume a finding in one register also covers the other.

## 2026-08-06 — reviewed stdin (e.g. git diff)

1) **Field/flow:** `docs/ai-roles/scripts/invoke-azure-foundry-agent.mjs --role data-privacy` sending review material (diffs/files) to a **Microsoft Foundry Prompt Agent** (third-party service boundary vs prior local Ollama), and writing results to `docs/privacy/data-privacy-sovereignty-register.md` (path now wired in the script).  
   **Concern:** This role’s whole purpose is “keep sensitive content off infrastructure that does not strictly need it,” yet the migration means **whatever Menno feeds into a privacy review can now be transmitted off-machine**—potentially including raw social post bodies, tenant identifiers, connector configuration, and (worst case) secrets if they ever appear in reviewed artifacts/logs. “Public” content is still personal data; and reviewer prompts often include *more than needed* context by default (entire ADRs, logs, sample payloads).  
   **Minimization change:** Make the Foundry invocation **deny-by-default on inputs**: send only (a) the smallest diff hunks needed to evaluate the privacy question, and (b) **redacted** excerpts for any payload-like content (posts, connector responses, headers, IDs). Never send full docs/whole-repo context unless explicitly required for a specific finding.  
   **Possible architecture/design changes:** Add a **local preflight scrubber** in the invocation script: regex-based secret scanning + structured redaction (Bearer tokens, API keys, cookies, emails/phones, usernames/handles), plus an **allowlist of file paths** allowed to be transmitted (e.g., ADR text OK; anything under `logs/`, `fixtures/`, `exports/`, `*.env*`, or “sample payload” folders blocked). Also add an option to run “privacy review in *local-only mode*” for any material that includes real post bodies or credential-adjacent data.

2) **Field/flow:** `docs/legal/legal-compliance-register.md` now contains a substantive entry describing **ADR-0038** as “transfer to third-party AI providers” for sentiment enrichment (i.e., outbound transmission of “post content” to an enrichment provider).  
   **Concern:** This is a direct minimization red flag: **sending raw post bodies off-platform** (even if “public”) is almost always *more* than needed to compute sentiment, and it creates an additional replication surface that the project then has to delete/DSAR-track. The legal register notes this is “unaddressed”; from a minimization standpoint, the default should be “don’t transmit raw content unless absolutely required,” and “don’t retain provider responses beyond the derived insight.”  
   **Minimization change:** If enrichment exists/ships, require it to operate on a **minimized payload**: sentiment should be computed on **redacted and truncated text**, with **no author identifiers**, no tenant-identifying tags, and no URLs unless strictly required. Persist **only** the derived score/label + minimal provenance needed for debugging (provider name + model/version + timestamp), not the full provider response and not the raw text that was sent.  
   **Possible architecture/design changes:** Put a hard boundary in the enrichment connector: a “PII/identifier stripper” stage before any network egress, plus tenant-level controls (explicit enablement, and a “no third-party processing” mode). If a first-party option exists (e.g., in-tenant/region processing you already operate), route there by default and treat third-party enrichment as an exception path with tighter logging/retention.

3) **Field/flow:** ADR-0042 (Proposed) Wikipedia connector modeling: `Author` = Wikipedia article (keyed by `pageid`), and one `SocialPost` per qualifying revision; attribution via `SocialPost.url` (revision permalink).  
   **Concern:** A “one post per revision” design can easily lead to storing **large amounts of near-duplicate free text** over time (entire article snapshots or substantial content), which is excessive for listening/insights unless you can show you truly need full bodies retained long-term. Wikipedia revisions can also include personal data and sensitive content; retaining complete revision text multiplies privacy impact and complicates deletion/offboarding discipline.  
   **Minimization change:** Default to storing **revision metadata + derived insights**, not full revision bodies: keep `pageid`, revision id, timestamp, permalink, and whatever minimal text slice is required for watchlist match/extraction (e.g., changed-section excerpt or bounded-length snippet), plus computed fields (entities/keywords/sentiment if used). Only retain full text when explicitly required for a defined insight function, and apply strict retention limits.  
   **Possible architecture/design changes:** Use **dedupe + delta storage**: store “diff-like” content (or normalized extracted terms) rather than full snapshots; keep the permalink for on-demand retrieval when a human needs to inspect source. If full text must exist for internal indexing, store it in a **separately TTL-governed store** (short retention) and persist only the long-lived analytical artifacts in Postgres.
