# Epic 10: Analytics, operations, and trust (ADRs 0086–0094)

Stories derived from the ADRs drafted in `docs/adr/`. Backend stories are sequenced before their frontend counterparts where both repos are touched.

---

## Story 10.1 — Prospecting list model and sharing (backend)

**Source:** ADR-0086 · **Status:** Blocked — pending ADR acceptance
**Built:** not yet

**As a** backend engineer,
**I want** `prospecting_lists` and `prospecting_list_entries` tables with RLS and sharing,
**so that** `Social-Selling-Strategist` can save, score, and share lead lists.

**Acceptance Criteria**
- `prospecting_lists` and `prospecting_list_entries` tables exist with tenant RLS.
- `GET /v1/prospecting-lists`, `POST`, `PATCH`, and `DELETE` are tenant-scoped and user-owned.
- A list can be `shared` so other `tenant_user`s in the same tenant can read it.
- `Tenant-Admin` can toggle `shared`; regular users cannot.
- Relationship stage values are constrained to `new`, `contacted`, `engaged`, `converted`, `passed`.
- `POST /v1/prospecting-lists/:id/entries`, `PATCH .../:entryId`, and `DELETE .../:entryId` manage entries that reference `Author` by `author_id`.
- `POST /v1/prospecting-lists/:id/export` returns a metadata-only CSV that does not include private contact data.
- `POST /v1/prospecting-lists/:id/crm-handoff` is defined but defers to the `CRMConnector` handoff story.
- Contract tests cover CRUD, sharing, and cross-tenant 404.

## Story 10.3 — Preconfigured analytics views (backend)

**Source:** ADR-0087 · **Status:** Blocked — pending ADR acceptance
**Built:** not yet

**As a** backend engineer,
**I want** `TopicDailyCount`, `SourceDailyCount`, `AuthorDailyCount`, `SentimentDailyCount`, and `WatchlistDailyCount` tables and a refresh worker,
**so that** dashboards and analytics can read fast, precomputed aggregates.

**Acceptance Criteria**
- All five daily-count tables exist with `(tenant_id, date, ...)` primary keys and indexes.
- A `RefreshAnalyticsViews` worker runs every 15 minutes and is idempotent.
- Late-arriving posts trigger re-computation for affected `(tenant_id, date)` buckets.
- The current partial day can be computed on demand or marked provisional.
- Dashboard endpoints prefer the precomputed tables over raw `social_posts`.
- `GET /v1/analytics/:view` exposes `topics`, `sources`, `authors`, `sentiments`, and `watchlists` views.
- Aggregate rows contain counts, sums, and identifiers only; no raw post bodies or `rawPayload` are stored in the views.

## Story 10.4 — Ad-hoc query endpoint (backend)

**Source:** ADR-0088 · **Status:** Blocked — pending ADR acceptance
**Built:** not yet

**As a** backend engineer,
**I want** `POST /v1/analytics/query` to accept a structured, allowlisted query and return a safe aggregation,
**so that** `Tenant-Business-Analyst` can ask custom questions without writing SQL.

**Acceptance Criteria**
- `dimensions` and `metrics` are validated against an allowlist.
- `QueryBuilder` translates the structured request into a parameterized, tenant-scoped SQL query.
- `timeGrain` supports `hour`, `day`, `week`, `month`.
- `limit` is capped at 1,000 and query runtime is capped at 30 seconds.
- The endpoint prefers `*DailyCount` tables and falls back to `social_posts` for drill-downs.
- Unknown `dimensions`/`metrics` return `400 UNKNOWN_DIMENSION` / `400 UNKNOWN_METRIC`.
- `format` supports `json` and `csv`; the endpoint is read-only.
- Response includes `columns`, `rows`, `rowCount`, `truncated`, `queryTimeMs`, and `source` (`precomputed` | `raw`).
- Per-tenant rate limit is 60 requests per minute (configurable).
- Contract tests cover allowed, disallowed, and timeout scenarios.

**so that** the platform operations dashboard has fast, cached infrastructure data.

**Acceptance Criteria**

## Story 10.8 — Data export posts CSV (backend)

**Source:** ADR-0090 / ADR-0111 · **Status:** Blocked — pending ADR acceptance
**Built:** not yet

**As a** backend engineer,
**I want** `GET /v1/posts/export.csv` to stream bounded CSV exports and `POST /v1/posts/export` for async large exports,
**so that** tenants can download their matched posts safely.

**Acceptance Criteria**
- Synchronous exports up to 5,000 rows, async up to 100,000 rows.
- CSV columns: `post_id`, `published_at`, `platform_id`, `author_name`, `author_url`, `body_markdown`, `sentiment`, `topics`, `reach`, `engagement`, `url`, `watchlist_ids`.
- Async exports write to Blob and track `export_jobs`.
- `GET /v1/posts/export.csv` supports `watchlistId`, `start`, `end`, `limit`, and `format=csv` query parameters.
- `limit` defaults to 1000; exports over 10,000 rows return `202 Accepted` with a `jobId` and `GET /v1/exports/:jobId/status` tracks `pending`, `ready`, `expired`, `failed`.
- Response returns `Content-Type: text/csv` and `Content-Disposition: attachment; filename="<tenant>-posts-<date>.csv"`.
- Rate limits are enforced per tenant.
- No `rawPayload`, `enrichment` JSONB internals, or connector secrets are exported.

## Story 10.9 — Real-time alert rules and delivery (backend)

**Source:** ADR-0091 · **Status:** Blocked — pending ADR acceptance
**Built:** not yet

**As a** backend engineer,
**I want** `alert_rules`, an `AlertEvaluationWorker`, and in-app/email/webhook delivery,
**so that** `Tenant-Brand-Reputation-Manager` is notified when thresholds are crossed.

**Acceptance Criteria**
- `alert_rules` table supports `volume`, `sentiment`, `keyword`, `topic`, and `connector-health` rule types.
- The worker consumes `SocialPostIngestedEvent` and `ConnectorHealthChangedEvent`.
- Cooldown (default 60 minutes) prevents alert spam.
- Delivery via in-app, email, and webhook is supported; email and webhook are opt-in.
- `tenant_alerts` table stores one row per trigger.
- Rule thresholds are validated per type (`volume`, `sentiment`, `keyword`, `topic`, `connector-health`).
- `AlertEvaluationWorker` emits an alert payload with `alertRuleId`, `alertRuleName`, `tenantId`, `triggeredAt`, `type`, `summary`, `matchingPostCount`, `watchlistId`, and `platformId`.
- Acknowledging a `tenant_alert` resets the rule's `last_triggered_at` cooldown.

## Story 10.11 — Author-initiated takedown (backend)

**Source:** ADR-0092 · **Status:** Blocked — pending ADR acceptance
**Built:** not yet

**As a** backend engineer,
**I want** a public takedown form, `data_subject_requests`, and a soft-redaction flow for `social_posts`,
**so that** authors can request removal of their content.

**Acceptance Criteria**
- `POST /public/v1/takedowns` accepts `platform_post_url`, `requester_email`, `requester_name`, and `requester_affirmation`.
- Magic-link verification is sent before the request becomes visible.
- `data_subject_requests` tracks `status` (`received`, `under_review`, `granted`, `denied`, `escalated`).
- On grant, `social_posts.body_markdown` and `rawPayload` are redacted, `redacted_at` and `redaction_request_id` are populated, and `post_watchlist_matches` are cleaned up.
- `RAGConnector.deletePost()` is triggered on redaction.
- `POST /public/v1/takedowns` is rate-limited to 3 submissions per IP per hour.
- Redaction does not remove the post from the original social platform.
- `Tenant-Admin` review UI is available (frontend in later story).

## Story 10.12 — DSR self-service portal (backend)

**Source:** ADR-0093 · **Status:** Blocked — pending ADR acceptance
**Built:** not yet

**As a** backend engineer,
**I want** a public DSR portal for access, correction, and erasure requests with a fulfillment worker,
**so that** the platform supports GDPR/CCPA data-subject rights.

**Acceptance Criteria**
- `POST /public/v1/dsr/requests` creates a request with a magic-link token that is tied to `requester_email` and expires after 7 days.
- `GET /public/v1/dsr/requests`, `GET .../:id`, and `GET .../:id/download` are scoped by the magic-link token.
- `access` requests produce a ZIP with CSV and JSON exports, plus a manifest, expiring after 7 days.
- `erasure` requests redact posts and remove the user row if applicable.
- `correction` requests create `correction_proposals` for `Tenant-Admin` review.
- Each request has a 30-day SLA from `received` to `resolved` by default.
- `GET /v1/admin/tenant/dsr-requests`, `POST .../:id/resolve`, and `GET .../:id/audit` support `Tenant-Admin` review.
- Accepted `correction` updates `social_posts.enrichment` or `correction_notes`; it does not modify the original public post on the source platform.
- SLA tracking and admin review endpoints are available.

## Story 10.13 — Compliance audit pack (backend)

**Source:** ADR-0094 · **Status:** Blocked — pending ADR acceptance
**Built:** not yet

**As a** backend engineer,
**I want** `compliance_audit_packs` and an async tamper-evident export generator,
**so that** `Tenant-Admin` and `Platform-Admin` can produce defensible audit records.

**Acceptance Criteria**
- `compliance_audit_packs` table tracks pack type, date range, status, storage path, and SHA-256.
- `POST /v1/compliance/audit-packs` creates an async generation job.
- Pack types: `dsr`, `takedown`, `ingestion`, `enrichment`, `full`.
- The pack is a `pack.json` file with a `manifest.json` containing `pack_id`, `tenant_id`, `generated_at`, `sha256` of `pack.json`, and a platform signing-key signature.
- `POST /v1/compliance/audit-packs` accepts `packType`, `startDate`, and `endDate`; `Tenant-Admin` can generate for their own tenant and `Platform-Admin` for any tenant.
- `GET /v1/compliance/audit-packs/:id` tracks `generating` | `ready` | `expired` | `failed` and returns the download URL.
- Presigned download URLs expire after 24 hours; blob objects expire after 90 days.
