## Story 9.1 — Watchlist connector count and preview volume endpoint

**Source:** ADR-0077 (Accepted 2026-08-23) · **Status:** Ready
**Built:** 2026-08-24 — social-listening-core@a4bf276

**As a** backend engineer,
**I want** `SocialConnector.count?()` and `POST /v1/watchlists/preview-volume` to return a per-connector, tenant-scoped estimate of how many posts a watchlist would match,
**so that** `Tenant-Admin` and `Tenant-Brand-Reputation-Manager` can see expected load before activating a watchlist.

**Acceptance Criteria**
- `SocialConnector` interface exposes an optional `count?()` method returning `ConnectorCountResult` with `count`, `confidence`, `sampleSize?`, `rateLimitCost?`, and `unsupportedOperators?`.
- At least one existing connector (e.g. `gnews`, `brave-search`) implements `count?()` using the platform's total-results field.
- Connectors without `count?()` fall back to a bounded preview sample (default **50**) and extrapolate; preview calls use `sample?()` when available or `poll()` in `mode: 'preview'` / `isDryRun: true` and do not update cursors or watermarks.
- `POST /v1/watchlists/preview-volume` is tenant-scoped, RLS-gated, and returns `WatchlistVolumePreview` with `estimatedPosts`, `confidence`, `sampleSize?`, `rateLimitCost`, `warning`, `errorCode?`, and `errorMessage?` per connector.
- Connector previews run concurrently; a single connector failure is returned as `confidence: 'unavailable'` with `errorCode` and `errorMessage` without failing the entire HTTP request.
- `high_volume`, `quota_risk`, and `unsupported_query` warnings are triggered by the thresholds in ADR-0077; `quota_risk` is raised via a `RequestGate.checkAvailability` pre-check.
- Contract tests cover exact count, estimate, fallback, `unavailable` partial failure, and cross-tenant 404/403 behavior.

## Story 9.2 — Metric explainability endpoint

**Source:** ADR-0078 · **Status:** Ready
**Built:** not yet

**As a** backend engineer,
**I want** `POST /v1/explain` to return a short, confidence-graded explanation for any dashboard metric,
**so that** `Tenant-Reader` and `Tenant-User` can understand what a number means without asking an analyst.

**Acceptance Criteria**
- `POST /v1/explain` accepts `metricKey`, `value`, `context`, and `locale` and returns `explanation` (`string | null`), `confidence` (`high` | `medium` | `low`), `generationId`, and optional `fallbackReason`.
- `metricKey` is validated against a core `MetricKey` allowlist; unknown keys return `400 UNKNOWN_METRIC_KEY`.
- String `value`/`previousValue` values are validated against `/^[a-z0-9-]+$/`; the prompt is built from structured JSON template variables, not raw string concatenation.
- Only aggregate data (`metricName`, `value`, `timeRange`, `previousValue`, `denominator`) is sent to the AI provider; no raw post bodies, `widgetId`, `watchlistId`, or PII are included.
- `confidence` is derived deterministically from context completeness on the server, never from the model's self-assessment.
- The endpoint calls `acquireForAiModel()` through the existing `RequestGate` per `ADR-0003`/`ADR-0020`.
- A dedicated user-scoped token bucket enforces `20` requests per minute per user and max `5` concurrent in-flight explanations per tenant, returning `429` when exceeded.
- A tenant `explanations_enabled` flag (default `true`, settable by `tenant_admin`) disables the endpoint with `403 EXPLAINABILITY_DISABLED` when `false`.
- Response caching is in-process only, keyed on `(tenantId, metricKey, value, timeRange, locale)` with a 5-minute TTL.
- The explanation prompt is versioned in `social-listening-core/.claude/skills/metric-explainability/SKILL.md` and covered by a permanent contract test.
- Contract tests cover `volume-spike`, `sentiment-share`, and `platform-mix` metrics, plus the validation, rate-limit, and refusal paths.

## Story 9.3 — Crisis template bundle and activation (backend)

**Source:** ADR-0079 (amended 2026-08-25) · **Status:** Ready
**Built:** not yet

**As a** backend engineer,
**I want** `crisis_templates`, `tenant_crisis_templates`, and `POST /v1/crisis-templates/:id/activate` to create a preconfigured `watchlist` from a template, recording thresholds and notification-channel intent for a future alert-delivery follow-on,
**so that** `Tenant-Brand-Reputation-Manager` can activate crisis monitoring in one click.

**Acceptance Criteria**
- `crisis_templates` table exists with `template_key`, `default_query`, `default_ast`, `default_thresholds`, `parameters`, and `playbook`.
- `tenant_crisis_templates` table tracks `watchlist_id`, `thresholds` (jsonb), `notification_channel_ids` (jsonb), `variables`, `custom_thresholds`, `playbook` snapshot, `created_by_user_id`, and `created_at` — no `alert_rule_id` column (amended 2026-08-25 per ADR-0079's Amendment: `alert_rule` creation is deferred to a follow-on gated on ADR-0091 acceptance).
- `GET /v1/crisis-templates` returns active templates with `template_key`, `name`, `description`, `default_query`, `default_thresholds`, `parameters`, and `playbook` for preview.
- `POST /v1/crisis-templates/:templateKey/activate` creates a `watchlist` from the interpolated `default_ast` under the caller's `user_id`, writes the `tenant_crisis_templates` record with `thresholds` and `notification_channel_ids` as stored intent, and returns `{ tenantCrisisTemplateId, watchlistId, status: 'active', playbook, thresholds, notificationChannelIds }` — no `alertRuleId` in the response.
- Every `required` parameter in `crisis_templates.parameters` must be present in the supplied `variables` map, or activation fails with a validation error before any write.
- `notificationChannelIds` is a required field in the activation request, stored as intent only — not resolved against any real channel service (none exists in v1).
- The entire activation flow (watchlist creation + `tenant_crisis_templates` write) executes inside a single database transaction; partial failures roll back.
- Activation copies defaults into the new `watchlist` and `tenant_crisis_templates`; later changes to the platform template do not retroactively change activated instances.
- `playbook` is advisory data; it is not a workflow engine in v1.
- Deleting the generated `watchlist` cascades and removes the associated `tenant_crisis_templates` record (`ON DELETE CASCADE`).
- Authorization: only `Tenant-Brand-Reputation-Manager` or `Tenant-Admin` roles may activate; all created data is scoped to the caller's tenant via RLS.

## Story 9.4 — Crisis threshold wizard (frontend)

**Source:** ADR-0079 (amended 2026-08-25) · **Status:** Ready (depends on Story 9.3)
**Built:** not yet

**As a** `Tenant-Brand-Reputation-Manager`,
**I want** a wizard in `social-listening-admin` that lets me preview and activate crisis templates,
**so that** I can start monitoring for reputation risks without writing a watchlist by hand.

**Acceptance Criteria**
- A `CrisisThresholdWizard` lists active `crisis_templates` from `GET /v1/crisis-templates`.
- Selecting a template shows `default_query`, `default_thresholds`, `parameters`, and `playbook` in a preview panel.
- The user can supply required `variables` (e.g. `brand_name`, `competitors`) and customize thresholds before activation.
- Activation calls `POST /v1/crisis-templates/:templateKey/activate` with `variables`, `customThresholds`, and `notificationChannelIds`, and navigates to the new watchlist on success.
- The wizard displays a persistent, plain-language disclosure that v1 does not deliver automated alerts — the activated watchlist provides monitoring only until a future release wires real alert delivery (amended 2026-08-25 per ADR-0079's Amendment).
- Errors (e.g. missing required variables, invalid thresholds, quota risk, authorization failure) are surfaced inline, not as console-only or navigation errors.
- The wizard is keyboard navigable and responsive (BRD-0079 NFR-004).

## Story 9.7 — RAGConnector provider abstraction (backend)

**Source:** ADR-0081 (Accepted 2026-08-25; revised same day per architectural review) · **Status:** Ready
**Built:** not yet

**As a** backend engineer,
**I want** a `RAGConnector` interface and at least one concrete provider (pgvector default) for upsert/search/delete,
**so that** the semantic-search layer is not locked to a single vector store.

**Acceptance Criteria**
- `RAGConnector` interface defines `upsert()`, `search()`, `deletePost()`, `deleteTenant()`, and `status()`.
- `RAGChunkMetadata` carries `tenant_id`, `post_id`, `chunk_index`, `content` (chunk text payload), `platform_id`, `published_at`, and optional `watchlist_ids`, `sentiment`, `topics`.
- A canonical, provider-agnostic `RAGFilter` shape is defined (`platformId`, `sentiment`, `watchlistIds`, `topics`, `dateRange`); each connector implementation translates it to vendor-native filter syntax. `tenant_id` is never a `RAGFilter` field — it comes from the mandatory `tenantId` parameter.
- `RAGSearchOptions` carries `topK`, optional `filter`, optional `textQuery` (hybrid search), and optional `minScore` (score threshold); `RAGSearchResult` carries `id`, `score`, and `metadata` (including `content`).
- Vector record ids follow the deterministic convention `${tenantId}:${postId}:${chunkIndex}`; `deletePost` removes all chunks of a post via predictable id range or metadata filter; re-indexing the same post overwrites the same ids.
- Chunk batching into provider-safe batches is the connector implementation's responsibility; callers pass the full per-post chunk set.
- The v1 default provider is pgvector (reusing the existing Azure Postgres instance); Pinecone Serverless and Azure AI Search are supported alternatives via the same interface.
- The v1 isolation model is a shared index with mandatory `tenant_id` metadata filtering on every `search()`; namespace-per-tenant is an optional internal optimization only.
- `RAGConnector` credentials use `platform_credentials` with `credential_type = 'rag'`, reusing the existing credential-envelope and ownership tiers.
- Embedding vector dimension is specified in connector configuration, matched to the chosen embedding model at index-creation time.
- The `RAGConnector` is instantiated by a dedicated `ragConnectorRegistry.ts`, separate from the `ProviderConnector` registry.
- Source of truth remains `social_posts`; the vector store (including stored chunk text) can be rebuilt.
- Contract tests verify upsert, search, and delete for one provider (pgvector default).

## Story 9.8 — RAG post chunking and embedding pipeline (backend)

**Source:** ADR-0082 (Accepted 2026-08-25; revised same day per architectural review) · **Status:** Ready (depends on Story 9.7 being built)
**Built:** not yet

**As a** backend engineer,
**I want** `RAGChunkingService` and an async `RAGIndexRequestedEvent` to chunk and embed posts after enrichment,
**so that** the vector store stays in sync with `social_posts` without blocking ingestion.

**Acceptance Criteria**
- `RAGChunkingService.split(post)` produces overlapping chunks from `body_markdown` (with optional title prepend `Title: {title}\n\n`) and enrichment metadata; each chunk carries `tenant_id`, `post_id`, `chunk_index`, and `content` (named `content` to match `RAGChunkMetadata.content` in ADR-0081).
- `RAGChunkingService.split(post)` uses a default 256-token chunk size with ~20% overlap and a 64-token minimum, preferring paragraph/sentence boundaries. Short posts (< 64 tokens) are never discarded — they are indexed as a single chunk.
- `AIProviderConnector.embed(tenantId, texts)` targeting a dedicated `text-embedding-3-small` (1536-dim) Azure OpenAI deployment is wired into the pipeline; it returns one vector per input string. Enrichment metadata is carried in `RAGChunkMetadata`, not embedded as `content`.
- `RAGIndexRequestedEvent` is emitted after `enrichPost()` and consumed by a worker that does not block the main ingestion pipeline.
- `rag_chunks_sync` tracks `post_id`, `tenant_id`, `chunk_count`, `embedding_model`, `status` (`synced`/`pending`/`failed`), `last_indexed_at`, and `error_message` per tenant.
- Re-indexing a post with fewer chunks than before deletes obsolete vector IDs (`${tenantId}:${postId}:${oldChunkCount}` through `${tenantId}:${postId}:${newChunkCount}`) before upserting new chunks — no orphaned chunks remain.
- Failures are retried (3 retries, exponential backoff 1s/5s/30s), then moved to DLQ with `rag_chunks_sync.status = 'failed'`; they do not block the main ingestion pipeline.
- Post deletion and tenant offboarding trigger `RAGConnector.deletePost()` / `deleteTenant()` and remove the corresponding `rag_chunks_sync` row(s).

## Story 9.9 — RAG vector-store RLS and metadata (backend)

**Source:** ADR-0083 (Accepted 2026-08-27) · **Status:** Ready (depends on Story 9.7)  
**Built:** not yet

**As a** backend engineer,  
**I want** vector records to carry tenant-scoped metadata, mandatory `tenant_id` pre-filtering on every search, and targeted metadata update capabilities,  
**so that** a multi-tenant vector index cannot leak data across tenants, preserves query recall, and avoids expensive re-embedding on metadata updates.

**Acceptance Criteria**
- Every vector record has metadata: `tenant_id`, `post_id`, `chunk_index`, `content` (chunk text payload, bounded <= 256 tokens / ~1.5 KB), `platform_id` (typed `PlatformId`), `published_at`, `watchlist_ids`, `sentiment`, `topics`.
- Total metadata payload size is bounded to `< 4 KB` per record (well within the 8 KB safe ceiling).
- `RAGConnector.search()` mandates **pre-filtering** within the vector index prior to or during graph traversal (k-NN search). `tenant_id` equality filter is mandatory on every query and comes from the required `tenantId` parameter.
- `RAGFilter` supports `platformId`, `sentiment`, `watchlistIds`, `topics`, and `dateRange`. Each connector translates `RAGFilter` to native index syntax (Pinecone `$in`, Azure AI Search `$filter`, pgvector SQL `WHERE`).
- If a vector store lacks native array-membership pre-filtering on `watchlist_ids`, `RAGSearchService` over-fetches ($k \times 3$) before applying in-memory filters to prevent candidate truncation.
- Vector record IDs follow deterministic format `${tenantId}:${postId}:${chunkIndex}`.
- Deletions are executed via metadata filter (`post_id == postId` AND `tenant_id == tenantId`) or deterministic batch ID array (`${tenantId}:${postId}:0..N`).
- Content updates and privacy redactions in `social_posts` invoke `deletePost(tenantId, postId)` followed by fresh chunking, re-embedding, and upserting.
- Human-in-the-loop overrides (ADR-0071) and watchlist updates invoke `RAGConnector.updateMetadata(tenantId, postId, partialMetadata)` without re-generating embeddings.
- Tenant offboarding (ADR-0043) invokes `RAGConnector.deleteTenant(tenantId)` to purge tenant records.
- A periodic background reconciliation worker purges orphaned vector records whose `post_id` no longer exists in `social_posts`.
- Stored chunk text in `RAGChunkMetadata.content` is a derived, rebuildable copy of public post text; no author PII is stored.

## Story 9.10 — RAG search and ask endpoint (backend)

**Source:** ADR-0084 (Accepted 2026-08-27) · **Status:** Ready (depends on Story 9.8 and 9.9)  
**Built:** not yet

**As a** backend engineer,  
**I want** `POST /v1/rag/search`, `POST /v1/rag/ask`, and `GET /v1/rag/status` to serve semantic search and generative Q&A (with SSE streaming),  
**so that** users can discover posts by meaning and ask natural-language questions with verified citations.

**Acceptance Criteria**
- `POST /v1/rag/search` accepts `query`, `searchMode?: 'semantic' | 'hybrid'`, canonical `RAGFilter`, and `pagination` (`topK` default 10, cap 50).
- `POST /v1/rag/search` returns normalized similarity scores `[0.00 .. 1.00]`, `snippet` (from vector metadata `content`), and deterministic `internalUrl` (`/app/posts/${postId}`).
- `POST /v1/rag/ask` supports standard JSON response and token-by-token Server-Sent Events (SSE) streaming (`Accept: text/event-stream` or `stream: true`).
- In SSE mode, `/ask` emits `citations` event on retrieval completion, `delta` events for token chunks, and `done` event with final confidence metadata.
- Context chunks in `/ask` are sandboxed with XML tags (`<context><chunk id="...">`) to defend against prompt injection.
- If context is insufficient, `/ask` outputs an honest refusal with `confidence: 'unsupported'` and `isGrounded: false`.
- `GET /v1/rag/status` returns indexing health, total indexed chunks, and lag behind ingestion.
- Per-tenant rate limiting and 429 quota enforcement (`RAG_QUOTA_EXCEEDED`) are applied.

## Story 9.11 — RAG UI/UX and loading patterns (frontend)

**Source:** ADR-0085 (Accepted 2026-08-27) · **Status:** Ready (depends on Story 9.10)  
**Built:** not yet

**As a** `Tenant-Reader`,  
**I want** an intuitive semantic search and real-time streaming Q&A interface with interactive citations and normalized match badges,  
**so that** I can discover insights across social posts with immediate visual feedback, verifiable source provenance, and clear guidance on ungrounded questions.

**Acceptance Criteria**
- A dedicated `RAGDiscoveryPage` is mounted at `/app/discovery` (or `/tenant/discovery`) and accessible globally via `Cmd+K` / `Ctrl+K`.
- `RAGUnifiedSearchBox` allows toggling between `Semantic Search` and `Ask AI Assistant`, with full filter bar support (Platform, Watchlist, Date, Topic, Sentiment).
- Semantic search results display `RAGResultCard` with normalized match badges (`score >= 0.85`: "Strong Match", `0.70–0.84`: "Relevant") and deep links to `/app/posts/:id`.
- Generative Q&A implements 3-phase SSE streaming: (1) 0–600ms shimmer, (2) immediate `RAGCitationsRail` mount on `event: citations` + token streaming with typewriter cursor on `event: delta`, (3) final lock with `RAGConfidenceBadge` on `event: done`.
- Streamed markdown answer parses `[^1]` markers into interactive citation pill buttons that highlight the source card in `RAGCitationsRail` on hover and open snippet preview on click.
- When `isGrounded: false` or `confidence: 'unsupported'`, `RAGRefusalCallout` displays an informative "Limited Context" card with actionable query suggestion chips instead of an error toast.
- Accessibility standards: `RAGUnifiedSearchBox` has `aria-label`, streamed text uses `aria-live="polite"`, and citation pills have accessible labels.
- Mobile layout: `RAGCitationsRail` stacks as a collapsible accordion below the answer on viewports `< 768px`.
