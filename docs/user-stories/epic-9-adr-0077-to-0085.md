## Story 9.1 — Watchlist connector count and preview volume endpoint

**Source:** ADR-0077 (Accepted 2026-08-23) · **Status:** Ready
**Built:** 2026-08-24 — social-listening-core@a4bf276

**As a** backend engineer,
**I want** `SocialConnector.count?()` and `POST /v1/watchlists/preview-volume` to return a per-connector, tenant-scoped estimate of how many posts a watchlist would match,
**so that** `Tenant-Admin` and `Tenant-Brand-Reputation-Manager` can see expected load before activating a watchlist.

**Acceptance Criteria**
- `SocialConnector` interface exposes an optional `count?()` method returning `ConnectorCountResult` with `count`, `confidence`, `sampleSize?`, `rateLimitCost?`, and `unsupportedOperators?`.
- At least one existing connector (e.g. `gnews`, `brave-search`) implements `count?()` using the platform's total-results field.
- Connectors without `count?()` fall back to a bounded preview sample (default **50**) and extrapolate; preview calls use `sample?()` when available or `poll()` in `mode: 'preview'` / `isDryRun: true` and do not update cursors or watermarks.
- `POST /v1/watchlists/preview-volume` is tenant-scoped, RLS-gated, and returns `WatchlistVolumePreview` with `estimatedPosts`, `confidence`, `sampleSize?`, `rateLimitCost`, `warning`, `errorCode?`, and `errorMessage?` per connector.
- Connector previews run concurrently; a single connector failure is returned as `confidence: 'unavailable'` with `errorCode` and `errorMessage` without failing the entire HTTP request.
- `high_volume`, `quota_risk`, and `unsupported_query` warnings are triggered by the thresholds in ADR-0077; `quota_risk` is raised via a `RequestGate.checkAvailability` pre-check.
- Contract tests cover exact count, estimate, fallback, `unavailable` partial failure, and cross-tenant 404/403 behavior.

## Story 9.2 — Metric explainability endpoint

**Source:** ADR-0078 · **Status:** Ready
**Built:** not yet

**As a** backend engineer,
**I want** `POST /v1/explain` to return a short, confidence-graded explanation for any dashboard metric,
**so that** `Tenant-Reader` and `Tenant-User` can understand what a number means without asking an analyst.

**Acceptance Criteria**
- `POST /v1/explain` accepts `metricKey`, `value`, `context`, and `locale` and returns `explanation` (`string | null`), `confidence` (`high` | `medium` | `low`), `generationId`, and optional `fallbackReason`.
- `metricKey` is validated against a core `MetricKey` allowlist; unknown keys return `400 UNKNOWN_METRIC_KEY`.
- String `value`/`previousValue` values are validated against `/^[a-z0-9-]+$/`; the prompt is built from structured JSON template variables, not raw string concatenation.
- Only aggregate data (`metricName`, `value`, `timeRange`, `previousValue`, `denominator`) is sent to the AI provider; no raw post bodies, `widgetId`, `watchlistId`, or PII are included.
- `confidence` is derived deterministically from context completeness on the server, never from the model's self-assessment.
- The endpoint calls `acquireForAiModel()` through the existing `RequestGate` per `ADR-0003`/`ADR-0020`.
- A dedicated user-scoped token bucket enforces `20` requests per minute per user and max `5` concurrent in-flight explanations per tenant, returning `429` when exceeded.
- A tenant `explanations_enabled` flag (default `true`, settable by `tenant_admin`) disables the endpoint with `403 EXPLAINABILITY_DISABLED` when `false`.
- Response caching is in-process only, keyed on `(tenantId, metricKey, value, timeRange, locale)` with a 5-minute TTL.
- The explanation prompt is versioned in `social-listening-core/.claude/skills/metric-explainability/SKILL.md` and covered by a permanent contract test.
- Contract tests cover `volume-spike`, `sentiment-share`, and `platform-mix` metrics, plus the validation, rate-limit, and refusal paths.

## Story 9.3 — Crisis template bundle and activation (backend)

**Source:** ADR-0079 · **Status:** Ready
**Built:** not yet

**As a** backend engineer,
**I want** `crisis_templates`, `tenant_crisis_templates`, and `POST /v1/crisis-templates/:id/activate` to create a preconfigured `watchlist` and `alert_rule` from a template,
**so that** `Tenant-Brand-Reputation-Manager` can activate crisis monitoring in one click.

**Acceptance Criteria**
- `crisis_templates` table exists with `template_key`, `default_query`, `default_thresholds`, and `playbook`.
- `tenant_crisis_templates` table tracks the `watchlist_id` and `alert_rule_id` created on activation.
- `POST /v1/crisis-templates/:id/activate` creates a `watchlist` and `alert_rule` owned by the caller and returns their IDs.
- Activation copies defaults into the new `watchlist` and `alert_rule`; changes to the template do not retroactively change activated instances.
- `playbook` is advisory data; it is not a workflow engine in v1.

## Story 9.5 — Onboarding checklist state (backend)

**Source:** ADR-0080 · **Status:** Ready
**Built:** 2026-08-25 (social-listening-core@3add125)

**As a** backend engineer,
**I want** `tenants.onboarding_checklist` and the `GET/PATCH /v1/tenants/:id/onboarding-checklist` endpoints to track and dismiss setup progress,
**so that** new `Tenant-Admin`s can see what setup steps remain.

**Acceptance Criteria**
- `tenants` has an `onboarding_checklist` JSONB column with `connect_source`, `build_watchlist`, `invite_user`, `verify_posts`, and `advanced_steps`.
- `GET /v1/tenants/:id/onboarding-checklist` returns the current state using single-query bundled `SELECT EXISTS` evaluation and one-way JSONB milestone caching.
- `PATCH` allows `Tenant-Admin` to dismiss or reset the checklist.
- Core steps are marked complete based on existing data (connector activation, watchlist, user invite, posts) and locked as historical milestones.
- Dismissed state is persisted and the checklist can be re-opened.
- `PATCH` does not allow manually marking core steps complete; it supports hiding/showing `advanced_steps` (`enable_enrichment`, `configure_alerts`).

## Story 9.7 — RAGConnector provider abstraction (backend)

**Source:** ADR-0081 · **Status:** Blocked — pending ADR acceptance
**Built:** not yet

**As a** backend engineer,
**I want** a `RAGConnector` interface and at least one concrete provider (e.g. Pinecone or pgvector) for upsert/search/delete,
**so that** the semantic-search layer is not locked to a single vector store.

**Acceptance Criteria**
- `RAGConnector` interface defines `upsert()`, `search()`, `deletePost()`, `deleteTenant()`, and `status()`.
- Configuration is stored per tenant in `platform_credentials` or a dedicated `rag_store_config`.
- Tenant isolation is enforced by `tenant_id` metadata on every query.
- Source of truth remains `social_posts`; the vector store can be rebuilt.
- `RAGConnector` credentials use `platform_credentials` with `credential_type = 'rag'`, reusing the existing credential-envelope and ownership tiers.
- Contract tests verify upsert, search, and delete for one provider.

## Story 9.8 — RAG post chunking and embedding pipeline (backend)

**Source:** ADR-0082 · **Status:** Blocked — pending ADR acceptance (depends on Story 9.7)
**Built:** not yet

**As a** backend engineer,
**I want** `RAGChunkingService` and an async `RAGIndexRequestedEvent` to chunk and embed posts after enrichment,
**so that** the vector store stays in sync with `social_posts` without blocking ingestion.

**Acceptance Criteria**
- `RAGChunkingService.split(post)` produces overlapping chunks from `body_markdown` and enrichment metadata.
- `AIProviderConnector.embed(chunks)` or a dedicated embedding model is wired into the pipeline.
- `RAGIndexRequestedEvent` is emitted after `enrichPost()` and consumed by a worker.
- `rag_chunks_sync` tracks `post_id`, `last_indexed_at`, `chunk_count`, and `store_id` per tenant.
- `RAGChunkingService.split(post)` uses a default 256-token chunk size with ~20% overlap and a 64-token minimum, preferring paragraph/sentence boundaries.
- `AIProviderConnector.embed(texts)` returns one vector per input string; enrichment metadata is carried in `RAGChunkMetadata`, not embedded as text.
- Failures are retried but do not block the main ingestion pipeline.

## Story 9.9 — RAG vector-store RLS and metadata (backend)

**Source:** ADR-0083 · **Status:** Blocked — pending ADR acceptance (depends on Story 9.7)
**Built:** not yet

**As a** backend engineer,
**I want** vector records to carry tenant-scoped metadata and a mandatory `tenant_id` filter on every search,
**so that** a multi-tenant vector index cannot leak data across tenants.

**Acceptance Criteria**
- Every vector record has metadata: `tenant_id`, `post_id`, `chunk_index`, `platform_id`, `published_at`, `watchlist_ids`, `sentiment`, `topics`.
- `RAGConnector.search()` always applies a `tenant_id` equality filter.
- `RAGFilter` supports `watchlistId`, `platformId`, `topicId`, `sentiment`, and `dateRange`.
- Post deletion and tenant offboarding trigger `deletePost()` and `deleteTenant()`.
- Chunk text is not stored in the vector store; display text is reconstructed from `social_posts` via `post_id` and `chunk_index`.
- A periodic reconciliation job deletes orphan vector records whose `post_id` no longer exists in `social_posts`.
- No PII beyond public post content is stored in the vector index.

## Story 9.10 — RAG search and ask endpoint (backend)

**Source:** ADR-0084 · **Status:** Blocked — pending ADR acceptance (depends on Story 9.8 and 9.9)
**Built:** not yet

**As a** backend engineer,
**I want** `POST /v1/rag/search`, `POST /v1/rag/ask`, and `GET /v1/rag/status` to serve semantic search and Q&A,
**so that** `Tenant-Reader` can ask natural-language questions over the tenant's posts.

**Acceptance Criteria**
- `POST /v1/rag/search` accepts a natural-language `query` and `RAGFilter` and returns top-N chunks with `postId`, `chunkIndex`, `score`, and `snippet`.
- `POST /v1/rag/ask` returns an `answer`, `citations`, and `confidence`.
- `GET /v1/rag/status` returns index health and lag.
- `search` `topK` defaults to 10 and is hard-capped at 50; `ask` `maxChunks` defaults to 5 and is hard-capped at 10.
- Monthly per-tenant quota is enforced; overages return `429 RAG_QUOTA_EXCEEDED`.
- Citations link back to the original posts and include `postId`, `chunkIndex`, `snippet`, and optional `url`.

## Story 9.11 — RAG UI/UX and loading patterns (frontend)

**Source:** ADR-0085 · **Status:** Blocked — pending ADR acceptance (depends on Story 9.10)
**Built:** not yet

**As a** `Tenant-Reader`,
**I want** a semantic search box and an "Ask" panel in the admin UI with clear loading states and citations,
**so that** I can find and understand posts by meaning, not just keyword.

**Acceptance Criteria**
- `RAGSearchBox`, `RAGResultsList`, `RAGResultCard`, and `RAGAsk` components are implemented.
- Search uses a skeleton list; `Ask` uses a progress bar.
- Each result shows an excerpt, platform, date, and a link to the original post.
- `RAGAsk` shows the generated answer and a list of citations.
- `RAGAsk` displays a `high`/`medium`/`low` confidence badge and keeps citations always visible (not hidden).
- `RAGSearch` shows optional filter chips for watchlist, platform, topic, sentiment, and date range.
- Loading states follow the 300 ms threshold (no loader under 300 ms), skeleton for search (300 ms–1.5 s), and a progress bar for `Ask` (>1.5 s).
- Keyboard accessibility and mobile layout are supported.
