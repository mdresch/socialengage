# Epic 7: Platform Admin UI

**Boundary, stated once here so every story in this epic inherits it rather than re-arguing it: no screen in this epic ever renders tenant content.** Platform Admin's own access boundary is decided at the ADR layer, not by this document — ADR-0030 §2 locks `platform_admin_role` to zero database access to any tenant-content table (`users`, `watchlists`, `social_posts`, `platform_credentials`, or anything a tenant would recognize as its own data), and ADR-0041 formalizes Platform Admin as a structurally distinct identity kind from Tenant-Admin/Tenant-User specifically to keep that boundary from blurring at the UI layer too. Concretely, **for this epic: no post content, no post metadata, no watchlist definitions, no connector credentials, and no per-tenant analytics derived from any of the above appear on any Platform Admin screen, now or in any future story added here** — including the Epic 4-derived operational metrics this file's own note below anticipates, which stop at infrastructure/connectivity signals (e.g. Story 6.6's database-health indicator) and never surface what a tenant is actually monitoring or what's been ingested for them. Story 6.6's own Acceptance Criteria restate this locally for its own four screens; this note exists so the same rule applies automatically to 6.6's still-unwritten successors, not just to what's already built.

**Created 2026-08-12**, split out of what was previously "Epic 6: Admin UI" (now `epic-6-tenant-admin-ui.md`, retitled **Epic 6: Tenant Admin UI**), at Menno's own direct request: *"to avoid confusion... have separate the Epic 6 Tenant Admin UI Designs"* from the Platform Admin surface. This is a **regrouping, not a renumbering** — Story 6.6 (Platform Admin console) below keeps its historical "6.6" ID exactly as it was, per Menno's own explicit choice, so every prior reference to "Story 6.6" (`docs/implementation-log.md`, `docs/implementation-plan.md`'s traceability table, git history, commit messages) stays literally correct with no edits needed anywhere else in this project. Only this file is new; the story's own content, ADR sourcing, and build history are unchanged from what was previously in the old "Admin UI" epic file (since renamed to `epic-6-tenant-admin-ui.md` at the same time as this split).

**Relationship to Epic 4 (Derived Data, Analytics & Health):** confirmed directly with Menno at this same split — Epic 4's own connector-health/analytics/derived-data work (`ConnectorHealth`, Story 4.3; the other derived-data stories in that epic) is the intended **backend basis** for this epic's own future growth, specifically the "infrastructure/operational metrics" scope Story 6.6's own Acceptance Criteria have deliberately deferred since 2026-08-04 ("once this project's actual operational limitations... are well enough known"). Story 1.10's `GET /v1/health` already broke a first, narrow piece of that deferral open for Story 6.6 (the database health indicator, added 2026-08-12). As Epic 4's own metrics surface matures, this is the epic that gets a UI put in front of it — not a new commitment to build anything beyond what's named below today, just the deliberate, named home for that future work rather than a permanently-deferred, unowned gap.

**Correction, 2026-08-12 — "break-glass request/execute mapping" (above) was never actually built; it's a paragraph of prose. Third confirmed instance of the same defect class as Stories 6.4/6.5's corrections (`epic-6-tenant-admin-ui.md`) above, found while Menno directly asked to validate this specific feature.** Confirmed directly: `social-listening-admin/src/app/platform-admin/page.tsx`'s "Provision tenant," "Update tenant," and "Break-glass" sections are each a single descriptive `<p>` — no `<form>`, no input, no button, no `onClick`/`onSubmit` anywhere. `createAdminTenant()`, `updateAdminTenant()`, `requestBreakGlassReset()`, and `executeBreakGlassRequest()` all exist as real functions in `core-client.ts` (confirmed working against the real Story 5.12/5.13 REST surface) but are never imported or called from this page or from any `api/` route — dead code behind zero UI. **The Tenant registry and Audit log sections are real** — both genuinely call `listAdminTenants()`/`queryAdminAuditLog()` and render the response; no rework needed there. Root cause is identical to 6.4/6.5: `story-6.6...contract.test.ts` is exclusively `fs.readFileSync` + `.toContain('requestBreakGlassReset')`-style checks, which confirm the function *exists in the file* and the word *appears in the page*, never that the page actually calls it.

**As** Platform Admin (in practice, Menno, the Sole Operator persona — `Stakeholder-Register.md`),
**I want** a console to provision/suspend tenants, adjust license seats, execute a break-glass Tenant-Admin credential reset, and review the audit log of every such action,
**so that** I can operate the platform without hand-writing SQL against production, while the zero-tenant-data-access boundary (ADR-0030 §2) stays real and enforced.

**A design-time reference exists, explicitly not implementation-ready:** `docs/design/platform-admin-console-mockup-2026-08-03.html` covers exactly these four screens (tenant list, tenant detail, break-glass confirmation, audit log), grounded in ADR-0030/0031. Per `docs/design/README.md`'s own stated limitation, it is plain HTML/JS, not Next.js, and is a layout/flow reference only — not yet reconciled screen-by-screen against ADR-0030 §3's two-phase break-glass workflow or ADR-0032 §9's `access_ends_at` model, and not to be ported or copy-pasted as code.

**Acceptance Criteria**
- Tenant list screen: name, domain, status, seat ceiling/active count, created date (ADR-0031's schema) — reading from a new `GET /v1/admin/tenants`-shaped core endpoint (does not exist yet — named as a required prerequisite, not built here).
- Tenant provisioning (create) and adjustment (status, `license_seat_count` only — never `active_seat_count`, per `tenants/SKILL.md`'s own column-scoped grant) via new core endpoints backed by `tenantStore.ts`'s existing functions, exercised only through `platform_admin_role` (ADR-0030 §2), never `app_user`.
- Break-glass flow implements ADR-0030 §3's own two-phase design exactly: a **request** step (recorded, no Entra action) separate from an **execute** step a Platform Admin explicitly picks up — never a single automated action, matching `breakGlassCredentialReset.ts`'s already-built mechanism (Story 5.7). The UI never displays the generated temporary password or the Temporary Access Pass code anywhere logged or persisted — shown once, per that mechanism's own load-bearing constraint.
- Audit log view surfaces every Platform-Admin-bypassed write (`platform_admin_audit_log`, Story 5.7) — acting identity, operation, target tenant, timestamp — read-only.
- No screen in this console renders any tenant-content table (`users`, `watchlists`, `social_posts`, `platform_credentials`, or anything a tenant would recognize as its own data) — verified directly against ADR-0030 §2's locked boundary, not merely asserted by the absence of a menu item.
- Infrastructure/operational metrics (server health, storage, connectivity) are explicitly out of this story's scope — `docs/design/README.md`'s own dated note defers this to "once this project's actual operational limitations... are well enough known," not decided or built here. **See this file's own top-of-page note on the Epic 4 relationship for where that eventually lands.**

**Revised Acceptance Criteria (2026-08-12 — only the three sections the correction above found non-functional; tenant list and audit log already satisfy the original AC list above and need no rework)**
- **Provision tenant**: a real form (name, license seat count) calling `createAdminTenant()` → `POST /v1/admin/tenants`; on success, the new tenant appears in the tenant registry table without a full page reload being required to notice it (a refetch/revalidate is sufficient — no optimistic-UI requirement).
- **Update tenant**: a real form/control per tenant row calling `updateAdminTenant()` → `PATCH /v1/admin/tenants/:id`, scoped to exactly `status` and `license_seat_count` — never `active_seat_count` or `domain` unless a future story explicitly extends this (per `tenants/SKILL.md`'s own column-scoped grant, carried forward unchanged).
- **Break-glass**: a real two-phase flow — a **request** control calling `requestBreakGlassReset()` → `POST /v1/admin/tenants/:tenantId/break-glass/request`, and a separate **execute** control (only reachable after a request exists) calling `executeBreakGlassRequest()` → `.../requests/:requestId/execute`. The generated temporary password/Temporary Access Pass code is displayed exactly once, in the execute response's own render, and is never written to any state that persists past that render (no `console.log`, no write to a store, no inclusion in any later re-render) — the same "shown once" constraint the original AC list already named, now actually enforceable because the flow exists to enforce it on.
- This story's own contract must make real behavioral assertions for all three (a real or realistically mocked fetch proving each control actually calls its named `core-client.ts` function with the right arguments) — a source-string-containment check is not sufficient, per this correction's own root cause.
- **Database health status** (added 2026-08-12, at Menno's own direct request while reviewing this same correction): a small, read-only indicator reading Story 1.10's real `GET /v1/health` — `ok`/`unavailable`, reflecting genuine current Postgres connectivity, not a fixture. **This is a narrow, explicitly scoped exception to the blanket infrastructure-metrics deferral two bullets above, not a reopening of it** — that deferral (Menno's own prior direction, `docs/design/README.md`) covers server/connectivity/storage metrics generally, "until systems limitations and requirements are well known"; Story 1.10 already named this exact endpoint as the future data source for this deferred screen "once it's actually designed." One boolean-shaped signal, sourced from an endpoint that already exists and is already contract-verified, is that narrow slice — not the broader dashboard the deferral still applies to. No new `core-client.ts` function is needed beyond a call to the already-public, unauthenticated `GET /v1/health` (Story 1.3/1.10's own boundary — no bearer token required for this one call). Still no tenant-content data of any kind, unchanged from the boundary already stated above.

**Named as required, not designed here:** the new core-side endpoints this story depends on (`GET/POST/PATCH /v1/admin/tenants`, break-glass request/execute endpoints, an audit-log query endpoint) are real `social-listening-core` scope, following that project's own contract-first discipline, for the AI Delivery Agent or Menno to build — not designed or implemented by this document.
