# Epic 18: Research-driven ADR revisions — Previews & Analytics Views (ADRs 0134–0135)

## Story 18.1 — Watchlist volume confidence UI and cost projection (frontend/backend)
**Source:** ADR-0134 (Accepted 2026-08-28) · **Status:** Built (*Documentation Steward correction, 2026-09-16: was "Ready" despite an already-populated Built field — same recurring drift class as Stories 14.1–14.4/15.1/15.2/17.1/17.2/17.3.*)  
**Built:** 2026-09-12 — social-listening-core@e479a59, social-listening-admin@e479a59  
*(Relates to Story 9.1)*

**As a** `Tenant-Admin` or `Tenant-User`,
**I want** `POST /v1/watchlists/preview-volume` to return downstream storage and AI enrichment cost estimates, and the UI to clearly distinguish exact counts from sample estimates,
**so that** I can accurately assess infrastructure and billing implications with honest confidence ratings before activating a watchlist.

**Acceptance Criteria**
- **AC1:** `WatchlistVolumePreview` includes an optional, additive `estimatedCost` block with `storageGbPerMonth` (number), `aiEnrichmentCallsPerMonth` (number), `currency: 'USD'`, and `confidence: 'exact' | 'estimate' | 'unavailable'`.
- **AC2:** `estimatedCost.confidence` inherits the least-confident connector in `breakdown`: `'unavailable'` if any connector is unavailable; else `'estimate'` if any connector is an estimate; else `'exact'` when all connectors are exact (or breakdown is empty).
- **AC3:** `estimatedCost` calculates monthly storage (5 KB per post for raw payload + metadata + enrichment) and AI enrichment calls (1 call per post) projected to a 30-day month from `totalEstimatedPosts` and query `timeWindow` (defaulting to 7 days).
- **AC4:** `POST /v1/watchlists/preview-volume` retains all ADR-0077 / Story 9.1 contracts (tenant scoping, RLS gating, partial failure isolation, warnings), returning `estimatedCost` as a strictly additive extension.
- **AC5:** Frontend `core-client.ts` exposes `previewWatchlistVolume()` calling the preview endpoint and returning typed `WatchlistVolumePreview` including `estimatedCost`.
- **AC6:** Frontend `VolumePreviewPanel` and `ConnectorVolumeRow` visually distinguish `confidence: 'exact'` (rendering formatted count e.g. `12,340`) from `confidence: 'estimate'` (rendering with tilde and indicator e.g. `~45,000 (estimated)`), and render `unavailable` status cleanly.
- **AC7:** Frontend `VolumePreviewPanel` renders the `estimatedCost` block showing projected storage growth in GB/month, AI calls/month, currency, and inherited confidence badge.
- **AC8:** `WatchlistForm` integrates volume preview via `/api/watchlists/preview-volume` proxy route so users can inspect volume and cost forecasts prior to saving or creating a watchlist.


## Story 18.2 — Preconfigured analytics view RLS table enforcement (backend)

**Source:** ADR-0135 (Accepted 2026-08-28) · **Status:** Built (*Documentation Steward correction, 2026-09-16: was "Ready" despite an already-populated Built field — same recurring drift class as Story 18.1 above.*)  
**Built:** 2026-09-13 — social-listening-core@f731949  
*(Relates to Story 10.3)*

**As a** platform architect and security auditor,
**I want** the five preconfigured analytics view structures (`source_daily_counts`, `author_daily_counts`, `sentiment_daily_counts`, `watchlist_daily_counts`, and `topic_daily_counts`) to be strictly verified and enforced as ordinary physical PostgreSQL tables with native Row-Level Security rather than literal PostgreSQL materialized views,
**so that** tenant-confidential aggregate analytics are reliably isolated by the database engine without relying on fragile application-level or security-barrier wrappers.

**Acceptance Criteria**
- **AC1:** Verification that all five rollup entities (`source_daily_counts`, `author_daily_counts`, `sentiment_daily_counts`, `watchlist_daily_counts`, and `topic_daily_counts`) are ordinary physical PostgreSQL tables (`relkind = 'r'`) in `pg_class`, and none are PostgreSQL materialized views (`relkind = 'm'`) or views (`relkind = 'v'`).
- **AC2:** Verification that every one of the five rollup tables has Row-Level Security enabled (`relrowsecurity = true`) and enforced (`relforcerowsecurity = true` / active RLS policy) in `pg_class` and `pg_policy`.
- **AC3:** Verification that each table has a valid tenant isolation policy restricting access to `tenant_id = current_setting('app.tenant_id', true)::uuid`.
- **AC4:** Worker refresh idempotency and non-locking execution: `runDailyAggregatesRefresh()` executes idempotent upserts (`INSERT ... ON CONFLICT DO UPDATE`) rather than `REFRESH MATERIALIZED VIEW`, preserving queryability during aggregation runs.
- **AC5:** Query routing and cross-tenant isolation: `GET /v1/analytics/:view` supports all five views (`sources`, `sentiments`, `topics`, `authors`, `watchlists`) and enforces cross-tenant isolation under active RLS session contexts.
