## No-story ADR convention (formalized 2026-08-03, at ADR-0035's acceptance)

Per this project's own "rule of three" discipline (the same threshold already applied elsewhere — ADR-0004's organization-as-Author question, ADR-0026's own deferral of generalizing it), three real, differently-reasoned no-story ADRs is enough evidence to state an explicit rule rather than keep improvising a named exception each time one occurs. **The "one user story per ADR" convention (opening paragraph, above) remains the default.** An ADR gets no story only if it falls into one of these three recognized categories — and must say which, explicitly, in its own "A note on this ADR's own place in the series' conventions" section, rather than silently omitting a story:

1. **Already satisfied by shipped code.** The ADR states a principle or constraint that existing, already-built code already fully practices — no further implementation work follows from accepting it. *Example: ADR-0027* (connector-as-technical-intermediary), already practiced by ADR-0024's and ADR-0026's shipped connectors before ADR-0027 ever stated it as a general rule.
2. **Not yet buildable — deferred to a later ADR's own story.** The ADR states a real, durable constraint, but nothing exists yet for a contract test to target (a missing table, mechanism, or dependency this ADR itself does not build). The eventual buildable interface is captured by whichever future ADR's story actually implements it, citing this ADR as the governing constraint at that time — not a permanent exception, a scheduling one. *Example: ADR-0028* (credential-creation-authority tiers), whose buildable content was ultimately delivered by Story 1.7/ADR-0034, not by an ADR-0028 story of its own.
3. **Project-structure decision with no interface of its own (yet).** The ADR decides a structural question — how many deployables, which repository, how code is organized — rather than introducing a new interface, stored field, or endpoint. This category *can* get a story if the decision happens to produce an immediately testable contract (ADR-0001 did, and has Story 1.1); it does not if nothing yet exists for the decision to be tested against. *Example: ADR-0035* (admin UI shape), which has no Platform-Admin-facing screen yet for its role-gated-routing decision to be tested against.

**A fourth no-story case must be checked against these three categories first.** If it genuinely fits one, name which and why, per the existing per-ADR convention above — don't invent a fourth category speculatively. If it doesn't fit any of the three, that is itself a signal the "one user story per ADR" default should hold, not that a new category should be added to accommodate it.

Picking a story up to build it follows [`docs/implementation-methodology.md`](../implementation-methodology.md) — a Jest contract written from its Acceptance Criteria before any implementation code, a component `SKILL.md` kept current, and permanent regression coverage. Invoke the `implement-story` skill rather than implementing ad hoc.
