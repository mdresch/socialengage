# Epic 14: Publishing extensions and research refinements (ADRs 0118–0121)

Stories derived from ADRs 0118–0121, extending ADR-0075's outbound publishing path, ADR-0076's Composer Deep Research, and the connector framework. All ADRs in this epic are Proposed — all stories are Blocked pending acceptance.

---

## Story 14.1 — Additional social platform publishing roadmap (backend)

**Source:** ADR-0118 · **Status:** Blocked — pending ADR acceptance
**Built:** not yet

**As a** backend engineer,
**I want** a build order and shared constraints for extending `SocialConnector.publish?()` to Instagram, Bluesky, Mastodon, Threads, and X,
**so that** the remaining Polypost Composer preview rails have a clear implementation sequence without premature commitment to high-cost or unverified platforms.

**Acceptance Criteria**
- The build order is documented: Mastodon → Bluesky → Instagram → Threads → X/Twitter, after Facebook (Story 2.29) and LinkedIn (Story 2.30).
- Each platform's `publish?()` implementation reuses the `outbound_activities` table and `SocialConnector.publish?()` contract from ADR-0075.
- Each platform uses `RequestGate` with key `(tenantId, providerId, 'outbound_post')`, separate from ingestion and research gates.
- Each platform requires a Tier-3 (user-bound) credential under ADR-0028/ADR-0014.
- v1 `publish()` for each platform supports text and link-card only; image/video media upload is explicitly out of scope (depends on ADR-0115).
- No per-platform implementation begins without a separate, primary-source-verified, accepted ADR for that platform (per ADR-0048 and ADR-0027).
- X/Twitter requires explicit re-evaluation before building, due to cost and review barriers.

**Dependencies:** Story 2.29 (Facebook publish) and Story 2.30 (LinkedIn publish) must be built first. Per-platform ADRs (e.g., a future Mastodon publishing ADR) must be drafted and accepted before any platform in this story's scope is implemented.

## Story 14.2 — Editing and deleting published outbound posts (backend)

**Source:** ADR-0119 · **Status:** Blocked — pending ADR acceptance
**Built:** not yet

**As a** `Tenant-User`,
**I want** to edit or delete a post I have already published through the Polypost Composer,
**so that** I can correct mistakes or remove outdated content while preserving a full audit trail of every change.

**Acceptance Criteria**
- A new `outbound_activity_revisions` table records every edit and delete as a separate row (`revision_type: 'edit' | 'delete'`, `status: 'pending' → 'applied' | 'failed' | 'cancelled'`), tenant-scoped via RLS.
- `outbound_activities` gains nullable `edited_at` and `deleted_at` columns, updated only when a revision reaches `'applied'`; the table does not store `current_body` — the latest non-failed `'edit'` revision is the source of truth.
- `PATCH /v1/outbound/activities/:id` creates an `'edit'` revision; if the parent is still `pending`, the body is updated in place without calling the connector; if `sent`, the connector's `edit?()` is called.
- `DELETE /v1/outbound/activities/:id` creates a `'delete'` revision for `sent` activities, or cancels `pending` activities without a revision.
- `GET /v1/outbound/activities/:id/revisions` lists all edits and deletes in `created_at` descending order.
- Connectors that do not implement `edit` return `422` with code `edit_not_supported`; connectors that do not implement `delete` return `422` with code `delete_not_supported`.
- Authorization: the caller must be the same `user_id` who created the original activity, or a `tenant_admin` in the same tenant; `platform_admin` has no access.
- `SocialConnector` interface gains optional `edit?()` and `delete?()` methods.

**Dependencies:** ADR-0075 (Story 2.28–2.30, outbound publishing) must be built first. Per-platform edit/delete support requires primary-source verification before each connector implements these methods.

## Story 14.3 — SearchProviderConnector abstraction (backend)

**Source:** ADR-0120 · **Status:** Blocked — pending ADR acceptance
**Built:** not yet

**As a** backend engineer,
**I want** a shared `SearchProviderConnector` interface for one-off web search,
**so that** Brave Search, Bing Search, and future search providers can be called on demand without duplicating query building and rate-limit logic across features.

**Acceptance Criteria**
- A new `SearchProviderConnector` interface is defined with `providerId` and optional `search?(ctx, request): Promise<SearchResponse>`.
- `SearchRequest` includes `q`, `limit` (default 5, hard cap 10), `freshness` (`'any' | 'day' | 'week' | 'month'`), and optional `market`.
- `SearchResponse` returns `results[]` with `title`, `url`, `snippet`, and optional `publishedAt`.
- Search providers are registered in the connector registry (ADR-0048) and loaded by `bootstrapConnectors.ts`.
- A search provider must be activated (`connector_activations`, ADR-0051) and have a tenant/user credential (ADR-0028) before it is callable.
- One-off search uses `RequestGate` with key `(tenantId, providerId, 'search')`, separate from ingestion, outbound, and research gates.
- `POST /v1/composer/research` (ADR-0076) is the first consumer; the existing internal `searchForResearch` helpers are refactored to use the new abstraction.
- Connectors that do not implement `search` return `search_not_supported` when called.

**Dependencies:** ADR-0076 (Stories 2.31–2.32, Composer Deep Research) must be built first, since this ADR generalizes its internal helpers.

## Story 14.4 — Composer Deep Research caching, re-trigger, and cost telemetry (backend)

**Source:** ADR-0121 · **Status:** Blocked — pending ADR acceptance
**Built:** not yet

**As a** `Tenant-User`,
**I want** Composer Deep Research results to be cached and re-triggerable with cost visibility,
**so that** iterating on a draft does not incur redundant provider costs and I can see what research is costing my tenant.

**Acceptance Criteria**
- A new `research_cache` table (RLS-scoped by `tenant_id`) stores results keyed by `text_hash` (sha256 of normalized text + active provider ids), with `expires_at` from `tenant_settings.research_cache_ttl_hours` (default 24, max 168).
- `POST /v1/composer/research?refresh=true` bypasses the cache, re-runs the pipeline, and overwrites the old cache row for the same `text_hash`.
- A new `research_runs` table records every research request with `tenant_id`, `user_id`, `text_hash`, `ai_provider_id`, `search_provider_ids`, `cache_hit`, `tokens_in`, `tokens_out`, `estimated_cost_usd`, and `created_at`.
- `research_daily_request_cap` (default 50, max 500) in `tenant_settings` returns `429 RESEARCH_DAILY_CAP_EXCEEDED` when exceeded.
- `research_monthly_cost_cap_usd` (optional, default `null`) returns `422 RESEARCH_MONTHLY_COST_CAP_EXCEEDED` when the monthly cost sum would exceed the cap (may be deferred to a later iteration per Decision §4).
- Re-trigger is user-initiated via `?refresh=true`; there is no background re-scheduler.
- `estimated_cost_usd` is a best-effort estimate, not a billing ledger (ADR-0027 — SocialEngage is not a billing intermediary).

**Dependencies:** ADR-0076 (Stories 2.31–2.32, Composer Deep Research) must be built first.
