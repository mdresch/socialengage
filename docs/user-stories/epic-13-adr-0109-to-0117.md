## Story 13.1 — Connector health auto-disable and recovery (backend)

**Source:** ADR-0109 · **Status:** Built
**Built:** 2026-08-31 — social-listening-core@29b274c

**As a** backend engineer,
**I want** `failing`/`degraded`/`disabled` health transitions and explicit re-enable rules,
**so that** failing connectors stop polling and can be safely re-enabled.

**Acceptance Criteria**
- `ConnectorHealth` transitions to `failing` after 5 consecutive failed `ingestion_runs`.
- Non-retryable failures immediately disable the connector.
- `POST /v1/connectors/:platformId/enable` re-enables a connector with a health-check attempt.
- Disabled connectors do not poll.
- `ConnectorIngestionAlertEvent` is emitted on `failing` → `disabled`.

## Story 13.2 — Per-connector query translation and validation (backend)

**Source:** ADR-0110 · **Status:** Built
**Built:** 2026-08-31 — social-listening-core@da31be9

**As a** backend engineer,
**I want** `ConnectorQueryTranslator` and `GET /v1/connectors/:platformId/query-capabilities`,
**so that** watchlist ASTs are translated to native queries and unsupported clauses fail at save time.

**Acceptance Criteria**
- Each connector has a translator implementing `supportedClauses`, `maxClauseCount`, `maxQueryLength`, and `translate()`.
- `GET /v1/connectors/:platformId/query-capabilities` returns capabilities.
- Save-time validation returns `422 UNSUPPORTED_QUERY_CLAUSE`.
- Contract tests assert native query shapes for reference ASTs.
- Fallback matching remains the safety net.

## Story 13.4 — Export bounding, streaming, and size caps (backend)

**Source:** ADR-0111 · **Status:** Built
**Built:** 2026-09-01 — social-listening-core@209b0d7

**As a** backend engineer,
**I want** `export_jobs`, sync/async thresholds, Blob lifecycle, and rate limits for CSV/JSON exports,
**so that** exports cannot overwhelm the platform.

**Acceptance Criteria**
- Synchronous exports up to 5,000 rows; async up to 100,000 rows.
- `POST /v1/posts/export` creates `export_jobs` and streams to Blob.
- `export_jobs` table tracks status, row count, blob path, SHA-256, and expiry.
- Rate limits: 60 sync/hour, 20 async/hour, 120 status/hour, 10 downloads/hour per tenant.
- Blob objects expire after 7 days; presigned download URLs expire after 24 hours.

## Story 13.7 — Metric explainability prompt and caching (backend)

**Source:** ADR-0113 · **Status:** Built
**Built:** 2026-09-01 — social-listening-core@05e1e43

**As a** backend engineer,
**I want** a versioned prompt, deterministic output, and 5-minute caching for `POST /v1/explain`,
**so that** metric explanations are consistent and affordable.

**Acceptance Criteria**
- Prompt template v1 is versioned and stored.
- Model is called with `temperature=0` and a fixed seed.
- JSON output contains `explanation` and `confidence`.
- Cache key uses `SHA256(tenantId, metricKey, value, timeRange, filters, promptVersion)`.
- Every call is logged in `platform_admin_audit_log`.

## Story 13.11 — Semantic drift detection (backend)

**Source:** ADR-0116 · **Status:** Ready (depends on Epic 9 RAG)
**Built:** 2026-09-02 — social-listening-core@bb0545a

**As a** backend engineer,
**I want** `SemanticDriftService` and `GET /v1/topics/:id/drift`,
**so that** `Topic-Center-Analyst` can see when a topic's meaning shifts over time.

**Acceptance Criteria**
- Compute centroid vectors for two time windows and return `driftScore`.
- Cluster chunks in each window and produce `topClustersNow` and `topClustersThen`.
- `driftScore >= 0.5` triggers `warning: 'significant'`.
- Results are cached for 24 hours.
- Depends on working `RAGConnector` and indexed chunks.

**so that** `Social-Selling-Strategist` can export or push leads to a CRM.
