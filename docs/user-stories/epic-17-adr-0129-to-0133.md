# Epic 17: Research-driven ADR revisions — Lists, Onboarding & Analytics (ADRs 0129–0133)

## Story 17.1 — Deduplicated prospecting list export and sharing ACLs (backend)

**Source:** ADR-0129 (Accepted 2026-08-28) · **Status:** Ready  
**Built:** 2026-09-08 — social-listening-core@53e63ba  
*(Relates to Story 10.1 — see epic-10 for foundation; relates to Story 11.17 and Story 13.13)*

**As a** `Social-Selling-Strategist` or sales team lead,  
**I want** granular workspace list sharing permissions (`private`, `workspace_read`, `workspace_write`) and automated cross-network author deduplication during CRM handoff,  
**so that** my team can collaboratively qualify leads without creating duplicate contacts or colliding accounts in the downstream CRM.

**Acceptance Criteria**
- `prospecting_lists` table schema updated with `sharing_scope TEXT NOT NULL DEFAULT 'private' CHECK (sharing_scope IN ('private', 'workspace_read', 'workspace_write'))`, backfilling existing rows where `shared = TRUE` to `'workspace_read'`.
- PostgreSQL Row Level Security (RLS) policies refined:
  1. Teammates in the same tenant can view lists with `sharing_scope IN ('workspace_read', 'workspace_write')`.
  2. Teammates can `INSERT`, `UPDATE`, and `DELETE` entries (`prospecting_list_entries`) when `sharing_scope = 'workspace_write'`.
  3. Mutating the list itself (modifying `name`, `description`, `sharing_scope`, or deleting via `DELETE /v1/prospecting-lists/:id`) remains strictly restricted to `owner_id`. Non-owner attempts to mutate list properties fail with `403 Forbidden`, and deletion attempts fail with `404 Not Found` via RLS isolation.
- `PATCH /v1/prospecting-lists/:id/sharing` accepts `{ "sharingScope": "private" | "workspace_read" | "workspace_write" }`, requiring `owner_id` authentication.
- `POST /v1/prospecting-lists/:id/crm-handoff?deduplicate=true` clusters multiple `Author` records sharing the same canonical social handle across networks (or verified cross-platform profile links) into a unified `DeduplicatedAuthorContact` CRM payload with merged notes, highest engagement/influence scores, and combined platform handles.
- Deduplication clustering preserves distinct records when handles do not conclusively match, avoiding false-positive author merges.
- Audit events recorded: `prospecting_sharing_scope_changed`, `prospecting_teammate_mutation`, and `prospecting_contacts_deduplicated`.
- Executable contract test citations: `social-listening-core/contracts/epic-17/story-17.1.prospecting-list-refinements.contract.test.ts`.

## Story 17.2 — Role-tailored onboarding journeys with automated probe verification (frontend/backend)

**Source:** ADR-0130 (Accepted 2026-08-28) · **Status:** Ready  
*(Relates to Story 9.5 — see epic-9 for foundation; relates to Story 5.11)*

**As an** onboarded tenant user with a specific enterprise role (`Tenant-Admin`, `Tenant-Social-Care-Agent`, `Social-Selling-Strategist`, or `Tenant-Brand-Reputation-Manager`),  
**I want** an onboarding journey tailored to my functional responsibilities with background verification probes that automatically confirm live data operations,  
**so that** I am guided through relevant operational workflows and milestones auto-complete based on real system traffic rather than superficial entity creation.

**Acceptance Criteria**
- `tenant_onboarding_state` schema expanded with `role_journeys JSONB NOT NULL DEFAULT ...` tracking milestone completion across 4 primary personas:
  1. `admin`: Connect live source, invite team member, configure crisis escalation rule.
  2. `care_agent`: Open unified inbox, claim unassigned ticket, dispatch outbound reply.
  3. `social_seller`: Search creator catalog, create prospecting list, execute CRM handoff.
  4. `brand_manager`: Define complex boolean query watchlist, configure notification digest, inspect metric anomaly explainability.
- Automated background verification probes (`AutomatedVerificationProbeRunner`) validate live operational traffic:
  1. *Ingestion Traffic Probe:* Verifies at least one successful ingestion run (`ingestion_runs.status = 'success' AND items_ingested > 0`).
  2. *Watchlist Match Probe:* Confirms matching posts exist (`post_watchlist_matches > 0`).
  3. *Triage Probe:* Confirms an actual care reply was dispatched (`outbound_activities.status = 'dispatched'`).
  4. *CRM Push Probe:* Confirms successful execution of CRM handoff (`crm_handoff status = 'success'`).
- `GET /v1/onboarding/checklist?role=<role>` executes active probes, updates `tenant_onboarding_state.role_journeys`, and returns the role step tree with progress percentages and next actionable steps.
- Frontend onboarding widget in `social-listening-admin` dynamically renders the tailored checklist based on current session role, with real-time status badges, completion percentage, and direct action links.
- Non-blocking execution: daily operations are never locked if onboarding steps remain incomplete, and steps can be completed in any order.
- Executable contract test citations: `social-listening-core/contracts/epic-17/story-17.2.onboarding-probes.contract.test.ts` and `social-listening-admin/contracts/epic-17/story-17.2.onboarding-journeys-ui.contract.test.ts`.

## Story 17.3 — Crisis threshold baseline calibration and escalation matrix (backend)

**Source:** ADR-0131 (Accepted 2026-08-28) · **Status:** Ready  
**Built:** not yet  
*(Relates to Story 9.3 — see epic-9 for foundation; relates to Story 11.9)*

**As a** brand reputation manager or on-call crisis responder,  
**I want** automated rolling 14-day statistical baseline calibration and multi-tier incident escalation matrices,  
**so that** crisis alerts reflect true statistical anomalies ($Z$-score deviations) rather than brittle static post counts, and unacknowledged critical incidents deterministically escalate through notification tiers.

**Acceptance Criteria**
- Database tables `crisis_baseline_metrics`, `crisis_escalation_rules`, and `crisis_incident_logs` created with PostgreSQL RLS isolation and time-bucket indexing.
- Baseline calibration worker continuously calculates rolling 14-day mean ($\mu$) and standard deviation ($\sigma$) of mention velocity and negative sentiment ratio per watchlist bucketed by hour and day-of-week.
- Statistical Z-score evaluation:
  $$Z = \frac{\text{Observed Hourly Volume} - \mu_{14\text{d}}}{\sigma_{14\text{d}}}$$
  Incident tiers trigger dynamically (Tier 1: $Z \ge 2.0\sigma$, Tier 2: $Z \ge 3.0\sigma$, Tier 3: $Z \ge 4.5\sigma$) when accompanied by elevated negative sentiment ($\ge 40\%$).
- Stateful escalation engine tracks unacknowledged incidents (`ack_timeout_minutes`, default 15m) and deterministically escalates:
  1. *Tier 1:* Slack/Teams webhook to Care Agent triage channel.
  2. *Tier 2:* SMS / PagerDuty alert to Brand Reputation Manager.
  3. *Tier 3:* Executive notification / emergency phone call broadcast.
- Incident lifecycle management API:
  - `POST /v1/crisis/incidents/:id/acknowledge` records responder identity and halts escalation timers.
  - `POST /v1/crisis/incidents/:id/resolve` archives the incident with mandatory root-cause notes and resolution timestamps.
- Executable contract test citations: `social-listening-core/contracts/epic-17/story-17.3.crisis-baseline-escalation.contract.test.ts`.

## Story 17.4 — Parameterized AST query templates with budget governor (backend)

**Source:** ADR-0132 (Accepted 2026-08-28) · **Status:** Ready  
*(Relates to Story 10.4 — see epic-10 for foundation; relates to Story 10.5)*

**As a** system architect / database administrator,  
**I want** ad-hoc analytics queries compiled strictly into parameterized AST templates with an active pre-execution cost governor,  
**so that** SQL injection and unindexed full-table cartesian scans cannot exhaust database shared memory or degrade tenant ingestion performance.

**Acceptance Criteria**
- Query generation completely eliminates dynamic string interpolation; all queries compile into immutable Abstract Syntax Tree (AST) templates with positional parameterized placeholders (`$1, $2, ...`).
- Pre-execution cost governor evaluates candidate queries via internal `EXPLAIN (FORMAT JSON)` against PostgreSQL planner:
  - If `Plan['Total Cost'] > 10,000` units, the query is rejected immediately with HTTP 422 `QUERY_COST_EXCEEDED`, returning estimated cost, budget ceiling, and suggested filter adjustments.
- Query execution runs within strict transactional safeguards: `SET LOCAL statement_timeout = '3000ms'` (reduced from 5000ms) and `SET LOCAL work_mem = '32MB'`.
- Maximum returned rows hard-capped at 5,000 to prevent Node.js heap buffer exhaustion.
- Role gating permits ad-hoc queries only for authorized analytics roles (`tenant_admin`, `analyst`); tenant isolation enforced via `app.current_tenant_id` session variables.
- Executable contract test citations: `social-listening-core/contracts/epic-17/story-17.4.ast-query-governor.contract.test.ts`.

## Story 17.5 — Metric anomaly statistical significance gate (backend)

**Source:** ADR-0133 (Accepted 2026-08-28) · **Status:** Ready  
*(Relates to Story 9.2 and Story 13.7 — see epic-9 and epic-13 for foundation; relates to Story 8.8)*

**As a** brand analyst or operations manager,  
**I want** metric shift explainability requests validated through a statistical significance gate ($p < 0.05$) and decomposed into root-cause factors before LLM generation,  
**so that** non-significant background fluctuations do not generate hallucinatory or wasteful LLM explanations, and significant shifts provide structured multi-factor attribution.

**Acceptance Criteria**
- Statistical significance gate pre-evaluates metric deltas against rolling 30-day baseline distribution ($\mu, \sigma$):
  $$Z = \frac{|\Delta - \mu|}{\sigma}, \quad p = 2 \cdot (1 - \Phi(Z))$$
- When $p \ge 0.05$ ($Z < 1.96$), the metric shift is categorized as background noise. `POST /v1/explain` returns HTTP 200 with `{ isStatisticallySignificant: false, zScore, pValue, explanation: "Metric shift is within expected natural variance...", tokenCostSaved: true }` without invoking Azure OpenAI.
- When $p < 0.05$, the system triggers multi-factor root-cause decomposition, calculating:
  1. Volume delta percentage (`volumeDeltaPercent`).
  2. Sentiment shift contribution (`sentimentShiftContribution`).
  3. Dominant contributing platform (`dominantPlatform`).
  4. Top contributing topic or keyword cluster (`topContributingTopic`).
  5. Top author influence concentration ratio (`topAuthorImpactRatio`).
- The structured decomposition is injected into the Azure OpenAI prompt, producing an authoritative, mathematically grounded narrative explanation with deterministic caching.
- Executable contract test citations: `social-listening-core/contracts/epic-17/story-17.5.metric-anomaly-significance-gate.contract.test.ts`.
