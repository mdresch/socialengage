# Epic 19: RAG architecture revision — namespace-per-tenant isolation (ADRs 0136–0140)

## Story 19.1 — RAG connector provider abstraction with namespace-per-tenant (backend)
**Source:** ADR-0136 (Accepted 2026-08-28 — this line previously said "Proposed", stale; corrected 2026-09-13 against ADR-0136's own status header and `docs/adr/README.md`) · **Status:** Built (*Documentation Steward correction, 2026-09-16: was "Ready" despite an already-populated Built field — same recurring drift class as Stories 17.1–17.3/18.1/18.2.*)  
**Built:** 2026-09-13 — social-listening-core@8962e1d  
*(Relates to Story 9.7)*

**As a** platform architect and security auditor,
**I want** `PgvectorRAGConnector`'s tenant isolation for `rag_chunks` to be enforced by the database (Postgres Row-Level Security) as the primary mechanism, not solely by application-level filtering,
**so that** a bug in the connector's own in-process filter logic cannot leak one tenant's vector-embedded post content to another tenant.

**Acceptance Criteria**
- **AC1:** `RAGConnector` gains an optional `ensureTenantNamespace?(tenantId: string): Promise<void>` hook; every existing implementer/caller requires no change.
- **AC2:** `RAGConnectorStatus` gains an `isolationModel` field; `PgvectorRAGConnector.status()` reports `'row-level-rls'`, only ever true because it is genuinely enforced.
- **AC3:** `PgvectorRAGConnector`'s tenant-scoped queries (`upsert`/`search`/`deletePost`/`deleteTenant`/`status(tenantId)`) execute via the non-superuser `app_user` role (`withTenant()`/`getPool()`), never the superuser admin pool that unconditionally bypasses RLS.
- **AC4:** A contract test proves `rag_chunks`' existing RLS policy blocks cross-tenant access at the database layer, independent of the connector's own application-level filter.
- **AC5:** The existing application-level `tenant_id` filter in `upsert`/`search`/`deletePost`/`deleteTenant` remains unchanged, as mandatory defense-in-depth.
- **AC6:** `deleteTenant()`'s deletion mechanics and the deterministic vector ID scheme (`${tenantId}:${postId}:${chunkIndex}`) are unchanged.
- **AC7:** `ragConnectorRegistry.ts` registers only `pgvector` at the end of this story (scope guard against Story 19.3 creep).

## Story 19.2 — RAG chunking and embedding namespace routing (backend)
**Source:** ADR-0137 (Accepted 2026-08-28 — this line previously said "Proposed", stale; corrected 2026-09-13 against ADR-0137's own status header) · **Status:** Built (*Documentation Steward correction, 2026-09-16: was "Ready" despite an already-populated Built field — same recurring drift class as Story 19.1 above.*)  
**Built:** 2026-09-13 — social-listening-core@a12b947  
*(Relates to Story 9.8)*

**As a** backend engineer maintaining the RAG chunking/embedding pipeline,
**I want** `indexPostForRAG()` to provision a connector's per-tenant namespace before writing vectors, and its own `rag_chunks_sync` bookkeeping write to be database-enforced per tenant the same way `rag_chunks` now is,
**so that** the pipeline is ready for a future namespace-capable vector-store provider without a second breaking change, and no sibling table is left with the same admin-pool RLS bypass Story 19.1 just closed for `rag_chunks`.

**Acceptance Criteria**
- **AC1:** `RAGChunkingService.split()`/`.embed()` and `indexPostForRAG()`'s `connector.upsert(tenantId, ...)` call require no signature change — namespace/shard/RLS routing stays fully encapsulated in the connector (ADR-0136).
- **AC2:** `indexPostForRAG()` calls `connector.ensureTenantNamespace?.(tenantId)` immediately before `upsert()`, inside the existing per-attempt retry block — a no-op for any connector that doesn't implement the hook.
- **AC3:** `indexPostForRAG()`'s `rag_chunks_sync` write executes via `withTenant()`/`getPool()` (`app_user`), never the superuser admin pool.
- **AC4:** A contract test proves `rag_chunks_sync`'s RLS policy blocks cross-tenant access to data written through the real `indexPostForRAG()` call site.
- **AC5:** `backfill.ts`, `ragReconciliationService.ts`, and the pipeline's own (pre-existing, separately-flagged) orphan-chunk-cleanup loop remain unchanged (scope guard against Story 19.3 and future Story 9.8 revisit creep).

## Story 19.3 — RAG vector-store namespace isolation and pgvector RLS (backend)
**Source:** ADR-0138 (Accepted 2026-08-28 — this line previously said "Proposed", stale; corrected 2026-09-14 against ADR-0138's own status header) · **Status:** Built (*Documentation Steward correction, 2026-09-16: was "Ready" despite an already-populated Built field — same recurring drift class as Stories 19.1/19.2 above.*)  
**Built:** 2026-09-14 — social-listening-core@1e71d7e  
*(Relates to Story 9.9)*

**As a** platform architect and security auditor,
**I want** `RAGReconciliationService`'s orphan-detection query to actually be evaluated under `rag_chunks`'/`social_posts`' Row-Level Security policies instead of running with no tenant session context at all,
**so that** the reconciliation logic genuinely finds and removes orphaned vector chunks when invoked, rather than silently failing closed and finding nothing, forever.

**Acceptance Criteria**
- **AC1:** `reconcileOrphanedRAGChunks()`'s real-DB branch calls `withTenant()` — confirmed pgvector's own RLS mapping (interface, connector queries, `FORCE ROW LEVEL SECURITY`) was already fully delivered by Story 19.1 and is not re-decided here.
- **AC2:** A genuine orphan (a `rag_chunks` row whose `post_id` no longer exists in `social_posts`) is found and deleted through the real production call site.
- **AC3:** A live post (present in both `social_posts` and `rag_chunks`) is left untouched by reconciliation.
- **AC4:** The orphan's corresponding `rag_chunks_sync` row is also deleted.
- **AC5:** Reconciling one tenant never touches another tenant's own orphaned rows.
- **AC6 (scope guard):** No Pinecone/Azure AI Search connector is built; the reconciliation scheduler itself (nothing currently invokes this service, ever) and `RAGChunkMetadata`/`RAGConnector` interface changes remain explicitly out of scope.
