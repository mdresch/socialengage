# Open decisions — unresolved ADR questions requiring a human go/no-go

**As of 2026-08-05.** Every Accepted ADR in `docs/adr/` locks a durable Decision and a set of implementation defaults — but several also carry their own explicitly-named "Open Question(s)" section: a sub-piece the ADR itself flags as genuinely undecided rather than blocking on. "All ADRs Accepted" (`docs/adr/README.md`'s own tracker) means nothing is left un-reviewed; it does not mean every question inside every ADR has been decided. This file is the first full sweep pulling those together into one place, so they can be decided deliberately instead of discovered one at a time.

**Scope and relationship to other docs:**
- This file is decisions not yet made. [`docs/open-items-and-deferred-work.md`](open-items-and-deferred-work.md) (its own Section D covers the same category more narrowly — see the pointer note added there) is work not yet built, a different thing — most items there are deliberate scope cuts with no decision pending, just implementation waiting on a trigger (a real subscriber, a second connector, a real deployment target).
- Each item below traces back to a specific ADR's own "Open Question(s)" section, or (for the last few) `docs/adr/README.md`'s own brainstorm/outstanding-items list. Check the cited ADR directly before acting on any of these — this file summarizes, the ADR is the source of truth.
- Not append-only, not CI-verified. Update in place as items get decided — cite the resolving ADR/Amendment Log/Acceptance note the same way `docs/adr/README.md` itself does, don't just delete the line.

**2026-08-06 — every item below is pre-Go-Live technical debt, not a live production risk.** `docs/project docs/Project Management Plans/Go-Live-Readiness-Definition.md` §1 states this explicitly: nothing in this project is reachable by a real end user today, so an open question here has zero current blast radius — it must still get resolved, and several items below are explicit Go-Live gate criteria (§5.3), but none represents an active danger while the system's classification stays at Stage 0.

- ~~**[ADR-0028]** Reddit's actual current API/commercial-use terms — flagged as secondary-sourced only, not yet verified to this project's primary-source bar. Matters once Reddit (the next connector on the roadmap) is scoped.~~ — **substantially resolved 2026-08-06, still secondary-sourced (Reddit's own domains are blocked from direct fetch in this environment):** self-service API registration closed late 2025 under Reddit's "Responsible Builder Policy" — every new OAuth token now requires prior approval via a request form, and community reporting is consistent that approval is "slow and often silent for commercial workloads" (SocialEngage's own use case) and "effectively closed for personal use." The Data API Terms (`redditinc.com/policies/data-api-terms`, last updated April 2023) require developers to delete Reddit content within 48 hours of its own deletion on Reddit, and to purge all author-identifying information when an account is deleted — a materially faster, narrower obligation than anything ADR-0018/ADR-0039 currently design for. ML training on Reddit content is barred without a separate licensing deal (relevant to ADR-0038 if Reddit is ever added). Net: Reddit is real access risk for this project's own commercial use case, not just an unverified-terms footnote — see the 2026-08-06 connector-comparison note below.
- **2026-08-06 — connector-comparison research, prompted by the Reddit finding above, covering X, YouTube, Meta, and Wikipedia** (secondary-sourced throughout; Reddit/X/Meta primary domains could not be directly fetched in this tool environment — Wikimedia's own domain could, and was fetched directly). Not yet a decision — recorded here as real, sourced groundwork for one:
  - **X (Twitter):** self-service but pay-per-use only since February 2026 — no free tier for new developers. $0.005/read, capped at 2,000,000 reads/month before an Enterprise contract (reportedly ~$42,000/month) is required. A single active watchlist doing real keyword/boolean matching could plausibly approach that cap on its own. Under ADR-0027/ADR-0028's existing "bring your own credential" model, this cost and ceiling would fall on each tenant individually, not SocialEngage — but a tenant would still need their own paid X developer account, a materially bigger ask than any connector built so far, and realistically requires that tenant's own internal approval (finance for the recurring cost, IT for provisioning) before they'd ever reach SocialEngage's own connect flow. Worth naming as its own vetting factor per the still-open "does a paid-tier signup mechanism itself warrant its own vetting criterion" question two lines up.
  - **YouTube:** free for commercial use, no paid tier exists (Google will not sell more quota at any price), self-service default 10,000 quota-units/day with a request form for higher limits. One real, unresolved conflict: YouTube's terms restrict "storing API data long-term beyond allowed windows" — the exact window isn't yet confirmed, but this is the same category of tension Reddit's 48-hour rule creates against ADR-0018's indefinite/tiered-retention design, at a smaller but still real scale.
  - **Meta (Facebook/Instagram):** confirmed easy, free, no-App-Review access exists for managing a tenant's *own* Page/account ("Standard Access"). **Not yet confirmed either way:** whether Meta's API supports the actual social-listening use case (searching/monitoring *other* people's public posts) at all — that capability was heavily restricted platform-wide after 2018 and is typically gated behind a separate Marketing Partner relationship, not ordinary app review. Treat "Meta connector" as two different, unequally-verified propositions (owned-page tracking vs. broad public listening) until the second one is actually checked.
  - **Wikipedia:** the best-grounded candidate found. Commercial reuse of content is explicitly permitted (CC BY-SA 4.0 / GFDL dual license, confirmed directly from `foundation.wikimedia.org`'s own Terms of Use); API access is self-service with no approval gate, just a compliant `User-Agent` header (Wikimedia's own User-Agent Policy, fetched directly); no commercial/non-commercial distinction exists in the API Usage Guidelines (fetched directly); attribution is satisfied by linking to an article's own contributor-history page rather than requiring a single named author, which resolves the "who is *the* author" data-model friction that would otherwise apply (ADR-0004's `Author` is a single-FK-per-post model, and a Wikipedia article typically has many editors); share-alike only triggers on modification of the text, not passive ingestion/display; licenses cannot be revoked once granted. One real, confirmed restriction: Wikimedia's API terms forbid sublicensing/reselling API access or white-labeling in a way that obscures Wikimedia as the provider — no obstacle to using the API to power SocialEngage's own product, the same posture ADR-0027 already establishes for every other connector.
  - **Net effect on connector order:** Wikipedia is a stronger near-term candidate than Reddit given everything above — not yet a formal decision (needs its own ADR, the same bar ADR-0024/0026 held Newswire/GNews to), but real enough to prioritize investigating over Reddit specifically. See `docs/implementation-plan.md`'s Phase 4 note for the corresponding dated update.
