# AI Role Charters

Reusable prompt charters for the externally-invoked AI reviewers registered in `docs/project docs/Stakeholder-Register.md` (S-10, S-14, S-15, S-16, and — added 2026-08-05 — S-22, S-23). Each is chartered to **pull hard on one domain** rather than produce a balanced, softened summary — see the Stakeholder Register's 2026-07-31 second addendum for the design principle and its real precedent (Story 2.5's traced-blast-radius-then-pause-for-sign-off pattern in `docs/implementation-log.md`). Reconciling what the different roles argue for is Menno's job as Sponsor, not something any of these roles do for him.

These are **human-mediated by default**, not wired into this repo's `implement-story`/`heal-contract-failure` enforcement: paste the charter's prompt block into the named model's own chat session along with the material under review, then bring the findings back yourself. That stays a deliberate boundary — see `docs/implementation-plan.md`'s repeated "don't build speculatively" discipline (the same reasoning behind ADR-0020's deferred distributed rate-limit gate); wiring these into the mandatory methodology would be a real, separate decision, not a side effect of defining the charters. **Human-mediation is unchanged by the cadence update below — a human (Menno) must still actually paste a charter into a session for anything to happen. The cadence update changes *when* that should happen, not whether a human still has to do it.**

## When to invoke — regular checkpoints, not purely ad hoc (added 2026-08-05)

Every one of this project's domain-pull roles — all eleven of them, external and internal alike (`Stakeholder-Register.md` §4 enumerates the full list; see that section rather than assuming a count here) — was originally described as invoked purely at Menno's own ad hoc judgment call, each time, with no standing trigger. That's now changed to a **standing cadence**, on top of (not instead of) Menno's own judgment for anything else that comes up:

1. **Before every architecturally significant ADR is accepted** — the same bar this project's own ADR series already uses to decide whether something needs an ADR at all (`docs/adr/README.md`'s own repeated "hard-to-reverse, real security/compliance consequence, not just a new field/endpoint shape" standard, e.g. ADR-0027/0028/0035/0036/0038's own framing). Consult whichever domain-pull reviewer(s) the ADR's subject matter actually implicates — a credential or tenant-boundary decision implicates Security; a retention/deletion/regulatory decision implicates Legal & Compliance and Data Sovereignty & Privacy Regulation; an entity/relationship-modeling decision implicates the Knowledge-Graph & Semantic Data Modeling Reviewer; and so on. Not every ADR needs every reviewer — match the reviewer(s) to the decision's actual subject matter, the same targeted-consultation judgment this project already exercises everywhere else.
2. **At each Phase milestone** in `docs/implementation-plan.md`'s own phase structure (Phase 0 through Phase 5, plus the inserted Phase 4.5) — a checkpoint pass across the domain-pull roles relevant to what that phase actually shipped, not a mandatory pass through all eleven every time.

This is a real governance change to *when* these roles get used, not merely new-role scoping — it applies to all eleven domain-pull roles, including the seven that predate this update, not just the three added 2026-08-05. See `Stakeholder-Register.md` §3.4's 2026-08-05 addendum and §4's updated "Keep Informed"/"Governed" framing for the register-side version of this same change.

**One exception, added 2026-07-31:** the Engineering Pragmatism Reviewer (Mistral) can also be invoked via real API automation, `docs/ai-roles/scripts/invoke-mistral-agent.cjs`, once its Mistral-hosted agent is configured with the charter below as its system instructions. Setup: copy `docs/ai-roles/.env.example` to `docs/ai-roles/.env` (gitignored — never commit real values) and fill in `MISTRAL_API_KEY` and the agent's ID. **A second exception, also added 2026-07-31:** the Data Privacy & Sovereignty Reviewer now has its own automated path too — `docs/ai-roles/scripts/invoke-ollama-agent.cjs` — but it's deliberately different in kind from the Mistral one: it only ever calls Ollama's *local* REST API (`localhost:11434`, no network egress to any third party), reads this charter's own "Prompt block" fresh from the `.md` file on every run instead of relying on a separately-configured hosted agent, and hard-refuses to run against any `:cloud`-suffixed Ollama model (Ollama's own hosted-proxy models, which would defeat the entire point). Setup: install Ollama and pull a model — no `.env`, no API key. Connectivity-tested 2026-07-31 on `qwen2.5:0.5b` (works, but too small for a substantive review); two larger local candidates (`llama3.1:8b`, `qwen2.5:3b`) both failed to load in this environment on memory-allocation errors, not a model-size-specific problem. **Update, 2026-08-05:** a working, meaningfully larger local model (`qwen3.5:9b`) is now available on Menno's machine, resolving that earlier blocker — but the Data Sovereignty & Privacy Regulation Reviewer role newly assigned to it (below) cannot yet be automated through this same script as written: `invoke-ollama-agent.cjs` today hardcodes a single charter path and default model (this role's own, S-16's). Generalizing it to a `--role` selector, mirroring `invoke-mistral-agent.cjs`'s own two-role pattern, is a real, named prerequisite, not yet built.

For the roles Claude Code *can* run natively as subagents (no human-mediated copy/paste needed), see `.claude/agents/`: `ba-requirements-analyst.md`, `qa-contract-author.md`, `documentation-steward.md`, the three `persona-*.md` persona-proxy agents, `ideal-manager.md`, and — added 2026-08-05 — `knowledge-graph-semantic-data-modeling-reviewer.md`. These plus the AI Delivery Agent itself are registered as **Governed** rather than externally invoked (Stakeholder Register S-09, S-11, S-12, S-13, S-17–S-19, S-20, and now S-24) — see that register's Section 3 for what each one actually does and, for the persona-proxy agents specifically, the hard limit on what their output is worth (design-time hypothesis, never real user validation).

**2026-08-05 addition — findings registers.** Until today, only the Security & Architecture Reviewer had a persistent findings log (`docs/security/security-register.md`, via `invoke-gemini-agent.mjs --register`); the other three pre-existing external reviewers (Product & Market-Fit, Engineering Pragmatism, Data Privacy & Sovereignty) have none yet — worth closing that gap in a future pass, following the same template, rather than leaving it inconsistent indefinitely. The two roles added today (Legal & Compliance, Data Sovereignty & Privacy Regulation) both got one from the start, plus the new internal Knowledge-Graph & Semantic Data Modeling Reviewer (`.claude/agents/knowledge-graph-semantic-data-modeling-reviewer.md`, not in the table above since it's Claude Code-invoked, not external) — see [`docs/architecture/knowledge-graph-register.md`](../architecture/knowledge-graph-register.md). That role has no invoke script at all (native Agent tool call) — its own charter instructs it to append its finding directly as the last step of every invocation, no manual copy/paste step needed the way the external roles require.

Product & Market-Fit and Engineering Pragmatism are two *separately configured* Mistral agents (different `agent_id`s, different personas, same account) — `docs/ai-roles/scripts/invoke-mistral-agent.cjs` takes a `--role pragmatism|product-market` flag to pick between them. This means two of the six external reviewers now share an underlying model, which dilutes some of the epistemic-diversity reasoning that motivated spreading roles across providers in the first place — accepted for practical reasons (OpenAI API access wasn't available on Menno's free-tier account), not because that reasoning stopped mattering. **Neither new role added 2026-08-05 was defaulted onto Mistral** for the same reason, made explicit rather than assumed: Mistral hit a real, concrete usage-limit/capacity exhaustion once already when it was the only provider available under load, and two of the four pre-existing external reviewers already share it. Mistral's own usage limits reset **2026-09-01** — this is a capacity-scarcity reason to prefer a different provider for these two roles *now*, not a permanent disqualification; **revisit Mistral for either new role, or for reducing the existing Product-Market/Engineering-Pragmatism overlap, once that reset has passed and capacity is confirmed less scarce.** Similarly, **Data Sovereignty & Privacy Regulation Reviewer now shares a model family (Ollama) with Data Privacy & Sovereignty Reviewer** — a second instance of the same two-roles-one-provider pattern already named above for Mistral, accepted here for a different, thematically-grounded reason (self-hosted/local hosting is a genuine fit for a role whose own domain is data sovereignty, not merely the provider that happened to be available) — see `data-sovereignty-privacy-regulation-reviewer.md`'s own "Provider selection, revised" section for the full reasoning and the honest capability trade-off it names.

**2026-08-06 addition — a third backend pattern, Microsoft Foundry Prompt Agents, and a real, empirically-corrected script for it (`docs/ai-roles/scripts/invoke-azure-foundry-agent.mjs`).** Requested directly by Menno, specifically to get hands-on with Foundry's own agent-authoring/prompt-optimization features, not purely to work around Mistral's capacity constraints (though that was the immediate trigger). This is a genuinely different invocation shape from the other two patterns already in this folder: Mistral's separately-configured hosted agent (referenced by opaque `agent_id`) and Gemini/Ollama's "send the charter's system instructions fresh on every call" pattern. A Foundry Prompt Agent is authored and versioned entirely in the Foundry portal (https://ai.azure.com) — this script's only job is to reference it by **name + version** and relay the material under review, authenticating via Microsoft Entra ID (`az login` / `DefaultAzureCredential`, **not** an API key, a real different credential shape from every other script here). Requires two new npm dependencies (`@azure/identity`, `@azure/ai-projects`) added to `docs/ai-roles/package.json`. **Product & Market-Fit Reviewer is the first role wired to this** — a real Prompt Agent, `ProductMarketFitReviewer` v2, already exists in Menno's own Foundry project, configured with this charter's own (2026-08-06-optimized) Prompt block. Legal & Compliance Reviewer has a provisioned Foundry model deployment but no Prompt Agent object of its own yet — not wired into this script speculatively ahead of that.

**Two real, empirically-found corrections during this same pass, not assumed from documentation or the portal's own generated sample code** (checked directly, Microsoft Learn — the generic docs describe an older, deprecated "classic" Threads+Runs REST flow that doesn't match current Prompt Agent invocation at all; even the Foundry portal's own "Code" tab sample turned out to be stale against the live API): (1) the request body's `agent` property is deprecated — the live API rejects it in favor of a top-level `agent_reference` object, with `type: "agent_reference"` nested *inside* that object, not beside it; (2) `AGENT_VERSION` cannot be the literal string `"latest"` — confirmed directly (a real `404 Agent ... with version latest not found`) — a published agent's version number must be bumped by hand in `.env` each time a new version is published in the portal. Both corrections are recorded in the script's own header comment, not just here.
