# Connector activation (decoupled from credential presence)

## What this is

`POST /v1/connectors/:platformId/activate` and `POST /v1/connectors/:platformId/deactivate` — a real, persisted, credential-independent "is this connector turned on" signal, separate from whether a credential is stored (`platform_credentials`) and separate from derived health (`ConnectorHealth`, ADR-0009). Closes two real, shipped bugs: `authMode: 'none'` connectors (Newswire) were hardcoded permanently "connected" with no opt-out; credentialed connectors conflated "has a stored secret" with "is turned on," so pausing one meant hard-deleting the credential via `deleteCredential()` and re-entering it later — the exact category of failure Menno described from the discontinued Microsoft Social Engagement product (a connector disconnected merely for exhausting quota).

## Governing ADRs and Stories

| ADR | Decision | Story |
|---|---|---|
| ADR-0051 | Two ownership-scoped activation tables, credential-independent; activation is a pure intent signal, asserting nothing about credential validity or health; lazy row creation (no pre-population); synchronous write only, no side-effecting call into ingestion | 1.11 |
| ADR-0028 | Tenant/user (Tier 2/Tier 3) ownership-scoping this story mirrors exactly | 1.11 |
| ADR-0034 | `connect`/`disconnect`'s own authorization split this story's `activate`/`deactivate` endpoints mirror — including the offboarding-override asymmetry (self-only for the "create/turn-on" action, self-or-tenant_admin for the "remove/turn-off" action) | 1.7, 1.11 |
| ADR-0051 Open Question 5 | `GET /v1/connectors/:platformId`'s response combines activation with derived health — `isActive` read fresh, never folded into `ConnectorHealthCache`'s 60s TTL, per ADR-0022's own dated note on this exact question | 1.12 |

## Contracts that constrain this component

- `contracts/epic-1/story-1.11.connector-activation.contract.test.ts` — both tables' schema/RLS; lazy row creation (no rows on tenant creation); `activate`/`deactivate` authorization split (`ownerType: 'tenant'` requires `tenant_admin`; `ownerType: 'user'` `activate` is always self, `deactivate` is self-or-`tenant_admin`); idempotent no-op on a repeat call to the same target state; `ownerType: 'user'` rejected `400` for an `authMode: 'none'` platform; scope independence (tenant-wide and user-specific never cross-affect each other); no side-effecting call into `runIngestionAttempt()`; `shouldAttemptIngestion()`'s new activation requirement; `disconnect` (Story 1.7) unaffected by `deactivate` and vice versa.
- `contracts/epic-1/story-1.12.connector-status-includes-activation.contract.test.ts` — `GET /v1/connectors/:platformId` returns `isActive` (tenant-wide scope), read fresh on every call rather than folded into the 60s `ConnectorHealthCache`; a never-activated platform returns `isActive: false`, never `null`/`undefined`; every existing `ConnectorHealth` field is still present, unchanged.
- `contracts/epic-2/story-2.3.error-handling-auto-disable.contract.test.ts` and `contracts/epic-2/story-2.4.bounded-queues-and-dead-lettering.contract.test.ts` — both updated (dated note, this story) to activate the connector before an assertion that depends on `shouldAttemptIngestion()` returning `true`, since that function now also requires activation, not just health. Neither file's own actual intent (auto-disable wiring, dead-letter/auto-disable independence) changed.

## How to extend this safely

- **Reading or writing activation state:** always go through `connectorActivationStore.ts`'s `isConnectorActive()`/`setConnectorActivation()` — never query `connector_activations`/`connector_user_activations` directly from a new call site. Both functions take `ownerType` explicitly (no default) the same way `credentialStore.ts`'s `getLatestCredentialId()`/`deleteCredential()` do, for the same reason: "most recently written" or an implicit scope is no longer safe once a tenant-wide and one or more user-bound activations can coexist for the same `(tenantId, platformId)`.
- **`shouldAttemptIngestion(tenantId, platformId, ownerType?, userId?)`** — `ownerType` defaults to `'tenant'`, backward-compatible with every pre-existing call site (Stories 2.3/2.4, which only ever checked the tenant-wide scope). A future per-user poller must pass `'user'` and its `userId` explicitly; there is no way to check "is this active for *any* scope" in one call, by design — activation is scope-specific, never scope-blind.
- **Determining a platform's `authMode`** for the `ownerType: 'user'`-on-`authMode: 'none'` `400` check: go through the shared registry (`getSocialConnector()`/`getAIProviderConnector()`, `registry.ts`), never a hardcoded providerId literal — `connectorsRouter.ts` is one of `story-2.10`'s own `CORE_FILES` (ADR-0048 §1), so a literal providerId string there would fail that story's own CI guardrail.
- **A new activation-table column or a synthetic `id`:** ADR-0051 Decision §1 explicitly left exact schema details as an implementation-time decision — safe to extend, just keep both tables' shape symmetric (whatever `connector_activations` gains, consider whether `connector_user_activations` needs the same).

## Load-bearing constraints — do not change casually

- **Rows are never pre-created.** No migration, no tenant-creation hook, no connector-registration step inserts a row into either table. Reading activation state is always "does a row exist with `is_active = true`" — never "does a row exist at all." Adding an eager-creation path (e.g. "insert one row per known platform when a tenant is created") would directly violate ADR-0051 Decision §1's own explicit lazy-creation rule.
- **Tenant-wide and user-specific activation are structurally independent** — no foreign key, trigger, or application-layer cross-write between the two tables. Don't add one "for convenience" (e.g. "deactivating the tenant-wide row also deactivates every user's personal row") — that's the exact conflation ADR-0051 Decision §3 exists to forbid.
- **`activate`/`deactivate` never invoke `runIngestionAttempt()` or any other ingestion code path.** A synchronous write to the activation table only (ADR-0051 Decision §2). Don't add an immediate poll-on-activate or poll-cancellation-on-deactivate — the effect is only honored on the next attempt, whenever that turns out to be (no scheduler exists yet).
- **Ownership authorization for `connector_user_activations` is application-layer, not a second RLS predicate** — mirrors `platform_credentials`' own real, verified pattern (`migrations/0019`'s own comment: "RLS is deliberately unchanged... ownership stays an application-layer check"), not `watchlists`' fully-private, RLS-enforced-ownership pattern. This was corrected in the story's own Acceptance Criteria text during implementation, after the original draft incorrectly claimed the `watchlists` shape — see `docs/user-stories/epic-1-repository-and-api-foundation.md`'s own dated correction on Story 1.11.
- **`deactivate`'s `ownerType: 'user'` allows a `tenant_admin` offboarding override; `activate`'s does not.** Mirrors `connect` (self-only) vs. `disconnect` (self-or-`tenant_admin`) exactly, for the same reason: a Tenant-Admin who may already destructively disconnect a user's credential must not be blocked from the strictly less destructive act of pausing that user's activation.
- **`connector_user_activations.user_id` is `REFERENCES users(id) ON DELETE CASCADE`** (mirrors `watchlists.user_id`'s own precedent and reasoning — personal state disappearing along with the person who owns it is correct here too) — this is *why* Story 3.8's tenant-deletion pipeline needed no changes: cascade deletion handles it, rather than adding this table to `tenantDeletion.ts`'s own explicit ordered batch-delete list. `updated_by` on both tables is `ON DELETE SET NULL` (an audit pointer, not ownership) — deliberately does not block deleting the user who last flipped the flag.

## Known gaps / deferred work

- **Live credential validation** and **system-driven auto-deactivation** — both explicitly out of scope (ADR-0051 Decision §6/§7), named as real, deliberately deferred future work, not built here.
- **The `retryable`/non-retryable auto-disable conflation fix** (`deriveConnectorHealth()` never reading the `retryable` column) — a separate, pre-existing gap against ADR-0010's own already-decided policy, addressed via dated Clarification notes on ADR-0010/ADR-0023, not by this story.
- **No `social-listening-admin` UI wiring yet.** These endpoints are API-only — the Story 6.3/6.5 connector screens still render the old hardcoded `authMode === 'none' → connected: true` / credential-presence-as-activation logic. A future story's job.
- **`GET /v1/connectors/:platformId`'s own response shape does not yet combine activation with derived health** (ADR-0051 Open Question 5) — a Tenant-Admin calling that endpoint today still can't see activation state from it. Not designed here.
- **No connector-registration bootstrap exists yet for `SocialConnector`s in a real running instance** — `registerSocialConnector()` has no real production call site for GNews/Newswire/tenant-owned-feed (only each connector's own contract test registers it, confirmed directly against every real connector's own SKILL.md). This means the `authMode: 'none'` `400` check above is provably correct in every contract test (which registers explicitly, the same way Stories 2.6/2.7/2.11/2.1 already do) but is not yet exercised against a live-running instance, since no connector-registration bootstrap or scheduler exists anywhere in this project yet (ADR-0051 Decision §7, ADR-0043 §3's own same finding). Wiring real production registration is a separate, future scheduler/bootstrap story's job, not this one's — named here so it isn't silently assumed to already work end to end.
- **Tenant export (`exportTenantData()`, Story 3.8) does not include activation state.** Not required by ADR-0051 or this story's own Acceptance Criteria; named here rather than silently omitted.
