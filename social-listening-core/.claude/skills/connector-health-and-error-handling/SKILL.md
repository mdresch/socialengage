# Connector health and error handling

## What this is

The judgment layer sitting on top of `IngestionRun` history: `src/ingestion/errorClassification.ts` classifies a failure as retryable or not; `src/ingestion/runIngestionAttempt.ts` is the generic orchestrator every real connector's poll/webhook handler will call through — it opens an `IngestionRun`, retries retryable errors with backoff, attempts an OAuth refresh once before surfacing a credential failure, and closes the run either way; `src/connectors/connectorHealth.ts` derives `ConnectorHealth` (and drives auto-disable) purely by querying that same run history. Two ADRs, two stories, one shared derivation — see ADR-0009/ADR-0010's own text and this project's epic docs, which flag this exact coupling directly.

## Governing ADRs and Stories

| ADR | Decision | Story |
|---|---|---|
| ADR-0010 | Retryable errors get backoff+retry; non-retryable fail immediately; OAuth refreshes once before surfacing a credential failure; auto-disable after the failure threshold, per tenant | 2.3 |
| ADR-0009 | `ConnectorHealth` (`healthy`/`degraded`/`failing`/`disconnected`, `credentialStatus`) is fully derived from `IngestionRun` history at read time — never separately stored mutable state | 4.3 |
| ADR-0059 Decision §4 | A fifth status, `reconnect_required` — a credential-class (401/403) failure on the single most recent run, checked before the ordinary rate/ceiling derivation below. Distinct from `failing`: a revoked OAuth grant will not self-heal no matter how many times it's retried, unlike a rate-limit/network blip. Backed by a new `ingestion_runs.is_credential_failure` column (migration `0032`), computed once, at `runIngestionAttempt()`'s own two `completeIngestionRun({status:'failed'})` call sites, via the already-existing `isCredentialError()` — any future connector gets this for free the moment it throws a credential-class `ClassifiableError`, no per-connector wiring needed. | 2.15 |
| ADR-0023 | `failing` is rate-relative (≥50% of ≥5 attempts in the trailing hour) with an absolute 20-consecutive-failure ceiling, superseding ADR-0009's/ADR-0010's flat "≥10/hour" rule — the only rule this ADR changes | 2.5 |
| ADR-0024 | `runIngestionAttempt()`'s `attempt` callback gains a `runId` parameter (additive) — the wiring a real connector needs to satisfy `insertSocialPost()`'s required `acquisitionId`; no change to retry/backoff/OAuth-refresh/health-derivation behavior itself | 2.6 |
| ADR-0010/ADR-0023 §Clarification (2026-08-12) | Corrects a confirmed implementation gap against ADR-0010's own already-Accepted policy: `deriveConnectorHealth()` now excludes retryable failures from `recentFailures`/`consecutiveFailures` — a run of purely retryable failures never trips `failing` on its own | 2.12 |
| ADR-0023 §Clarification (2026-08-17) | The absolute ceiling had no recovery path once tripped — `shouldAttemptIngestion()` gains a bounded circuit-breaker "half-open" probe allowance, `PROBE_COOLDOWN_MS` | healing pass (Story 2.5's own contract, AC5/AC6) |

## Contracts that constrain this component

- `contracts/epic-2/story-2.3.error-handling-auto-disable.contract.test.ts` — retryable errors retry with backoff; non-retryable errors fail immediately with no further attempts; a failed OAuth refresh (not a successful one) is what surfaces; `shouldAttemptIngestion()` flips to `false` once the connector-level failure threshold is crossed (Story 2.5 owns the exact rule), with `getAutoDisableReason()` returning the most recent failure's message; a second tenant is provably unaffected.
- `contracts/epic-4/story-4.3.derived-connector-health.contract.test.ts` — no `connector_health` (or similarly named) table exists at all; all four `ConnectorHealth` states derive correctly from a manually inserted `IngestionRun` sequence; `credentialStatus` reads from `platform_credentials.status` directly, independent of run-derived `status`.
- `contracts/epic-4/story-4.3.health-derivation-index.contract.test.ts` (healing pass, 2026-07-29) — `ingestion_runs` has an index covering `(tenant_id, platform_id, started_at)`, the exact columns `deriveConnectorHealth()`'s query uses, confirmed via live `pg_indexes` introspection.
- `contracts/epic-2/story-2.4.bounded-queues-and-dead-lettering.contract.test.ts` — a gate wait abandoned on TTL, reclassified by a synthetic `attempt()` into a `ClassifiableError`, records a non-retryable failed `IngestionRun`; a request that exhausts retries for a genuinely retryable error gets a distinctly-worded "dead-lettered" `errorSummary`, and dead-lettering one request alone does not cross `shouldAttemptIngestion()`'s threshold — the two mechanisms proven independent.
- `contracts/epic-2/story-2.5.proportional-failure-threshold.contract.test.ts` — ≥50% failure rate with ≥5 attempts (including exactly the 50% boundary) is `failing`; fewer than 5 attempts never triggers the rate rule regardless of failure percentage; 20 consecutive failures is `failing` regardless of the trailing-1-hour window (proven with failures spread far enough apart that none fall inside it); a high-frequency (rate-triggered) and low-frequency (ceiling-triggered) connector under equivalent "mostly broken" conditions are both correctly flagged. **AC5/AC6 (healing pass, 2026-08-17):** `shouldAttemptIngestion()` still returns `false` for a ceiling-triggered connector whose most recent attempt is within `PROBE_COOLDOWN_MS`; it returns `true` (a real probe allowed through) once the most recent attempt is older than the cooldown — proven by reusing AC3's own `recordSpreadOutFailures()` fixture, whose most recent failure already lands 2 hours in the past.
- `contracts/epic-2/story-2.6.newswire-connector.contract.test.ts` — exercises `runIngestionAttempt()`'s `attempt(runId)` parameter and the `acquireForProvider()` → `ClassifiableError` reclassification pattern via a real connector for the first time (see `.claude/skills/newswire-connector/SKILL.md`); doesn't itself constrain the retry/health-derivation rules above.
- `contracts/epic-2/story-2.12.retryable-failures-excluded-from-auto-disable.contract.test.ts` — a run of purely retryable failures (even past the 20-consecutive ceiling) never trips `failing`; a run of purely non-retryable failures still trips it exactly as before; a mixed run counts only the non-retryable failures toward `recentFailures`/`consecutiveFailures`; a connector recovering from a purely-retryable blip (successes present) reads `healthy`, not `degraded`; a `NULL` `retryable` value (an unclassified failure) is treated conservatively, as non-retryable.
- `contracts/epic-2/story-2.15.facebook-connector.contract.test.ts` — a credential-class (401/403) failed run derives `ConnectorHealth.status === 'reconnect_required'`, distinct from an ordinary non-credential failed run (still `failing`/`degraded` as before) — see `.claude/skills/facebook-connector/SKILL.md` for the connector-specific half of this story.

## How to extend this safely

- **Wiring a real connector's HTTP calls:** call `runIngestionAttempt({ tenantId, connectorInfo, attempt, refreshOAuthToken? })`, where `attempt` makes the real platform call and throws a `ClassifiableError` (not a raw `Error`) for anything that should be retried, refreshed, or failed — a raw thrown error propagates as a genuine programming bug, not an ingestion outcome, by design (see Load-bearing constraints). If `attempt` calls `acquireForProvider()`/`acquireForAiModel()` (Story 2.2/2.4) and it throws `QueueTtlExceededError`/`QueueDepthExceededError`, catch and reclassify into `ClassifiableError('queue_ttl_exceeded' | 'queue_depth_exceeded', ...)` — `RequestGate` itself has no ingestion-domain knowledge, so this reclassification is the connector's job, not the gate's.
- **Adding a new error kind:** add it to `ErrorKind` in `errorClassification.ts` and place it in `RETRYABLE_KINDS`/`CREDENTIAL_KINDS` (or neither, defaulting to non-retryable) — never add ad hoc classification logic inside `runIngestionAttempt()` itself.
- **Checking whether to schedule the next poll:** call `shouldAttemptIngestion(tenantId, platformId)` before running one — never introduce a separate "disabled" column/flag anywhere; that would reintroduce exactly the drift risk ADR-0009 exists to prevent.
- **Reading connector status for the admin UI:** don't call `deriveConnectorHealth()` directly from a router — go through Story 4.4's cache (`getCachedConnectorHealth()`, `.claude/skills/derived-data-caching-and-refresh/SKILL.md`), which itself only ever calls this function to populate an entry.
- **Tuning the `failing` rule (Story 2.5, ADR-0023):** `RATE_FAILURE_THRESHOLD`/`RATE_ATTEMPT_FLOOR`/`CONSECUTIVE_FAILURE_CEILING` live together at the top of `connectorHealth.ts` — change them there only, per ADR-0023's own Amendment Log convention (an implementation-default change, not a new decision). Never touch `degraded`/`disconnected`/`healthy`'s logic as a side effect; ADR-0023 explicitly doesn't touch those.

## Load-bearing constraints — do not change casually

- **`runIngestionAttempt()` only catches `ClassifiableError` — anything else rethrows.** This is deliberate: an unclassified exception is a bug in the connector's own code, not a legitimate retryable/non-retryable ingestion outcome, and swallowing it into a "failed" `IngestionRun` would hide real programming errors behind ADR-0010's error-handling policy.
- **The `failing` rule (rate ≥50% with a ≥5-attempt floor, OR ≥20 consecutive failures — ADR-0023, Story 2.5) lives in exactly one place** (`connectorHealth.ts`) and is what both `deriveConnectorHealth()`'s `failing` state and (transitively, via `shouldAttemptIngestion()`) Story 2.3's auto-disable both consult. It supersedes the original flat "≥10/hour" placeholder (ADR-0009's/ADR-0010's own text — see each ADR's "Supersession update" note) — this is the *only* rule ADR-0023 changes; `degraded`/`disconnected`/`healthy` and `credentialStatus` are unaffected, per that ADR's own text.
- **The rate rule and the absolute ceiling are independent OR'd conditions, not layered.** A connector can be `failing` via the rate rule with very few total lifetime attempts (if recent ones cross the floor+rate), or via the ceiling with attempts spread so far apart that *zero* fall inside the trailing-hour window at all (proven by Story 2.5's own AC3) — the ceiling exists specifically so a low-frequency, persistently-broken connector can't hide behind never reaching the rate rule's attempt floor within any single hour.
- **Auto-disable has no stored flag anywhere — it is entirely `shouldAttemptIngestion()`'s live read of `deriveConnectorHealth()`.** Don't "optimize" this into a cached boolean column on some connector-config table; that reintroduces the exact drift risk ADR-0009's Alternatives Considered section explicitly rejected.
- **`shouldAttemptIngestion()`'s probe cooldown (`PROBE_COOLDOWN_MS`, 2026-08-17) exists specifically because the absolute ceiling has no other time dimension to decay through** — the rate rule already self-heals as its 1-hour window ages, but a ceiling-triggered `failing` state, read literally, would block every future attempt forever, since the one attempt that could prove the connector is fixed is exactly what's blocked. Don't remove this thinking "the credential/root cause is fixed now, so it doesn't matter" — the deadlock is real regardless of whether the underlying cause is ever fixed, because nothing else re-tests the condition.
- **`credentialStatus` and run-derived `status` are independent axes, not merged into one value.** A connector can be `healthy` by run history while its credential is `expired` (the credential just hasn't been *used* yet to fail a run) — this is correct, not a bug, per ADR-0009's explicit separation.
- **Dead-lettering (Story 2.4, ADR-0020) is a distinctly-worded `errorSummary` on retry exhaustion, not a stored flag, a new `ingestion_runs.status` value, or a separate DLQ table.** It only applies when retries were genuinely exhausted for a retryable error (`isRetryable(err.kind) && attemptsMade > maxRetries`) — an immediate non-retryable failure is a different case and is never worded as dead-lettered. It is deliberately independent of the `failing` threshold/auto-disable (individual-request granularity vs. aggregate connector-wide pattern, per ADR-0020's own Decision text) — don't wire one to trigger the other.
- **Stories 2.3's and 4.3's contracts were edited for this ADR-0023 change, with dated notes, not left to silently rot or rewritten wholesale.** Only Story 2.3's AC4 needed new numbers (its old ones only made sense under the flat rule); Story 4.3's assertions were unaffected (its 10-failure fixture still clears the new rule too, just for a different reason) — see each file's own dated 2026-07-30 note before assuming either needs further changes.
- **`reconnect_required` (Story 2.15) is checked on `runs[0]` alone (the single most recent run, already ordered DESC) — before the rate/ceiling derivation, and returned immediately if true, never blended with `failing`/`degraded`.** A later successful run naturally becomes `runs[0]` and clears the status on its own — don't add a "sticky until manually acknowledged" mechanic; that would misrepresent a tenant who already fixed the credential as still needing to.
- **A retryable-failed run is fully invisible to `failing`/`degraded`/`healthy`, not merely down-weighted (Story 2.12).** It counts toward neither `recentFailures` nor `recentAttempts` (the rate-formula denominator), and neither extends nor breaks the `consecutiveFailures` streak — the streak simply skips over it, as if it hadn't happened for this derivation's purposes. `lastAttemptAt` still reflects that an attempt did happen, regardless of retryable classification — this exclusion is scoped to the `failing` derivation only. A `NULL` `retryable` value (a fixture row created without classifying it, e.g. Story 4.3's own `recordRun()` helper) is treated as non-retryable, the conservative default — an unclassified failure must never be silently excluded.

## Known gaps / deferred work

- **The Newswire connector (Story 2.6, ADR-0024) is now the first real connector calling `runIngestionAttempt()`**, including the `acquireForProvider()` → reclassify → `ClassifiableError` wiring this file's own "How to extend this safely" section prescribes — see `.claude/skills/newswire-connector/SKILL.md`. `runIngestionAttempt()`'s `attempt` callback also gained a `runId: string` parameter as part of that story (additive only — every existing zero-arg `attempt` callback in this component's own contracts above remains valid). RSS/News's real connector (Phase 1's "also build, not storied" scope) still doesn't exist.
- `acquireForAiModel()`'s equivalent reclassification (the AI-provider half) still isn't exercised by any real caller — no real `AIProviderConnector` exists yet (Phase 2 work).
- Story 4.4's read-through cache (ADR-0022, accepted 2026-07-29, implemented 2026-07-30) builds directly on this component — see `.claude/skills/derived-data-caching-and-refresh/SKILL.md`.
- ADR-0023's `deliveryMode`-based threshold variation (push vs. poll) remains an open, deliberately-deferred question per that ADR's own Acceptance note — not this story's scope, and not built.
- **Distributed (Redis-backed) `RequestGate` state across more than one process instance (the other half of Story 2.4, ADR-0020) is deliberately not built** — see `provider-connector-framework`'s SKILL.md for why (solo-deployment, single-instance is the real shape right now).
- ADR-0014's Negative consequences names Key Vault throttling/outage as "almost certainly retryable" for connector error handling, but `errorClassification.ts`'s `ErrorKind` has no dedicated kind for it — flagged by the same 2026-07-29 consistency audit that caught the two gaps below, deliberately left open (generic `network`/`http_5xx` may already cover it adequately; revisit if a real Key Vault-dependent connector call shows otherwise).

## Corrections

- **2026-08-17 (healing pass):** the absolute ceiling (ADR-0023) had no recovery path once tripped — `shouldAttemptIngestion()` checked `health.status === 'failing'` and blocked unconditionally, forever, since the only thing that could clear the streak (a fresh successful poll) was exactly what was blocked. Found live: a real tenant's GNews connector legitimately hit the ceiling via a genuine credential-storage bug (since fixed), then stayed permanently stuck even after the credential existed and the connector was reactivated — no code path anywhere re-tested the condition. Fixed with a bounded circuit-breaker "half-open" probe (`PROBE_COOLDOWN_MS`) — see ADR-0023's own new Clarification and Story 2.5's contract, AC5/AC6.
- **2026-07-29 (healing pass):** a full ADR/story consistency audit found two gaps this component had shipped without: `ingestion_runs.retryable` (ADR-0005 names it as a field; Story 3.2's own migration deferred it to "Story 2.3," which then shipped without adding it) and the `(tenant_id, platform_id, started_at)` index ADR-0009's own Negative consequences names as needed. Both fixed in this pass — see the two new contracts above and `runIngestionAttempt.ts`/the migration for the fix itself.
