# Ingestion events (thin event shapes + Service Bus publishing)

## What this is

`buildSocialPostIngestedEvent()`/`buildConnectorHealthChangedEvent()` (`src/events/socialPostIngestedEvent.ts`/`connectorHealthChangedEvent.ts`) construct ADR-0012's deliberately thin event payloads — IDs and status fields only, never post text, engagement metrics, or raw payload. `publishEvent()` (`src/events/serviceBusPublisher.ts`) sends a constructed event body to the real `social-listening-events` topic on the `social-listening-dev` Service Bus namespace, setting `tenantId` and `schemaVersion` as Service Bus application properties (ADR-0013's Clarification / ADR-0019's Decision — SQL subscription filters can only evaluate message properties, not payload body content). `GET /v1/posts/:id` (`src/http/versions/v1/postsRouter.ts`, backed by `getSocialPostById()` in `socialPostStore.ts`) is the paired REST-fetch-on-demand half of ADR-0012: a subscriber that only got a thin event can fetch full post data by `postId` when it actually needs it.

## Governing ADRs and Stories

| ADR | Decision | Story |
|---|---|---|
| ADR-0012 | Events carry IDs and minimal fields only; full data fetched via REST on demand | 5.1 |
| ADR-0013 | Per-tenant event filtering via Service Bus subscription SQL filters on `tenantId`, which must be a message application property, not only a payload field | 5.2 |
| ADR-0019 | `schemaVersion` (starting at 1) as a Service Bus application property on every event; additive changes don't bump it; a breaking change bumps it and dual-publishes during a coordinated cutover | 5.5 |

## Contracts that constrain this component

- `contracts/epic-5/story-5.1.thin-events.contract.test.ts` — `buildSocialPostIngestedEvent()` returns exactly `tenantId`/`postId`/`platformId`/`watchlistId`/`sentiment`/`publishedAt`/`occurredAt`, nothing else; `buildConnectorHealthChangedEvent()` returns exactly `previousStatus`/`newStatus`/`tenantId`/`platformId`/`occurredAt`; `GET /v1/posts/:id` returns full post data for a known id, 404s for an unknown one, and never returns another tenant's post even by the right id (RLS).
- `contracts/epic-5/story-5.2.per-tenant-event-filtering.contract.test.ts` — against the real namespace/topic: a published event carries `tenantId` as a Service Bus application property, readable without deserializing the body; a subscription with a SQL filter on `tenantId` receives only the matching tenant's events; a second, differently-filtered subscription requires no change to `publishEvent()` itself — proven by reusing the same publish calls against a different subscription's filter.
- `contracts/epic-5/story-5.5.event-schema-versioning.contract.test.ts` — a published event carries `schemaVersion=1` by default; an additively-shaped payload body still yields `schemaVersion=1` (the version signal is independent of payload content); `publishEvent()` can emit an explicit `schemaVersion` (proving the mechanism a future breaking-change cutover would use); a subscription SQL-filtered on `schemaVersion` receives only matching-version messages.
- `contracts/epic-5/story-5.19.wire-ingestion-events.contract.test.ts` (ADR-0058) — real, end-to-end proof that the real ingestion pipeline actually publishes: `listActiveWatchlistsForTenant()` is tenant-wide, distinct from the owner-scoped `listWatchlists()`; a post matching a real tenant watchlist targeting a connector produces a real `SocialPostIngestedEvent` on the real topic; a post matching two watchlists publishes exactly two events, zero watchlists publishes none; watchlists are fetched exactly once per poll batch, not once per post; `publishEvent()` only fires once the post-insertion transaction has actually committed; a tenant's very first ingestion attempt publishes exactly one `ConnectorHealthChangedEvent`, an unchanged-status attempt publishes none; a rejecting `publishEvent()` never fails or blocks the surrounding ingestion attempt, for either event type.

## How to extend this safely

- **Adding a field to an existing event type:** add it to the builder function's return object and its TypeScript interface together — and re-read ADR-0012's Decision text first; a field beyond what it names (e.g. post text, engagement metrics, raw payload) is exactly what this ADR exists to keep out. A genuinely new *optional* field is ADR-0019's "additive, no `schemaVersion` bump" case — don't pass a `schemaVersion` override for it.
- **A genuine breaking change to an existing event type's shape:** call `publishEvent(tenantId, newBody, { schemaVersion: <incremented> })` for the new shape while the old call path keeps publishing the old shape at the prior version, until all known subscribers confirm they've upgraded (ADR-0019's coordinated-cutover policy) — then remove the old-version publish call. There is no real breaking change happening yet, so no dual-publish exists in this codebase today; this is the mechanism to use when one does.
- **Publishing a real event:** call `publishEvent(tenantId, body, { schemaVersion? })` with the result of a `build*Event()` function — never construct the Service Bus message shape ad hoc elsewhere. Omit `schemaVersion` for the normal case (defaults to 1).
- **Adding a new connector's own event publishing (Story 5.19, ADR-0058):** at the top of the connector's own `ingestXItems()` function, load watchlists exactly once — `(await listActiveWatchlistsForTenant(tenantId)).filter((w) => w.platformIds.includes(YOUR_PROVIDER_ID))` — never inside the per-post loop. After each post's `insertSocialPost()` call has resolved (never before — see Load-bearing constraints), call `publishSocialPostIngestedEvents(tenantId, YOUR_PROVIDER_ID, watchlists, { postId, text, authorExternalId, publishedAt })`, where `text` is the same `enrichmentText` the connector already composes for `enrichPost()`. No change to `runIngestionAttempt()` is needed for a new connector's `ConnectorHealthChangedEvent` — it's already automatic for every caller.

## Load-bearing constraints — do not change casually

- **`publishEvent()` always sets `tenantId` and `schemaVersion` as Service Bus `applicationProperties` entries, never only inside the JSON body.** This is a mechanical requirement of ADR-0013's and ADR-0019's SQL-filter mechanisms, not a style choice — a filter on either field literally cannot evaluate against payload-only data. Checked directly by Story 5.2's AC1 and this story's own AC1/AC4 contracts.
- **The builder functions (`build*Event()`) stay pure — no I/O.** `publishEvent()` is the only place that talks to Service Bus; it takes an already-constructed body, it doesn't build one itself. Keeps the payload-shape contract (Story 5.1) and the transport contract (Stories 5.2/5.5) independently testable.
- **Namespace/topic come from `SERVICE_BUS_NAMESPACE`/hardcoded `TOPIC_NAME`, following `KEY_VAULT_URI`'s override pattern** — default `social-listening-dev.servicebus.windows.net` / `social-listening-events`. Auth is `DefaultAzureCredential` (the same `az login`-backed chain as Key Vault) — no connection-string secret to manage.
- **`GET /v1/posts/:id` follows the same `X-Tenant-Id` header placeholder as `GET /v1/posts`** — see `posts-api`'s SKILL.md Load-bearing constraints for why that isn't a real security boundary yet (Phase 5's job). The RLS-backed cross-tenant 404 (Story 5.1's own AC) is real isolation; the header itself is not authentication.
- **`publishSocialPostIngestedEvents()` (Story 5.19) always uses the fallback AST evaluator (`matchesAst`), never `resolveWatchlistAstDispatch()`'s `'native'` shortcut, even for a connector (GNews) that declares real `supportedQueryFeatures`.** Found live by Story 5.19's own AC3: `'native'` mode's contract assumes the connector's own outbound fetch was actually parameterized by *that specific watchlist's* translated query — none of the three real connectors do that (each polls one fixed query/feed set, unrelated to any individual watchlist). Trusting `'native'` here would match every TERM-capable watchlist unconditionally, regardless of real post content. Revisit only once a connector's actual poll call is genuinely driven by a specific watchlist's translated query — a separate, undesigned future capability (`translateWatchlistQuery()` is already declared but never wired into any real poll call, per Story 2.7's own explicit out-of-scope note).
- **`publishSocialPostIngestedEvents()`/the `ConnectorHealthChangedEvent` publish inside `runIngestionAttempt()` are both best-effort — wrapped in `try/catch`, logged, never re-thrown.** A Service Bus outage must never fail or roll back real ingestion (posts actually stored, queryable via `GET /v1/posts`) — the same precedent `enrichPost()` already established (ADR-0038). Never remove this try/catch to "make errors visible" — that would reintroduce a real availability coupling this project deliberately avoided.
- **Watchlists are loaded exactly once per poll batch inside each connector's own `ingestXItems()` function, never once per post.** A per-post reload would turn one poll cycle into O(posts) extra DB round-trips — ADR-0058 Decision §6's own named safeguard, checked directly by Story 5.19's AC4.
- **`listActiveWatchlistsForTenant()` (`watchlistStore.ts`) iterates the tenant's own users and calls the existing, unmodified `listWatchlists()` once per user — it does not use a new Postgres role or relax `watchlists`' own owner-scoped RLS policy.** Considered and rejected during Story 5.19: `watchlists`' RLS (`migrations/0025`) requires `app.user_id` to match a real owner, with no "see every user" fallback, and this project's own `tenant_deletion_role` precedent confirmed no existing role bypasses it either (that role relies on `ON DELETE CASCADE`, not a direct query). A new role would be a genuinely new, standing elevated-privilege credential purely to save a small, poll-batch-scoped loop — rejected as disproportionate. See ADR-0058's own Amendment Log.

## Known gaps / deferred work

- **No real coordinated-cutover dual-publish exists.** ADR-0019 itself frames "is coordinated cutover operationally realistic" as an open, decision-level question to revisit once a real subscriber (likely Brand Reputation & Alerts) exists — not resolved here. The mechanism (`publishEvent(..., { schemaVersion })`) exists; using it for an actual two-version cutover is future work tied to a real breaking change.
- **`sentiment` on `SocialPostIngestedEvent`** currently has no real source — nothing in `social_posts`/`enrichment` populates a top-level sentiment value yet (Phase 2's "also build, not storied" enrichment pipeline owns that). The builder accepts it as an input parameter; Story 5.19's own real callers all pass it as `null`.
- **No throttling/batching for a post matching many watchlists** — each match publishes its own `SocialPostIngestedEvent` independently (ADR-0058 Decision §1, intentional). Named, not designed, in ADR-0058's own Open Questions — revisit if real Service Bus message volume ever demonstrates a need.
- **Documentation Steward correction, 2026-08-19: the bullet that previously read "Wikipedia's own connector (Story 2.13, separately paused pending ADR-0058) does not yet publish events" is stale and removed.** Story 2.13 resumed and shipped the same day this gap was written (`social-listening-core@591b0b8`, 2026-08-17), adopting this exact wiring pattern as part of its original build (ADR-0058 Decision §5) — confirmed directly against `pollWikipedia.ts`, which calls both `listActiveWatchlistsForTenant()` and `publishSocialPostIngestedEvents()` at its own real production call site, not only in a contract fixture. `wikipedia-connector/SKILL.md`'s own "Relations to other components" section already states this correctly; this file's own "Known gaps" list was the one left behind.
- **No real subscriber consumes either event type in production today** — Story 5.19 closes the publish-side gap only; ADR-0019's own already-named "no real coordinated-cutover subscriber exists yet" gap is unchanged.
- `schemaVersion` is not mirrored into the JSON payload body — ADR-0019 calls that optional and the property the source of truth; no AC requires the mirror, so it isn't built.
- These stories' contracts create and delete their own throwaway subscriptions per run (same pattern as `credential-envelope-encryption`'s test Key Vault key) — no subscription needs to pre-exist, and none are left behind by a clean run (an `autoDeleteOnIdle: PT10M` TTL is the safety net if cleanup itself fails).
- **Every test subscription must be scoped with a SQL filter on its own randomUUID `tenantId`, even in ACs that aren't testing filtering itself.** Jest runs contract files across parallel workers by default (no `maxWorkers` cap in `jest.config.js`), and `TOPIC_NAME` is one fixed real topic shared by the whole suite — an unfiltered subscription (Service Bus's default "match everything" rule) can receive a message published by *any* other contract file running concurrently, not just its own test's `publishEvent()` call. Hit in practice: Story 5.5's AC1-AC3 and Story 5.2's AC1 originally created unfiltered subscriptions and intermittently received another test's message (wrong `tenantId`/`schemaVersion` on an otherwise-defined message) — fixed by scoping every subscription to the test's own `tenantId`, mirroring Story 5.2's existing `createTenantFilteredSubscription`/Story 5.5's `createIsolatedSubscription` helpers. A new AC in either contract that skips this scoping will reintroduce the same intermittent failure.
