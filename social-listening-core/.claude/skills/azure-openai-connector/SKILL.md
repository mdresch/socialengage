# Azure OpenAI connector — the second real AIProviderConnector

## What this is

`azureOpenAiConnector.ts` calls the real, live Azure OpenAI Service `chat/completions` endpoint (`gpt-5-mini` deployment) with GA structured/JSON-schema-constrained output (`response_format: json_schema`, `strict: true`) to return all four enrichment fields — sentiment, sentimentScores, entities, keyPhrases, detectedLanguage — in a **single** real HTTP call, in contrast to `azureAiLanguageConnector.ts`'s four separate per-capability calls (Story 2.8). This realizes the single-call efficiency argument ADR-0038 Decision §2 named as the reason an LLM-based second provider was wanted at all. `enrichPost.ts` (Story 2.8) was rewritten by this story to be provider-agnostic — it tries each real `AIProviderConnector` in a fixed order, skipping any a tenant hasn't connected and failing over to the next on an exhausted/non-retryable failure — proving `AIProviderConnector` swappability by real execution rather than assumed from interface shape alone (Story 2.9's own stated purpose).

**Same-day follow-up (2026-08-10, at Menno's request):** the system prompt now instructs the model to self-review its own extraction (check every entity actually appears in the text with a valid category, sentimentScores are consistent with the chosen sentiment label, nothing was fabricated or missed) and silently correct itself before returning the final answer — a single-call self-verification pass, not a second real HTTP call. The model also reports a new `overallConfidence` field (0.0-1.0): its own honest, post-review confidence in the whole answer. See `AnalyzeResult`'s own doc comment (`types.ts`) and this file's own Load-bearing constraints below for why this is a genuinely different kind of number than `entities[].confidenceScore`.

## Contracts that constrain this component

- `contracts/epic-2/story-2.9.second-ai-provider-connector.contract.test.ts` — a registered `AIProviderConnector` with a `providerId` distinct from `azure-ai-language`; `analyze()` rejects with no credential; a real call against the real Azure OpenAI resource returns all four enrichment fields plus `overallConfidence` (a real number in `[0,1]`) from one structured-output call; neither `pollGNewsSearch.ts` nor `pollNewswireFeeds.ts` references this connector directly (no core pipeline change); a tenant on either provider enriches successfully (provider swap); a tenant with neither provider connected, or with only the other provider connected, still resolves cleanly (skip); a tenant's broken credential for one provider never affects a different tenant on the other provider; two tenants on different providers gate independently; a malformed Azure OpenAI credential resolves to `undefined`, never throws.
- `contracts/epic-2/story-2.32.azure-openai-research-capability.contract.test.ts` (ADR-0076) — `azureOpenAiConnector.research()` returns a structured `ResearchResult` (key phrases, related topics, search queries, context summary, comparison) from one `chat/completions` call; `azureAiLanguageConnector.research` is undefined; a missing/invalid credential throws the same `ClassifiableError('http_401')` path as `analyze()`.
- `contracts/epic-2/story-2.10.connector-registration-transparency.contract.test.ts` — proves this connector's own `AZURE_OPENAI_PROVIDER_ID` literal (`'azure-openai'`) appears nowhere in any core ingestion/orchestration file (ADR-0048 §1).
- `contracts/epic-2/story-2.17.azure-openai-summary-field.contract.test.ts` — a real call against the real Azure OpenAI resource returns a non-empty `summary` string, genuinely shorter than the input, alongside the five existing fields; a real `enrichPost()` result for a tenant served by this connector round-trips `summary` through `insertSocialPost()` into `SocialPost.enrichment.summary` unchanged; a tenant served by Azure AI Language instead (both providers connected/active, the existing fixed-order default) has `enrichment.summary` absent, not a placeholder.

## Registration transparency (ADR-0048)

- **Registration location:** `src/connectors/azureOpenAi/azureOpenAiConnector.ts` (the connector object, `providerId: AZURE_OPENAI_PROVIDER_ID`), registered by a real `registerAIProviderConnector(azureOpenAiConnector)` call at the top of `src/connectors/azureAiLanguage/enrichPost.ts` (a module-load side effect), and appended to that same file's `PROVIDERS` array.
- **Extension points used:** the `AIProviderConnector` interface (`src/connectors/types.ts`), `registerAIProviderConnector()` (`src/connectors/registry.ts`), and `enrichPost.ts`'s own `PROVIDERS` array — exactly the "implement + register + append" integration surface named in "How to extend this safely" above; no other core file was touched to add this connector.
- **No-core-change verification:** `contracts/epic-2/story-2.10.connector-registration-transparency.contract.test.ts` mechanically greps every designated core file (deliberately excluding `enrichPost.ts` itself, which *is* the documented extension point) for the literal string `azure-openai` and fails if found.

## How to extend this safely

- **Adding a third `AIProviderConnector`**: implement the full interface (see `azure-ai-language-connector`'s or this component's own file as a template), call `registerAIProviderConnector()` on it, and append it to `enrichPost.ts`'s `PROVIDERS` array — that's the entire integration surface (Story 2.9 AC2's "registration/configuration is sufficient"). No other file needs to change.
- **A new Azure OpenAI capability or a different deployment tier**: extend `ENRICHMENT_SCHEMA`'s properties (and `AnalyzeResult` in `types.ts` if the field is new) — keep it a single structured-output call, don't split into multiple `chat/completions` calls; that would give up the exact efficiency win this connector exists to realize. **Story 2.17's own `summary` field is the reference example of this** — one more schema property, one more `required` entry, one more system-prompt sentence, one more `AnalyzeResult` field, zero new HTTP calls.
- **Changing the entity `category` enum**: it's deliberately constrained to Azure AI Language's own real, documented top-level NER taxonomy (`Person`, `PersonType`, `Location`, `Organization`, `Event`, `Product`, `Skill`, `Address`, `PhoneNumber`, `Email`, `URL`, `IP`, `DateTime`, `Quantity`) — not left free-form. Changing this changes what both providers can jointly express; verify against Microsoft's own current taxonomy page before editing it, don't invent categories.
- **Extending the self-review instruction**: it lives entirely in the system prompt string in `callChatCompletions()` — no separate second call, no separate verification step in code. Add more self-checks by extending that prompt text, not by adding a second `fetch()`; a second real call would give up the single-call efficiency win this connector exists to realize.

## Real, root-caused issue found and fixed during validation — not left as unexplained flakiness

- **The deployment's initial `--sku-capacity 1` (1,000 TPM) was too low to survive this story's own contract** — confirmed directly via Microsoft Learn (`learn.microsoft.com/azure/ai-foundry/openai/how-to/quota` — "Quota is allocated in terms of units of capacity"; 1 capacity unit = 1,000 TPM for `GlobalStandard`), not assumed. A single real `enrichPost()` call already uses ~1,481 tokens (see the reasoning-token note below) — more than the entire 1,000 TPM ceiling in one call. This reproduced deterministically (3/3 full-file runs failed at the same test, 429s confirmed via temporary diagnostic logging), not transient flakiness, and was root-caused before touching any application code. Fixed by raising the deployment to `--sku-capacity 20` (20,000 TPM/20 RPM) — a `GlobalStandard` (pay-per-token) SKU, so raising this ceiling has no pre-committed cost, unlike Provisioned Throughput Units. If a future story's own real call volume needs more headroom, raise this further the same way; don't "fix" a 429 by weakening `enrichPost()`'s own retry/failover logic, which was already behaving correctly.

## Load-bearing constraints — do not change casually

- **`enrichPost.ts` never throws — this is unchanged from Story 2.8 and now applies per-provider, not just to Azure AI Language.** A missing credential for a given provider, or (healed 2026-08-12) an inactive one, is a "skip, try the next provider" (not a failure); an exhausted/non-retryable failure from a connected provider is also a "skip, try the next provider." Only after every provider in `PROVIDERS` has been tried does `enrichPost()` return `undefined`. Never let a provider-specific failure propagate out of `tryProvider()`.
- **Healed 2026-08-12 — activation (Story 1.11/ADR-0051), not just credential presence, now gates each provider.** `tryProvider()` checks `isConnectorActive(tenantId, connector.providerId, 'tenant')` before ever reading a credential — found live: the admin UI's Activate/Deactivate control already renders for this connector too, but had no actual effect on enrichment before this fix. See `azure-ai-language-connector/SKILL.md`'s own matching note.
- **`PROVIDERS` in `enrichPost.ts` is a fixed, explicit array — not `registry.listAIProviderConnectors()`.** Both connectors *do* call `registerAIProviderConnector()` (a real, module-load side effect — proving Story 2.9 AC1's "registered... alongside" for real, not just structurally), but `enrichPost()` itself iterates the local array. This is deliberate: the shared registry's `__resetRegistryForTests()` exists solely for cross-contract-file test isolation (`provider-connector-framework/SKILL.md`'s own Load-bearing constraint) — Jest gives each contract file its own fresh module cache, so a module-load registration side effect is safe per test file, but making `enrichPost()`'s own real gating logic depend on live registry state would be a needless coupling to a mechanism this project has never otherwise relied on at runtime (every other real connector — GNews, Newswire, Azure AI Language — is wired by direct import, not registry lookup). Don't switch this to `listAIProviderConnectors()` without re-checking that reasoning first.
- **Provider try-order in `PROVIDERS` is Azure AI Language first, Azure OpenAI second** — matches ADR-0038 Decision §1/§2's own sequencing (shape-matched, lower-risk provider first). A tenant with both providers connected *and active* always gets Azure AI Language's result unless it fails; this is a real, order-dependent behavior, not an unspecified race. **Confirmed 2026-08-12 (Menno's own direct direction): this is an intentional default, not an accidental artifact of build order** — no ADR/story had actually decided it as policy before this. A per-tenant preference between the two remains real, separate, unbuilt scope — don't infer one is coming; it's simply undecided beyond "keep the current default."
- **The tenant's own credential is a JSON string `{endpoint, key, deployment}`** — three parts, not two like Azure AI Language's `{endpoint, key}`, because Azure OpenAI addresses models by *deployment name* in its URL path, not a fixed model id. `parseCredential()` is the one place that (de)structures it.
- **`AZURE_OPENAI_ENDPOINT`/`AZURE_OPENAI_KEY`/`AZURE_OPENAI_DEPLOYMENT` in `.env` are a real, dedicated test-fixture credential** (the resource is `socialengage-openai`, `rg-socialengage-cognitive`, `swedencentral`, co-located with the Azure AI Language resource) — never a SocialEngage-operated production credential; in production every tenant supplies their own via the ordinary connect flow, stored the same way as any other `api_key`-authMode connector's credential.
- **`overallConfidence` is a self-reported LLM confidence score, never a calibrated probability — do not treat it the same as `entities[].confidenceScore` or `sentimentScores`.** Azure AI Language's own scores come from a real, calibrated classifier; `gpt-5-mini`'s `overallConfidence` is the model's own after-the-fact self-assessment following the system prompt's self-review instruction — a fundamentally different kind of number with no guaranteed statistical meaning. `azureAiLanguageConnector.ts` never populates this field (it's `undefined` there) — don't backfill it with a placeholder to "match shape"; its absence for that provider is correct, not a gap.
- **`summary` (Story 2.17) is only ever populated when this connector is the one that actually runs — never universally.** `enrichPost.ts` tries Azure AI Language first (see the ordering constraint above); Azure AI Language's own four capabilities have no summarization output of their own (real Azure AI Language document summarization is a separate, asynchronous endpoint, verified 2026-08-18 — not integrated anywhere in this project). A tenant with both providers connected and active, enriching ordinary-length content, will have `enrichment.summary` absent — this is correct, not a bug, the same "absence is correct" treatment `overallConfidence` already established. Don't backfill a placeholder summary for the Azure AI Language path to "complete" the shape.
- **Self-review happens inside the single structured-output call, via the system prompt — not as a separate verification pass.** `enrichPost()`'s own retry loop only fires on HTTP-level failures (429/5xx/network); it has no knowledge of `overallConfidence` and doesn't retry a low-confidence-but-successful response. A caller that wants to act on low `overallConfidence` (e.g. discard the enrichment, or escalate to the other provider) must do so itself downstream — not built here, see Known gaps.

Verify directly in Azure Cost Management once real usage accrues.
- **No third `AIProviderConnector`** — Story 2.9's own scope is proving two-provider swappability, not building a third.
- ~~No admin-UI connect flow exists at all — corrected 2026-08-10, this bullet previously overstated what Story 6.3 built.~~ **Documentation Steward correction, 2026-08-13 — this bullet is itself now stale.** Story 6.3 was healed the same day (`social-listening-admin@1dbd26a`, later on 2026-08-10, after this bullet was written) to build a real connect/disconnect flow — see `social-listening-admin/.claude/skills/connector-connect-disconnect/SKILL.md`. `tenant/connectors/page.tsx`'s real `PLATFORMS` array now includes `azure-openai` with a real three-field (`endpoint`, `key`, `deployment`) `ConnectForm`, wired to a real `POST /v1/connectors/:platformId/connect` call — confirmed directly against current source. A real tenant can connect this provider through the UI today.
- **`gpt-5-mini` is a reasoning-family model, confirmed with real, measured cost/latency data, not left speculative.** A real probe call this session (one sample post, default `reasoning_effort`) took **10.4s end-to-end** and spent **832 of 1,232 output tokens (67%) on invisible reasoning** — billed as ordinary output tokens even though never returned in `message.content`. This is a materially different cost/latency profile than `gpt-4o-mini`'s plain chat-completion model, which ADR-0038's original pricing research assumed (no reasoning-token overhead). Real production cost per `enrichPost()` call will be dominated by reasoning tokens, not the visible JSON payload — worth setting `reasoning_effort: 'minimal'` (supported per Microsoft Learn's own reasoning-models doc) as a follow-up if per-post latency/cost at this level proves too high in practice; not changed here since this story's own AC bar (a working, real, structured-output call) is already met.
- **Nothing downstream reads or acts on `overallConfidence` yet** — it's captured and contract-verified as real, bounded model output, but no code path (this connector, `enrichPost.ts`, or anything storing `SocialPost.enrichment`) currently discards, flags, or escalates a low-confidence result. Added at Menno's request as the data point a future decision would need; the decision itself (what threshold, what happens below it) is not made here.
