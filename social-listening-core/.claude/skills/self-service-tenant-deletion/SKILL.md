# Self-service tenant deletion

## What this is

Four `tenant_admin`-only, own-tenant-only actions, no `:id` param anywhere (the caller's own resolved identity is the only tenant this flow ever touches): `POST /v1/tenants/self-service-deletion/request` (halts ingestion immediately, starts the 30-day grace period), `POST /v1/tenants/self-service-deletion/export` (JSON or CSV, re-triggerable, requires an active request), `DELETE /v1/tenants/self-service-deletion` (cancel, available until confirmed), `POST /v1/tenants/self-service-deletion/confirm` (only reachable once the grace period has genuinely elapsed — kicks off the real, irreversible, cross-tier hard-delete). Fully self-service — Platform Admin has no approval step anywhere in this path, and no access to any tenant-content table or to the two new lifecycle columns either.

## How to extend this safely

- A new tenant-content table added by a future story must be added to `summarizeTenantForDeletion()`'s row-count set (if reintroduced) and `executeTenantDeletion()`'s own deletion sequence in `tenantDeletion.ts`, in FK-safe order (anything referencing another tenant-content table must be deleted before the table it references) — this is not currently enforced mechanically, only by this note. It must also get its own `GRANT SELECT, DELETE ... TO tenant_deletion_role` — `app_user`'s own grants are not sufficient for the final execution step (see Load-bearing constraints).
- The grace-period length (`GRACE_PERIOD_DAYS`, `tenantDeletion.ts`) is a named, explicit, revisable implementation default (ADR-0043 §5) — changing it is a one-line edit, not an ADR-level decision, unless the change is large enough to materially affect the safety argument ADR-0043 §5 makes for 30 days specifically.
- `runIngestionAttempt()`'s own deletion-halt guard (ADR-0043 §3) is the one real, shared choke point every ingestion attempt funnels through today — a future scheduler or a third connector does not need its own copy of this check, it inherits the guard automatically by calling `runIngestionAttempt()`.

## Load-bearing constraints — do not change casually

- **`platform_admin_role` has zero access here, deliberately, with no exception** — unlike the Platform-Admin-initiated design this story replaced. Migration 0023 grants nothing to `platform_admin_role` at all. Do not add a grant to `platform_admin_role` to "make deletion easier to debug" or similar — that is exactly the mistake this story's own history (above) already made and corrected.
- **The final, irreversible hard-delete runs under `tenant_deletion_role`, a dedicated, narrowly-scoped role — never under a standing `app_user` grant.** `app_user` is one shared Postgres role every `tenant_admin` AND every `tenant_user` session uses concurrently; a standing `DELETE` grant on `users`/`tenants` there would be constantly present across every session, gated only by RLS + an application-layer role check, not a narrow, code-path-only privilege. `tenant_deletion_role` is connected to only inside `executeTenantDeletion()` itself (`getTenantDeletionPool()`), never exposed to any HTTP route. It deliberately does **not** `BYPASSRLS` either, unlike every other specialized role in this project (`platform_admin_role`, `tenant_signup_role`, `identity_resolver_role`) — a bug in the deletion code (a missing `WHERE` clause, a wrong `tenantId` variable) still cannot cross a tenant boundary, since RLS keeps enforcing `tenant_id`/`id` scoping regardless of this role's own table-level grants.
- **`app_user` only ever touches the two new, narrowly per-column-granted lifecycle columns** (`deletion_requested_at`, `deletion_confirmed_at`) for the request/export/cancel steps — it is never granted `DELETE` on any tenant-content table for this flow's own purposes (those already had full CRUD from earlier stories, unrelated to this one).
- **There is nothing per-tenant or per-credential to "revoke" from Key Vault.** Confirmed directly: every credential, for every tenant, is wrapped by one single, shared, environment-configured Key Vault key (`process.env.KEY_VAULT_KEY_ID`, `connectorsRouter.ts`) — envelope encryption (ADR-0014) stores the actual secret material (`wrapped_dek`, `ciphertext`) only in Postgres's own `platform_credentials` row, never in Key Vault itself. Deleting that row is the complete, sufficient, irreversible deletion. **Never attempt to disable/delete the shared Key Vault key as part of tenant deletion** — that would break every other tenant's still-active credentials simultaneously.
- **Deletion order is FK-driven, not arbitrary.** `social_posts.acquisition_id REFERENCES ingestion_runs(id)` with no `ON DELETE` clause (default `NO ACTION`) — `social_posts` must be deleted before `ingestion_runs`. `tenants` itself must be deleted last: `platform_admin_audit_log.target_tenant_id` (plain `text`, never an FK) and `domain_signup_attempts.tenant_id` (an FK until migration 0023 dropped it specifically for this reason) must both remain queryable as tombstone references throughout.
- **Archived `ingestion_runs` are only discoverable via a referencing `social_posts.acquisition_id`.** A run that produced zero posts that later aged into the archival tier is not enumerable this way and will not be deleted by it — a real, accepted gap, not silently glossed over.
- **`executeTenantDeletion()` is never awaited by the HTTP handler that confirms deletion.** A caller polling for completion must query `platform_admin_audit_log` for a `tenant_deletion_completed` entry (`target_tenant_id` = the tenant), not the `tenants` row's own disappearance — those are not the same moment; the function's own trailing audit-log write still has to execute afterward.
- **`ensure_ingestion_runs_partition()` (migrations/0011) must be called before inserting a row with an aged `started_at` value in a test fixture.** Migration 0011 only pre-creates `-24..+3` months' worth of `ingestion_runs` partitions once, at migration-apply time; nothing re-creates them afterward. `archiveAgedIngestionRuns()` `DETACH`+`DROP`s every past-cutoff partition it finds in one sweep, not just one caller's own fixture month — any earlier contract in the same full-suite run that has already exercised archival once will have already dropped a given month's partition. Without re-creating it first, an aged `INSERT` silently falls through to `ingestion_runs_default`, which the archival discovery query deliberately never matches — making that row permanently unarchivable for the rest of the run. This is a real, previously-hit failure mode (see this story's own contract test's comment for the full account), not a hypothetical.

## Known gaps / deferred work

- Deletion batches sequentially, table by table, not literally reusing ADR-0018's own partition-`DETACH` mechanism — a tenant's rows are scattered across many monthly partitions shared with other tenants' data, so whole-partition detachment doesn't apply to a single-tenant deletion the way it does to time-based archival.
- No rate limit or cooldown on repeated request/cancel cycles (ADR-0043's own Open Question, not designed there either) — acceptable at this project's own current scale; revisit if it ever becomes a real problem.
- The exact wording/channel of a user-facing warning as the grace period nears its end, and the `social-listening-admin` UI surface for this flow entirely, are not built — Epic 6 territory, out of this story's own backend scope.
- Cross-tenant isolation (a `tenant_admin` can never target another tenant's deletion) is structural, not separately tested: every route derives its target tenant purely from the caller's own resolved identity, with no `:id` param anywhere in this flow for a test to even attempt injecting.
