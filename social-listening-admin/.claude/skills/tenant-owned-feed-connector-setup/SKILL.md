# Tenant-owned-feed connector setup UI

## What this is

`/tenant/connectors/tenant-owned-feed` is the only path by which a real tenant can configure the `tenant-owned-feed` connector (Story 2.11). **As of Story 6.20 (ADR-0057), this is a real per-tenant list, not a single-activation flow** — `page.tsx` fetches every activation for the tenant server-side (`GET /v1/connectors/tenant-owned-feed/activations`, any status), and `TenantOwnedFeedSetup.tsx` renders one row per activation, each independently able to be at `pending` (mid-DNS-verification), `verified`, `expired`, or `removed`. Per-row actions: "Verify now" (`pending` only), "Edit feed URL" (any status, `tenant_admin` only), "Remove" (any status, soft — `tenant_admin` only), plus a persistent "Connect another feed" action always reachable, not gated on the list being empty.

This is a dedicated screen, not a fifth entry in Story 6.3's `PLATFORMS` array — `ConnectForm.tsx`/`DisconnectButton.tsx` assume a single-field-or-JSON credential submitted once; this connector has `authMode: 'none'` (no credential at all) and a pending/verified activation state neither of those components has any notion of.

## Contracts that constrain this component

- `contracts/epic-6/story-6.12.tenant-owned-feed-connector-setup.contract.test.ts` — the screen is its own dedicated route (not folded into Story 6.3's `PLATFORMS`); the connect form calls the real `POST /connect` via `core-client.ts`'s `connectTenantOwnedFeed()`; "Verify now" calls the real `POST /verify-domain` via `verifyTenantOwnedFeedDomain()` and is re-clickable (never disabled after one call); a `pending` response shows retry-later copy, never a hard failure; a `verified` response transitions to an active state; `core-client.ts` stays the sole Bearer-attachment choke point. **Its original AC4 (`?activationId=` URL persistence) was retired 2026-08-17 by Story 6.20 below, which makes the whole mechanism unnecessary — see that file's own dated note.**
- `contracts/epic-6/story-6.17.tenant-owned-feed-activation-control.contract.test.ts` — `page.tsx` reads real tenant-wide `isActive` via the already-existing `getConnectorStatus()` (degrading to `false` on a failed call, never crashing the page) and computes `isTenantAdmin` from the resolved role, passing both to `TenantOwnedFeedSetup`; the already-existing, unmodified `ActivateDeactivateButton` (Story 6.15) is rendered with `platformId="tenant-owned-feed"`/`ownerType="tenant"`, gated `isTenantAdmin`-only, never an `ownerType="user"` variant.
- `contracts/epic-6/story-6.20.tenant-owned-feed-multi-feed-administration.contract.test.ts` — `page.tsx` fetches the full activations list server-side and passes it down (degrading to `[]` on failure, never a crash); a `pending` row shows real `txtRecordHost`/`txtRecordValue`/`tokenExpiresAt` with "up to 72 hours" propagation copy, never under an `alert` role; "Connect another feed" and per-row Edit/Remove are `tenant_admin`-only and always reachable, never gated on the list being empty; a banner appears when feeds exist but the tenant-wide connector switch is off; `listTenantOwnedFeedActivations()`/`updateTenantOwnedFeedActivation()`/`removeTenantOwnedFeedActivation()` attach the bearer token correctly; the new `[id]` proxy route forwards PATCH/DELETE outcomes verbatim. **Dated note, 2026-08-20 (Story 6.28):** `updateTenantOwnedFeedActivation()` widened from a positional `(id, feedUrl)` signature to `(id, updates: {feedUrl?, name?})` — this story's own existing test call was updated to match (`{ feedUrl: ... }`), the real assertion (a PATCH with the given body, bearer-attached) unchanged.
- `contracts/epic-6/story-6.28.tenant-owned-feed-friendly-naming.contract.test.ts` — the connect modal gains an optional Name field, sent only when non-empty (never an empty string); the edit modal is pre-filled from the activation's current `name` and always re-sends `name` on submit (`null` when left blank — an explicit clear, not "unchanged"); the list row shows `name` as its primary label when set, falling back to `domain`, with `domain` still shown as a secondary line rather than hidden; both proxy routes (`connect`, `[id]` PATCH) forward `name` correctly, the `[id]` route distinguishing "not sent" from "sent as `null`" via `hasOwnProperty`; `core-client.ts`'s `connectTenantOwnedFeed()`/`updateTenantOwnedFeedActivation()` carry `name` through correctly.

## How to extend this safely

- **The list is fetched server-side in `page.tsx` (`listTenantOwnedFeedActivations()`), the same "Server Component fetches, Client Component only mutates" pattern `/tenant/users` established** — `TenantOwnedFeedSetup.tsx` never fetches the list itself, only reacts to its own `activations` prop. Every mutating action (connect, verify, edit, remove) calls `window.location.reload()` on success, the same simple `AccessControl.tsx`-established pattern, rather than client-side state sync.
- **Adding automatic re-check polling** (ADR-0050 Decision §3's own 1-minute-then-15-minute cadence) is explicitly named as a future Admin UI concern, not built here — this project has no background-job/timer infrastructure for a Client Component to drive one safely; a manual, re-clickable "Verify now" is the mechanism, per-row.
- **Activation (Story 6.17) reuses `ActivateDeactivateButton` unmodified** — don't fork or reimplement it for this screen. It's the one tenant-wide, connector-level switch, orthogonal to the per-feed list (Story 6.20) — see the Load-bearing constraint below on keeping that distinction visible.
- **A new feed on a domain the tenant already verified auto-verifies server-side (ADR-0057 Decision §1a)** — the connect proxy call is unchanged; the backend alone decides whether to skip the TXT step. Don't add client-side logic trying to detect or short-circuit this — the response's own `status` field already tells the truth.

## Load-bearing constraints — do not change casually

- **`core-client.ts` is the sole place a bearer token is attached (ADR-0036 §2).** `TenantOwnedFeedSetup.tsx` (a Client Component) never calls `social-listening-core` directly — it calls this repo's own same-origin proxy routes (`/api/connectors/tenant-owned-feed/connect|verify-domain|[id]`), which call `core-client.ts`'s own functions.
- **A `pending` verify-domain response is never treated as an error.** DNS propagation is outside the tenant's control once the record is published (ADR-0050 Context) — the UI must keep offering "Verify now" and must not show error styling for a `pending` result.
- **`domain`/`feedUrl` submission never JSON-encodes or reshapes the two fields** — unlike `ConnectForm.tsx`'s multi-field credential encoding, this connector's backend expects `{domain, feedUrl}` as two plain top-level fields (Story 2.11's own route shape), not a single opaque `credential` string.
- **The `[id]` PATCH proxy only ever forwards `feedUrl` — never `domain`, even if a caller somehow sent one.** `domain` is the exact claim DNS TXT verification proves; the backend rejects it with a `400` as defense in depth, but this proxy route doesn't even read `body.domain` in the first place.
- **The per-feed list and the tenant-wide `ActivateDeactivateButton` must stay visually distinguishable (ADR-0057 Decision §6).** A `verified` row does not mean that feed is being polled if the connector-wide switch is off — the inactive banner (`tof-banner-inactive`) exists specifically to prevent a tenant from seeing "Verified" everywhere and wondering why nothing is being ingested. Don't remove it as "redundant" with the per-row status pill; they answer different questions.

## Known gaps / deferred work

- **Closed 2026-08-17 (Story 6.20, ADR-0057):** multi-domain/multi-feed management (previously "out of v1 scope," ADR-0050 Open Question 2) and the "TXT instructions lost on reload" gap (previously named here) are both closed — the real list, fetched fresh on every page load, carries full data for every activation regardless of status.
- **No automatic re-check polling** — "Verify now" is manual/re-clickable only, per-row (ADR-0050 Decision §3's own named Admin UI deferral).
- **No feed-count cap per tenant** (ADR-0057 Decision §3) — deliberately unbounded.
- **No scheduled cleanup for stale `pending`/`removed` rows** (ADR-0057 Open Question 2) — a tenant can manually `Remove` a stale `pending` row, but nothing does so automatically.
- **`rawPayload.feedName` (social-listening-core's own Story 2.19 denormalization) isn't read anywhere in this repo yet.** Nothing in `postDisplay.ts`/`PostsFeedClient.tsx`/`OverviewTab.tsx` surfaces which named feed a given ingested post came from — only this setup screen's own list knows a feed's `name`. A future story could wire it into the Posts feed's provider badge or a dedicated field, but that touches `extractProviderBadge()`'s own semantics (used for filtering/CSS/Analytics grouping today) and needs its own scoping pass, not a silent addition here.
