# Connector connect/disconnect flow

## What this is

`/tenant/connectors` lets a tenant see each real, shipped connector's actual connection state and submit or remove a credential — the only path by which a real tenant can ever connect `gnews`, `azure-ai-language`, or `azure-openai` (all `authMode: 'api_key'`) to their own account. `newswire` and `wikipedia` (both `authMode: 'none'`) have no credential to connect/disconnect, but are **no longer rendered as always-active** — see Story 6.15 below. Every state shown and every action taken goes through a real HTTP call to `social-listening-core`'s existing connect/disconnect endpoints (Story 1.7, ADR-0034) — nothing here is hardcoded or simulated.

**Healed 2026-08-10 (Menno's explicit authorization), not built new.** The version of this screen originally shipped under Story 6.3 was a static placeholder: a hardcoded `[gnews, newswire]` array with hardcoded `connected` booleans, no credential form, and no backend API call anywhere in `core-client.ts`. Story 6.3's own contract at the time only checked the page existed and contained specific text strings — it never proved a real credential could be submitted. Discovered while confirming whether the two new AI provider connectors (Story 2.8, Story 2.9) could actually be used by a real tenant — they couldn't, and neither could GNews/Newswire despite Story 6.3 being marked built. See `docs/implementation-log.md`'s healing-pass entry for the full account.

## How to extend this safely

- **Adding a connectable platform**: add one entry to `PLATFORMS` in `page.tsx` (id, name, `authMode`, `credentialFields` if `api_key`) — usually no other file needs to change. This mirrors `azure-openai-connector/SKILL.md`'s own "adding a third `AIProviderConnector`" guidance on the core side; the two lists (core's real connectors, this screen's `PLATFORMS` array) are not automatically kept in sync — there is no "list all registered connectors" backend endpoint (see Known gaps) — so a new core connector must be added here by hand. **Real exception, Story 6.21:** if the new platform's own icon/color pair would be visually identical to an existing one on the same screen, `PlatformDef['icon']`/`['color']` (`ConnectorsClient.tsx`) each need one new value, plus matching `.cv-platform-icon-<color>`/`.cv-card-subtitle-<color>` CSS in `globals.css` — the "no other file needs to change" claim held for four platforms that never needed their own distinct identity beyond the four already-existing pairs; a fifth needing genuine visual distinctness (Wikipedia, alongside GNews's own globe/blue) is a real, small, one-time exception to it, not a pattern to repeat casually.
- **A platform needing a multi-field credential**: give it `credentialFields` with more than one entry — `ConnectForm.tsx` automatically JSON-encodes multiple fields into the single opaque `credential` string the backend expects (ADR-0014, no new storage pattern); a single-field platform submits that one value raw, unencoded.
- **A platform with `authMode: 'none'`** (like Newswire): omit `credentialFields` — no connect/disconnect action renders, but the platform still gets a real Active/Inactive label and a tenant-wide-only activation control (Story 6.15), since it has no personal/Tier-3 scope to activate.
- **`ActivateDeactivateButton`'s tenant-wide vs. personal controls**: gate exactly like `ConnectForm`'s own `allowTenantWide` (`isTenantAdmin`) and `authMode !== 'none'` — don't invent a third gating condition. The personal control's own `isActive` prop is always passed `false` (see Load-bearing constraints below) — never wire it to the tenant-wide `isActive` value.
- **A platform with `authMode: 'oauth'`** (Facebook, Story 6.23): no `ConnectModal`/`credentialFields` involved at all — the "Connect" action is a real browser redirect to `/api/connectors/facebook/oauth/start`, not a form submission. `tenantScopeAllowed: false` (a new `PlatformDef` field, defaulting to `true` — every existing platform is unaffected) suppresses the tenant-wide `ActivateDeactivateButton`/disconnect control unconditionally, even for `isTenantAdmin`, since the backend has no tenant-wide credential path for this connector at all (ADR-0059 Decision §4). A future OAuth-shaped connector should follow this exact shape — `src/lib/facebookOAuth.ts` (authorize-URL builder, cookie-name constants) and the four `src/app/api/connectors/facebook/oauth/*` route handlers are Facebook-specific today, not yet generalized into a reusable OAuth-connector pattern; generalizing them is real, deferred work if a second OAuth connector (e.g. Reddit) is ever built, not designed here.
- **A platform with genuine multi-item-per-user cardinality** (Facebook's multiple connected Pages, Story 6.27, ADR-0060 Decision §6, the first real instance in this repo): the shape is a real-data-fetching list component (`FacebookConnectedPagesList`, `ConnectorsClient.tsx`) with its own `initialX`-named testability seam prop (mirroring `initialFacebookPending`'s own established pattern) and its own same-origin proxy routes (`GET`/`DELETE /api/connectors/facebook/pages[/:id]`) — never folded into the platform-level `ConnectorInitialState`/`stateMap`, which stays a real, useful platform-wide rollup (Decision §4's own backward-compatible default). A future multi-item connector should follow this shape rather than inventing a new one.

## Load-bearing constraints — do not change casually

- **Connection state is always derived from `credentialStatus !== null`, computed client-side (well, server-side in the Server Component) from `GET /v1/connectors/:platformId`'s response — never a separate "is connected" field or a client-tracked boolean.** This is the same derivation `deriveConnectorHealth()` uses on the backend (ADR-0009) — don't introduce a second, independently-tracked notion of "connected."
- **Disconnect is always a two-click confirm sub-state (`useState`), never `window.confirm()`.** Matches `AccessControl.tsx`'s (Story 6.8) own established pattern for every destructive action in this repo — a native browser dialog is untestable in this project's own contract style and inconsistent with every other confirm flow here.
- **`core-client.ts` is the sole place a bearer token is attached (ADR-0036 §2)** — `ConnectForm.tsx`/`DisconnectButton.tsx` (Client Components) never call `social-listening-core` directly; they call this repo's own same-origin proxy routes (`/api/connectors/[platformId]/connect|disconnect`), which call `core-client.ts`'s `connectPlatform()`/`disconnectPlatform()`. Don't add a second way for a Client Component to reach core.
- **A failed `getConnectorStatus()` call for one platform degrades that platform to "not connected," not a failed page render.** A transient core-side issue affecting one connector must never block a tenant from seeing or acting on the others — `loadConnectorState()`'s own `try/catch` is load-bearing, not incidental.
- **`credential` on the wire is always a single string** — `connectPlatform()`/the backend's own `POST .../connect` never inspect or reshape it. Multi-field JSON-encoding is a `ConnectForm.tsx`-only concern; don't push that logic into `core-client.ts`, which stays a thin, credential-shape-agnostic transport layer.
- **Activation and credential management are separate, visibly distinct actions (ADR-0051 Decision §3) — never merge `ActivateDeactivateButton` into `ConnectForm`/`DisconnectButton`, and never let deactivating a connector hide or disable either.** A credential can be connected-but-inactive or disconnected-but-was-once-active; the two states are independent by construction.
- **`ConnectorStatus.isActive` (Story 1.12) is tenant-wide scope only.** There is no per-user (`ownerType: 'user'`) read yet — the personal `ActivateDeactivateButton` on both screens is always rendered with `isActive={false}` (an honest "unknown, assume off" default, not a real read of the user's own personal state) rather than reusing the tenant-wide value, which would misrepresent a user's own activation state. Don't "fix" this by wiring the personal control to the tenant-wide `isActive` — that's actively wrong, not an approximation improvement.
- **The Facebook OAuth flow's two remaining short-lived cookies each have one job — never conflate them.** `se_fb_oauth_state` (5 min) is pure CSRF proof for the `start`→`callback` round trip. `se_fb_oauth_pending` (5 min) carries the callback's own `{sessionToken, pages}` result to the picker via the `pending` route — read-once, deleted immediately by that route, mirroring the backend's own single-use session Map (`facebookOAuthRouter.ts`). Never persist an access token or any Meta-supplied secret in either — the `pending` cookie's own `pages` array is exactly what the backend's `exchange` response already omits tokens from. **Retired 2026-08-18 (Story 6.27, ADR-0060 Decision §6):** the third cookie, `se_fb_connected_page` (a purely cosmetic Page-name cache), is gone — `GET /v1/connectors/facebook/pages` (`listFacebookPages()`) now returns real per-Page names/status/health directly, making the workaround obsolete. Don't reintroduce a client-side cache cookie for data a real backend endpoint already serves.
- **`FacebookConnectedPagesList` never shows a `status: 'removed'` row.** The per-Page list is "one row per connected or orphaned Page" (ADR-0060 Decision §6's own text) — a soft-removed Page survives only as backend history (`facebookPagesRouter.ts`'s own `GET` still returns it for that reason), never re-surfaced in this UI. Don't change the `visiblePages` filter to include it without a real UI need for a "removed Pages" history view.
- **The card-level `reconnect_required` badge is a pure rollup once a Page is connected — it must never again render a single "Reconnect {platform.name}" link/button that re-enters the OAuth flow (ADR-0060 Decision §6's own last bullet).** The real per-Page remediation lives at the row level (`FacebookPageRow`'s own "Reconnect" action, shown for an `orphaned` row or a row whose own `connectorHealth.status === 'reconnect_required'`) and via the always-present "Connect another Page" action — both happen to point at the same `/api/connectors/facebook/oauth/start` URL (Meta's own flow can't be scoped to one Page), but the entry point and its copy are deliberately different from the retired card-level "restart everything" action.

## Healing note, 2026-08-17 (real behavior unchanged; the file layout it lives in did)

`tenant/connectors/page.tsx` is now a thin Server Component (data-fetching, gating, the `PLATFORMS` list) — every rendering concern this doc previously attributed to it (the ADR-0027 disclosure, the connect modal, the disconnect confirm flow, `ActivateDeactivateButton` usage, the `Scope`/`isTenantAdmin` gate) actually lives in **`ConnectorsClient.tsx`** now. **`ConnectForm.tsx` and `DisconnectButton.tsx` are dead code** — confirmed via a repo-wide grep, nothing imports either anymore; `ConnectorsClient.tsx` reimplements their behavior inline (`ConnectModal`, `handleDisconnectConfirm` + the shared `ConfirmModal` from `@/components/ui`), a real loss of the standalone-component boundary this doc's own "How to extend this safely" section still describes, not fixed by this healing pass (named here, not actioned). The Active/Inactive label is the shared `StatusBadge` component (`src/components/ui`) — its `inactive` variant default label is **"Paused"**, not the literal word "Inactive," matching `frontend-design-specification.md` §6.1's own documented "watchlist or connector paused" semantics; every real-behavior claim elsewhere in this file about an "Active"/"Inactive" label should be read as "the `active`/`inactive` `StatusBadge` variant," not literal text.

## Fix, 2026-08-17 — a real, live gap: personal-scope credential/activation for AI providers had no effect

Found live: a real tenant activated Azure AI Language via the personal (`ownerType: 'user'`) control, which succeeded with no error, but `enrichPost.ts` (`social-listening-core`) never reads a personal credential or activation for any `AIProviderConnector` — only tenant-wide. ADR-0028 Decision §1 already settles Azure AI Language/Azure OpenAI as Tier 2 (tenant-owned) only, with no Tier 3/personal variant — this was never mechanically enforced at the surface. Fixed both sides:

- **`social-listening-core`**: `connectorsRouter.ts`'s `forbidsUserScope()` (renamed from `authModeForbidsUserScope()`) now also rejects `ownerType: 'user'` for any `AIProviderConnector`, applied to both `/connect` (previously had no such check at all) and `/activate`. See ADR-0028's own dated Clarification and `contracts/epic-1/story-1.7...`'s AC8/`story-1.11...`'s AC12.
- **This repo**: `PlatformDef.personalScopeAllowed` (new field, set per-platform in `page.tsx`'s `PLATFORMS` array — `false` for `azure-ai-language`/`azure-openai`, `true` for `gnews`) now gates every personal-scope UI affordance: the Scope selector in `ConnectModal` (no longer shown for a `personalScopeAllowed: false` platform — `ownerType` is always `'tenant'`), the personal `ActivateDeactivateButton` in both `ConnectorsClient.tsx` and `status/ConnectorStatusClient.tsx`. A `personalScopeAllowed: false` platform's "not connected" state, viewed by a non-`tenant_admin`, now shows an honest "Ask your Tenant-Admin to connect this platform" note instead of a Connect button that would just 403.

## Known gaps / deferred work

- **No "list all registered connectors" backend endpoint exists** — `PLATFORMS` in `page.tsx` is a manually-maintained list, not fetched dynamically from core. Story 6.5's own SKILL.md already names this same gap from the status-view side. A real fix would be a core endpoint this screen (and Story 6.5's) could both query; not built here.
- **The disconnect-personal / Tenant-Admin-offboarding-a-user's-own-credential case (ADR-0034 §3's own named dual-actor rule) is not distinguished in the UI** — `DisconnectButton` always passes the caller's own resolved `ownerType`; a Tenant-Admin disconnecting a *different* user's personal credential on their behalf (the offboarding case ADR-0034 explicitly permits) has no UI path yet, only the backend's own `?userId=` query param support.
- **No credential validation before submission** — a malformed `{endpoint,key}` JSON for Azure AI Language, or a wrong-shaped key for GNews, is only caught when the backend actually tries to use it (or not even then — `storeCredential()` stores whatever string it's given). No client-side or connect-time format check exists.
- **The personal `ActivateDeactivateButton`'s own initial `isActive` state is always assumed `false` on page load** (Story 6.15) — `GET /v1/connectors/:platformId` only exposes tenant-wide activation (Story 1.12's own named scope limit). A user who already personally activated a connector sees "Activate" instead of "Deactivate" until they interact with it or a real per-user read is built. Named, not silently wrong-by-accident.
- **Live credential validation, system-driven auto-deactivation, and `GET /v1/connectors/:platformId`'s own activation+health response-shape design remain out of scope** (ADR-0051 Decision §6/§7, Open Question 5/6) — see `.claude/skills/connector-activation/SKILL.md` (in `social-listening-core`) for the fuller account of what's deferred and why.
- **Closed 2026-08-18 (Story 6.27, ADR-0060):** the connected Facebook Page's name is no longer a client-side cookie cache — `GET /v1/connectors/facebook/pages` is a real `social-listening-core` endpoint returning every connected Page's own name/status/health directly, independent of any cookie's own lifetime or a specific browser.
- **No true "switch to a different Page" (in-place credential replacement) flow** — connecting an additional Page and disconnecting an unwanted one are both now real, independent per-Page actions (Story 6.27), which covers the practical need; there is still no single "replace this Page's credential without a separate disconnect+reconnect" action, named here as a real but minor remaining gap, not solved.
- **Multiple different users independently connecting the same underlying Facebook Page (ADR-0060 Decision §4's own named blind spot) is not solved anywhere in this UI** — each user's own per-Page list is scoped to their own `userId` only (the backend enforces this), so this UI has no way to even detect the case, let alone reconcile it.
- **The OAuth start/callback/pending route handlers are Facebook-specific, not a generalized "OAuth connector" framework** — see "How to extend this safely" above.
