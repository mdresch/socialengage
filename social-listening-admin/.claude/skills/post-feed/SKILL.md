# Post feed

## What this is

`/tenant/posts` (list, real cursor-paginated `GET /v1/posts`) and `/tenant/posts/:id` (detail, real `GET /v1/posts/:id`) — the first and, as of this story, only frontend surface anywhere in this project for the actual posts every connector has been ingesting since Phase 1. `postDisplay.ts` holds the pure, non-JSX extraction helpers (`extractDisplayText`, `extractProviderBadge`, `extractEnrichmentSummary`) both screens share, since `rawPayload`'s shape is heterogeneous per connector and both screens need to derive the same title/snippet/provider/enrichment display data from it. **2026-08-19 — `FlatPost`/`flattenPost()` (the combined "raw post + all derived display fields" shape both `PostsFeedClient.tsx` and, since this date, the Analytics Overview drawer consume) also live here now**, moved from `PostsFeedClient.tsx` since they're built entirely from this file's own `extract*()` functions. The rich per-post detail body (full Markdown, AI enrichment panel, telemetry, raw JSON toggle) is its own component, `PostDetailPanel.tsx` — extracted from `PostsFeedClient.tsx`'s Slideover body so a second call site (Analytics Overview) can render the identical view without duplicating it.

## How to extend this safely

- **A new connector's posts should never need a follow-up "add it to the Provider filter" story (Story 6.26).** The filter's options are derived from `flat`'s own real `provider` values — a new connector's posts become filterable the moment they exist, automatically. The only thing worth adding by hand is a nicer display label in `PROVIDER_LABELS` (`PostsFeedClient.tsx`) — its absence only means the raw `providerId` is shown as the label, never that the provider is unfilterable. Don't gate the options list itself on that lookup table.
- **Adding a new connector's `rawPayload` shape:** `extractDisplayText()` in `postDisplay.ts` only ever looks for a `title` field (optionally `description`), then `message` (Facebook), then `permalink_url` (Facebook, media-only-post fallback) — it does not branch on `providerId`. A new connector whose posts have a `title` field (with or without `description`) needs no change here at all; one that doesn't falls back to raw JSON automatically. Only touch this function if a genuinely new *shape* (no `title`/`message`/`permalink_url` field at all, but real display-worthy content) needs its own branch — and add a **direct unit test of `extractDisplayText()` itself**, not a `Page()`-render assertion (see the next bullet for why that doesn't actually prove anything about this function).
- **Found live 2026-08-18 — the Story 6.11 contract's own `Page()`-render "per-shape title extraction" tests don't actually exercise `extractDisplayText()` at all.** `page.tsx` returns `<PostsFeedClient posts={posts} .../>` — a single element whose `props.posts` is the raw, unprocessed post array; `PostsFeedClient` (a Client Component) is never invoked by `JSON.stringify(element)`, so a title-field string appearing in that output only proves the raw `rawPayload` value round-tripped through as prop data, not that extraction produced it. This is how Facebook's own missing-title bug (posts silently rendering as raw JSON in the real feed) shipped invisibly for two stories (2.15, 2.18) without any contract catching it. **The fix (this same commit) adds direct unit tests calling `extractDisplayText()` itself** — the only way to actually prove this function's behavior; the three pre-existing `Page()`-render assertions (GNews/Newswire/mystery-connector) were left as-is, not rewritten, since fixing their own tautology is separate, broader scope than the Facebook regression this pass closes. A future addition to this function should always pair with a direct unit test, never rely on a `Page()`-render check alone.
- **Search/filter (search box, Provider/Sentiment/Watchlist) is real, client-side, and — as of Story 6.18 — operates over the tenant's entire fetched post set**, not one page. `page.tsx`'s own `fetchAllPosts()` pages through every real `GET /v1/posts` result before `PostsFeedClient` ever filters anything, so this is no longer "a client-side filter over an unfiltered fetch" (this doc's own prior, now-corrected warning) — the fetch itself is now the full set. A genuinely new query dimension `GET /v1/posts` itself doesn't support (e.g. server-side full-text ranking) would still need real `social-listening-core` scope first; a new filter over fields already present in `SocialPostSummary`/`enrichment` does not.
- **`fetchAllPosts()`'s `MAX_PAGES` circuit breaker is defensive, not an approximation ceiling** — same precedent as `fetchAnalyticsSummary.ts`. A real tenant approaching it is ADR-0054 Open Question 2's own named client-side-aggregation scale ceiling becoming real here too, not a bug to silently raise the constant past.
- **Adding a friendlier author name or ingestion-run summary to the detail screen:** requires a new `social-listening-core` REST endpoint first (no `/v1/authors/:id` or per-post ingestion-run route exists today — confirmed directly, not assumed). This screen's own `authorId`/`acquisitionId` display is the honest v1 ceiling until one exists; don't fabricate a client-side "friendly" mapping.
- **2026-08-19 — a second real caller now exists outside this screen: the Analytics Overview tab's own post-detail drawer** (`analytics-dashboard/SKILL.md`'s own Relations section). It fetches one post's full detail on demand via the new `GET /api/posts/[id]` route (a thin proxy calling `core-client.ts`'s `getPost()`, mirroring `.../enrich/route.ts`'s existing pattern), flattens it with this component's own `flattenPost()`, and renders it with this component's own `PostDetailPanel`. Any future change to `PostDetailPanelPost`'s shape, `flattenPost()`, or the fields `PostDetailPanel` renders now needs both call sites checked, not just this screen.
- **Found live 2026-08-20 — `extractAuthor()` never read `rawPayload.issuer`, so every real Newswire post's author rendered blank everywhere `extractAuthor()` feeds a display**, despite the Newswire connector (`social-listening-core`'s `newswireConnector.ts`, ADR-0024) deliberately treating the feed's `<dc:contributor>` issuing organization as the post's author ("issuer-as-Author", that connector's own header comment) — this admin-side function just never had the matching branch. `NEWSWIRE_POST`'s own fixture in this story's contract already carried `issuer: 'Acme Corp'` for exactly this case, unused until now — the same "a fixture existed but nothing exercised the field" shape as the Facebook `extractDisplayText()` regression above. Fixed with a direct `extractAuthor()` unit test, same convention.
- **Same-day follow-up, found live 2026-08-20 — the same gap existed for Facebook, plus a second one on `extractUrl()`.** `extractAuthor()` had no branch for Facebook's own attribution field at all (`rawPayload` never carried the connected Page's name — see `facebook-connector/SKILL.md`'s own dated note for the `social-listening-core`-side fix, `pollFacebook.ts` now denormalizes `pageId`/`pageName`); `extractUrl()` never recognized `permalink_url` (Facebook's own field for "the actual post, live on Facebook" — already read by `extractDisplayText()` as a text fallback, but never by `extractUrl()`), so the "Open original"/"view on Facebook" link silently never rendered for any real Facebook post, on either call site (`PostsFeedClient.tsx`'s Slideover footer, and the Analytics Overview drawer's detail panel — which gained its own matching footer action row in the same pass, previously missing entirely since `PostDetailPanel` deliberately excludes footer chrome by design).

## Load-bearing constraints — do not change casually

- **The cursor is opaque — this component never constructs or parses one.** `listPosts(cursor, limit)` forwards whatever string it's given straight through as the `cursor` query param, untouched. Story 6.18 moved cursor-following entirely inside `page.tsx`'s own `fetchAllPosts()` loop (never user-visible, never a URL param) — building a page-number control, or any client-side cursor math anywhere in this component, reopens the exact bug ADR-0011 exists to prevent.
- **`getPost()` returns `null` specifically on a 404 — every other non-2xx still throws.** A 404 is a real, expected outcome (unknown id, or another tenant's id — RLS makes the two indistinguishable, per `posts-api/SKILL.md`) the detail page must render as "not found," not crash on; any other failure (5xx, network) is a genuine backend problem the caller should not silently swallow into the same "not found" state.
- **`postDisplay.ts` is pure — no JSX, no `next/*` imports.** Both the list and detail pages import the same extraction functions; keeping them JSX-free is what lets both screens share them without either page depending on the other's rendering.
- **`fetchAllPosts()`'s returned array is most-recently-ingested-first (Story 6.25) — a `.reverse()` on the already-fully-paged array, applied once, after the fetch loop completes.** The backend's own `GET /v1/posts` ordering (`ORDER BY seq ASC`, ADR-0011) is unchanged — don't "fix" this by asking the backend for a different order; the reversal is deliberately client-side, over data already fully fetched into memory (Story 6.18). `PostsFeedClient` itself has no `.sort()` of its own — order is inherited entirely from its `posts` prop; don't add a sort there either, or it would need to duplicate this same reasoning in a second place.
- **`PostsFeedClient.tsx` no longer takes a `nextCursor` prop at all (Story 6.18)** — `posts` is now the complete, already-fetched set; reintroducing server-side "next page" pagination here would silently narrow search/filter back to a partial set, the exact defect this story closed.
- **Post body rendering uses `react-markdown` exclusively — never `dangerouslySetInnerHTML`, never hand-rolled regex/markup parsing (Story 6.19, ADR-0053).** `body_markdown` is real, canonical Markdown produced by `social-listening-core`'s own trusted `htmlToMarkdown()` pipeline, not arbitrary user HTML — but `react-markdown` (renders to real React elements) is still the only rendering path used, so this stays true even if that trust assumption ever needs revisiting.
- **The card-list snippet flattens `bodyMarkdown` to plain text — it never block-renders it (2026-08-17 enhancement).** `<ReactMarkdown allowedElements={[]} unwrapDisallowed>` is the sanctioned way to get a real, parser-verified plain-text excerpt (never hand-rolled regex stripping, same standard as the block-rendering path) — a disallow-everything-but-unwrap config, not a smaller allow-list, so any element type (including ones invented by a future connector's content) degrades to its text content rather than being silently dropped. Only a bounded prefix (`CARD_SNIPPET_SOURCE_LENGTH`) is ever passed in — the visible truncation is CSS (`-webkit-line-clamp: 3`), this constant only bounds DOM/parse cost across a page of many cards. Rendering full block Markdown (headings/lists) here would break that CSS clamp — reserved for the Slideover/detail-route surfaces only.
- **`jest.config.js`'s `transformIgnorePatterns` is a named allow-list of `react-markdown`'s specific ESM dependency tree (unified/remark/mdast/micromark/hast/vfile/etc.), not a blanket "transform all of node_modules."** A `react-markdown` version bump that adds a new transitive ESM dependency will need that package name added to the list, or Jest fails with `SyntaxError: Unexpected token 'export'` on that new package — check this list first if that error appears after a dependency update.

## Healing note, 2026-08-17

`app/tenant/posts/page.tsx` is now a thin Server Component (data-fetching, gating) — the actual list rendering (search/filter bar, post cards, pagination link) lives in **`PostsFeedClient.tsx`** now, a Client Component. Post selection no longer navigates to a separate route at all: **`PostsFeedClient.tsx` opens the selected post in its own in-page `Slideover` (`activePost` state), not a link to `/tenant/posts/:id`.** The standalone `/tenant/posts/[id]/page.tsx` detail route (this file's own "What this is" section above) still exists and is still real, contract-verified, reachable by direct URL — it is simply no longer linked to from the feed. Treated as an intentional design choice (Menno's explicit call, healing-pass session), not a regression to reverse.

## Known gaps / deferred work

- No `watchlistId`/`platformId` server-side query filter or date-range search — `GET /v1/posts` has no such params yet. As of Story 6.18, Provider/Sentiment/Watchlist/free-text filtering all exist client-side, now over the *complete* fetched set (not a real gap anymore in effect) — a genuinely server-side version of the same filters remains unbuilt, not because it's blocked, but because nothing currently needs it beyond what the client-side version already provides.
- No friendlier author-name or ingestion-run-summary resolution — no REST endpoint exists for either yet; the raw `authorId`/`acquisitionId` values are the honest v1 ceiling, not an oversight.
- Client-side aggregation over paginated `GET /v1/posts` does not scale indefinitely (same named-not-resolved ceiling as `analytics-dashboard/SKILL.md`'s own matching note) — no specific tenant post-volume threshold is decided as "too slow, needs server-side search instead," left to real usage to surface.
